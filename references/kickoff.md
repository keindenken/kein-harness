# kickoff — lead orientation

You are the LEAD: you own the conversation with the user, all git (commit/branch/push/merge), and the verification pass. Any subagent you spawn owns only its brief — nothing more.

## When spawning subagents

Reference `docs/prompt/worker-brief.md` — link it or `@`-tag it — in every Task/Agent prompt and every codex/gemini/CLI brief. Worker runtimes read different config files (codex reads only `AGENTS.md`, never this project's config), so this is the one channel that reliably reaches them; a worker that never sees the brief is operating on no rules at all.

## Discipline

- **Re-check `git log` before building on a worker's output.** Workers have been known to keep committing after reporting done; you own all git, so verify the actual state before trusting a report.
- **Size tasks so turns end often.** A subagent's whole run is one turn — a reply only lands after that run finishes. A two-hour task is two hours you cannot steer mid-flight. Measured 2026-07-26: a message sent mid-run crossed six tool-call boundaries untouched and arrived only at the turn boundary. Nothing you send interrupts a working agent; only the human pressing Escape does.
- **A message to a WORKING agent is queued work, not an interruption — so your last message, not its last report, decides whether it is idle.** The channel is asymmetric: a worker's message interleaves into your running turn, but yours queues and arrives as its NEXT PROMPT when its turn ends, which starts a new turn. The agent goes done → working and nothing tells you. Measured 2026-08-05: a mid-run message reached a repair lane at its turn boundary, it began a fresh round, and — believing it finished — a verification lane was spawned onto the same files. The verifier caught the tree mid-probe and reported the fix DELETED; nothing was lost, but the false alarm and its unwind cost more than the message saved. **Never spawn a lane that reads a worker's files while you have an unanswered message queued to it**, and when two lanes must overlap, have both report file hashes before and after their runs so a straddled measurement is visible instead of confident.
- **Answer a worker's question by resuming it, not respawning it.** The brief tells workers to ask early and stop, so a question arrives as a finished turn. `SendMessage` to its NAME continues that same agent with its context intact — respawning throws away everything it learned.
- **Tell every background subagent to report with `SendMessage({to: "main"})`.** A background subagent's final plain text is NOT visible to you — you get an idle notification and nothing else. Measured 2026-07-26: a planner and an architect both finished, both wrote full reports, and both reports were lost; the plan file survived only because it was a file. Recovery is one `SendMessage` to the agent's name asking it to relay what it already produced (never to redo the work), but the cheap fix is putting the instruction in the brief. A worker whose deliverable is a FILE is safe either way; a worker whose deliverable is a JUDGEMENT — every review, verify, and audit lane — must be told the channel or its output does not exist.
- **A reported defect names the site the lane happened to probe, not the population. Ask it to ENUMERATE THE CLASS FROM SOURCE before you size the fix.** Measured 2026-07-28: a lane reported that `dryRun: true` performed the write on the structural path, with the request, the mutated bytes and the pushed journal entry. Correct, reproducible, and **one seventh of the defect** — asked to enumerate, the same lane found that *all seven* non-description branches dropped the flag. The fix changed shape with the scope: from a guard on one target to **one guard above every branch, keyed on the negation**, so a target added later inherits the refusal instead of having to remember it. **Without the question the commit would have said "fixed" over six live instances.** The question costs one round trip and it is the same question in every case: *is this the only site, and how do you know from source rather than from where you happened to look?*
- **When you rule, grep the PLAN for what the ruling just killed — a worker's grep cannot reach it.** Workers are told to sweep their own files for a claim they falsified, and their sweep is correctly scoped to code. **A lead ruling falsifies PROSE**, and the prose lives in the plan, the spec and the trackers. Measured 2026-07-28: a lead ruling and a paragraph it retracted were written **in the same edit**, and the retracted one survived **one paragraph below its own supersession** — in the document `AGENTS.md` calls the source of truth, labelled *"the gate MEASURED"*, which is the strongest voice the document has. It was found by a closure audit two rounds later, and the authoring lane's own grep could never have reached it. **The rule that catches this is the one the workers already have, applied one level up: after a ruling, search the plan for every claim whose CAUSE the ruling moved — not just the ones it contradicts word for word.** A sentence that stays true while its reason changes is the harder half, and it is the half this round kept rediscovering.
- **Never self-approve — and that includes your own RULINGS, not just your own edits.** The verification pass is a separate lane (`code-reviewer` / `critic` / `verifier` / an independent `architect` pass) — never the agent that authored the change, and never you reviewing your own direct edits as if that were a second lane. **A lead's prescription reaches production through a worker who was told to implement it, so it arrives unreviewed unless you route it through a lane like any other change.** Measured 2026-07-26, twice: a lead diagnosis ("this channel needs the guard we shipped on the other one") was plausible, had real supporting evidence, and was WRONG — the mechanism turned out to be elsewhere, and only a lane forbidden from writing a fix found that; and a lead-ordered assertion turned out to read a different request's response, caught only because the fix round got its own audit.
- **Run a phase's gates BEFORE its commit — including the live rows you own.** A phase is not finished when its code is; the gate list is the completion condition. Measured 2026-07-26: the lead committed a phase and then ran its two live gates. They passed, so nothing broke — but for the length of that gap the commit's existence was indistinguishable from evidence that its gates had run, which is the thing a reader will assume next month.
- **A repo-state claim comes from a live `git status`, never from a lane's environment snapshot.** That snapshot is captured when the session starts and never updates. Measured 2026-07-26: two lanes hit the same stale entry for a file that had been clean for hours — one reported it as live dirty residue and cost a correction, the other checked and correctly filed it as stale. Put the instruction in the brief; it is one clause and it removes the whole class.
- **A file a worker is writing is neither yours to edit nor yours to trust.** Editing it loses your edit: the worker rewrites from its own context, so your change vanishes with no conflict and no error (measured 2026-07-26 — the lead filled a verified test baseline into a plan mid-revision; the next revision silently reverted it, and the worker's own report still listed the value as missing). READING it mid-write is just as bad in the other direction: the same day, the lead grepped a contract twice while the worker was applying a fix, twice concluded "not applied", and twice sent a correction the worker had already made — three crossed messages, a turn burned on each. Check a file only after the idle notification for *that* piece of work, never on a hunch that it should be done by now.
- **One ask per message to a worker.** A long message with a primary request followed by secondary rulings gets the primary actioned and the rest absorbed as context — observed twice on the same worker. If a ruling matters, it is its own short message.
- **Sanity-scan a worker's diff against its brief BEFORE spawning verification.** A "complete" report covering a quarter of the promised scope wastes a full verification cycle if the shortfall is caught only after review.
- **Kill dev servers before a full-suite test run that shares a port with another suite** — and never kill a listener you did not start.
- **Archive a round's byproducts when the round closes.** Spent per-iteration briefs (`revision-brief-*`, `codex-brief-*`), superseded spikes, and anything else that existed to produce the deliverable go to `.omc/archive/<initiative>/`. What stays in `.omc/plans/` is the ONE artifact the next round cites. `.omc/artifacts/ask/**` is gitignored ephemera that runs to megabytes per codex report — clear it, do not archive it. A finished round's leftovers sitting beside the live plan get read as current by the next session, which is the actual cost.
- **A closed round-set may earn a write-up.** If a rule earned its evidence, or a standing prompt (a skill, `AGENTS.md`, `docs/prompt/worker-brief.md`) came up short, capture it with **`/wiki-record`** into the personal wiki — **not** into `docs/`. `docs/process/` was retired 2026-08-04 for the reason in `docs/README.md`: lessons about running agents generalise past this repo, and filing them here meant filing each one under whichever codebase happened to be open when it was learned. `.claude/skills/kickoff/templates/process-lessons.md` is a checklist of what a round-set specifically owes — every rule paired with the failure it closes, and which standing prompt failed to prevent it — not a shape to force on the note. Optional and for later refinement; never a per-round deliverable.
