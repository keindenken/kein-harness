## What it is for and who reads its output

It writes marketing and product copy (landing pages, CTAs, product descriptions, error and empty-state microcopy, blog and help pages) and produces SEO/GEO specifications (meta tags, JSON-LD, canonicals, hreflang, `llms.txt`, `robots.txt`). There are three readers. End users read the copy; the file sets the persona in `docs/PRD.md` as the target ("Write for them, not for a generic user."). Other agents read the specs, and the file names that bar: "You produce specifications precise enough for @frontend-developer to implement without a follow-up question." The orchestrator reads the final report. The agent also maintains one standing document, `docs/content/CONTENT_STRATEGY.md`.

## Operating procedure in brief

1. Size the task (small, medium, large) and scale the process: a small task gets "One polished version — no variants, no full checklist."
2. Read the persona in `docs/PRD.md` and the existing voice, keywords and CTA library in `CONTENT_STRATEGY.md`.
3. Classify the task as conversion copy, SEO content, or technical SEO/GEO spec, and pick a framework (AIDA, PAS, FAB, value-proposition hierarchy).
4. Give 2-3 variants only for primary headlines and CTAs.
5. Run the on-page SEO checklist, and the GEO checklist for informational pages.
6. Append decisions to `CONTENT_STRATEGY.md`.
7. Hand implementation to other agents with the spec, and report: files changed, `[verify]` items, handoffs.

## What it has that the proposed writer lacks (verbatim)

- An explicit source of truth for what may be claimed, which is the proposal's point 2 applied to marketing: "`docs/user/USER_GUIDE.md` — Source of truth for what the product actually does; never write copy for features that do not exist", and in Constraints, "Do not write copy for features that are not yet built — check `docs/user/USER_GUIDE.md` and the codebase, not the plan". The last clause names a specific trap: the plan (PRD) describes features that do not exist yet, so a writer grounded in the PRD would sell vapor. The proposal names code as the evidence for project docs but does not warn that planning documents are not evidence of what exists.
- A marker for unknown facts, returned to the caller: "Do not guess at search volumes or ranking difficulty — note them as `[verify]` and flag to the human for confirmation with real keyword tool data", and the report must list "items marked `[verify]` needing real data". The proposal says interpretation is marked; this marks missing evidence in place and routes it back.
- Effort sized to the task: "Classify every task before starting and scale the process to it" and "When in doubt, start small and escalate." The proposal has no rule on how much process a one-line fix deserves.
- Missing inputs handled without blocking or inventing: "**Missing docs are normal**: in a fresh project, `CONTENT_STRATEGY.md` may not exist yet. Create it as part of your work and say so — never block on it. If `docs/PRD.md` personas are missing, ask for the target audience in your report rather than inventing one." The audience is the one input it refuses to invent, which fits the proposal's point 1.
- Scope discipline with a place for side findings: "**Stay in scope**: write what was asked. Copy problems you notice elsewhere go in your final report as flagged items, not silent rewrites." This is a concrete version of the proposal's separate output for the caller.
- Standalone passages, which is a reader-first rule for a reader who arrives mid-document (here, an answer engine lifting a passage): "**Self-contained passages**: no passage should depend on a previous paragraph to make sense. Resolve pronouns — \"[Product] syncs in real time\" beats \"It syncs in real time\"; the second is unusable out of context." and "**Answer first, elaborate second**: every H2/H3 section opens with a 1–3 sentence direct answer to the question the heading poses." Both carry over to project docs that readers enter from search or a link.
- Consistent naming of entities: "**Consistent entity naming**: refer to the product, company, and features by the same exact name everywhere. Aliases and cute variations fragment the entity in the engine's model."
- Decisions that belong to a human are named and routed, not made: "**AI-crawler allow/block is a business decision** — present the trade-off (GEO visibility vs. content reuse) to the human; never decide unilaterally."
- A banned-phrase list with the reason attached to each entry: "\"Seamless\" / \"frictionless\" / \"intuitive\" (show it, don't claim it)" and "Any claim without a number or proof point: \"significantly faster\", \"many customers\"".

## Where it conflicts with the proposal

- Scope of the role: this is one role per doc family, carrying about 4,000 words of domain rules (SEO checklists, JSON-LD templates, robots.txt syntax) in the role body. The proposal puts that material in path-scoped rules or the brief. Most of the file is exactly what the proposal would move out; the role-level material is the "Operating Discipline" and "Constraints" sections.
- The standing document is a working log inside a deliverable: "**Update `CONTENT_STRATEGY.md`**: log new keyword targets, copy decisions, voice notes, and CTAs added during the task." It is a shared record meant for later tasks, so it is closer to a ledger than to reasoning leaking into the copy. It does not violate point 3, but it is a second output the proposal does not plan for: state that persists across tasks.
- The specificity push partly works against point 2. "Any claim without a number or proof point" is forbidden, and the example "Prefer \"reduces build time by 43% (internal benchmark, 2026)\" over \"significantly faster\"" shows a number with a source label. The `[verify]` rule covers search volumes and the report's "items marked `[verify]` needing real data", but no rule says that a performance number or customer count must come from a named file. A model under pressure to avoid vague claims can fill the source label itself.
- Judging its own output: "**Run the On-Page SEO Checklist** (see below) before marking any page copy task complete" and the GEO checklist are self-checks. Many items are mechanically checkable (character counts, one H1, slug form), which is the part of self-review a script could replace.

## What it gets wrong or what looks untested

- An internal error in the framework block: the heading reads "### AIDA — Awareness → Interest → Desire → Action" while the body uses "Attention: Interrupt the scroll with a bold claim or provocative question." AIDA is Attention; the heading is wrong.
- Several numeric rules are asserted without source and some are dated: "**Word count**: informational content ≥ 800 words to cover the topic" and "The value prop belongs in the first 150px of the viewport." The GEO claim "passages containing a specific number, a named source, or a direct quote are measurably more likely to be included in generated answers" says "measurably" but cites nothing, which is the kind of claim its own rules would forbid in copy.
- It asserts facts about the agent's tools that the frontmatter must keep true: "**No shell access**: you cannot run commands or create git commits." The frontmatter lists `tools: Read, Write, Edit, Glob, Grep`, so the two agree today, but the sentence will silently go stale if a copy adds Bash.
- "Choose the framework that matches the audience's awareness level." relies on an awareness level that no input provides; the PRD persona is not said to contain one.
- The main instructions are long (4,210 words) and mostly reference material. No example of a finished deliverable or report is included, and nothing indicates which sections were exercised in runs.

## Verdict

It is the best exemplar in this batch for a marketing, product-copy and SEO path rule, and it has the best general-writer material in the batch as well, but it is not a base for the general role as written. For the general role, lift the operating discipline almost as is: task sizing, "never block on it" for missing docs, ask for the audience instead of inventing one, side findings go to the report, and `[verify]` markers returned to the caller. Also lift the source-of-truth rule ("the codebase, not the plan"). For a marketing/SEO path rule keyed on landing, content or marketing paths, lift the forbidden-phrase list, the answer-first and self-contained passage rules, and the checklists, with the mechanical checklist items better enforced by a script. Add what it lacks: every number and customer claim cites a file or is marked `[verify]`. Its evidential weight is one author's template (7 repos, 1 voice), with one visible revision.
