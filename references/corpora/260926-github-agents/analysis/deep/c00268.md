## What it is for and who reads it

It writes or rewrites the body of one concept document under `kb/`, in one of three registers (article, whitepaper, reference). Two readers: the knowledge-base reader, whose needs are carried by register cards and style files the agent loads (not in this file), and the dispatching agent, which gets a short report. The dispatch contract is in the description:

> The dispatching prompt must name the target file and its register (article, whitepaper, or reference).

## Operating procedure in brief

1. Before writing: read the three shared style files (voice, diagrams, altitude), then the named register card; the authoring conventions; the target file's frontmatter and its neighbour concepts; and the pinned sources in the frontmatter.
2. While writing: follow the register card's shape and voice.md's banned-pattern table; open with the answer; keep the frontmatter description and opening consistent; link neighbours with the relationship named; diagram flows and state machines with numbered captions; mark unverified claims inline.
3. After writing: one reread limited to banned patterns and register drift; run `morphir kb check`; report file, register, sources, and unverified or open items.

## What it has that the proposed writer lacks (verbatim)

This file is already close to the proposal's architecture: a thin role, with type differences carried by files the caller names. What it adds:

  > If no register was named, derive it from the routing table in `.claude/skills/kb/SKILL.md` and say which you chose.

  The proposal puts type knowledge in path rules or the brief but does not say what the writer does when the brief is silent.
- Sources pinned per document, read before writing, and cited from what was read:

  This is point 2 with a mechanism: the evidence set is declared in the document itself, so the writer and any reviewer read the same sources.

## Where it conflicts with the proposal

- Point 1 (start from the reader): the file itself never names a reader or what they will do. This may live in the register cards and altitude.md, which are not in the corpus, so the conflict may be only apparent. As a standalone prompt, reader-first is delegated, not stated.
- Point 2 scope: the evidence set is the pinned sources only. The "Before writing" list does not include reading code, even though the knowledge base documents a code project. A claim about behaviour that is not in a pinned source has two outlets: be marked unverified, or be written anyway. The proposal's evidence tiers (runs > vendor docs > recurring independent sources > single source) have no counterpart; all pinned sources weigh the same.
- Point 3 (cutting is the default): nothing in this file says to cut; it may be in voice.md. Working notes are kept out implicitly by the report format, not by a stated rule.
- Combining several drafts: not covered. It rewrites one document from sources, not from competing drafts, so the proposal's claim-level merge has no counterpart here.

## What it gets wrong or what looks untested

- Most of its behaviour lives in eight files outside the prompt (voice.md, diagrams.md, altitude.md, three register cards, SKILL.md's routing table, authoring.md). The analysis here cannot see them, so claims like "the banned-pattern table is absolute, including the em-dash rule" cannot be assessed. The prompt is only as good as those files.
- "Read, in order" requires loading at least five style and convention files plus neighbours and sources on every dispatch, even for a small rewrite. There is no guidance for a small edit.
- "fix any error your change introduced" leaves pre-existing lint errors in place. That is a sensible scope rule, but the report format has no field for errors it saw and left, so the caller does not learn about them.
- There is no sign in the file of runs or evals. The one mechanical guard, `morphir kb check`, is stated to enforce "caption presence and sequence"; whether it checks anything about sources or unverified marks is not stated.
- The prose is hard-wrapped mid-sentence (a lint-irrelevant cosmetic issue, noted only because one quote above spans a wrap).

## Verdict

The best base exemplar of the five for the proposed writer, for project docs and knowledge-base prose, and the closest to the proposal's design as a whole. It is a short, general role; type differences come from register cards the caller names; evidence is pinned per document and cited; unverified claims are marked where they appear; a linter and a scoped reread replace open-ended self-judgment; and the caller gets a report separate from the deliverable. To serve as the base it needs three additions from the proposal: an explicit reader-and-task opening (point 1) rather than delegating it to register cards, code as an evidence source alongside pinned documents, with the evidence tiers, and a stated cutting default. It also suggests two additions to the proposal: a fallback-and-disclose rule when the brief names no type, and propagation of edits to mirrored text (index bullets, parent links). Evidence weight: one organization, two repos; it is a strong design exemplar but a single voice.
