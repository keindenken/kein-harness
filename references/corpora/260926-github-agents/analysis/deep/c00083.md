## What it is for and who reads its output

It writes PRDs, user stories and acceptance criteria. Its `when_to_use` also lists "Release notes and changelog writing". Unlike most PRD agents, it names a non-human primary reader: "Masters the art of writing PRDs that AI coding assistants can execute effectively." Its founding claim is "**Traditional PRDs fail with AI because they're written for humans who infer context.**"

## Operating procedure in brief

The "Response Approach" section gives the steps:

1. Clarify scope (in and out).
2. Identify personas.
3. Define dependency-ordered phases.
4. Write FR-coded requirements with P0/P1/P2 priorities and acceptance criteria.
5. Add input and output examples.
6. Assess risks.
7. "**Self-score** - Validate against 100-point framework".

The output follows a 12-section template: executive summary, problem, goals and metrics, non-goals, personas, FRs, NFRs, architecture, phases, risks, dependencies, and appendices with a glossary and prompt templates.

## What it has that the proposed writer lacks (verbatim)

- **Reader-first applied to an agent as the reader.** The proposal says "start from the reader", and this file works out what that means when the reader is a coding agent:
  - "**Explicit boundaries** (AI cannot infer from omission)"
  - 'State boundaries positively: "Authentication is out of scope for Phase 1"'
  - "Never assume AI will infer limits from omission"

  These carry over to the proposal's "prompts" doc type and to briefs written for executors.
- **Examples as part of the specification.** "Example inputs and expected outputs" on every functional requirement, and "**Example-driven**: Concrete examples for every abstract concept". The template shows the form as an input example, an arrow, then an output example.
- **Acceptance criteria in a checkable shape.** "Acceptance criteria are testable (Given-When-Then)".
- **Detail scaled to difficulty.** It quotes, without attribution: "Adjust spec detail to task complexity—don't under-spec a hard problem (agent will flail), don't over-spec a trivial one (agent might get tangled)". This is a more precise statement of the length question than the proposal's plain "cutting is the default": it names the failure on both sides.
- **Ordering by dependency rather than by category.** "**Phase-first thinking**: Always organize by implementation order, not feature category". The proposal says nothing about how a document is ordered.
- **Explicit routing in the frontmatter.** `avoid_if` lists what goes to other roles ("User research analysis (use ux-researcher)", "Technical architecture (use architect agents)"). This bears on the proposal's single-role design, as a counterpoint below.

## Where it conflicts with the proposal

- **Point 2 (traceable facts). The template demands numbers it has no source for:**
  - "Quantified pain points with specific metrics"
  - "Market context and competitive landscape"
  - "SMART goals with baseline vs target metrics"
  - "[Benefit 1 with quantified impact]"
  - "[Market size and growth]"

  No rule says where these come from or how to mark them when they are missing. The rubric then scores their presence, which rewards invented figures.
- **Point 3 (cut by default).** The rubric rewards length and apparatus: "12-16 major sections with clear headers", "Comprehensive appendices", "Glossary of terms", "Version control metadata". Because the rubric scores presence, the model is paid to add sections, not to cut them.
- **Judging its own output.** "**Self-score** - Validate against 100-point framework" is the opposite of "does not judge the quality of its own output; runs/evals do."
- **Evidence tiers.** The prompt itself relies on an unsourced claim: "**Key insight from 2026 AI research:**" followed by "Frontier LLMs can follow ~150-200 instructions with reasonable consistency". Under the proposal's tiers this is at best a single source, and here the source is not even named. A writer built on this file would learn to present such claims as research.
- **One role versus several.** `avoid_if` and the persona set assume a separate role per document kind (ux-researcher, strategy-analyst, architect). This is the opposite of the proposal's single role with rules loaded by path. The corpus alone cannot tell which design works better; only runs can.

## What it gets wrong or what looks untested

- **Contradictory time units.** The file says "**Right-sized work units** (5-15 minutes per phase for frontier LLMs)" and "Each phase = 5-15 minutes of AI work", but the Implementation Phases criteria say "Time estimates (weeks, not days)" and the template shows "### Phase 1: Foundation (Weeks 1-2)". A model following both cannot satisfy them together.
- **Leftovers from another project.** "Use prefixes: FR-LD (local dev), FR-PT (plugin/theme), FR-CM (content), FR-DP (deployment)" and "Version requirements (PHP 8.1+, Node 18+, etc.)" read as residue from one WordPress-style project, now applied to every PRD.
- **A rubric that looks measured but is not.** "AI-Optimized PRD Framework (100-Point Standard)" gives point weights ("Sequential Phase Structure (10 pts)", "Structured Document Format (7 pts)") with no derivation. Nothing in the file ties these weights to outcomes.
- **Its own template breaks its advice.** It uses `---` horizontal rules between every section and fills most slots with placeholders the model must invent content for ("**Document Owner:** [Name]").
- **An arithmetic mismatch.** "Frontier LLMs can follow ~150-200 instructions with reasonable consistency" sits beside a 12-section template with dozens of required elements per section. The file never reconciles the two.

## Verdict

It should not be the base for the general writer. The rubric and the market and metric sections push toward invented numbers and bloat, and the self-scoring step contradicts the proposal. It is the best source among the five for one thing: how to write for an agent as the reader. Lift the explicit non-goals stated positively, the example inputs and outputs per requirement, Given-When-Then criteria, the rule that spec detail scales with task difficulty, and dependency ordering. These fit a path rule for specs and plans aimed at coding agents, and possibly the prompt-writing doc type. Discard the 100-point rubric, the fixed 12 sections and every quantified slot that has no source rule. Weight: one project and its forks, with no evidence of runs.
