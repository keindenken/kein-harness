## What it is for and who reads its output

It writes a `prd.md` for a feature or project. The file names the reader and the use: "The document should be complete enough that a development team can build the entire application from your specifications."

## Operating procedure in brief

1. Pick the location: use the path the user gave, otherwise propose one and ask.
2. Write a fixed 10-section PRD: overview, goals and non-goals, personas, functional requirements, UX, narrative, success metrics, technical considerations, milestones, and user stories.
3. Give every user story an ID, a title, a description and acceptance criteria. Cover primary, alternative and edge cases, plus authentication when relevant.
4. Review the PRD against a 4-question checklist.
5. Apply the formatting rules: sentence-case headings, no horizontal rules, no conclusion, no disclaimers.

## What it has that the proposed writer lacks (verbatim)

- **A hard output boundary.** "Your only output should be the PRD in Markdown format. You are not responsible or allowed to create tasks or actions." The proposal says reasoning goes to a separate output but never says the writer must not also act (create tasks, edit code).
- **Asking when the destination is missing.** "You will create a `prd.md` document in the location requested by the user. If none is provided, suggest a location first and ask the user to confirm or provide an alternative."
- **IDs so requirements can be traced downstream.** "Assign a unique requirement ID (e.g., US-001) to each user story for direct traceability". This is the reverse direction from the proposal's traceability. The proposal traces the writer's claims back to evidence. Here the IDs let later work (tasks, tests) trace forward to the document.
- **Testability as the acceptance bar for a requirement.** "Make sure each user story is testable" and the checklist question "Are acceptance criteria clear and specific?".
- **A rule for how the document ends.** "Do not add a conclusion or footer (user stories section is the last section)" and "Format the PRD in valid Markdown, with no extraneous disclaimers". These are concrete cuts. The proposal's "cutting is the default" is abstract, and this names what to cut.

## Where it conflicts with the proposal

- **Point 2 (factual sentences traceable).** The only source rule is "fill them with details derived from the user's requirements". Several required sections cannot come from user requirements without invention: "Success metrics (user-centric, business, technical)", "Milestones & sequencing (project estimate, team size, suggested phases)", and "Provide specific details and metrics where required". The file gives no instruction to mark assumed numbers as assumptions, and none to leave a gap.
- **Point 3 (cut by default).** The file pushes toward exhaustiveness: "List ALL necessary user stories including primary, alternative, and edge-case scenarios", "Ensure no potential user interaction is omitted", "Be thorough, specific, and ensure all requirements are clearly documented", and "List ALL User Stories in the output".
- **Point 1 (reader first).** It names the reader (the development team) but does not ask what the reader already knows, or whether a 10-section document is the right size for a small feature. The section list is fixed regardless of scope.
- **Judging its own output.** Step 7 is a self-review checklist. It is short and concrete, but the proposal leaves this to runs.

## What it gets wrong or what looks untested

- **An unsatisfiable completeness demand.** "Ensure no potential user interaction is omitted" cannot be met, so it acts as pressure to pad. "Do we have enough user stories to build a fully functional application?" has the same effect.
- **An arbitrary naming rule.** 'When referring to the project, use conversational terms like "the project" or "this tool" rather than formal project titles'. Nothing explains it, it lowers precision, and it looks like one author's taste frozen into a rule.
- **Fiction presented as a requirement.** "Narrative (one paragraph from user perspective)" asks for invented prose inside a requirements document, and the file gives no marker that separates it from requirements.
- **Asking the user from inside a subagent.** "suggest a location first and ask the user to confirm" assumes the agent can talk to the user. When it runs as a delegated subagent, the question goes back to the caller and ends the run. The caller should pass the path in the brief instead.
- **Tools the prompt never uses.** The tools include `Task`, `Bash` and `WebSearch`, but no step uses research, and the role is told it may not "create tasks or actions".
- **No sign of testing.** The file has no example output and no calibration. The formatting rules ("Do not use dividers or horizontal rules") look like fixes for observed output, but nothing records that.

## Verdict

It should not be the base for the general writer. It has no evidence discipline, and its completeness pressure runs against points 2 and 3. It is a modest seed for a PRD path-scoped rule. Keep the section list trimmed to what the brief supports, the story ID plus acceptance-criteria format, the testability bar, the ending rule and the boundary that the document is the only output. Any rule built on it must add what it lacks: numbers such as metrics, estimates and team size come from the brief or are marked as assumptions, and they are never invented. Weight: one author, redistributed widely through collections, with no evidence of measured runs.
