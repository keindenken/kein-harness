## What it is for and who reads the output

It is the documentation role in a multi-agent Copilot CLI framework. The framework also has an orchestrator, a developer, an architect, a reviewer, and a shared "Board" of JSON artifacts. The role writes READMEs and guides, API docs, `.github/` instructions, rules and skills, changelogs and release notes, and doc comments. It names a reader for each doc type: first-time users for the README, API consumers, Copilot agents for `.github/` files, and users and team members for release notes. It frames its job against the developer's:

> 実装者（developer）が「何を作ったか」を知っているのに対し、

> ライターは「読者が何を知る必要があるか」を考える。

(The developer knows "what was built"; the writer thinks about "what the reader needs to know".)

## Operating procedure

It is called by the orchestrator after implementation and before the PR, after review findings, when `.github/` changes, and at release time. It reads Board fields: `feature_id`, `maturity`, `artifacts.implementation` including `public_api`, `architecture_decision`, and `review_findings`. It runs three parallel `explore` subagents: one for public API signatures, one for related existing docs, and one for design decisions. It checks signatures against source when the Board is insufficient. It sets doc depth by `maturity`, then writes. It returns two things: a JSON artifact (`files[]` with path, action, summary) that the orchestrator mirrors into the Board, and a markdown report with a table of changed files and a consistency-check section.

## Where it conflicts with the proposal

- Evidence order. It ranks another agent's summary above the code:

  > - `artifacts.implementation.public_api` — **公開 API のシグネチャ・戻り値・例外情報**（ドキュメントの事実正確性の第一情報源）

  (public API signatures, return values, exception info: the primary source for factual accuracy.)

  The code is only a fallback when the Board entry is "insufficient". The proposal treats code as the evidence for project docs. Under the proposal, a Board summary is at best a pointer to the code. The incident in its own Why line (a missing Board entry led to a guess) shows the risk of relying on an intermediate summary.
- Scope of the evidence rule. The source check applies only when writing signatures, exception types and return types. The general principle is stated in one table cell and applies to everything, but no procedure goes with it:

  > | **正確性** | コードの実態と矛盾しない。推測で書かず、必ずコードを確認する |

  (Accuracy: do not contradict the code; do not guess; always check the code.)

  The proposal applies traceability to every factual sentence and asks for interpretation to be marked. This file never mentions interpretation.
- Placement. It carries per-doc-type guidelines, a release-notes template and SemVer criteria inside the role. The proposal would move those to rules or the brief. Release management is also wider than writing:

  > - Semantic Versioning（`MAJOR.MINOR.PATCH`）を推奨する

  (Recommend Semantic Versioning.)

- It has nothing on combining several drafts or outside examples, and no claim ledger.

## What it gets wrong or what looks untested

- Apart from the one Why line, nothing shows it was tested. The maturity table, the fixed "overview, setup, usage, contributing" README order and the emoji-headed release template read as the author's design, not as measured results.
- It always spawns three explore agents, whatever the size of the doc change:

  > > 3つの explore エージェントが並列で動作し、結果を統合してドキュメントに反映する。

  (Three explore agents run in parallel and their results are merged into the docs.)

  That costs as much for a one-line changelog entry as for a new guide.
- The consistency check has no definition. The report template has a place for results, but the file never says what is compared with what, beyond one line in the "does" list:

  (Consistency check between existing docs and implementation.)

- The prohibitions appear twice: under やらないこと (lines 29-30) and again under 禁止事項 (lines 251-252). Each says no production code and no test code.
- The frontmatter pins a model (`model: claude-sonnet-4.6`). That is fine in a Copilot file, but it would break this repo's rule that `agents.json` sets tier.
- Its conciseness rule is a single generic cell that gives no way to decide what to cut:

  > | **簡潔性** | 冗長な説明を避け、必要十分な情報量にとどめる |

  (Conciseness: avoid redundant explanation; keep to what is necessary and sufficient.)

## Verdict

Of the five, this one is closest in shape to the proposal: a single general-purpose writer called by an orchestrator, with a scope boundary, a structured return to the caller, and one rule backed by a run. Use it as the **skeleton exemplar for the role in an orchestrated pipeline, for project docs and API reference**. Take from it the named scope boundary, the "do not guess type or exception names" rule with its incident, the consistency report in the caller output, and maturity as a depth input the caller supplies in the brief. Remove the doc-type guidelines and the release-management content and move them to rules. Reverse its evidence order so that code outranks the Board summary. Before relying on path-scoped rules, check its warning that `rules/` do not auto-load in some runtimes against the actual runtime (for example, whether Claude Code subagents receive path-scoped rules). The proposal assumes they do. It is one author with 3 stars, so it counts as one voice.
