## What it is for and who reads the output

It is a worker in a plan-driven multi-agent pipeline. It writes technical docs, READMEs, API docs and diagrams, and it writes "walkthrough" completion reports for a finished plan. Its output has two readers. The orchestrator reads the raw JSON status. The document's audience is passed in as a field:

> "audience": "developers|end_users|stakeholders",

## Operating procedure

Initialize: read AGENTS.md and parse the task. Execute by `task_type`. A walkthrough writes `docs/plan/{plan_id}/walkthrough-completion-{timestamp}.md`. Documentation reads the source and existing docs, drafts, and checks against the code. Update takes a baseline, finds the delta, and checks only the delta. Then come Validate (errors, diagrams render, no secrets), Verify (code parity), Self-Critique (a confidence-threshold loop), Handle Failure (a YAML log), and Output (JSON only).

## What it has that the proposed writer lacks

1. An update mode scoped to what changed. The proposal describes writing, not maintaining:

   > - Read existing documentation to establish baseline.

   > - Identify delta (what changed).

   > - Verify parity on delta only.

2. An evidence rule for URLs with a budget and a stopping point. It names the kind of site where fetch fails, and it ends by reporting to a human instead of searching further. This is the most specific evidence rule in the file, and it was added locally, which suggests it came from use:

   > - **Link verification**: never cite a URL unless it was just confirmed live via a tool call/fetch this turn. Never invent/reconstruct URLs from memory. For JS-heavy/SPA doc sites (Salesforce Help/Developer docs, Trailhead, Lightning Design System, or any site returning empty content via fetch), go straight to a browser tool (Playwright: `browser_navigate`+`browser_snapshot`) instead of retrying fetch/search tools. Verification budget is max 2 attempts per link (1 fetch + 1 Playwright, or 1 Playwright directly for known JS-heavy sites) — if still unverifiable or Playwright is unavailable, stop and tell the user instead of continuing to search.

   The proposal says every factual sentence is traceable. It does not say what counts as having checked a link, or when to stop trying.

3. The caller states coverage in the input. A `coverage_matrix` in the input says what must be covered, and the self-check refers to it:

   > - Verify: all coverage_matrix items addressed, no missing sections or undocumented parameters.

   The proposal leaves the brief's contents open. A coverage list is a concrete brief field.

4. Guards against describing a generic stack and against shipping placeholders:

   > - Use project's existing tech stack for decisions/ planning. Document the actual stack, not assumed technologies.

   > - NEVER use TBD/TODO as final.

5. Style taken from existing docs, not from the prompt:

   > - Read existing docs/README/CONTRIBUTING.md for style, structure, and tone conventions.

## Where it conflicts with the proposal

- It grades its own work. The proposal says the writer does not judge the quality of its own output. This file makes self-scoring a step and returns the scores as fields:

  > - If confidence < 0.85 or gaps found: fill gaps, improve explanations (max 2 loops), add missing examples.

  > "parity_verified": "boolean",

  > "coverage_percentage": "number"

  An orchestrator that reads `parity_verified: true` is trusting the writer's report about itself.
- Gaps have no place in the caller output. The only output besides the files is a summary of at most three sentences and a failure log. When the writer cannot find evidence, the instruction is to "fill gaps", not to report them. The proposal wants a separate output for exactly that material.
- Project-local rules are baked into the role:

  > - **Language**: all documentation must be written in English only, regardless of the chat language used to request it.

  The Salesforce site list is in the role too. The proposal would put both in a rule or the brief. That this variant had to edit the shared role to add them is a small piece of evidence for the proposal's split.
- "Code parity" is asserted, never traced. There are no citations, no file or line references, and no ledger. The proposal's point (2) and its claim ledger go further.
- It has nothing on combining drafts and no interpretation marking.

## What it gets wrong or what looks untested

- `confidence < 0.85` is a number the model gives itself. No scale is defined. `code snippet parity (100%)` has no definition of what is compared.
- Two directives contradict each other:

  > - Execute autonomously. Never pause for confirmation or progress report.

  > if still unverifiable or Playwright is unavailable, stop and tell the user instead of continuing to search.

- Template boilerplate that does not fit a doc writer:

  > - Output ONLY the requested deliverable. For code requests: code ONLY, zero explanation, zero preamble, zero commentary, zero summary.

  > - Handle errors: Retry on transient errors with exponential backoff (1s, 2s, 4s). Escalate persistent errors.

  A model agent cannot wait 1, 2 or 4 seconds on its own. "Retry up to 3 times on any phase failure" gives no rule for what counts as a failure.
- `Limit to 200 lines per read.` is an arbitrary read cap. For a doc writer that has to check signatures across a file, it risks partial reads.
- "Walkthrough" is a status report about a plan, not project documentation. Putting it in the same role means one audience enum and one parity check cover two different reader tasks.
- Except for the link rule, nothing shows the rules were measured. The family has at least nine variants in the corpus, which suggests people keep editing it, not that it was validated.

## Verdict

It is not a base for the role's content. The role's core, reader and evidence, is thin here, and self-grading goes against the proposal. It is a useful exemplar for **the caller-contract side of project docs in an orchestrated pipeline**: a typed brief with `audience`, `task_type` and `coverage_matrix`, and an update mode that checks only the delta. It is also the best source in this set for a **URL-verification rule** with a budget and an explicit stopping point, which can go into the role's evidence rule nearly unchanged (the site list moves to a rule file). Drop the confidence threshold and the self-reported `parity_verified` and `coverage_percentage`. Replace them with a gaps list in the caller output and let an eval check parity. The whole gem family counts as one source.
