## What it is for and who reads its output

It turns a repo-generated context bundle (`artifacts/pr_context.summary.txt` and `artifacts/pr_context.appendix.txt`) into a GitHub pull-request body. The bundle holds commits, a diff stat, changed files, classified issue references and feature-doc excerpts. There are two readers:

- human reviewers ("Actionable for reviewers")
- GitHub automation, where a `Closes #NNN` line has a side effect because it closes the issue on merge

## Operating procedure in brief

1. Read the bundle and only the "Additional Context files" it lists.
2. Emit `Suggested title: …`, then 11 sections in fixed order: Summary, Why, What Changed, Architecture, Verification (Completed / Recommended), Backward Compatibility, Risks, Review Guide, Follow-ups, GitHub Auto-close, Related issues/PRs.
3. Apply the issue-number rules and the fallback bullets.
4. Check the pre-flight list.

## What it has that the proposed writer lacks (verbatim)

- **A closed set of sources, fixed by the caller.** The bundle carries "an enumerated list of Additional Context files you are allowed to reference (the ONLY extra sources besides the context itself)", and the rule is repeated: "Never cite or summarize content from outside the pr_context summary/appendix bundle and its enumerated Additional Context files." The proposal says "every factual sentence is traceable to evidence" but not who decides what counts as evidence. Here the caller's brief bounds it. That is a clean division of labor for the proposal's design, where the brief carries the doc-type specifics.
- **Separate sources for "why" and "what".** "Rely on embedded feature-doc excerpts (spec/plan/user-story) and PR Intent fields as the sole “why” sources; do not speculate beyond provided sources." The proposal names "code for project docs" as the evidence, but a diff can show what changed and never why. This file assigns motive claims their own source, and the proposal has no equivalent.
- **Fixed wording for what was not verified.** "Do not invent tests/results; if not in context, state “Not verified in this PR” and list what should be run." Verification is split into "“Completed” (only what’s clearly true from context)" and "“Recommended” (commands to run locally/CI)". This puts the proposal's "interpretation is marked" into a form a reader can scan: a checked fact is visibly separated from a suggestion.
- **Rules for identifiers that have side effects.**
  - "You may ONLY mention an issue/PR number if it appears verbatim somewhere in the provided context file."
  - "You MUST NOT treat PR numbers as issues."
  - "If the context notes GitHub validation is unavailable/unverified, do not emit `Closes` and use the fallback `None` bullet."

  The fallback is written out in full: "- None (no verified closing issues listed; fill PR Intent to enable auto-close)". The proposal treats all claims alike. This file recognizes that some tokens (issue numbers, closing keywords, paths, commands) act on the world, so a hallucinated one is worse than a wrong sentence.
- **Order by importance, with secondary work kept but demoted.** "Lead with the *primary product/feature/architecture change*" and "Preserve important secondary work (tooling/docs/devcontainer) but keep it secondary unless instructed otherwise." The quality bar repeats it: "Summary leads with the true primary change." The proposal says nothing about ordering.
- **Guidance tied to what the reader will do.** "Suggested order to review (3–10 bullets)" and "Call out noisy mechanical moves (e.g., R100 renames), generated artifacts, or large diffs if present". This is the proposal's "start from the reader and what they will do with the document", made concrete for a reviewer.
- **Labels on uncertainty, and conservative inference.** "Keep uncertain points explicitly labeled as such." and "If the main change is unclear, infer conservatively from:" commit subjects, clusters in changed files, and embedded feature-doc excerpts.
- **Summarizing instead of listing.** "If changes span many commits, summarize into themes rather than enumerating each commit." and "Use file and directory names when it improves clarity, but do not dump long lists". These are concrete cutting rules.

## Where it conflicts with the proposal

- **Point 3 (cut by default) against a fixed section list.** "Use these sections, in this order:" lists 11 sections with no rule for dropping an empty one, so a one-line fix still gets Architecture, Risks, Migration Notes and Follow-ups. The file is also inconsistent here. Output rule 4 says "If scope is large, include a **Review Guide**", which makes the Review Guide conditional, but the section list includes it unconditionally as section 8.
- **Point 2 for sections without a source rule.** "Enumerate realistic risks and mitigations" (Risks and Mitigations) and "Provide a short, accurate wiring diagram in text" (Architecture / How It Fits Together) must be inferred from a diff stat and file list. The file gives no rule marking these as interpretation, unlike Verification and Why. The closed-source rule does limit what can be cited, but it does not stop speculation inside these two sections.
- **Nowhere to put notes for the caller.** "Output **only** the PR text body in GitHub-flavored Markdown." This agrees with the proposal that reasoning stays out of the deliverable. But the only outlet for uncertainty is an inline label inside the PR body, and the file has no second output that could tell the caller what the agent could not determine.
- **Judging its own output.** "Quality Bar (Pre-flight Checklist)" is a self-check, though every item on it is an evidence check ("Verification is not fabricated.", "No hallucinated issue/PR numbers."). It is not a taste check.

## What it gets wrong or what looks untested

- **A tension between the closed sources and repo norms.** "Provide concrete commands aligned to repo norms (poetry/pwsh/etc.)" assumes the agent knows the repo's commands. Under the closed-source rule it may learn them only from the bundle, and the prompt does not say the bundle contains them.
- **A body that mixes in a title.** "Output **only** the PR text body" sits against "Generate a suggested PR title at the top of the body under: `Suggested title: …`". The result is a body that has to be edited before it is pasted.
- **Signs of hand edits.** In the issue-rule block, the bullet for "You may ONLY mention an issue/PR number" is indented deeper than its sibling "You MUST NOT treat PR numbers as issues.", and some rules sit deeper than their siblings under output rule 6. This suggests the file was edited without being rendered or reviewed. The meaning survives.
- **No fallback without the bundle.** Everything depends on "the **standard PR context files** (generated by repo tooling)". The prompt does not say what to do when the bundle is missing or stale.
- **No evidence of runs.** The file has no example PR body and no record of measured failures. The very specific issue-number rules ("“Related:” is forbidden inside the auto-close section.") read like fixes for failures someone saw, but that is inference.

## Verdict

Of the five, this is the closest fit to the proposed writer and the best base exemplar, for code-derived project docs: PR descriptions, changelogs and release notes. Four of its rules make the proposal's point 2 operational and carry over to any doc type:

- the caller bounds the sources
- "why" needs its own source
- a fixed phrase for unverified claims
- a zero-tolerance rule for identifiers that have side effects

Its reviewer-oriented ordering is a concrete case of point 1. What is specific to the doc type (the 11 sections, the `Closes #NNN` syntax, the bundle file names) belongs in a path-scoped rule or the caller's brief. Fixes needed before reuse:

- let empty sections drop
- mark Risks and Architecture as interpretation
- add a side output for unresolved points
