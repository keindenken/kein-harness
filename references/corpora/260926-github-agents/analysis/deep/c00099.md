## What it is for and who reads its output

It adds missing `///` XML documentation comments to a C# file without touching code. The comments are read by developers in IntelliSense and by generated API docs. The file never names the reader. It defines quality by C# XML-doc tag rules: which tags, in what order, and on how many lines.

## Operating procedure in brief

1. Read the file or selection.
2. List the types and members that have no XML doc. Skip documented ones and event handlers or UI callbacks.
3. Add a comment to each remaining member, following the tag order, the single-line or multi-line form, and the per-tag rules.
4. Run the quality checklist and return the complete updated file.
5. If existing docs look wrong, ask whether to Update, Recreate or Ignore before touching them.

## What it has that the proposed writer lacks (verbatim)

- Rules that tie tags to the code, which makes point 2 checkable at the member level: "Use `<exception>` only for exceptions explicitly thrown by the member implementation." and "Do not invent behavior that is not supported by the implementation." The first is a strong form of traceability: a tag is allowed only when the code shows a `throw` for it.
- Completeness defined by the code signature: "Every documented method and constructor parameter must have a matching `<param>` tag." and "Every documented non-`void` method must have a `<returns>` tag." For API comments, the signature decides what must be present, so "cutting is the default" has a floor.
- An explicit rule for existing text: "Preserve existing XML documentation unless explicitly told to change it." plus a three-way question when existing docs look wrong: "`Update`: improve the existing documentation", "`Recreate`: replace the existing documentation", "`Ignore`: leave the existing documentation unchanged". The proposal does not say what the writer may do to text it did not write.
- A worked trap in the skip rule: "Do not skip a method solely because its name starts with `On`." This reads like a response to an observed over-application of the event-handler rule. It is the kind of line the proposal's run-driven revision would produce.
- A no-side-effects boundary: "You only document code. You do not refactor, reformat, rename, or change logic." with a matching checklist item, "No code logic, formatting, indentation, or naming was changed."
- A rule against restating names: "Use concise wording and avoid repeating the member name unnecessarily."

## Where it conflicts with the proposal

- Mostly, it does not. It is what the proposal expects a path-scoped rule for `**/*.cs` to contain: tag grammar, order, line form, and skip rules. It conflicts only if it is used as a role, because the proposal keeps doc-type knowledge out of the role.
- Point 1 (reader). There is no reader step. Which members get `<remarks>` or `<example>` is decided by "when extra context is useful" and "when the member would clearly benefit from a usage example", with no reader named to decide it for.
- Judging its own output. It ends with a self-review checklist ("Before returning output, verify:"). The proposal leaves quality judgment to runs. Most of these items are mechanical tag checks, though, and a linter could check them as well as a run could.
- Asking. The "Ask first" branch stops for a human. In an unattended subagent run, a question may have no one to answer it. The proposal expects the caller's brief to settle this in advance.

## What it gets wrong or what looks untested

- Its own example breaks its main rule. The documented `Save` method contains only an argument check and `return true;`. Yet its comment claims `<see langword="true"/> if the document is saved successfully; otherwise, <see langword="false"/>` and "It does not create parent directories automatically." The code never returns `false` and never saves anything. That is behavior "not supported by the implementation". A model that imitates the example learns to describe the method its name suggests, not the code in front of it.
- The example uses a tag the prompt does not list. `<see langword="true"/>` appears in the example, but the inline-tag list does not include `langword`. It also ends with a `<seealso>` to the general Microsoft XML-doc page, which is unrelated to the member.
- Two rules are in tension: "Do not reformat code." and "Indent `<code>` contents for readability, but do not otherwise change file formatting."
- The output form assumes a chat reply: "Return the complete updated file content." In a tool-using agent this means echoing the whole file, which costs tokens and can drift from what is on disk. Nothing says whether to edit in place.
- The file starts with an HTML comment and the `---` frontmatter comes after it. Many frontmatter parsers read YAML only when `---` is on the first line, so `name` and `description` may be ignored. This was not checked against the host that loads `.github/agents/`.
- There is no sign of runs beyond the `On` trap line and the date stamp.

## Verdict

It is a good exemplar for a path-scoped rule for C# XML doc comments. It is not a base for the general writer role, because it has no reader, evidence or cutting guidance that would carry across types. Lift the tag-to-code rules (exceptions only if thrown, param and returns completeness), the branch that preserves existing docs and asks before rewriting them, the no-code-change boundary, and the `On` trap. Replace the example with one that documents only what its code does. Two principles carry over to the general role: completeness is defined by the source, and existing text is left alone unless the brief says otherwise. Evidence weight: one author in 5 repos.
