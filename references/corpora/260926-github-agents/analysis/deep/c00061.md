## What it is for and who reads its output

It checks an existing piece of text against a fixed list of 34 house-style rules and returns suggested edits. The reader of its output is the author or editor of the piece, who decides which edits to accept. The reader of the piece itself (a newsletter or article reader) is never mentioned. The description says "Reviews and edits text content", but the body says "suggest edits" and the output format is a list, so in practice it is a reviewer, not a writer.

## Operating procedure in brief

1. Go through the rule list one rule at a time against the text.
2. For each violation, quote the original, give the corrected version, and name the rule.
3. Change only what the style guide requires; keep the author's voice.
4. Return a numbered list of edits, grouped where related; if nothing violates the guide, say so.

## What it has that the proposed writer lacks (verbatim)

- Every edit carries its rule, in a three-part record: "Quote the original text", "Provide the corrected version", "Briefly explain which style rule applies". This is the proposal's ledger idea (claim, source, evidence) applied to edits: each change is traceable to a named rule. It is a ready-made format for the editing mode of a writer, and for the ledger the proposal returns beside a merged file.
- A minimal-change mandate when the text belongs to someone else: "**Maintain the author's voice** - Make only the changes necessary for style compliance while preserving the original tone and meaning". The proposal's point 3 makes cutting the default, which is right for the writer's own draft but not obviously right for another author's text.
- Rules that are checkable on the text itself, with no judgment needed: "Spell out numbers one through nine (except years at sentence start); use numerals for 10+", "Em dashes—like this—with no spaces (max 2 per paragraph)", "Numbers over 999 take commas: 1,000", "Use \"earlier/later/previously\" instead of \"above/below\"". Most of the 34 rules are of this kind. They are the sort of content the proposal routes into a path-scoped rule file, and many could be a lint script instead of prose.
- A procedure that forces coverage: "**Systematically check each style rule** - Go through the style guide items one by one, checking the text against each rule". For a long rule list, walking the list is how a model avoids checking only the rules that come to mind.

## Where it conflicts with the proposal

- Mostly it supports the proposal rather than conflicting with it. The file is a style guide wrapped in an agent: a thin role (4 procedure lines, an output format) plus a doc-type-specific rule list. Under the proposal the list would be a path rule or a referenced style file, and the general writer would load it. The fact that someone had to create a whole agent to carry a house style is a small data point for the proposal's split.
- Point 1 (start from the reader): nothing in the file mentions the reader of the piece. Several rules are reader-motivated in their origin ("Use \"earlier/later/previously\" instead of \"above/below\"" assumes the reader may not see the layout), but the agent is told to apply them as compliance, not to reason from the reader.
- Point 2 (factual sentences traceable): out of scope for this agent. It checks form, not facts. The rule "Identify people by company/title (except well-known figures like Mark Zuckerberg)" touches facts but does not ask for any check that the title is right.
- Judging its own output: the "If the text is already compliant with the style guide, acknowledge this and highlight any particularly well-executed style choices." line asks for praise, which is a quality judgment in the deliverable and adds text the author did not ask for.

## What it gets wrong or what looks untested

- It mixes checkable rules with judgment calls without saying which is which. "Cut adverbs where possible" and "Avoid clichés and jargon" have no threshold, and they pull against "Make only the changes necessary for style compliance while preserving the original tone and meaning". With a strong voice, "where possible" can mean every adverb.
- The role and its tools disagree. The frontmatter grants `Edit, MultiEdit, Write, NotebookEdit` and even `ExitPlanMode`, while the body only asks for suggestions. The description, "Reviews and edits text content to conform to Every's editorial style guide", leaves it open whether the agent should change the file. A model with Edit and "edits" in its description may apply changes the author never approved.
- Some rules are ambiguous as written. "Use commas between independent clauses only" can be read as banning commas anywhere else. "Capitalize after colons only if introducing independent clauses" and "Hyphenate compound adjectives except with adverbs ending in \"ly\"" are clear to a copy editor but give no example, and the file has almost no worked examples.
- The only anchor for "well-known figures" is one name, "(except well-known figures like Mark Zuckerberg)", so the boundary is left to the model.
- There is no sign of evaluation: no sample input and output, and the copies are identical in body.

## Verdict

It is not a base for a writer role; it is a reviewer with no evidence or reader component. It is a good exemplar of two things the proposal needs. First, the shape of a house-style rule file that a path-scoped rule would load: concrete, one line per rule, mostly checkable, with the mechanical rules better moved into a lint script. Second, the output contract for editing someone else's text: quote, correction, named rule, which doubles as a small ledger. For a blog or newsletter path rule, lift the rule list as a template for form (not the Every-specific content), and lift the minimal-change mandate for the editing mode. Fix the tools-versus-body mismatch and drop the praise line. Its evidential weight is one publication's style, copied into 7 repos by 4 owners.
