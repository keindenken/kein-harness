## What it is for and who reads the output

It is a general technical writer for developer docs, technical blogs, tutorials, ADRs, and user guides. Readers are listed as four audience tiers (junior developers, senior engineers, technical leaders, non-technical stakeholders). The caller is a person in Copilot chat. No orchestrator is assumed and no return contract is defined.

## Operating procedure

It follows a five-phase process: Planning (audience, objectives, an outline with word targets, references), Drafting ("completeness over perfection", with `[TODO]` markers where facts need checking), Technical Review (verify claims and code, versions, security, performance data), Editing (flow, simplification, redundancy), and Polish (formatting, links, images, proofread). Next it gives per-type tone rules and full templates for five doc types, then a quality checklist the agent checks against itself.

## What it has that the proposed writer lacks

1. A named place to put unverified facts during drafting. This comes close to the proposal's "interpretation is marked", but it covers *unchecked* facts:

   > - Mark areas needing fact-checking with [TODO]

2. It asks for data behind performance claims and decisions, which is traceability applied to the claims readers are most likely to act on:

   > - Validate performance claims with data

   > - Include metrics/data that informed the decision

3. Negative scope in reference docs. The proposal's reader-first point does not tell the writer to say when *not* to use something:

   > [When NOT to use it]

4. A task-shaped rule for user guides that turns "start from the reader" into a heading test:

   > - Task-oriented, not feature-oriented ("How to export data" not "Export feature")

5. It shows command output alongside the command, so the reader can confirm the step worked:

   > - **Command examples**: Show both command and expected output

6. It names outside references by URL (Nygard ADR format, Write the Docs). The proposal's evidence tiers have a "vendor documentation" tier. This file shows what citing one looks like inside a role:

## Where it conflicts with the proposal

- **Doc-type differences live inside the role.** The proposal carries them outside, in path-scoped rules or the brief. Here, five templates and per-type tone rules make up most of the file. Every run carries the blog template even when writing an ADR.
- **Cutting is not the default. Engagement devices are required:**

  > - Open with a hook that establishes relevance

  > - Include "lessons learned" and failure stories

  > - End sections with key takeaways

  Summaries at the end of each section and invented "lessons learned" are the padding the proposal's third point cuts.
- **Drafting is told to grow first, then trim later:**

  > - Write first draft focusing on completeness over perfection

  > - Include all code examples and technical details

- **Serving many readers at once** runs against "start from the reader and what they will do":

  > - Create comprehensive documentation that serves multiple audiences

- **The agent judges its own output.** The checklist is self-assessed and partly subjective. The proposal leaves quality judgement to runs and evals:

  > - [ ] **Engagement**: Would you want to read this?

- There is no split between deliverable and working notes, and no ledger. `[TODO]` markers go into the deliverable itself, and nothing says they must be cleared or reported.

## What it gets wrong or what looks untested

- **It asks for verification the tools cannot perform.** The frontmatter grants `tools: ['codebase', 'edit/editFiles', 'search', 'web/fetch']`, which includes no terminal or run tool, yet it requires:

  > - Verify all code examples compile/run

  With these tools, "verify" can only mean reading the code. The instruction reads like a check that was never run.
- **It asks for steps the agent cannot do:**

  > - Test with actual users before publishing

- **Two voice rules contradict each other:**

  > - **For Technical Blogs**: Conversational yet authoritative, using "I" and "we" to create connection

  > - **Inclusive language**: "We discovered" not "I discovered" (unless personal story)

- **The blog template invites invented numbers.** `[Quantified improvements]` and `[Unexpected discoveries]` are required sections, and nothing requires a source for them. A writer with no measurements is pushed to make them up.
- It closes with an inspirational line that carries no behaviour:

  > Remember: Great technical writing makes the complex feel simple, the overwhelming feel manageable, and the abstract feel concrete.

- `model: GPT-5` is in the frontmatter. The body does not depend on it.

## Verdict

It is not a base for the writer role. Its structure is the opposite of the proposal's: type differences are in the role, engagement padding is required, and the agent judges its own work. Some pieces are worth taking into **per-type rule files**: the ADR template and its rules ("One decision per ADR", "Immutable once accepted", "Include metrics/data that informed the decision") for decision records, the user-guide task-orientation rule, and the "When NOT to use it" slot for reference docs. The `[TODO]` fact-check marker supports the proposal's evidence point, with one change: the marker should go into the caller-facing ledger, not stay in the file. This file is also a cautionary example. The corpus's most-copied general-purpose writer asks for code verification its own tool list cannot perform. So "verify" in a role only means something if the tools and the run can actually carry it out.
