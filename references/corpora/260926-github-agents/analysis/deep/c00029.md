## What it is for and who reads the output

It maintains the root-level Markdown docs of one Jekyll theme (`README.md`, `INSTALL.md`, `CUSTOMIZE.md`, `FAQ.md` and others). It names its reader precisely, and this is its strongest part:

> You write for academics and researchers who may not have a coding background

> **Audience:** Many users are academics without coding experience; explain technical terms when you must use them

It also names what the reader does with each section:

> Each section should answer: "What is this?" and "How do I use it?"

## Operating procedure

It has no step-by-step procedure. It is a standing brief with six parts:

1. Role and reader (above).
2. A project inventory: tech stack, dependencies, and a directory map about 40 lines long.
3. Documentation standards: keep it simple, link instead of copying, point to source files, avoid UI descriptions, code-block style, structure (headers, table-of-contents markers, blockquote warnings).
4. A purpose line for each doc file, and a description of the repository's path-scoped Copilot instruction files.
5. Writing style, a list of typical tasks, and a glossary of terms to explain on first use.
6. Boundaries in three tiers: always, ask first, never.

The nearest thing to a procedure is the trigger list under "Typical tasks", for example:

> **Update configuration documentation** when `_config.yml` changes

It never says what to return to a caller, how to report what changed, or what to do when the code and the docs disagree beyond "Keep documentation in sync with actual code and configuration".

## What it has that the proposed writer lacks

1. **Link, don't copy, as a drift control.** The proposal treats cutting as a default, but it does not say that pointing to the source of truth beats restating it. This file makes that the rule, with a good/bad pair:

   > Link to existing files instead of duplicating content

   > - Good: "See the configuration options in `_config.yml`"
   >   - Bad: Copying the entire YAML structure into docs

   > Reference well-documented configuration files rather than repeating their content

   This is traceability done by reference rather than by restatement: a pointed-to fact cannot drift from its source.

2. **A durability test for content.** It excludes things that will change even when they are true today. The proposal's evidence rule checks whether a sentence is true now. It does not check whether the sentence will stay true.

   > Don't document button locations, menu items, or visual layouts that may change

   > - Good: "Enable dark mode by setting `enable_darkmode: true` in `_config.yml`"
   > - Bad: "Click the moon icon in the top right corner to toggle dark mode"

3. **Reader-specific vocabulary control.** Starting from the reader leads to a concrete rule: explain each term once, where it first appears, with a worked example.

   > **When to explain:** If a document uses a technical term that readers might not know, briefly explain it in parentheses or a footnote the first time it appears:

4. **Verification of instructions by running them.** For project docs, "traceable to code" is weaker than "the command was run". The file asks for the stronger one:

   > Test commands and instructions before documenting them

   > Commit without testing documentation examples

   (The second line is in the "Never do" list.)

5. **Placeholders need a tracking issue.** This is a narrow rule, but it stops a class of unverifiable text from shipping:

   > Include placeholder text like "TODO" or "Coming soon" without an issue tracking it

6. **Write scope limits.** The role may edit docs only. Code, config, and workflows are off limits:

   > Modify source code files (`_layouts/`, `_includes/`, `_sass/`, etc.)

   > Edit `_config.yml` or other configuration files

   The proposal does not say what a writer may touch. For a writer that edits files, this matters as much as the prose rules.

7. **Preservation of machine-read markers.**

   > Preserve existing table of contents markers (`<!--ts-->` and `<!--te-->`

   (The closing parenthesis is missing in the source.)

## Where it conflicts with the proposal

- **Placement of type-specific content.** The same repository has already split per-file-type guidance into path-scoped files, and the agent describes them:

  > `.github/instructions/liquid-templates.instructions.md` (applies to `**/*.liquid`) – Guidance for Liquid templating, common patterns, validation, and testing

  But the rules for writing the root docs live in the role, not in a path-scoped file for `*.md`. So this repository uses path scoping for code and a dedicated role for docs, the reverse of the proposal's default. It is one voice, so it proves only that the split is workable. It does not show the split is better.

- **Project knowledge inside the role.** About a quarter of the file is an inventory of directories and dependencies. Under the proposal that belongs in the repository's instruction file or the brief. The copies show it going stale: the CalaW variant (c00100) carries a shorter tech stack without Docker, Prettier or pre-commit, and the v1.x rewrite (c00105) drops the inventory entirely and points to `docs/BOUNDARIES.md` instead. The later version moved toward the proposal's position. This is inferred from the variants; I do not have their dates.

- **Ask-first gates.** The file stops for human approval on structural changes:

  > - ⚠️ **Ask first:**
  >
  >   - Major restructuring of documentation organization
  >   - Adding entirely new documentation files

  The proposal's writer is called by a caller and answers to that caller. In an unattended run, "ask first" has to become "return the proposal to the caller instead of doing it". The file has no return channel to do that with.

- **No separate output for notes.** There is no output contract (record flag `output_contract` false). Reasoning, change rationale, and open questions have nowhere to go except into the docs or into chat. The proposal's third core point is absent.

- **No fact/interpretation marking.** Docs for end users are mostly instructions, so this matters less here. Still, nothing marks a guess about behaviour as a guess.

## What it gets wrong or what looks untested

- **Internal contradictions on examples and UI.** Three rules collide:

  > Be direct and concise; avoid unnecessary examples unless they clarify significantly different use cases

  > **Examples:** Provide real, concrete examples from the repository; show exactly what to type or where to click

  > Don't document button locations, menu items, or visual layouts that may change

  "Show … where to click" directly contradicts the UI rule and its "moon icon" bad example. "Avoid unnecessary examples" and "provide concrete examples" pull in opposite directions, and nothing says which wins. This reads like rules added at different times and never run against each other.

- **Permission to restyle conflicts with ask-first.**

  > Use existing documentation style and structure (or improve it with patterns from this agent)

  > Changing the documentation format or style guide

  The first is under "Always do". The second is under "Ask first". A model can reasonably do either.

- **"Test commands" with no way to test.** The frontmatter declares no tools, and the file gives no build or serve command. So the strongest verification rule has no stated means of carrying it out. It is an aspiration, not a procedure.

- **A glossary entry that misuses its own term.** "Frontmatter" is defined as metadata between `---` lines, and then two sections later:

  > **Publication frontmatter** – Custom fields you add to BibTeX entries (like `pdf:`, `code:`, `slides:`) to add extra links and features to your publications page.

  BibTeX fields are not frontmatter by the file's own definition. An agent told to explain terms "using the common terms reference provided" will spread this.

- **A persona without behaviour.** "You are a documentation specialist" adds nothing the rest of the file does not already say.

- **Length versus its own advice.** At 1,710 words, the file violates "Link to existing files instead of duplicating content": the directory map duplicates what `ls` and the repository's `.github/copilot-instructions.md` already hold. That is the rule the upstream apparently applied in the v1.x rewrite.

- Nothing in the file refers to a run, a failure, or a measurement. Every rule reads as the authors' taste or as reasoning from principles. The good/bad pairs are clear, but I found no sign that they were tested.

## Verdict

It is not a base for the general writer role. It is single-type by design, carries a project inventory that drifts, has no output contract, and contradicts itself on examples.

It is the best exemplar so far for **the path-scoped rule file for end-user project docs** (README, install, customize, FAQ, troubleshooting), with these parts worth lifting nearly as written:

- a named reader with a named skill gap
- "What is this? / How do I use it?" as the per-section test
- link rather than copy, with the good/bad pair
- exclude content that will change (UI positions)
- explain each term on first use
- test commands before documenting them
- no TODO without a tracking issue

Two items belong in the role itself, because they apply to every doc type and the proposal lacks them. The first is "reference the source of truth rather than restate it", which extends core point 2 from "traceable" to "pointed-to where possible". The second is "exclude claims that will not stay true", a durability test. Drop the inventory, the glossary (project-specific, and partly wrong), and the ask-first tier (replace it with return-to-caller). Its 17 owners count as one source.
