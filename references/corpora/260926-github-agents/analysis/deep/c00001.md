## What it is for and who reads the output

It writes and edits pages for one documentation site (opencode's web docs). The file never names a reader. From the rules you can infer a user of the tool who is skimming a docs page. The frontmatter is a routing trigger, not a role:

> description: ALWAYS use this when writing docs

## Operating procedure

It has none. The file lists page-format rules: a one-to-three-word title, a 5-10 word description, text chunks of at most 2 sentences, `---` dividers between sections, section titles in sentence case and the imperative mood, no trailing semicolons in JS/TS snippets, and a `docs:` commit prefix. It does not say to read code, check facts, look at audience, or return anything.

## What it has that the proposed writer lacks

1. It anchors style to one local exemplar file instead of describing the style in prose. The proposal says style lives in path-scoped rules or the brief. It does not say that a rule or brief can point at a model page in the repo.

   > Check out the /packages/web/src/content/docs/docs/index.mdx as an example.

2. Its constraints can be checked mechanically: counts, casing, mood, and separators. A run or a lint can check each one without judgement.

   > Chunks of text should not be more than 2 sentences long

   > The section titles are in the imperative mood

   > The title of the page should be a word or a 2-3 word phrase

3. It has a rule against repeating the title term in section titles, and it admits the rule sometimes has to give way. The admitted exception is useful.

   > This might be unavoidable in some cases, but try to avoid it.

4. It has repository-workflow conventions tied to the doc (a commit prefix). These belong to the repository, not the writer.

   > If you are making a commit prefix the commit message with `docs:`

## Where it conflicts with the proposal

- Scope and placement: the whole file is house style for one site, loaded as an agent role. The proposal would put exactly this content in a path-scoped rule that loads when `packages/web/src/content/docs/**` is touched, not in a role. So this is an agreement about content and a disagreement about where it lives. It shows the kind of content the proposal wants to move out of the role.
- `ALWAYS use this when writing docs` routes all docs work to a site-specific style. A README or report written through it would get rules that only make sense for this site's MDX pages. That is the failure the proposal's path scoping prevents.
- The file has none of the proposal's three core points: no reader or task, no evidence or traceability, and no separate output for notes.

## What it gets wrong or what looks untested

- There is no factual discipline at all. A docs agent with no instruction to check what it writes against the code can produce well-formatted pages that are wrong.
- Two style lines pull against each other:

  > You are not verbose

  > Use a relaxed and friendly tone

  A friendly tone tends to add words. The 2-sentence cap is the only thing holding it back. Nothing in the file shows which rule wins when they collide.
- "Expert technical documentation writer" is a persona line with no behaviour attached.
- The file itself is hard-wrapped mid-sentence (lines 14-15 and 25-27), so an agent reading it as an example could copy that wrapping. That is minor.
- The description rules are given as absolute numbers (`should be 5-10 words long`). There is no sign they were tested against output. They read as the maintainers' taste, which is fine for a house rule. It is not evidence about what works.

## Verdict

It is not a base for the writer role. It is a good model of a **path-scoped style rule for one project-docs site**: short, mechanically checkable, and anchored to an in-repo exemplar page. Borrow its shape (countable constraints and "see file X as the example") for the rule files the proposal places outside the role. Borrow nothing for the role's core. Its popularity (99 repos) measures fork traffic from one project, not independent agreement, so it should count as one source.
