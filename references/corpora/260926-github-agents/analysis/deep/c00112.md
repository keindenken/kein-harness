## What it is for and who reads the output

It is a subagent that writes or edits Markdown for a parent agent. The frontmatter hides it from users (`user-invocable: false`), so the direct reader of its return is the parent, not a human:

> You operate in an isolated context window. The parent agent handles the user's broader goal; you handle the markdown.

The file never names the final human reader. Its job is defined by form ("follows all formatting rules"), not by purpose.

## Operating procedure

1. Load three named skills: lint rules, `doc-hygiene` (anti-drift and link integrity), and `markdown-sanitization-chain` (for external content).
2. Write or edit the Markdown.
3. If a diagram is needed, leave a fixed-form placeholder for a separate illustrator worker instead of drawing it.
4. If a link target or path is unknown, leave a `VERIFY` placeholder instead of inventing one.
5. Return only the Markdown, optionally with one sentence of decisions after a `---` divider. If the task cannot be done, return a single `CANNOT_COMPLETE` line instead.

## What it has that the proposed writer lacks

1. **A failure return with a fixed shape, and a ban on partial output.** The proposal says what the writer produces when it succeeds. It does not say what the writer returns when it cannot proceed.

   > If the brief is unclear, contradictory, or the task requires information you do not have, return exactly:

   > CANNOT_COMPLETE: <one-sentence reason>

   > Do not guess at content. Do not produce partial output and hope the parent fills in the gaps. The parent will either re-brief you or handle the task itself.

2. **An in-band marker for an unverifiable reference.** The proposal requires every factual sentence to be traceable. It does not say what to do with a sentence whose source the writer cannot find. This file answers that for links and paths:

   > **Never invent file paths, link targets, or filenames.** If a reference is needed and you don't know the target, return a placeholder marked `<!-- VERIFY: <description> -->`.

   The same mechanism, extended from links to claims, would give core point 2 a failure path.

3. **Splitting work by output medium, not doc type.** The one delegation boundary here is diagrams versus prose. It is handled with a placeholder the parent can find by string match:

   > <!-- ILLUSTRATOR: <one-sentence description of the diagram needed> -->

   > **Never invoke the illustrator yourself.** Return a placeholder; the parent orchestrates.

   This bears on the proposal's rule that a separate role is created "only when runs show the general one failing on that type". Here the split is by medium (diagram), not by doc type. It suggests the axis for splitting roles may be medium or skill, and not document genre.

4. **A caller-facing note channel with a size cap.** This is close to the proposal's "working notes go to a separate output". The difference is that it caps the notes at one sentence and names what counts as worth reporting:

   > Return only the requested markdown. No preamble, no postscript, no "I'll now..." narration. If you made non-trivial decisions (split a section, renamed a heading, dropped a redundant paragraph), state them in one sentence at the very end after a `---` divider.

5. **A precedence rule between instruction sources, tied to a named bug.** It is the only rule in the file that cites a failure it came from:

   > **Never copy stale rule values from user memory if a skill defines the same field.** Skills win. (This is the precedence rule that prevents the `edgeLabelBackground: 'transparent'` class of bug.)

   The proposal moves type knowledge into path-scoped rules and briefs. That creates several instruction sources, and the proposal does not say which one wins when they disagree.

6. **Review dating.** The frontmatter carries `currency: 2026-05-01` and `lastReviewed: 2026-05-01`. The later version (c00197) adds a "Would Revise If" section with countable triggers, for example:

   > - Invented file paths or link targets ship without `<!-- VERIFY: ... -->` markers ≥1 time (the verification fallback is being skipped)

   (quoted from `corpus/fabioc-aloha_AIRS_Data_Analysis__.github_agents_markdown-author.agent.md`). This matches the proposal's position that runs, not the writer, judge quality, and it goes further by writing down in advance what observation would change the prompt.

## Where it conflicts with the proposal

- **No reader, no evidence tiers, no cutting rule.** It has none of the proposal's three core points in substance. The reader is the parent agent. "Verify" covers only link targets. Cutting shows up only as an example of a decision worth reporting ("dropped a redundant paragraph").

- **Notes travel in the same return as the deliverable.** The decisions sentence sits after a `---` divider in the same text. If the parent writes the return to a file unchanged, the note ends up in the document. The proposal requires a separate output. This file relies on the parent to strip the tail, and `---` is also a valid Markdown horizontal rule, so the parent cannot reliably tell the note from content.

- **Placeholders inside the deliverable.** `VERIFY` and `ILLUSTRATOR` markers are working notes placed in the file on purpose. That conflicts with the literal proposal ("never into the deliverable"). The conflict is productive: an in-band marker at the exact spot is easier for a caller to act on than a separate list. The proposal could allow machine-findable markers that the caller must resolve before the file ships. That would be an exception to write down, not a reason to drop the rule.

- **Direction of iteration.** The later version moves type-specific content *into* the role. c00197 swaps the skill list for inline rules and adds a roughly 240-line "Frontmatter Standard" for `docs/**/*.md`, scoped by path in prose:

  > The rules below apply ONLY to `docs/`; leave brain-artefact frontmatter alone unless explicitly asked to edit it.

  The proposal would put exactly that in a path-scoped rule file. This owner went the other way. The file does not say why. One possibility is that skills were not being loaded reliably, which would fit the change from "load and follow these skills" to "apply these rules". That is a guess. It is still worth checking in the kein setup: if the general writer does not reliably load path-scoped rules, the proposal's split fails in the same way.

## What it gets wrong or what looks untested

- **It says not to duplicate the skills, then duplicates them.**

  > When invoked, load and follow these skills exactly. Do not duplicate their content here:

  The next line lists nine markdownlint rule IDs with their meanings. Either the skill load was not trusted or the line was never reread.

- **A precedence rule imported from another worker.** `edgeLabelBackground` is a Mermaid diagram setting, but this worker is forbidden to make diagrams. The rule was apparently written after an illustrator failure and copied here, where it guards against nothing this agent does. That makes it the one run-derived rule in the file, and it is in the wrong file.

- **References the worker cannot resolve.**

  > **Never use em-dashes (`\u2014`).** Use commas, colons, semicolons, parentheses, or full stops. (Cardinal Rule 2 in the heir brain.)

  The file itself says the worker runs "in an isolated context window", so "Cardinal Rule 2 in the heir brain" names something it cannot see. The rule works without the citation. The citation is for the human maintainer. Also, the em-dash is written as the escape `\u2014`, not as the character. A model will likely read it correctly, but the c00197 trigger shows em-dashes shipping was a failure the owner was watching for.

- **"Do not guess" versus "no partial output".** A brief that is 90% answerable has two permitted responses: a `VERIFY` placeholder for the missing part, or `CANNOT_COMPLETE` for the whole task. The file does not say where the line falls. In practice this pushes toward whichever the model finds easier.

- **The frontmatter grants tools the prose never uses.** `search/codebase` and `search/usages` are granted, but no instruction says to search before writing. c00197 narrows the tools to `['edit', 'read']`. That could be a fix, or it could reflect a different repository. It does not show that search was misused here.

- **A contradiction in the successor, noted for completeness.** c00197's standard mandates YAML frontmatter, yet one of its revise-if triggers lists "docs under `docs/` ship with synonym field names, YAML frontmatter, trailing `\` artifacts" as a non-conformance. This is probably a leftover from the retired bold-label format. It shows the long inline version was not proofread against itself.

## Verdict

It is a good base for the **interface** of a general writer role. It is not a base for the role's substance, and it is not tied to a doc type: it is type-agnostic Markdown work by design, and it has been used for project docs and ADR-style docs.

Take:

- the fixed failure return
- the ban on partial output
- the `VERIFY` placeholder, extended from links to any claim whose source was not found
- the medium-based delegation placeholder
- "no narration"
- the rule that decisions are reported, capped in length

Change one thing: the decisions note should go in a separate output, not after a `---` in the same text.

Supply from elsewhere everything it lacks: the reader, evidence tiers, cutting, and fact versus interpretation.

The strongest lesson is from its successor, not its text. Writing "what would make us revise this" into the role gives the proposal's claim that runs judge quality something concrete to check. All 8 files count as one source.
