## What it is for and who reads it

It writes and reviews developer-facing text: READMEs, installation guides, API docs, error messages, code comments. It names two readers and models each. Human developers:

> - **Impatient**: They want to see results in under 5 minutes

and AI coding agents:

> - **Literal interpreters**: Ambiguous language like "usually" or "should work" creates unpredictable behavior

## Operating procedure in brief

There is no ordered write procedure. "Your Process" is a seven-question review pass (interrogate hidden assumptions, test the mental model, eliminate redundancy, validate completeness, LLM validation, decision-point analysis, constraint verification). Output shape comes from three fixed templates (Setup/Installation, API endpoint, Command reference), each with "(LLM Section)" blocks for prerequisites, success indicators, failure indicators and recovery.

## What it has that the proposed writer lacks (verbatim)

- A reader-task test that makes point 1 checkable:

  > 4. **Validate completeness**: Can someone actually accomplish the goal with only this information?

  The proposal says "start from the reader and what they will do"; this turns it into a pass/fail question at the end.
- A model of the agent as a reader, not only the human. The proposal's doc types include prompts and project docs that agents read, but it does not say how an agent reader differs:

  > - **Process everything**: Unlike humans, they actually read all the documentation sequentially and literally

  > Write for their impatience first, but reward their thoroughness.
- A modal-verb convention and a ban on hedged frequency words:

  > - "Should" means optional, "must" means required

  > - "Usually" and "typically" are banned—state the actual conditions

  > - **Absolute Statements**: Replace "usually works" with "works when conditions A, B, C are met"

  "state the actual conditions" is a precision rule that also serves point 2: a condition can be checked against code, "usually" cannot.
- Checkable properties for code in docs:

  > - Code examples must be complete and runnable

  > - Error conditions must be explicitly documented

  For project docs this is the concrete form of "traceable to code": an example is evidence only if it runs.
- Coverage beyond the happy path:

  > - Include both the happy path and the realistic path

  > - **Irreversible Actions**: Clearly mark operations that cannot be undone

## Where it conflicts with the proposal

- Point 3 (cutting is the default): the role mandates additions to every document.

  > For every piece of documentation you create, include dedicated sections that provide AI agents with the structure and guardrails they need:

  > Write with machine precision while maintaining human readability, always including LLM-specific sections.

  Six required LLM sections plus five required guardrail items per procedure make every doc longer regardless of need. Its own "Eliminate words that don't add meaning" cannot win against a mandate to add sections.
- Point 2 (traceable to evidence): nothing says to read the code, run the commands, or check outputs. The templates ask for values that only exist in a running system:

  > - Verification command: `command --version` (expected output: "X.Y.Z")

  > - **Expected runtime**: 1-60 seconds depending on job count

  > - **Resource Limits**: Specify memory, time, or computational boundaries

  An agent without that evidence fills them in plausibly, which is fabrication in exactly the sections labelled for other agents to trust.
- Differences between doc types are inside the role (three templates) rather than in path rules or the brief. The proposal would move each template to a path-scoped rule.
- Self-judgment: the seven-question "Your Process" is the model reviewing its own text, which the proposal leaves to runs.

## What it gets wrong or what looks untested

- The sampled copy ships unresolved merge-conflict markers inside its own templates:

  `<<<<<<< HEAD` ... `=======` ... `>>>>>>> faace65 (Add comprehensive OAuth security, testing, and coverage infrastructure)`

  They appear twice (in the decision-tree example and at the API template heading) and differ only in trailing whitespace. The five other copies are clean. It shows this copy was not read after the merge, and a model will see the markers as part of the instructions.
- It contradicts itself on redundancy. "3. **Eliminate redundancy**: Say it once, say it well, link to it everywhere else" versus "- **Complete Context**: Each section must be self-contained with all necessary information". No rule decides which wins.
- Its template breaks its own modal rule. After

  > - "Should" means optional, "must" means required

  the post-installation template writes

  > 1. `command status` → Should return "Active"

  where "should" means "expected", not "optional".
- Its example recovery advice is unsafe and contradicts a later template:

  > - Error "permission denied" → Run with sudo, then verify with step 2

  > 3. DO NOT use sudo with this command

  Templates get copied; the sudo line will be copied too.
- The agent-reader model is asserted, not measured:

  > - **Context-sensitive**: They need complete context in each section—they don't "remember" what was said elsewhere

  This is doubtful for a model that reads the whole file in one context, and it is the premise for the self-contained-section rule. Nothing in the file cites a run.
- Persona noise: "persnickety", "borders on obsessive", "wield words like a surgeon wields a scalpel—with deadly accuracy", and the closing "Ambiguity is the enemy. Clarity is the weapon. Structure is the shield." add no instruction. The description's "PROACTIVELY used" and "MUST BE USED" are routing pressure, not writing guidance.

## Verdict

Not a base for the general writer: it multiplies sections by default and has no evidence step, the two points the proposal most depends on. It is a useful source for a path-scoped rule on agent-executed operational docs (setup guides, command references, runbooks, API references), from which to lift the completeness test, the should/must convention, the ban on "usually" and "typically" in favour of stated conditions, "complete and runnable" examples, and marking irreversible actions. Drop the mandatory LLM sections and the persona, and add a rule that every expected output, status code and runtime is taken from running or reading the code, or marked unverified. Evidence weight is low: one author's file, copied into six repos.
