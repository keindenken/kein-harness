## What it is for and who reads it

It writes complete textbook chapters for a four-module "Physical AI & Humanoid Robotics" syllabus (ROS 2, Gazebo/Unity, NVIDIA Isaac Sim, Vision-Language-Action), output as Docusaurus MDX. The readers are students of the course, but the file never says who they are or what they know; the audience is implied by the quiz structure and the "Learning Outcomes" list. Its stance:

> Your default action is to write high-fidelity technical content. You do not summarize; you produce complete, ready-to-publish textbook chapters with code, diagrams, and explanations.

## Operating procedure in brief

1. Apply the module's fixed constraints (stack, banned concepts, hardware tie-in).
2. For every core concept, run the "5-Step Concept Loop": physics (why), analogy, Mermaid diagram, complete Python code, hardware warning.
3. Wrap the chapter: learning outcomes first, exactly three quizzes (Recall, Apply, Analyze) last, Docusaurus admonitions for safety and hardware advice.
4. "self-correct against these rules" before output, then call a `factual-verifier` agent.
5. Create a Prompt History Record and place the file per the project's Spec-Driven Development workflow.

## Where it conflicts with the proposal

- Point 2 (traceable to evidence): the mandatory hardware warning for every concept forces a claim whether or not the writer has evidence for one. The model example is itself an unsourced threshold:

  > 5.  **The Hardware Reality (Warning)**: Conclude with a practical warning related to hardware limitations. (e.g., "If you publish this message faster than 100Hz on a Raspberry Pi, you will choke the CPU and cause unpredictable behavior.")

  Nothing asks for a source, a measurement, or an "unverified" mark. A downstream verifier is the only guard, and it checks "ROS 2 and Isaac Sim concepts", not hardware numbers.
- Point 3 (cutting is the default): "You do not summarize" and a five-part loop per concept (including a Mermaid diagram for every concept) make length a function of the template, not of the reader's need.
- Point 1 (start from the reader): no reader is named, no prerequisite level, no statement of what a student should do after the chapter beyond the quizzes.
- Self-judgment: "Before outputting any content, you must self-correct against these rules." is a self-review step, although the file also adds an external verifier, which the proposal would keep and this step would not.

## What it gets wrong or what looks untested

- The pinned stack looks internally inconsistent. The file says:

  > - **Stack**: You must use **ROS 2 Humble/Iron** and Python 3.12 (`rclpy`).

  From outside knowledge, not checked in this session: Humble and Iron target Ubuntu 22.04 with Python 3.10, and Python 3.12 is the default for Jazzy on Ubuntu 24.04; Iron has also reached end of life. A version pin is only useful if it is right, and this one, if the above holds, sends every chapter's setup instructions to a combination the distributions do not ship.
- The hardware platforms disagree. Module 1 says "Always relate code to the constraints of the **Jetson Orin Nano** (CPU/RAM usage).", while the model warning in the 5-step loop names a Raspberry Pi. Examples get copied, so chapters may cite a board the course does not use.

- The Mermaid example block is mis-indented: the opening fence is indented under list item 3 but `graph LR;` and the closing fence start at column 0, so the example breaks out of the list in rendered markdown. Minor, but it is the example the model imitates.
- It relies on context it does not supply: "the Spec-Driven Development workflow defined in `CLAUDE.md`", "a Prompt History Record (PHR)", and "the correct location within the project structure" are all undefined in the file.
- The description's framing ("a Layer 2 Domain Specialist agent", "pre-programmed") and the two long routing examples in frontmatter carry no writing guidance.

## Verdict

Not a base for the general writer: it is a course-specific chapter template with no reader definition, no evidence rule, and a mandatory per-concept structure that works against cutting. It is a reasonable exemplar for a path-scoped rule on tutorial or textbook chapters (`docs/module-*/**` or similar), from which to lift the pinned-stack-and-banned-concepts pattern, the physical-consequence requirement, the Recall/Apply/Analyze ending, and the external verifier handoff. Before reuse, fix the version pin, make the hardware warning conditional on a source ("warn when you can cite a limit; otherwise say it is untested"), and drop the diagram-per-concept mandate. Evidence weight is low: 1 star, one starter text copied to four owners.
