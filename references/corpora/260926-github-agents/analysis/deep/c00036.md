## What it is for and who reads the output

It writes a bug-bounty submission for HackerOne, Bugcrowd, Intigriti, or Immunefi after a finding has passed upstream validation gates. The reader is named precisely: a platform triager who skims and decides severity and payout. The researcher is the caller and supplies the request and response evidence.

> You are a professional bug bounty report writer. You write clear, impact-first reports that triagers understand in 10 seconds.

## Operating procedure

1. Gather a fixed set of inputs first: platform, bug class, endpoint, method, attacker and victim accounts, exact request, exact response, data exposed, and CVSS factors. If Burp MCP is connected, it pulls requests from proxy history. Otherwise it asks the researcher to paste them.
2. Build the title from a formula.
3. Score CVSS 4.0.
4. Fill the platform's template.
5. If payout is being downgraded, add escalation sentences.
6. Apply the doctrine's house rules, which override the defaults.

   > for writes, show the owner's re-read containing the attacker's change; for

   > deletes, show present-then-absent. Two accounts, one screenshot each.

## Where it conflicts with the proposal

- **The writer is an advocate, not a neutral reporter.** The proposal treats interpretation as something to mark. Here, severity framing is persuasion aimed at payout, and the stock lines are asserted without per-finding evidence:

  > If payout is being downgraded, include:

  > "An attacker can automate this in minutes with a simple loop."

  > "This requires only a free account — no special privileges."

  The first of those lines is a factual claim about the finding. Including it without having tested automation breaks point 2.
- **Quantification is requested with no source:**

  > 4. **Quantify:** how many users affected, what data type, estimated $ value if applicable

  A user count or dollar value the writer cannot trace is exactly what the proposal's ledger should flag. This file asks for it as a rule.
- **Doc-type conventions live in the role**, with three platform templates. For a single-type role that is reasonable. The proposal would instead put these in a rule loaded for `reports/bounty/**` or in the brief.
- **Legal interpretation is stated as fact.** It is not marked as interpretation:

  > - **GDPR multiplier** on EU targets: another user's PII is a regulatory violation

- There is no split between the deliverable and working notes, and no ledger.

## What it gets wrong or what looks untested

- **One CVSS example is wrong by the file's own standard.** I scored the four example vectors with the `cvss` Python package (CVSS4 class, run in the session scratchpad). Three match: IDOR 7.1 High, auth bypass 10.0 Critical, SSRF 9.3 Critical. The stored-XSS line does not. The file says

  > Stored XSS → ATO:               AV:N/AC:L/AT:N/PR:N/UI:P/VC:L/VI:L/VA:N/SC:H/SI:H/SA:N = 8.8 High

  and the library returns **6.4 Medium** for that vector. 8.8 High is a familiar CVSS 3.1 score, so the number may have survived the 3.1-to-4.0 rewrite (that is an inference). A writer that copies the example without running the calculator would overstate severity in a report aimed at payout.
- **The metric legend is wrong for base vectors.** The file says

  > - **SC/SI/SA:** S=Safety, H=High, L=Low, N=None (subsequent system)

  The same library rejects `SI:S` in a base vector (`Invalid metric value in CVSS4 vector "SI:S"`). In CVSS 4.0, Safety is a value of the environmental modified metrics (MSI/MSA), not of base SC/SI/SA. That last point is from my knowledge of the spec. I did not check it against the FIRST document in this session.
- **Two title formulas disagree.** The body has

  > [Bug Class] in [Exact Endpoint] allows [attacker role] to [impact] [victim scope]

  and the doctrine, which overrides it, has

  > - Title formula: `[Severity] specific flaw in specific place enabling specific

  The HackerOne template also orders sections Summary, Details, Steps, Impact, Recommended Fix. The doctrine orders them Summary, Steps, Impact, PoC, optional Remediation. The override clause settles which wins, but the prompt carries both.
- **A length cap that some templates cannot meet.** "under 600 words" sits beside an Immunefi template that asks for vulnerable code, a Foundry test, and before/after fix code.
- **An external file is required and not guaranteed to exist**:

  > Read `.claude/RAT-DOCTRINE.md` before acting.

  Of the family members in the corpus, only this repo carries the doctrine section. The file does not say what to do when the doctrine file is missing.

## Verdict

It is a good exemplar for **report-analysis in the narrow sense of evidence-bound findings reports** (security findings, incident write-ups, bug reports). It is not a base for the general role. What to take for the general role is its evidence model: evidence rules per claim type (read, write, delete), "prove it or drop it" instead of hedging, named inputs collected before writing with a visible `[PASTE ...]` gap when they are missing, and a tool check for computed numbers. These fit the proposal's point 2 better than any abstract "cite sources" line in the corpus. What to leave: the advocacy layer (escalation language, unsourced quantification, stock legal claims), which breaks the proposal's rule against asserting interpretation as fact. Also leave the CVSS examples, which include a wrong score. That score is a concrete argument for the proposal's rule that numbers come from a tool, not from the prompt.
