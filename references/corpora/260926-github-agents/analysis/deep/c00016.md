## What it is for and who reads the output

It writes documentation for one product family: the TaxCore fiscal invoicing platform and its Secure Element Reader desktop app. The description says it can also "review" docs. It names three reader groups and gives each its own method:

> - Tailor content to the audience: taxpayers and tax officers (end users), developers/integrators, or tax authority operators

## Operating procedure

It has no step sequence. The file is a domain glossary (lines 14-61), a product summary (lines 63-71), responsibilities, a method for each doc type (end-user guides, developer docs, reference, setup guides), structure requirements, a canonical PIN-lock table, a seven-item quality checklist, and a list of situations that call for a clarifying question. It declares `tools: ["codebase"]`.

## What it has that the proposed writer lacks

1. Controlled vocabulary with forbidden synonyms. The proposal has no terminology mechanism:

   > - Use correct TaxCore terminology consistently (e.g., "Secure Element" not "chip", "TAP" not "portal", "SE Applet" and "PKI Applet" as distinct components)

2. A canonical table that must be reproduced, not paraphrased. The writer gets fixed wording for a safety-relevant state space:

   > Always document PIN lock states using these exact canonical names and descriptions:

   > | PKI Applet locked, SE Applet OK | 5 wrong TAP login attempts | Return card to tax authority; card can still issue invoices |

   > In all locked cases: the smart card must be returned to the tax authority, replaced, and the Secure Element must be revoked.

   This is a way to keep facts consistent across documents that the proposal's evidence rule does not cover: some facts are fixed by the owner and copied word for word.

3. Scope marking for each feature by platform:

   > - Always distinguish Windows-only features (audit, pending commands) from cross-platform features

   A reader on macOS who follows an audit guide would fail. The rule ties the reader's situation to a fact that has to be marked on the page.

4. A check against the real UI, naming the elements:

   > 7. Verify step-by-step instructions match the actual application UI (Get Reader, Get Certificate, Verify PIN buttons)

5. Concrete triggers for asking the caller, each tied to a fact the doc depends on:

   > - If the target audience is ambiguous (taxpayer vs. developer vs. tax authority operator)

   > - If the documentation should reference a specific TaxCore version or jurisdiction

6. A rule for novice readers that the proposal's "start from the reader" implies but never spells out:

   > - Assume no technical background; avoid jargon or define it on first use

## Where it conflicts with the proposal

- The prompt is used as the evidence. The product facts (lock after 5 attempts, which features are Windows-only, ".NET 6 and Avalonia", button names) are stated in the role and never traced to code or product documentation. The proposal's point (2) wants each factual sentence traced to code. Here the writer is told to trust the prompt:

  > You are deeply familiar with the following TaxCore concepts and must use them accurately in all documentation:

  If the product changes, the role keeps stating the old facts, and nothing in the file would catch it.
- Placement. The whole file is product-specific. The proposal would make the glossary, the canonical table and the platform marks a path-scoped rule (or a reference file the rule points to) for the TaxCore docs tree. The general role would stay free of them. This file is essentially that rule, packaged as a role.
- It does not favour cutting, and one structure rule adds material by default:

  > - Include a table of contents for documents with more than 5 sections

- No caller output. It returns only the document. Assumptions, uncertain terminology and platform ambiguities go to a clarifying question if they go anywhere. In an unattended run there is no channel for them.
- It has nothing on combining drafts or on evidence tiers.

## What it gets wrong or what looks untested

- It sets a check that its tools cannot perform:

  > 6. Confirm all code examples are syntactically correct C# / .NET 6

  With `tools: ["codebase"]` it can read code but cannot compile. "Confirm" here means the model's own judgement.
- Some facts in the prompt may be out of date. .NET 6 reached end of support in November 2024. The role still presents it as the stack, with no date and no source. That is the risk of keeping facts in a role, shown in the role itself.
- The quality checklist is all self-review ("Verify TaxCore terminology is used correctly"). It has no mechanism beyond the glossary in the same prompt.
- The description says it will "review documentation", but the file has no review procedure or output format. Only the checklist exists.
- A large glossary (about 45 lines) is loaded on every call, including a one-paragraph fix. In a rule file it would load only when TaxCore docs are touched.
- It records no incident or measurement. It reads as one domain expert's knowledge written down, which is valuable as knowledge but untested as prompting.

## Verdict

It is not a base for the general writer role. It has no procedure, no evidence tracing and no caller output. It is the best exemplar in this set for a **path-scoped domain rule file for one product's project docs and end-user guides**. That file would hold controlled vocabulary with forbidden synonyms, canonical tables to reproduce word for word, platform-scope marks, the named UI elements that steps must match, and ask-triggers tied to specific facts. Two changes are needed before borrowing that shape. Each fact in the rule should carry its own source (a code path or product doc) and a date, so the rule does not become untraceable evidence. The compile check should become something a run does, not something the writer claims. Its popularity is catalogue traffic, so it counts as one source.
