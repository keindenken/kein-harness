## What it is for and who reads its output

It is a general documentation role for a software project: API references, tutorials, how-to guides, explanations, ADRs and changelogs. Its readers are developers who use the code, and each doc type assumes a different reading mode: "API references that developers can scan in seconds, tutorials that build confidence through incremental complexity, and architecture documents that capture the reasoning behind decisions."

## Operating procedure in brief

1. Pick the Diataxis type: reference, tutorial, how-to, or explanation.
2. Audit existing docs against the code.
3. Name the audience for each document.
4. Write the document with the type-specific shape: reference extracted from source, tutorials as numbered steps with visible results, how-tos organized by intent.
5. Add runnable examples, set up doc tests and auto-generation in CI, and write a style guide.
6. Check the result: run the examples, confirm API coverage, check links, build cleanly, and have an unfamiliar person review it.

## What it has that the proposed writer lacks (verbatim)

- A reader definition with three parts, which makes point 1 concrete: "Define the audience explicitly for each document including their assumed knowledge level, common goals, and the questions they arrive with." The proposal says "start from the reader and what they will do". "the questions they arrive with" is a usable prompt for that.
- A doc-type classification before writing: "Identify the documentation type needed: reference (API docs), tutorial (learning-oriented), how-to guide (task-oriented), or explanation (understanding-oriented) using the Diataxis framework." The proposal carries type differences in path rules or the brief. A path cannot tell a tutorial from a reference when both live under `docs/`, so the writer or the caller still has to classify. Diataxis is the most common classification scheme in the corpus.
- An audit of existing docs against three kinds of evidence: "Audit existing documentation for accuracy by cross-referencing code signatures, configuration schemas, and runtime behavior against what is documented." The proposal says "code for project docs". This line breaks that into signatures, schemas and runtime behavior, and applies it to docs that already exist, not only to new text.
- A completeness check, which balances cutting: "Verify every public API function appears in the reference documentation." The proposal makes cutting the default and has no rule for when leaving something out is an error. For reference docs, coverage of the public surface is that rule.
- A statement of scope in the document itself: "Create how-to guides organized by user intent with clear prerequisites, concise steps, and explicit statements about what is not covered."
- Execution as evidence for examples: "Run all code examples from documentation and confirm they execute without errors." This is the "measured" tier applied to a document's own code blocks.
- Type-specific required fields, for example "API reference entries must document parameters, return types, thrown exceptions, and at least one usage example." and "Deprecated features must be documented with migration paths and removal timelines."

## Where it conflicts with the proposal

- Scope. It is a docs-program owner, not a writer. Steps 8 to 10 build infrastructure: "Implement documentation testing by extracting code blocks and running them in CI", "Set up auto-generation pipelines for API references using TypeDoc, rustdoc, Sphinx, or equivalent tools integrated into the build process", and "Create a documentation style guide". A writer that is told to cut would not add CI pipelines and a style guide to a request for one page.
- Cutting (point 3). Its example rule points the other way: "Add runnable code examples for every public API surface" and "Every code example must specify the language for syntax highlighting and include expected output." These are fixed volume rules, not decisions made for the reader.
- Where type knowledge lives. Keep a Changelog sections, the ADR headings and the reference-entry fields are all inside the role, while the proposal puts them in path rules. The file is short, so this costs little here. The pattern still grows badly as more types are added.
- Evidence and interpretation. It has no rule that separates interpretation from fact. ADRs "capture the reasoning behind decisions", but nothing says where that reasoning comes from (commit history, issues, the requester) or that it must be marked as reconstructed.
- Working notes. It has no output contract and no place for reasoning outside the deliverable.

## What it gets wrong or what looks untested

- A verification step an agent cannot do: "Review with a person unfamiliar with the project to validate that tutorials can be followed without supplementary context." With no person available, the agent either skips the step silently or pretends to do it. No fallback is given, for example a fresh-context subagent that follows the tutorial.
- A checklist it cannot keep: "Confirm the documentation builds cleanly with the static site generator without warnings." It assumes a site generator exists. "Links must use relative paths within the documentation set and be validated in CI" assumes CI.
- It is a list of best practices with no priority. There are ten process steps, seven standards and six checks, and nothing says which to drop when a request is small. That is where padding tends to come from.
- `model: opus` in the frontmatter fixes the model inside the role file.
- There is no sign of evaluation: no worked example, no failure case, and nothing in the wording that points to an observed failure.

## Verdict

It should not be the base for the general writer. It mixes writing with building doc infrastructure and has no cutting rule. It is a good source for a path-scoped rule for software documentation (`docs/**`, API reference trees): the Diataxis classification, the three-part audience line, the audit against signatures, schemas and runtime behavior, the public-API coverage check, and the rule to run every example. One line is worth lifting into the general role's point 1: "the questions they arrive with". The Diataxis idea has independent recurrence behind it (28 owners). The rest is one catalog voice.
