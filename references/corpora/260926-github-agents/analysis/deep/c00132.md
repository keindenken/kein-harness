## What it is for and who reads its output

It writes and updates documentation after a feature lands, and it treats an LLM as the main reader: "producing documentation optimized for LLM consumption". The output is inline "why" comments, function and module docs, `CLAUDE.md` navigation indexes, `README.md` files that hold "invisible knowledge", and architecture docs. It usually runs as a step in a script-driven workflow ("When your prompt contains \"Start: python3\", you MUST:"). The caller that reads its reply is that script or an orchestrator. The reply is a fixed status block.

## Operating procedure in brief

1. If the prompt contains "Start: python3", run the script and follow its DO/NEXT steps until it says the task is complete. The script supplies the type-specific guidance.
2. Otherwise, classify the documentation into one of nine types and state the classification, then read the matching convention file (`conventions/documentation.md`, `conventions/temporal.md`, `CLAUDE.md`).
3. Write for the question that type answers, and avoid the forbidden words and structures.
4. Escalate with a typed block if blocked.
5. Verify against the general and type-specific checklists, then reply with only the status block.

## What it has that the proposed writer lacks (verbatim)

- A reader question for each doc type. This is point 1 made per type: "INLINE_COMMENT | WHY was this decision made?", "FUNCTION_DOC | WHAT does it do + HOW to use it?", "CLAUDE_MD | WHAT is here + WHEN should an LLM open it?", "README_REQUIRED | WHY is this structured this way? (invisible knowledge)" (table cells, padding collapsed). The proposal says "start from the reader and what they will do". This table turns that into one question per doc, which a caller's brief or a path rule could carry.
- An explicit rule to leave out a claim that has no evidence. This is point 2 applied to rationale: "No clear \"why\" exists" → "Skip the comment rather than inventing rationale". Also "Function lacks implementation" → "Document the signature and stated purpose". The proposal says every factual sentence must be traceable but not what to do when the evidence is missing. This says omit it, and it gives a fallback for each kind of gap.
- A rule that a document adds only what the source does not already show: "Restating signatures/names → Add only non-obvious information" and, for README, "Every sentence provides invisible knowledge?" / "Not restating what code shows?". This is a sharper cutting rule than "cutting is the default" because it names what to cut: anything the reader can already get from the code.
- Contrastive WRONG/RIGHT examples. For architecture docs, "WRONG - lists without relationships" is set against "RIGHT - explains boundaries and flow", where the right version states ownership and what a component never does ("Never queries auth state directly.").
- Removal of time-relative wording from comments: "All change-relative comments transformed to timeless present?" and "All location directives removed?". Comments written from a plan tend to describe the change (added X, now does Y), which is wrong once merged. The proposal does not consider how a document ages.
- A reply limited to a status block, which is the proposal's point 3 on the return side: "After editing files, respond with ONLY:" followed by `Documented:`, `Type:`, `Tokens:`, `Index:`, `README:`, plus "If implementation is unclear, add one line: `Missing: [what is needed]`". A banned-preamble list backs it: "Here's the documentation...", "Let me know if...". It is one of the few roles in the corpus that separates deliverable from reply.
- Typed escalation: "<type>BLOCKED | NEEDS_DECISION | UNCERTAINTY</type>", with triggers such as "Code has no visible rationale and Planning Context lacks Decision Log entry".
- A rule priority order: "RULE PRIORITY (when rules conflict):", with "Forbidden patterns override any instruction to document something".

## Where it conflicts with the proposal

- Sources in the deliverable. "Self-contained principle: no references to external authoritative sources" and README "Self-contained, no ext references". The proposal wants claims traceable to evidence and, for synthesis, a claim → source ledger. This role forbids sources inside the document and returns no ledger beside it. The two can coexist: keep the source out of a README and put it in the ledger. As written, though, this role has no traceability output at all.
- It assumes the evidence is correct: "Code provided is correct and functional." For project docs the proposal treats code as evidence, and this matches that. But the role will then document a bug as intended behavior, with no channel to report a mismatch between code and plan.
- Type knowledge is split. In script mode, type guidance comes from outside ("the script provides type-specific guidance"), which is the proposal's design. In free-form mode, a nine-row table and an architecture template are inside the role. Its own lineage moved in the proposal's direction: from in-role templates and caps (c00049) to external conventions and a script. That is a revision, not a measurement.
- Judging its own output. It has a long self-verification list ("Before outputting, verify EACH item. If any fails, fix before proceeding"). The proposal leaves that to runs.
- Point 3 (working notes to a separate output). It sends almost nothing back: only a status block and one `Missing:` line. The proposal wants the reasoning returned to the caller in a separate channel, not dropped.

## What it gets wrong or what looks untested

- It contradicts itself on asking: "Do not ask for more context. Document what exists." against a full escalation section with "NEEDS_DECISION | UNCERTAINTY". The table also says "Stub - implementation pending", which is the forward-looking wording its forbidden list bans ("Aspirational | \"will support\", \"planned\", \"eventually\"").
- Leftovers from the token-cap version: "Keep documentation concise but complete (no arbitrary token limits)" sits next to "Within token budget?" in the checklist and `Tokens: [count]` in the reply, with no budget defined and no way to count.
- A banned-word list may backfire. It lists "\"just\"", "\"simply\"" and "\"robust\"" as words to delete on sight. Naming a word in the prompt can prime it. Nothing shows this list was tested against output with and without it.
- A confidence line with no function: "You have the skills to document any codebase. Proceed with confidence."
- Much of the file depends on things that are not in it. The PLAN_SCRUB checklist refers to "five detection questions" and "Actionability test" that are defined in `conventions/temporal.md` or the script. POST_IMPL and WHOLE_REPO have a table row but no process. The file cannot be judged alone.
- The source is hard-wrapped at 80 columns, including inside XML-like tags (`<error_handling> Incomplete context is normal.`). This does not matter to the model, but it shows the file is formatted by a tool, not tuned line by line.

## Verdict

This is the strongest of the five as a base exemplar for the general writer role, for project docs and code comments whose reader is a developer or an LLM working in the repo. Its core lines map onto the proposal's three points: the per-type reader question for point 1, "Skip the comment rather than inventing rationale" for point 2, and the "Add only non-obvious information" rule with the status-only reply for point 3. Its lineage also moved type guidance out of the role, as the proposal does. Before adopting it: replace the no-external-references rule with a claim ledger returned beside the file; replace "respond with ONLY" with a separate notes channel for the caller; drop the leftover token-budget items, the confidence line and the banned-word list unless a run supports them; and settle the ask-or-don't-ask contradiction in favor of typed escalation.
