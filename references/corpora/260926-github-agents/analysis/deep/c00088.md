## What it is for and who reads the output

It writes documentation for the AdCP advertising protocol and its SDKs, published with Mintlify. It is unusual because it names three readers and treats two of them as machines:

> 1. **Human developers** reading docs in a browser

> 2. **Coding agents** (Claude Code, Cursor, Copilot) building integrations from your docs

> 3. **AI assistants** retrieving docs via RAG/search at runtime

It also covers formats whose reader is always a model: SKILL.md files, MCP/A2A tool descriptions, and CLAUDE.md rules files.

## Operating procedure

The procedure is short. The rest of the file is format templates and rules for each doc type. The procedure is the "Response Framework" at the end (lines 293-302): identify the audience, choose the format, write for the primary reader first, make every example complete and runnable, test readability, and keep sections self-contained. There is no step for reading code or specs, no input contract, and no return format apart from the document itself.

## What it has that the proposed writer lacks

1. A reader test phrased as a question a separate run could answer. The proposal's point (1) says to start from the reader. It does not turn that into a check. This line does, for a reader that is an agent:

   > 5. **Test readability** — would a coding agent with no prior context produce correct code from this doc alone?

   An eval could run this directly: give the doc to a fresh agent and see whether the code it produces works. That fits the proposal's rule that runs judge quality, not the writer.

2. Retrieval as a reader with its own constraints. The proposal has no idea of a reader that sees only one section at a time:

   > - **Self-contained sections** — each H2/H3 section should make sense without reading the rest of the page

   > 6. **Keep sections self-contained** — assume RAG retrieval may return any single section in isolation

   > - **Keyword-rich headings** — use the terms developers actually search for, not clever names

3. Concrete rules for agent-facing example code. Each one can be checked in the output:

   > 1. **Always show the import** — agents don't know your package's export structure

   > 3. **One operation per code block** — agents extract individual blocks, not pages

   > 6. **No "..." elision** — show every required field, even if the example is longer

   > - **Request + response pairs** — always show what goes in and what comes back

4. A traceability rule for prompt files. It has the same idea as the proposal's point (2), applied to rules files:

   > - Don't write aspirational guidelines — only document what's actually enforced

   > - Don't duplicate what's in tsconfig/eslint/package.json — agents can read those

5. Scope exclusions for a document type, which say what a SKILL.md must leave out:

   > 7. **No authentication details**: Handled by transport layer, not task reference

   > 8. **No version numbers**: Skill files describe current behavior only

   > 9. **No implementation details**: No databases, infrastructure, or internal architecture

## Where it conflicts with the proposal

- Placement. Almost all of the file is format rules for particular doc types (SKILL.md, tool descriptions, SDK quickstarts, CLAUDE.md, Mintlify). The proposal would move each block into a path-scoped rule. The file's sections already line up with paths (`SKILL.md`, `CLAUDE.md`, `/docs/**/*.mdx`), so the split would be easy. That supports the proposal's placement, even though the file itself does the opposite.
- It has no evidence step. Its standard is "runnable", not "true to the source". It asks for invented but plausible values and gives no source to check them against:

  > 4. **JSON examples with realistic values**: Not `"string"` or `"example"` — use plausible data

  > 2. **Always show the response shape** — as a comment after the call, with realistic values

  A made-up response shape written as a code comment reads as documented behaviour. The proposal's point (2) would require each shape to come from the schema or a captured response.
- It treats reasons the opposite way for prompt files. The proposal keeps working reasoning out of the deliverable. This file removes the reasons behind the rules as well:

  > - Don't explain why — agents need the rule, not the reasoning

  That is a separate question from where working notes go. Anthropic's own prompting guidance (the vendor-documentation tier) recommends giving the motivation behind an instruction. For the prompt doc type this rule sits below vendor documentation and should not be adopted without a run.
- It has nothing on combining drafts or outside examples, and no ledger.

## What it gets wrong or what looks untested

- Several numbers and mechanisms are stated as fact without a source:

  > - **Sections under 500 words** — large sections get truncated or summarized by retrieval systems

  > 1. **First sentence is everything** — models often only read the first line to decide relevance

  > 3. **Budget ~100 tokens per tool description** — tool descriptions compete for context window space

  Retrieval chunk sizes depend on the retrieval system. A model is given the whole tool description, not only its first line. The front-loading advice may still help, but the stated reason is a guess. None of the three has a measurement behind it.
- The "every sentence actionable" rule for agent readers pulls against the progressive-disclosure rule for human readers on the same page. The file never says which wins when one page serves both:

  > - **No narrative filler** — agents skip prose looking for structured content. Every sentence should be actionable.

  > - Progressive disclosure: overview, details, edge cases

- "Every example must be complete and runnable" has no step that runs anything, and the file declares no tools. It is a stated standard with no check behind it.
- The "Platform Translation Knowledge" section (TTD, DV360, Meta, Amazon DSP hierarchies) is reference material that no step uses. It adds tokens to every invocation, including a CLAUDE.md edit.
- The persona line ("expert technical documentation specialist with deep knowledge") has no behaviour attached to it.

## Verdict

It is not a base for the general writer role, because it has no evidence discipline and its core is doc-type format. It is the best exemplar in this set for **agent-consumed documents**: prompt-instructions (SKILL.md, CLAUDE.md, tool descriptions) and API reference that coding agents will read. Split its blocks into path-scoped rules for those paths. Move two items into the role or the eval: the "coding agent with no prior context" test as the reader check for agent-facing docs, and "only document what's actually enforced" as the traceability rule for prompt files. Drop the invented-values rule, or rewrite it so that values come from schemas or captured responses. Treat the 500-word, first-line and ~100-token figures as single-source claims until a run tests them. It is one owner's file, so it counts as one voice.
