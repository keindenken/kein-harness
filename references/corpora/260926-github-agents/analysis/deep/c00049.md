## What it is for and who reads its output

It documents a feature after it is implemented: module or package header comments, function docs, usage examples and ADRs. The readers are developers who maintain or call the code. The file does not name them. The closing line states the design goal: "Concise documentation is more likely to be read and maintained. Every word must earn its place."

## Operating procedure in brief

1. Read the implementation and find "the one core pattern/abstraction" and "the most common usage scenario".
2. Fill the matching template (module doc, example, ADR) and stay within the token cap.
3. Cover practical use: how to use it, how errors are handled, what breaks it.
4. Check consistency with CLAUDE.md, confirm that examples would work, and count tokens before submitting.

## What it has that the proposed writer lacks (verbatim)

- An ordered cutting procedure. The proposal says "cutting is the default" but not what to cut first: "If approaching limit, remove: 1. Adjectives and adverbs 2. Redundant explanations 3. Optional details 4. Multiple examples (keep one)". An explicit order is easier to follow and to check than a general instruction to cut.
- A length budget per doc type: "Package docs: 150 tokens MAX. Function docs: 100 tokens MAX." The proposal gives no size for anything. A per-type budget belongs in a path rule, not in the general role, but it is one concrete form that "cutting is the default" can take.
- A distinction between actual and intended behavior, which sharpens point 2 for code docs: "Understand actual behavior, not intended". Together with "NEVER write aspirational documentation" and "NEVER document unimplemented features", this names the most common way code docs go wrong: the doc describes the plan, not the code.
- Failure modes as required content: "What breaks it" and "How to handle errors" under "Focus on practical usage". The proposal's reader-first point does not say that the reader's first question about code is often how it fails.
- A guard against writing unrequested docs: "NEVER create docs unless asked".
- A preference for showing over telling: "ALWAYS prefer code examples over prose".

## Where it conflicts with the proposal

- Point 2, through the template. The module template makes the writer fill slots whether or not the code supports them: "Error handling uses [pattern]. Thread safety: [safe/unsafe] because [reason]." A writer that must fill "Thread safety" will produce a claim even when the code gives no basis for one. The proposal requires every factual sentence to be traceable, and a mandatory slot works against that. Its successor, c00132, adds the missing escape: its table maps the case `No clear "why" exists` to "Skip the comment rather than inventing rationale".
- The ADR template makes the writer state a decision's status and rationale: "Accepted - [Date]" and "[Problem in 1-2 sentences. Current pain point.]". It gives no source for either, and the agent runs "after feature completion", when the decision context may not be in view. Under the proposal, a reconstructed rationale is interpretation and must be marked.
- Where type knowledge lives. Three templates and two caps are inside the role. The proposal puts them in path rules.
- Point 1. There is no reader step. The record's audience_first flag is false.
- Working notes. There is no output contract. Nothing keeps reasoning out of the deliverable or sends it to the caller.

## What it gets wrong or what looks untested

- The model is asked to count tokens it cannot count: "ALWAYS count tokens before submitting" and "Count tokens before finalizing". No tool is given. The conversion table ("150 tokens ≈ 100-120 words ≈ 6-8 lines of text") is a workaround, which suggests the author knew this. The cap is called absolute ("If you exceed limits, rewrite shorter. No exceptions."), but nothing checks it.
- Its own lineage dropped the cap. The newer version, c00132, reverses the rule: "Keep documentation concise but complete (no arbitrary token limits)". One adopter archived this file as `.archive_deprecated_20251025_technical-writer.md`. The file shows no measurement either way. The revision is the closest thing to evidence, and it points against the hard cap.
- "ALWAYS verify examples would work" asks for a mental simulation ("would work"), not execution, although the model has no tool restriction.
- "Module/package docs identical across all related files" is unexplained. Read literally, it asks for duplicated text.
- "ALWAYS skip test directories" is a project-specific rule placed in a general role.
- "RULE 0 (MOST IMPORTANT)" puts length above accuracy. A doc that is short and wrong passes rule 0.

## Verdict

It should not be a base. Its own lineage moved away from its central rule, and its templates force claims the code may not support. A few parts are worth lifting. The ordered cut list (adjectives, redundancy, optional detail, extra examples) could go into the general role as the concrete form of point 3. "actual behavior, not intended" and "What breaks it" could go into a path rule for code comments. The per-type caps might go into such a rule as soft budgets, if runs show they help. Evidence weight: one upstream voice, and the same voice as c00132.
