## What it is for and who reads the output

It writes developer documentation: READMEs, API references, tutorials, and conceptual guides. The reader is a developer using a project, placed on a user journey. The file also gives the role docs infrastructure work (Docusaurus/MkDocs setup, CI docs builds, analytics) and team process (standards, contribution guides).

## Operating procedure

It has six steps: understand before you write (interview the engineer, run the code, read issues and tickets), define the audience and entry point, outline first using Divio's four categories, write, test and validate (test examples in a clean environment, read aloud), a review cycle (engineering, peer, user testing), and publish and maintain (same PR as the feature, a review calendar, analytics). Then come templates (README, OpenAPI, tutorial, docusaurus.config.js) and success metrics.

## What it has that the proposed writer lacks

1. Reader-first made concrete: it places the document on the reader's path rather than only naming a reader. The proposal says "start from the reader and what they will do". This is a checklist for doing that:

   > - Where does this doc sit in the user journey? (discovery, first use, reference, troubleshooting?)

   > - What do they already know? What must be explained?

2. Evidence about where readers fail, not only evidence for facts. The proposal's traceability covers claims ("code for project docs"). It says nothing about finding out what readers get wrong:

   > - Read existing GitHub issues and support tickets to find where current docs fail

3. A self-test of setup instructions by execution, which is a traceability check for procedures:

   > - Run the code yourself — if you can't follow your own setup instructions, users can't either

4. A deletion test tied to the reader's action. This is the proposal's third point written as a rule, and the corpus's best-known phrasing of it (see `themes/length.md`):

   > - **Cut ruthlessly**: If a sentence doesn't help the reader do something or understand something, delete it

5. Precise failure text in place of vague advice:

   > - **Be specific about failure**: "If you see `Error: ENOENT`, ensure you're in the project directory"

6. A rule that keeps document kinds apart, which the proposal does not address:

   > - **Divio System**: Separate tutorials (learning-oriented), how-to guides (task-oriented), reference (information-oriented), and explanation (understanding-oriented) — never mix them

7. A fast README acceptance test:

   > - Every README must pass the "5-second test": what is this, why should I care, how do I start

## Where it conflicts with the proposal

- **The role goes beyond writing.** It includes setting up docs pipelines, CI integration, analytics, A/B tests, and content audits. The proposal's writer produces a document plus a ledger for a caller. This file's role is a whole documentation function.

  > - Set up documentation pipelines using Docusaurus, MkDocs, Sphinx, or VitePress

  > - A/B testing different README structures to see which drives higher adoption

- **Type conventions live inside the role** (README, OpenAPI, and tutorial templates, and a full `docusaurus.config.js`), where the proposal moves them to path-scoped rules.
- **Success is defined by outcomes the agent cannot observe.** The proposal leaves judgement to runs and evals. This file sets targets no single run can measure:

  > - Support ticket volume decreases after docs ship (target: 20% reduction for covered topics)

  > - Developer NPS for docs ≥ 7/10

- There is no separate output for notes or reasoning, and no ledger. The `termination` field ("Documentation published...") names publishing as the end, not a hand-back to a caller.

## What it gets wrong or what looks untested

- **Invented memory.** The persona claims experience and recall the agent does not have. This can lead the model to state "what developers read" as fact with no source, which is the opposite of the proposal's traceability:

  > - **Memory**: You remember what confused developers in the past, which docs reduced support tickets, and which README formats drove the highest adoption

- **Steps a subagent cannot perform**:

  > - Interview the engineer who built it: "What's the use case? What's hard to understand? Where do users get stuck?"

  > - User testing with a developer unfamiliar with the project (watch them read it)

  Unless the caller supplies answers, these either get skipped quietly or get simulated. A simulated interview is fabricated evidence.
- **An absolute test claim with no stated means.** The frontmatter lists no tools, so whether a snippet can be run depends on the host:

  > - **Code examples must run** — every snippet is tested before it ships

- **The README template ships placeholder badges and links** (`badge.fury.io/js/your-package`, `docs.yourproject.com`). A model filling it in is likely to leave or invent badge URLs. GSD's c00006 forbids this explicitly ("Do not fabricate badge URLs").
- **The numbers look chosen, not measured**: "within the first 30 seconds", "under 15 minutes", "≥ 80%", "≤ 2 days". None has a source.
- **Keep versus cut is unclear.** "Deprecate old docs, never delete" is a docs-site policy, but it sits beside "Cut ruthlessly" with no scope note. A writer might read it as "never remove content".

  > - **Version everything** — docs must match the software version they describe; deprecate old docs, never delete

## Verdict

It is not a base for the role. It is persona boilerplate from a generator, it takes on a scope far wider than writing, and its success metrics cannot be checked in a run. Take its **reader-location questions** (user journey stage, what the reader already knows), its **evidence-of-reader-failure step** (issues and tickets), and its **deletion test** as candidate wording for the proposal's points 1 and 3. Each is one line and fits a general role, not only project docs. Put the Divio split and the 5-second README test in path-scoped rules for project docs. Keep in mind that the family's wide spread (54 repos plus translations) comes from one template being copied. It is not evidence that the lines work.
