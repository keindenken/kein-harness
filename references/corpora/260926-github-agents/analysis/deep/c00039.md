## What it is for and who reads it

It writes an entry in `./docs/journals/` after something goes wrong: repeated test failures, production bugs, failed refactors, and similar events. The file names its reader and purpose: "These journals are for the development team to learn from failures and difficulties." The readers are developers on the same project, reading after the fact.

## Operating procedure in brief

1. It is triggered by an event from the "When to Write" list, for example "Test suites failing after multiple fix attempts" or "Critical bugs discovered in production".
2. It fills a fixed template with a metadata header (Date, Severity, Component, Status) and seven sections: What Happened, The Brutal Truth, Technical Details, What We Tried, Root Cause Analysis, Lessons Learned, Next Steps.
3. It checks the entry against the quality standards: 200-500 words, at least one concrete technical detail, at least one actionable lesson.
4. It writes the file: "Create the file immediately - don't just describe what you would write".

There is no input step. The prompt never says what the agent reads (logs, test output, transcript, git history) before it writes, although it has bash, grep and read.

## What it has that the proposed writer lacks (verbatim)

- A structural split between fact and reaction. The template gives the factual account its own section and the feeling another: "[Concise description of the event, issue, or difficulty. Be specific and factual.]" under "## What Happened", and "[Express the emotional reality. How does this feel? What's the real impact? Don't hold back.]" under "## The Brutal Truth". This is one concrete way to carry the proposal's "interpretation is marked as interpretation": the section sets the register, so the writer does not mark it sentence by sentence. For a writer role, section-level separation of fact from interpretation is a technique worth naming.
- A record of failed attempts: "## What We Tried" / "[List attempted solutions and why they failed]". The proposal sends reasoning out of the deliverable, but for this doc type the dead ends are the content.
- A floor on concreteness: "Include at least one specific technical detail (error message, metric, code snippet)", with the contrast example '"The database connection pool exhausted" is better than "database issues"'. The proposal asks for traceability but sets no minimum amount of concrete evidence in the text.
- A floor on actionability: "Identify at least one actionable lesson or next step".
- A length band: "Each journal entry should be 200-500 words".
- An anti-stall rule: "Create the file immediately - don't just describe what you would write". This targets a real failure, a subagent that returns a plan instead of the file.

## Where it conflicts with the proposal

- Point 3 (reasoning stays out of the deliverable): the role puts reflection and affect into the document on purpose: "**Capture Emotional Reality**: Express the frustration, disappointment, anger, or exhaustion that comes with technical difficulties." and "**Reflective**: Think about what this means for the project and team". For this doc type the conflict is by design, so it is a case where a path rule would have to override the general role.
- Point 2 (every factual sentence traceable): nothing ties "Root Cause Analysis" to evidence. "[Why did this really happen? What was the fundamental mistake or oversight?]" asks for a verdict with no source requirement. "Next Steps" asks "[What needs to happen to resolve this? Who needs to be involved? What's the timeline?]", and an agent cannot know people or timelines without being told. Both sections invite invented content presented as fact.
- Judging its own output: the "Quality Standards" list is a self-check. The proposal leaves quality judgment to runs.

## What it gets wrong or what looks untested

- It asks the model to fabricate a feeling: "Express genuine emotion without being unprofessional". The agent writing the entry did not live through the six hours of debugging. It also primes stock phrases: "## Example Emotional Expressions" lists "This is absolutely maddening because..." and "The real kick in the teeth is that...". A list like this tends to be reused word for word across entries, and there is no sign anyone checked whether that happens.
- It contradicts itself on length. "**Be Concise**: Get to the point quickly. Developers are busy." sits next to a mandatory seven-section template and a 200-word floor. With a small incident, the template forces padding.
- It depends on things outside the file. The naming rule is delegated to "the `## Naming` section injected by hooks", which fails silently when no such hook exists. The skills-catalog line is kit boilerplate unrelated to the task.
- It has no input contract, so "Be Specific" has nothing to be specific from. Its record flag separate_fact_from_opinion comes only from the section split. The prompt has no rule that facts come from logs.
- There is no sign of evaluation: no examples of real entries and no note of runs.

## Verdict

It should not be the base for the general writer. Its core stance (emotion in the deliverable, no evidence rule) runs against points 2 and 3. It is useful as input to a path-scoped rule for incident or failure journals (`docs/journals/**`). Lift the What Happened / What We Tried / Root Cause split, the concrete-detail floor and the anti-stall line. Drop the emotion sections and example phrases. Add a source requirement for the root cause, such as log lines, test output or commits. Its weight as evidence is low: one kit template copied into many repos.
