## What it is for and who consumes the output

A live, interaction-first QA walkthrough of a running web app "AS a real user", aimed at behavioural and usability bugs that code review misses. The consumer is the developer who owns the app: each finding carries reproduction steps, evidence paths, a suspected `file:line`, and a "Smallest possible patch", and Phase 7 offers to fix them in-session. Output is a verdict report (Pass / Conditional Pass / Fail / Incomplete).

## Operating procedure in brief

Seven phases: pre-flight (persona lock, browser tool, URL, 1440×900 viewport, one-call capability tests); discovery (sitemap, 3–5 user "threads", per-route element inventory); walkthrough (a timestamped Interaction Manifest, thread traversal as the persona, element exhaustion, a multi-pane × viewport stress matrix, a mandatory first-time-user lens, click-and-watch smoke, round-trip checks, responsive sweep); polish (visual polish sweep, component checklist, axe-core, a perf budget); stress (11 scenarios plus stress recipes); verdict (hard-gate scorecard, Top 5, a fresh-sub-agent self-critique pass, "Hold this in your hands" paragraph, roadmap); fix-and-verify.

## How it gets evidence about the UI

Entirely from a driven browser, and it refuses to run without one:

> | **Neither available** | **Stop** | Ask the user to connect Chrome MCP or install Playwright |

and it tests the tools before starting ("Before any walkthrough, prove the tools work — one call each:" a screenshot, a console read, a network request inventory, an element selector query). It also distrusts code as evidence for behaviour: "Code reading verifies a button exists and has an `onClick`. It does not verify clicking actually does something observable." Claims need artefacts: "Each checkbox in the report cites a proof artefact (screenshot, console line, DOM selector, code reference). No proof = doesn't count." It names Chrome MCP and Playwright MCP as the tools; no tools are declared in frontmatter, so it relies on the session having them.

## What it does that the PROPOSED DESIGNER lacks

Most of it is QA, which is neither the designer nor the proposal's reviewer exactly. A few pieces bear on the designer's item (3) (render and look) and item (6) (what it returns):

- A capability test before relying on a tool: prove screenshot/console/selector work with one call each, then start. The proposal's role "cannot assume" a browser; this is a concrete way to find out at the start rather than at the end.
- Interaction, not presence, as the test for a prototype control: "**Click it.**" / "**Watch the DOM.** Did something visibly change — new element, removed element, state transition?" / "**If nothing changed in (2) or (3), that's a bug.**" The proposal's render-and-look step does not ask the designer to exercise what it built.
- The first-time-user lens as a design check, not only an audit check: "Are field labels in plain language, not internal vocabulary? | `agentClass`, `slug`, `webhook_id` leaking into UI" and "Do dropdowns / pickers show **what each option does**, not just an ID?" The proposal's "name the user and the task" has no test for leaked internal vocabulary.
- A layout hazard band worth naming for responsive work: "the 2026-04-29 vertical-text-in-spaces bug only manifested at 1024-1280px with all three panes open", and the widths "375 / 768 / 1024 / 1280 / 1440 / 1920". The proposal's "responsive behaviour" has no widths.
- A per-change lightweight check that a designer could run on its own prototype, "The 30-Second Dogfood Drill": "Open the affected page", "Type into any input", "Click the primary action", "Watch the next state for 2 seconds", "Open a related view (thread, modal, detail)", "Read the console".
- Realistic-content stress: "Validation that strips characters silently (apostrophe, accents, RTL)" and "i18n (long German, RTL Arabic, CJK widths)". Useful as a state for the proposal's item (4).

## Where it conflicts with the proposal

- It stops when no browser is available; the proposal's role must still produce a result and say what is unverified. For a designer, "stop" is the wrong default; for a QA audit it is defensible.
- It says to drive from the main session, not a sub-agent ("**Drive the audit from the main session, not a sub-agent.**"), which is incompatible with a dispatched role.
- It fixes what it finds (Phase 7 "Patch each one"), crossing the proposal's design/implement boundary and the design/review boundary.
- It asks the user mid-run ("Ask once", "**Ask first**: Destructive actions (delete, send, publish, pay).", "After the report, offer the loop:"). A dispatched subagent in this harness runs without mid-run human approval.
- Scale: an exhaustive audit with 11 mandatory scenarios, a 6-width × 4-pane matrix, and "Stop only when a full pass produces no new findings" is unbounded; nothing in the proposal is that size.

## What looks wrong or untested

- It contradicts itself on sub-agents three times. "**Hand screenshots to a sub-agent for review** at the end of each thread." and the tip "**Sub-agents for screenshot review and write findings incrementally.**" against "**Use the browser tool directly.**" followed by "Don't hand screenshots to a fresh agent for opinions."
- The axe gate is stated two ways: the table says "axe-core Critical violations on any audited page | > 0", the prose says "(>1 violation on any single page fails)".
- The anti-rushing checks rely on numbers the agent itself writes. "Median gap between manifest entries < 0.5s" and "Phase 3 took < 1m" are computed from timestamps the agent logs in the manifest; an agent that fabricates the manifest can fabricate the gaps. Nothing ties manifest timestamps to tool-call records.
- The self-critique prompt only marks "KEEP / GENERIC / DUPLICATE", but the audit-the-audit table says filler patches ("Suggested fix" / "Consider X") are "flipped to Incomplete by the self-critique pass"; the prompt as given does not check for that.
- "**Use the eyedropper liberally.**" is advice for a human in DevTools; an agent has no eyedropper and would need computed-style reads instead.
- Hard gates are strict to the point of noise without the allowlist: "A console warning is High *minimum*." and any warning fails the audit.
- "Loop to exhaustion with variations" and "Stop only when a full pass produces no new findings" has no budget; a model can always generate a new angle.

## Verdict

Neither a base for the designer role nor a taste skill. It is a QA/acceptance skill, closer to the proposal's separate review than to design, and heavier than a design reviewer needs. For the designer role, three small things are worth lifting: a one-call capability probe at the start to learn whether a browser exists (which then decides whether item (3) reports what was rendered and looked at or lists what is unverified); click-it-and-watch-the-DOM as the minimum test of any control in a prototype, in the spirit of the dogfood drill; and the first-time-user vocabulary check. The rest (hard gates, manifest, scenario battery, fix loop) belongs, if anywhere, to a QA skill used on production code after an implementer has integrated the design.
