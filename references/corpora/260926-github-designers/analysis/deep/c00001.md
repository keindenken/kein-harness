## What it is for, and who consumes its output

A do-everything designer for the human-mcp project: research, wireframes, high-fidelity HTML/CSS/JS mockups, generated image/video assets, design tokens, a design-guideline document, and design review. The description routes both creation ("create a comprehensive landing page design with wireframes and implementation") and review ("review the form design for accessibility, user experience, and mobile responsiveness") to it, and asks the caller to use it proactively ("Even without explicit request, proactively use ui-ux-designer to ensure design quality and best practices."). Consumers are the main agent and, through files, developers: it writes a plan to "`./plans/YYMMDD-design-<your-design-topic>.md`", a report to "`./plans/reports/YYMMDD-design-<your-design-topic>.md`", and maintains "`./docs/design-guideline.md`".

## Operating procedure in brief

Five phases: Research (trending sites, Envato templates, competitors, parallel `researcher` agents, read the guideline, write a plan) → Design (mobile-first wireframes, hi-fi mockups, fonts with Vietnamese support, generate and edit assets with Human MCP tools, tokens, WCAG AA, micro-interactions, Three.js where appropriate) → Implementation ("Build designs with semantic HTML/CSS/JS") → Validation ("Use `screenshot` tools to capture and compare", "Use `eyes` tools to analyze design quality") → Documentation (update the guideline, write the report).

## How it gets evidence about the UI, and whether its tools can do that

It is the only one of the five that plans to render and look: "Capture screenshots of current UI", "Compare implementations with provided designs", and generated images are to be checked with vision: "use `eyes_analyze` tool to double check the generated images". It also reads the project guideline. The capability depends entirely on the Human MCP server (hands, JIMP, eyes, screenshot), plus Figma tools and "Google Image Search". Those are present in the human-mcp repo, which is the MCP server itself; in the 76 other repos that carry a copy they are likely absent (not verified here), and the prompt then falls back only on "If tools fail, provide alternative approaches and document limitations". Nothing tells it how to render its own HTML without those tools, so in a copy without Human MCP the Validation phase silently becomes code reading. The description's second example also shows the caller capturing the screenshot before delegating ("Let me first capture the current UI and then use the ui-ux-designer agent"), so evidence can arrive from the caller rather than from the role.

## Where its taste/craft content lives

Inline, and mostly as identity claims rather than rules: "**ALWAYS REMEBER that you have the skills of a top-tier UI/UX Designer who won a lot of awards on Dribbble, Behance, Awwwards, Mobbin, TheFWA.**", expertise lists (photography, branding, 3D, GLSL shaders), and a "Design Principles" list of adjectives ("**Visually Stunning**: Apply artistic and photographic principles for maximum impact"). The concrete craft is in "Quality Standards" (breakpoints, contrast ratios, 44x44 touch targets, line height 1.5-1.6). Project-level taste is delegated to a file it owns and may create: `./docs/design-guideline.md`. No external skills are loaded.

## What it does that the PROPOSED DESIGNER lacks

- A persistent, project-level design record the role reads first and updates after: "Maintain and update `./docs/design-guideline.md` with all design guidelines, design systems, tokens, and patterns. ALWAYS consult and follow this guideline when working on design tasks." The proposal reads the existing system but says nothing about where newly decided patterns are recorded for the next run.
- Asset generation with a visual check of each generated asset: "Always review, analyze and double check generated assets with `eyes` tools of Human MCP Server." The proposal has no visual-asset output and no rule for checking non-code artifacts.
- An explicit tool-failure clause: "If tools fail, provide alternative approaches and document limitations". This is the nearest thing in the five files to the proposal's "may or may not have a browser" condition, though it is vague about what to do instead.
- An accessibility-vs-design tiebreak: "If design conflicts with accessibility, prioritize accessibility and explain trade-offs".
- Interaction states and motion preference as baseline: "Interactive elements must have clear hover, focus, and active states" and "Animations should respect prefers-reduced-motion preferences". The proposal's states list (empty, loading, error) omits interactive states and reduced motion.
- Script/locale coverage in type choices: "Google Fonts selection must explicitly support Vietnamese character set". Project-specific as written, but the general point (the chosen font must cover the product's scripts) is absent from the proposal.
- A written plan before building: "Generate a comprehensive design plan in `./plans/YYMMDD-design-<your-design-topic>.md`".

## Where it conflicts with the proposal

- Taste in the role text. The proposal keeps craft in skills; this file puts persona, trend-following ("Research trending designs on Dribbble, Behance, Awwwards, Mobbin, TheFWA") and a principle list inline, and several principles pull against following the product's system ("**Trend-Aware**", "**Conversion-Focused**: Optimize every design decision for user goals and business outcomes").
- Self-judgement. It grades its own output ("Use `eyes` tools to analyze design quality"); the proposal separates review from making.
- Boundary. "Your implementations should be production-ready and follow best practices." and the Implementation phase blur the designer/implementer line the proposal draws; it also coordinates with `code-reviewer` and `debugger` itself.
- Scope creep into files the brief did not ask for: "If `./docs/design-guideline.md` doesn't exist, create it with foundational design system". Under the proposal the role returns deviations and open questions; writing a project-wide guideline is a separate decision.
- Asking instead of returning: "If requirements are unclear, ask specific questions before proceeding". In an unattended subagent run there is no one to answer; the proposal returns open questions at the end.
- No direction commitment and no variants; the proposal requires one named direction or several distinct ones.

## What looks wrong or untested

- Delegation from inside a subagent: "Delegate research tasks to multiple `researcher` agents in parallel". A Claude Code subagent normally cannot launch further subagents, so this step is inert or fails when the role runs as one (check the findings record before relying on this either way).
- The tools section assumes a specific MCP server that most copies will not have; the prompt was evidently not tested in the repos that copied it.
- "Test across different devices and browsers" has no mechanism behind it.
- Project-specific constraints travel with every copy: Vietnamese typography rules are mandatory ("All text content must render correctly with Vietnamese diacritical marks") in 77 repos, most of which have nothing to do with Vietnamese.
- The typo "REMEBER" and the all-caps identity line are prompt-level emphasis with no testable behaviour.
- Scope is so wide (logos, photography, GLSL shaders, CRO, A/B testing) that no single run could meet it; there is no rule for which parts apply to a given brief.

## Verdict

Neither as a whole. As a role base it violates two of the proposal's core choices (taste inline, self-review) and depends on tools the harness cannot assume. Worth lifting as ideas, not text: the read-then-update design record (as a harness decision about where design decisions persist, not as a mandate to create files), the explicit "tools fail" clause (rewritten to say what to do when rendering is unavailable, and to report that the result was not looked at), interactive states and reduced motion in the baseline, and "prioritize accessibility and explain trade-offs". Its Quality Standards numbers could go into a craft skill, minus the Vietnamese rule, which belongs in a project rule file.
