## What it is for, who consumes the output

This is a visual QA-and-fix agent. It does not originate designs. It makes a running UI match a design system that already exists (`docs/design/tokens.json`). It has three modes: Iterate (render, critique, fix, re-verify), `--sync` (extract an observed token baseline from an existing codebase) and `--real` (a findings-only audit through a real logged-in browser). The output goes to an SDLC orchestrator ("SDLC lead resume") and then to `a11y-compliance`, as a Completion Manifest, `docs/design/ITERATION_LOG.md`, screenshots under `docs/screenshots/design-iterate/iter-*/` and edited source files.

## Operating procedure in brief

1. HANDOFF intake: read the `docs/work/HANDOFF_*.md` file, then keep a checkbox ledger in `docs/work/TASKS_<agent>-<slug>.md`.
2. Read the loop-prevention and context-budget shared files, plus the two reference docs, on every invocation.
3. Vision check. Without vision it falls back to token-lint plus accessibility-snapshot checks only.
4. Iterate mode runs eight phases: Ground → Render → Capture (375/768/1440, snapshot and console) → Token-lint (computed-style diff against tokens.json) → Critique (vision) → Fix (smallest change, existing framework only) → Re-verify → Log and exit.
5. It works in micro-steps: one screen at one viewport at a time, and findings are written to disk immediately.
6. Hard caps limit the iterations. It returns a Completion Manifest that names a separate Verifier.

## How it gets evidence about the UI; can its tools do that

- It reads code: "Before any fix: read `package.json` and 2–3 existing components; find the styling system (tailwind config, theme file, CSS modules) and the component library."
- It renders and screenshots: "Capture: 375/768/1440 screenshots + snapshot + console per target screen". It also measures computed styles: "Token-lint: computed-style diff against tokens.json".
- Tools: none are declared. It assumes a Playwright MCP: "Tool names are the current @playwright/mcp surface (`browser_take_screenshot`, `browser_fill_form`, snapshot-ref clicks) — on tool-not-found, list live tools and adapt; never retry stale names from older docs". Mode 3 reaches claude-in-chrome as its tier T4. Nothing in the file says what to do if no browser tool exists at all. It only covers the case where the model cannot see images.
- Its evidence rule is the strictest in this set: "Never fix without a screenshot showing the problem; never close without a screenshot showing the fix".

## Where taste and craft live

Almost none is inline. The rubric is built from the project's `tokens.json` plus "principles + checklist", which live in `references/design-review-checklist.md` (not collected). The agent deliberately carries no aesthetic doctrine: "Every finding cites a token or a named principle — no vibes". Structurally this matches the proposal's split (craft outside the role), taken to the extreme where the craft is the project's own spec.

## What it does that the PROPOSED DESIGNER lacks (verbatim)

- A fallback when visual inspection is impossible, and a method label on the output. The proposal requires rendering but also says the role cannot assume a browser. This text resolves that tension for the no-vision case:
  > If your model cannot see images: run only the deterministic token-lint and accessibility-snapshot checks, head every output with `**Method: token-lint only — visual critique not performed (no vision)**`, and lower confidence. Never describe a screenshot you cannot see — that is confabulation, not critique.
- Before and after evidence per change: "Never fix without a screenshot showing the problem; never close without a screenshot showing the fix".
- It treats drift between spec and code as a finding and never picks one silently: "If tokens.json and the code's theme file disagree, that disagreement is a finding, not a license to pick one silently." In `--sync` mode it also says "the drift IS the finding".
- A no-new-stack rule for fixes: "never introduce a new framework, library, or styling approach, and never hardcode a value the token system expresses."
- Bounded effort: "Hard caps: 3 iterations per screen, 5 fixes per wave, 2 attempts per finding".
- It refuses to invent a spec: "Missing + greenfield → `BLOCKED: no tokens.json — run design-system-lead first`; do not invent a spec to iterate against."
- Maker and verifier are separated in the report: "Verifier: <who independently checked — never the same identity as Maker>". This agrees with the proposal's "review is separate".
- The report form requires evidence paths: "PASS — <what you checked> — evidence: `<path/to/artifact that exists>`" and "(a bare "tests pass" is not checkable, and a shell command is not an artifact)".
- Explicit routing to sibling roles: "The fix wave touches component architecture or needs new components → `frontend-design`" and "Findings are structural UX, not visual (wrong flow, missing states in the spec) → `ux-engineer`".

## Where it conflicts with the proposal

- Boundary (5): Iterate mode edits production source ("this agent's PRODUCE list includes the code files it fixes"). The proposal sends production integration to an implementer.
- "Does not judge the quality of its own design": the whole loop is a critique of screens, and it closes its own findings. It escapes the self-review problem only because it critiques someone else's design against someone else's spec. Its "Verifier" line admits the closure needs an independent check.
- Contract (2): it never names a user or task and never commits to a direction. Its only direction is the existing tokens.json. It is a conformance tool, not a designer.
- Contract (4): states, responsive behaviour and accessibility are covered only through the viewport matrix and "accessibility-snapshot checks". Empty, loading and error states are pushed to `ux-engineer` as "missing states in the spec".
- It blocks on greenfield work, while the proposal expects new directions when the brief asks for them.

## What looks wrong or untested

- The protocol is elsewhere. The file says "the reference doc is authoritative — read it, don't work from this summary", and those files were not collected, so the critique rubric and the capture procedure cannot be assessed.
- The caps may be inconsistent. The shared loop-prevention summary says "hard cap at 15 total / 4 per work-unit". The Capture phase alone takes 3 viewports times a screenshot, a snapshot and console per screen, repeated for up to 3 iterations. One screen could exceed 15 calls. It is not stated whether the 15-call cap covers browser tools or only research calls.
- The ledger rule contains a runtime claim that nothing in the file supports: "The runtime re-injects this ledger's status into every turn, so trusting it costs nothing". That holds only for this author's opencode setup.
- About half the file is pipeline plumbing (HANDOFF intake, progress banners, context budgets for "32k context (small/local)", web research tools). None of it is about design, and all of it is specific to one orchestrator.
- The vision rule calls itself "the sanctioned exception to the repo's snapshot-first doctrine". The critique therefore depends on a vision-capable model, and the no-vision fallback degrades it to token lint. That is honest, but in that case the design critique does not happen at all.

## Verdict

It should not be the base for the designer role, and not for a design skill either. It is a visual conformance and fix loop that runs after design, closer to a reviewer-plus-implementer than to a designer, and its protocol is in files not collected. It is the best source in this set for contract clause (3). The designer should lift four things from it: the no-vision or no-browser fallback with an explicit method line, the rule that no visual claim is made without a screenshot on disk, spec-versus-code drift reported as a finding, and caps on render-fix iterations. If the harness ever wants a separate "design review/iterate" role, this file is the template for it.
