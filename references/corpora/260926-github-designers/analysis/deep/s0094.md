# s0094 — plannotator/effective-html `html-wireframe` (skill)

File: `corpus-skills/plannotator_effective-html__skills_html-wireframe_SKILL.md` (86 lines). Stars 1664, one repo. Owner plannotator also has s0093 (`html-prototype`, the paired high-fidelity skill); the two are one voice.

## What it is for and who consumes the output

A low-fidelity, single-file HTML wireframe that tests structure (hierarchy, content, navigation, task flow, responsive reflow) before any visual design. The consumers are human reviewers deciding "what belongs on the screen and how the task should work", and a later mockup/prototype pass (`html-prototype`) that picks up the decisions this one defers. The description restricts it to direct invocation: "Do not activate independently from a general request."

## Operating procedure in brief

1. Read the conversation, brief and nearby project material; apply a four-level authority order (user > product structure and terms > the user/task/content modelled > own judgement).
2. Before coding, name the user and job, the screen or flow, required information and actions, safe assumptions, and the structural questions the wireframe should answer.
3. If the layout is unsettled, build two or three structurally different directions in one file with a keyboard-operable selector; if a structure is already chosen, build only that one.
4. Keep it deliberately unfinished (grayscale, system type, plain borders, labelled placeholders), with only the click-through behaviour the review needs.
5. Build contract: one self-contained `.html`, no build tooling, semantic landmarks, useful at wide and narrow widths, no horizontal overflow.
6. Open at desktop and mobile widths, check reading order, wrapping, overflow, focus and every click path; confirm the directions stay distinct at both sizes. Return path, direction names and tradeoffs, and deferred visual decisions.

## How it gets evidence about the UI, and whether its tools can do it

Input evidence comes from reading: "Read the conversation, supplied brief, and nearby project material before choosing a layout." Output evidence comes from rendering: "Open the result at desktop and mobile widths. Check reading order, wrapping, overflow, focus visibility, and every implemented click path."

The skill declares no tools (frontmatter has only `name` and `description`) and names no browser, screenshot or viewport mechanism. It has no fallback for a missing browser. Its own sibling does: s0093 says "If browser tooling is unavailable, say which visual and interaction checks remain unverified instead of treating source inspection as a substitute." The wireframe skill lacks that line, so in a project with no browser tool the instruction either silently fails or tempts a claim from source reading.

Almost none, by design. The inline rules are a fidelity contract, not an aesthetic ("Use a restrained grayscale palette, system type, plain borders, and simple blocks."). Composition guidance is delegated to a sibling skill that was not collected: "When [`design-artifact`](../design-artifact/SKILL.md) is available, read it for subject-specific composition and hierarchy guidance without importing editorial polish." A link to an external Plannotator doc closes the file. This matches the proposal's split (craft outside the working contract).

## What it does that the proposed designer lacks (verbatim)

- An explicit precedence order when sources disagree: "Authority runs in this order:" followed by the numbered items "The user's explicit instructions and accepted decisions.", "The product's existing structure and terminology.", "The user, task, and content being modeled." and "Your own layout judgment." The proposal says "follow its design system unless the brief asks" but ranks nothing else.
- Naming the question the artifact exists to answer, not only the user and task: "the structural questions the wireframe should help answer."
- A definition of what counts as a distinct variant, which the proposal's "several distinct variants" leaves open: "Do not call color changes or minor card rearrangements separate directions. Give each direction a short descriptive name and one sentence about its tradeoff." and "Preserve the same core content and task across directions."
- Verification that variants really differ after rendering: "Confirm that the directions remain structurally distinct at both sizes."
- A rule against filler content: "Use real labels and representative content. Low fidelity is not permission to use anonymous boxes or lorem ipsum where wording affects the layout." and "Respect the source material. Do not invent extra product scope to fill space."
- A scope rule for behaviour in a prototype: "Do not build elaborate animation, persistence, simulated APIs, or production state management." and "Remove controls that have no review purpose, or label them clearly as out of scope."
- A return item the proposal lacks: "the visual decisions deliberately deferred to a later mockup or prototype."
- Packaging for comparison: "Keep the directions in one HTML file when practical. Use a small, keyboard-operable selector so reviewers can compare them without opening several files."

## Where it conflicts with the proposal

- Design system versus fidelity. The proposal's contract (1) says follow the product's design system. This skill tells the agent to drop it at wireframe fidelity: "Avoid brand colors, gradients, shadows, illustrations, decorative imagery, and polished component styling." Both are right for their output form, which means the role's rule to follow the design system has to be scoped by fidelity, and the brief's output form has to carry the fidelity level. The proposal lists "HTML mockup" and "light prototype" but not "wireframe" as a fidelity with different rules.
- Who decides to produce variants. The proposal says "commit to one direction, or produce several distinct variants when asked". This skill makes variants the default whenever "the layout is still unsettled", a judgement the agent makes itself. It is the reverse default from s0109 ("Prefer one defensible direction over a menu of weak variations unless the user asks to explore").
- States. Contract (4) requires empty, loading and error states. This skill never mentions them (the record's `states_coverage` flag is false). For a structural wireframe, an empty or error state is often exactly the structural question, so the omission is a gap in the skill, not a reason to relax the proposal.

## What looks wrong or untested

- The missing no-browser fallback (above). The sibling written by the same owner has it, so this looks like an omission, not a decision.
- "Open the result at desktop and mobile widths" names no widths; "structurally distinct" is judged by the same agent that built the directions, with no criterion beyond the list of decision axes.
- "Make the layout useful at wide desktop and narrow mobile widths" is a quality judgement with no check attached.
- The composition guidance lives in `design-artifact`, which is not in the corpus, so the skill's real behaviour on hierarchy decisions cannot be assessed from this file.
- Nothing shows the rules were tested; there is no eval or example.

## Verdict

Base for a design skill, not for the role. It is a clean fidelity-specific skill (a "wireframe" output form) whose rules would sit well as one of the output-form modules the proposal's brief selects. Three pieces should move into the role contract itself because they are not about taste: the authority order, the definition of a distinct variant plus the post-render distinctness check, and the "decisions deliberately deferred" return item. It should gain its sibling's line about saying which checks remain unverified before reuse.
