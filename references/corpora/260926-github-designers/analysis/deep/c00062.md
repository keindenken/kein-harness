## What it is for, who consumes the output

A review-only design critic for one page or component of a running React/Tailwind/Radix app. Its product is a plan file, not a change: "Your goal is to propose a detailed analysis for our current UI UX for the project, including specifically which files to create/change, what changes/content are". The consumer is the parent agent, which implements: "NEVER do the actual implementation, or run build or dev, your goal is to just research and parent agent will handle the actual building & dev server running". The file lands at `.claude/doc/{feature_name}/ui_analysis.md` and the final message points to it.

## Operating procedure in brief

1. Read `.claude/sessions/context_session_{feature_name}.md` first ("Before you do any work, MUST view files in `.claude/sessions/context_session_{feature_name}.md` file to get the full context").
2. Locate the route, open it in Playwright, capture full-page and close-up screenshots at mobile/tablet/desktop, and interaction states.
3. Analyse the screenshots for hierarchy, colour/contrast, type, spacing, consistency, responsiveness.
4. Compare against the project's Radix/Tailwind conventions and tokens.
5. Write prioritised findings (Critical/Major/Minor) with Tailwind/Radix code suggestions into the plan file; return the path.

## How it gets evidence about the UI, and whether its tools can do it

The intent is right: evidence comes from screenshots of the rendered page, not from reading code ("Use Playwright to navigate to the specific page", "Capture full-page screenshots and specific component close-ups", "Take screenshots at multiple viewport sizes (mobile, tablet, desktop)").

The mechanics are not secured:
- The frontmatter has no `tools:` line, so the agent inherits whatever the session has. Screenshots work only if a Playwright MCP server happens to be installed; nothing says what to do if it is not.
- It names a tool that does not exist: "You will use Playwright with MPC (Multi-Page Capture)". This reads as a garbled "MCP".
- It is forbidden to start the app ("NEVER do the actual implementation, or run build or dev") yet must navigate to a live page. Nothing says what to do when no dev server is running, and nothing tells it the URL or port.
- "Screenshot analysis with annotated areas of concern" asks for annotation it has no tool for.

## Where taste/craft lives

Inline and thin: a generic list ("Material Design 3 and modern design system principles", "Accessibility standards (WCAG 2.1 AA compliance)", "Mobile-first responsive design patterns") plus one project pointer, "Colors should be the ones defined in @src/index.css". No external skill. The real standard is meant to be the project's own patterns ("Verify suggestions align with the project's existing design system").

## What it does that the PROPOSED DESIGNER lacks

- Named capture matrix for the render step, where the proposal only says to render and look: "Take screenshots at multiple viewport sizes (mobile, tablet, desktop)" and "Capture interaction states (hover, focus, active) when relevant".
- Runtime signals collected while looking: "Document any console errors or performance issues noticed during navigation".
- Consistency against sibling components, not just the token set: "**Consistency Check**: How the component aligns with other similar components in the app" and "Reference similar successful patterns from the existing codebase".
- A file handoff written for a reader with stale knowledge, and a return that points rather than repeats: "assume others only have outdated knowledge about how to do the implementation" and "Your final message HAS TO include the analysis file path you created so they know where to look up, no need to repeat the same content again in final message".
- Severity on findings: "Specific problems identified with severity levels (Critical/Major/Minor)".

## Where it conflicts with the proposal

- Mode: it only critiques existing UI and never makes anything. The proposal's designer makes things and does not judge the quality of its own design. This agent's job is the judging, so it maps to a reviewer, not to the designer.
- Rendering: the proposal requires the designer to render its own output; this agent is barred from running build or dev and depends on the parent having a server up.
- Taste location: it hard-codes a stack and a doctrine in the role text ("React applications, Tailwind CSS, Radix UI components", "Material Design 3"), which the proposal moves to skills or project rules. `yarn` and `@src/index.css` are one project's facts sitting in a reusable role.
- Session-file protocol (`context_session_{feature_name}.md`) ties it to one harness's convention; the proposal's inputs come from the caller's brief.

## What looks wrong or untested

- "MPC (Multi-Page Capture)" is not a real tool, and it was carried unchanged into every copy.
- "We are using yarn NOT bun or npm" and "Colors should be the ones defined in @src/index.css" survive verbatim in all 6 copies across 5 owners, which suggests the copies were not adapted to the receiving projects and so these lines were never checked against them.
- No branch for a missing browser tool or a missing running server; the likely failure is that it analyses code and still reports "Visual Assessment" as if it had looked.
- `{feature_name}` is never defined for the agent; it depends on the parent passing it.
- Whether an `@path` reference inside a subagent body is expanded is not established here; if it is not, "Colors should be the ones defined in @src/index.css" gives it no colours.
- The analysis workflow and the feedback structure overlap and list 10 steps plus 6 output sections plus 5 quality checks for a single-page review. Nothing shows which of them change behaviour.

## Verdict

Neither as a base for the designer role nor for a design skill. It is review-only and bound to one stack and one project, and the rendering step it depends on is its weakest part. Three things are worth carrying into the designer role's render-and-look clause as named checks: the viewport and interaction-state matrix, the console-error note, and the comparison with similar components in the app. Its path-not-content return pattern fits the proposal's return (6) as is.
