## What it is for, who consumes the output

It is taste and process guidance for the agent that builds UI itself: "Guidance for distinctive, intentional visual design when building new UI or reshaping an existing one." The consumer is the same agent writing the code. The imagined client is a human ("confirm with the client"). The posture is a studio design lead paid for distinctiveness: "This client has already rejected proposals that felt cliché or templated".

## Operating procedure in brief

1. Ground the design in subject matter. If the brief lacks a subject, propose "one concrete subject, the design's audience, and the design's primary job".
2. Work in two passes. First write a compact token plan: 4–6 named hex values, typefaces and their roles, a layout concept with ASCII wireframes and alignment, and principles. Then review that plan against the brief for generic defaults, revise it, and say what changed.
3. Build, taking care with CSS specificity.
4. Critique while building, with screenshots if the environment supports them.
5. Remove one thing ("remove one accessory").

A separate section covers the interface copy.

## What it does that the PROPOSED DESIGNER lacks (verbatim)

- A plan artifact before building, with a fixed shape: "First, brainstorm a short design plan based on the client's design brief: create a compact token system with color, type, layout, and principles." and "Color: describe the core base palette as 4–6 named hex values."
- A check of the plan against genericness, done before code: "Then review that plan against the brief before building: if any part of it reads like the generic default you would produce for any similar page (work through a similar prompt to see if you arrive somewhere similar) rather than a choice made for this specific brief — revise that part, say what you changed and why."
- Deference to the brief is stated explicitly: "Where the brief pins down a visual direction, follow it exactly — the brief's own words always win, including when it asks for one of these looks."
- Grounding in the subject: "The subject's industry, subject matter, materials, and vernacular are where distinctive visual choices come from".
- Structure has to carry meaning: "Visual structure is information." and "Before adding numbered markers, check the content really is a sequence."
- Interface copy is part of the design: "A CTA says exactly what happens when it is used: "Save changes," not "Submit."", "An action keeps the same name through the whole flow, so the button that says "Publish" produces a toast that says "Published."" and "Treat failure and emptiness as moments for direction, not mood." ## Where it conflicts with the proposal

- Contract (1): the proposal starts from the existing product and follows its design system unless told otherwise. This skill starts from distinctiveness ("make deliberate, opinionated choices about palette, typography, and layout that are specific to this brief, and take aesthetic risk if justified") and never mentions an existing design system. Loaded into a designer working on an existing product, it pulls toward novelty unless the role's clause (1) is ranked above it.
- Clause (6), "It does not judge the quality of its own design": "Critique your own work as you build". In this skill, self-critique is the main quality mechanism.
- Asking: "identify it yourself before designing, and confirm with the client". A subagent cannot confirm mid-run. The "as a proposal" wording turns into an assumption reported back to the lead.
- Memory across projects: "if you have a space to quickly jot down notes about what you've tried, it can help you in future passes." This assumes persistent notes a harness subagent may not have. It is harmless but not actionable.
- Output: it has no report contract at all (`output_contract: false`). Nothing is returned beyond the built UI.

## What looks wrong or untested

- The calibration list is dated by nature ("AI-generated design right now clusters around some traits"). The hex tells (for example "near #F4F1EA", "near #D97757") will go stale, and nothing in the file says when to revise them.
- It contradicts s0005 (Leonxlnx taste-skill) on headline emphasis. This skill lists as a generated tell "Accenting just a single word or phrase in a headline, like putting one word in italic/bold or a different color." s0005 prescribes exactly that: "use **italic or bold of the SAME font**" and "Italic/bold emphasis in the same family is the right move." Two of the most-starred design skills cannot both be loaded as standing taste without a ranking rule.
- "Using all caps for labels." is banned outright as a tell, which is broad for product UI, where all-caps table headers and badges are a common system convention. That is fine for a landing page and questionable for an existing product's design system, which again depends on clause (1) taking priority.
- The screenshot step is optional and unverifiable: nothing says what to report when no screenshot was taken.
- The scope leans toward web marketing and hero pages ("For web designs, the hero is the first thing viewers will see."). Dense product screens, forms and data views get little specific guidance.

## Verdict

This is the strongest base for a design skill (craft and taste) that the designer loads. It is short (71 lines), self-contained, and made of principles rather than a stack mandate. It already defers to the brief ("the brief's own words always win"), and its two-pass plan-then-review step fits the proposal's clause (2). It is not a base for the role: it has no working contract, no grounding in the existing product, no report and no boundary. Two adjustments are needed when pairing it with the proposed role: the role must rank "follow its design system unless the brief asks for a new direction" above the skill's distinctiveness posture, and the self-critique step should be recast as rendering and inspecting (clause 3), with quality judgment left to the separate reviewer.
