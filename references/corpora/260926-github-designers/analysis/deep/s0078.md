## What it is for and who consumes the output

A repeatable UX review of one screen of LobeHub against two benchmarks: Tidwell's _Designing Interfaces_ pattern language and the in-repo `ux` checklist skill. It answers "**which patterns does the surface use** (and how well), and **where is the experience weak**". Consumers are the LobeHub team (findings go to Linear sub-issues or are fixed directly), the `ux` skill itself (findings are written back into it), and the next audit (the report is saved as a worked example). Output is a written critique only.

## Operating procedure in brief

1. Pick layers: L1 static (read code) always; add L2 visual (screenshots) for hierarchy, rendered states, responsive; add L3 dynamic (drive the journey through the `acceptance` skill, measure CLS/LCP/INP) for journeys, forced states and performance. Default is L1, plus L2 if screenshots are supplied.
2. Before reading code, name the surface's class and list what mature comparable products offer; audit gaps against that list.
3. Walk the pattern catalog before proposing a fix for any "redundant" control.
4. Report strengths with evidence, not only gaps.
5. Rank gaps with a three-tier severity rubric; each cites a checklist item or catalog pattern, the layer and its evidence, and a one-line remedy.
6. Land the findings: fix or file bugs, write generalizable gaps and good cases back into `ux`, save the audit as a reference example.

## How it gets evidence about the UI

This is its strongest part. It reads code (L1, cites `file:line`), looks at screenshots it has verified ("a screenshot you **verified with the Read tool** (L2)"), and drives the running app through another skill (L3, "agent-browser CDP: snapshot / eval / screenshot / GIF"). It declares no tools of its own and depends on the `acceptance` skill and a running environment with auth for L3. The key rule is that a verdict may only come from a layer able to see it:

> The core rule: **a verdict must come from a layer that can see it.** Don't tick a visual or runtime verdict off the code.

with a coverage matrix (e.g. "Real visual hierarchy / is the dominant control the primary action" is "❌ misleads" at L1, and "Focus order / keyboard reachability" is ❌ at both L1 and L2) and a named trap (ticking "one primary button" or an empty state being a real page from a `variant` prop in the code):

> Those are **L2** verdicts — confirm them on the render, never from L1 alone.

Its default ("default is L1 (+ L2 if screenshots are supplied)") means it runs without a browser and scopes its claims to what code can show, which is the exact posture the proposed role needs when no browser is present.

## Where taste/craft lives

Out of this file. Composition vocabulary lives in `references/pattern-catalog.md` (Tidwell); behavioural rules live in the separate `ux` skill; visual design-system rules live in a doc that s0077 cross-references. The audit file is method only. This is the same split the proposal makes.

## What it does that the PROPOSED DESIGNER lacks

- A per-claim evidence rule, sharper than the proposal's item (3). The proposal says "claims about how the result looks come from that inspection, not from reading the code". This skill says which kinds of claim need which kind of evidence, including that some cannot be settled even from screenshots (focus order, in-progress states, which variant is better). The coverage matrix could be lifted almost as is into the designer's reporting rule.
- Benchmarking the class of surface, not only the product's own code. The proposal's item (1) is "start from the existing product", which this skill shows is structurally blind to missing capabilities:
  > Reading our code can only surface flaws in **what we built** — it is structurally blind to a capability we **never built at all**, because an entirely-absent affordance leaves no `file:line`, no dead branch, no half-wired button to grep for.
  > Write this expected-capability list _first_, then audit gaps against it — otherwise the audit only ever polishes the paths that already exist and silently blesses a missing one.
  For a designer, the equivalent is: before designing a screen of a known class (OAuth consent, checkout, share dialog, file picker), list what comparable products offer.
- Outcome over craft when comparing variants. The proposal allows "several distinct variants" but says nothing about how they are presented or compared:
  > **Name the success metric _first_, then judge against it.**
  > For a gateway / interstitial surface — onboarding, consent, paywall, a loading gate — the two diverge hard: the best version is often the _least_ version, because the surface stands _between_ the user and what they came for.
  > No funnel data → say "insufficient evidence, here's what I'd need", and stop.
- Composition before subtraction: "_same intent, different scope?_ → the fix is a sibling, not a delete." A redesign rule the proposal has no counterpart for.
- Every failure rule is backed by a recorded miss in this product (the OAuth switch-account miss, the Agent-vs-Classic onboarding rollback, the AskUserQuestion dedupe). This is the only file in the batch whose rules show evidence of having been tested by failure.

## Where it conflicts with the proposal

- It is review, which the proposal separates from the designer ("It does not judge the quality of its own design; review is separate."). Most of it belongs to the reviewer side of the harness, not the designer.
- It edits things beyond its output. "**Concrete bugs** → fix the top 🔴" makes the auditor an implementer, and the mandatory 回灌 step makes every run edit another skill ("Every run **must** close the loop back into the `ux` skill"). In the kein harness, whether a rule is added to a skill is decided by `/kein:deliberate`, not by the run that found the case; this step would be the wrong mechanism here.
- Project-specific wiring: Linear "UX Audit" parent issues, the `acceptance` skill, LobeHub file paths, Chinese value terms (意义感, 自然, 确定性) defined elsewhere.

## What looks wrong or untested

- L3 depends on a separate `acceptance` skill with "Step 0 env + auth" green; when that is absent the skill has no rule for how to report L3-only findings as unverified beyond the coverage matrix itself.
- "a screenshot you **verified with the Read tool**" assumes the agent can view images; it does not say what to do when screenshots cannot be produced at all, other than staying at L1.
- The Output list mixes an unescaped heading marker into a bullet ("a **dedicated section** (`## … — Strengths / good cases`)" is broken across a line in the source, so the Markdown renders oddly). Minor.
- The mandatory write-back has no bar for when a gap is "generalizable"; with "silence is not an acceptable close", the incentive is to add a rule every run, which the kein repo's own records warn against (rules added without evidence prime behaviour).
- "one surface per run" is sound, but the file gives no size bound on a "surface" beyond "one screen".

## Verdict

Not a base for the designer role, and not a taste skill; the best base in the batch for the **separate design reviewer** (review-side skill or role) that the proposal assumes exists. Two pieces should move into the designer role itself, because they govern what the designer may claim and what it must consider before designing: the layer/coverage rule ("a verdict must come from a layer that can see it", with the matrix), and the surface-class benchmark ("Write this expected-capability list _first_"). The variant-comparison ground rule belongs to whoever picks among the designer's variants, which may be the lead or the reviewer, but the designer's report should carry the success metric each variant targets. The write-back loop and the fix-it-yourself step should not travel.
