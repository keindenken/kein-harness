## What it is for, who consumes the output

A pre-planning gate over a design document, not over a UI. `gsd-ui-researcher` writes `UI-SPEC.md` (the design contract); this agent checks the contract before any code is planned: "Verify that UI-SPEC.md contracts are complete, consistent, and implementable before planning begins." The consumer is the `/gsd:ui-phase` orchestrator, which blocks planning on a BLOCK ("**BLOCKED** if ANY dimension is BLOCK → plan-phase must not run"), and the researcher, who does the fixing ("Report findings, let the researcher fix.").

## Operating procedure in brief

1. Read every file in `<required_reading>`, then project `CLAUDE.md` and the index files of project skills.
2. Read `UI-SPEC.md`, plus `CONTEXT.md` (locked user decisions, deferred ideas) and `RESEARCH.md` (standard stack) if present.
3. Score six dimensions (Copywriting, Visuals, Color, Typography, Spacing, Registry Safety) as PASS/FLAG/BLOCK against fixed criteria.
4. Return a structured verdict (APPROVED or BLOCKED) with an exact fix for each BLOCK. Write nothing.

## How it gets evidence about the UI, and whether its tools can do it

It never looks at a UI, and it does not need to: its object is a markdown spec. `tools: Read, Bash, Glob, Grep` is enough for that. The evidence rule is sound for a document gate: "**Evidence-based:** Each verdict cites the exact UI-SPEC.md content that triggered it". For the proposal this means the checker says nothing about rendering. It checks whether the design was specified, not how it looks.

## Where taste/craft lives

Inline, as hard thresholds that decide the verdict: "More than 4 font sizes declared", "More than 2 font weights declared", "Any spacing value declared that is not a multiple of 4", "Spacing scale contains values not in the standard set (4, 8, 16, 24, 32, 48, 64)", "60/30/10 split not explicitly declared", and generic-label bans (quoted in full below). It defers to project skills only for context ("This ensures verification respects project-specific design conventions."), and the thresholds are not overridable by them.

## What it does that the PROPOSED DESIGNER lacks

These are things a design must declare. The checker enforces them on the designer's output, so they indicate what the designer's return is missing:
- Copy is part of the design: `Any CTA label is "Submit", "OK", "Click Here", "Cancel", "Save" (generic labels)`, `Empty state copy is missing or says "No data found" / "No results" / "Nothing here"`, and `Error state copy is missing or has no solution path (just "Something went wrong")`. The proposal's clause (4) covers the existence of empty/loading/error states but not what they say.
- Destructive actions: "Destructive action has no confirmation approach declared" and "No destructive color declared when destructive actions exist in copywriting contract".
- A declared focal point and hierarchy: "No focal point declared for primary screen" with the reason "No focal point declared — executor will guess visual priority".
- Accent discipline as a declared list, not a vibe: `Accent reserved-for list is empty or says "all interactive elements"` with the fix "List specific elements: primary CTA, active nav item, focus ring".
- Third-party component supply-chain vetting, with evidence rather than intent: "Are third-party component sources actually vetted — not just declared as vetted?"
- Respect for locked decisions: "**Context-aware:** Respects CONTEXT.md locked decisions (don't flag user's explicit choices)" and "`## Deferred Ideas` | Out of scope — UI-SPEC must NOT include these."
- A gate discipline that keeps review from turning into opinion: "**No false positives:** Only BLOCK on criteria defined in dimensions, not subjective opinion".

## Where it conflicts with the proposal

- It is a reviewer. The proposal keeps review separate from the designer, so this is the proposal's architecture viewed from the other side, not a conflict in role design. The GSD split (researcher writes the spec, checker gates it, auditor scores the build) is a three-role version of the proposal's designer plus separate review.
- Taste as law in role text. The proposal puts type/colour/spacing rules in skills or project rules; here they are hard-coded BLOCK criteria. They are also not reconciled with an existing design system: the only exemption is `CONTEXT.md` user decisions. A product whose tokens use 3 font weights or a 12px step fails the gate for following its own design system, which the proposal's clause (1) requires.
- The designer's output here is a spec document with a fixed template. The proposal's designer produces mockups, prototypes, components or critique; a spec-only gate cannot check those.

## What looks wrong or untested

- The spacing rules contradict their own example. The BLOCK list includes "Spacing scale contains values not in the standard set (4, 8, 16, 24, 32, 48, 64)", but the example fix for a 10px value is "Use 8px or 12px instead". 12 is not in the standard set, so following the fix triggers another BLOCK. This is present in all 4 copies, so nobody running the gate has caught it (or the copies predate a fix).
- Banning "Cancel" and "Save" as CTA labels is a strong claim with no source. "Cancel" as the secondary action in a dialog is a platform convention, and the rule would BLOCK it anyway.
- "More than 2 font weights declared" as a BLOCK rules out a common regular/medium/bold set. Nothing in the file justifies the number.
- The read-only rule and the approval write pull against each other: "You are read-only — never modify UI-SPEC.md." but "If APPROVED: update UI-SPEC.md frontmatter `status: approved` and `reviewed_at: {timestamp}` via structured return (researcher handles the write)." The parenthetical resolves it, but the first half reads as an order to write.
- The file-reading rules ("**No re-reads:** Once a file is loaded via `<required_reading>` or a manual Read call, it is in context — do not read it again.", "Never reload the whole file for a second dimension.") are context-budget rules. They are unrelated to design, and there is no evidence that they are needed.

## Verdict

Not a base for the designer role: it makes nothing and never sees a UI. It is a reasonable base for a separate spec-gate reviewer, and its dimension list is the most useful thing in it for the proposal. Focal point, accent reserved-for list, specific CTA/empty/error copy, destructive confirmation, and third-party component vetting are items the designer's return could be required to declare so a reviewer has something to check. The numeric thresholds are skill or project-rule material at most, and only as defaults an existing design system overrides. The 12px contradiction shows they were never run against their own examples.
