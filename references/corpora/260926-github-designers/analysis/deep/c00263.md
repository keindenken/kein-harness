## What it is for and who consumes its output

A visual reviewer that runs after someone else has built frontend code. The lead agent is told to call it without being asked:

> Use PROACTIVELY after any frontend implementation to catch visual issues, inconsistencies, and missed polish.

Its output is a scored critique the lead agent reads and routes back to whoever implemented the UI. It explicitly does not review code quality.

## Operating procedure

1. Start the project's dev server.
2. Open the page in a browser MCP and screenshot it.
3. Walk a checklist of about 30 items in six groups (layout and spacing, visual design, interactivity, animation, responsiveness, polish).
4. Return a 1–10 score and issues sorted into critical, polish and nice-to-have, plus what works.

## How it gets evidence about the UI, and whether its tools can do it

This is the role's centrepiece, and it is stated as a hard rule:

> NEVER review visual output by reading source code alone.

> If the dev server can't start, state this explicitly — don't review code and guess at visual output.

But the declared tools cannot do it:

> tools: Read, Grep, Glob, Bash

In Claude Code a `tools:` allowlist on a subagent restricts it to the named tools, and MCP tools have to be named individually to be included. The browser steps it requires (`browser_navigate`, `browser_screenshot`, `visual_baseline`, `visual_compare` from a "Glance MCP") are not in the list, so as written the subagent cannot take the screenshot its first rule demands. `Bash` could start the dev server, but a foreground `npm run dev` does not return, and the role gives no instruction to background it or to wait for readiness. The escape hatch covers only "the dev server can't start", not a missing screenshot tool, so the most likely real failure has no declared behaviour. This is the proposal's exact risk ("the role cannot assume" a browser), shown in the wild.

## Where taste/craft lives

Entirely inline, in the checklist. Several items are aesthetic doctrine rather than checks, and some are contestable:

> Background is NOT plain white/black (needs texture, gradient, or subtle pattern)

> Transitions on all state changes (not instant jumps)

> Scroll-triggered reveals for below-fold content

There are no references or skills; the checklist is the taste.

## What it does that the proposed designer lacks

- A declared fallback when rendering fails, phrased as a prohibition on guessing. The proposal's item (3) says "claims about how the result looks come from that inspection" but not what to do when there is no inspection:

> If the dev server can't start, state this explicitly — don't review code and guess at visual output.

- Named widths instead of "responsive behaviour":

> Works at 320px (small phone)

(followed by 768, 1024 and 1440).

- Before/after comparison for changes to existing UI, which fits the proposal's "redesign of existing UI" output:

> Use `visual_baseline` + `visual_compare` for before/after comparisons

- Interaction states beyond empty/loading/error:

> EVERY button/link has hover state

> Focus states are visible (for keyboard users)

> Active/pressed states exist

- Motion safety as part of the accessibility baseline:

> `prefers-reduced-motion` respected

- A specificity rule for reported findings, with a worked example:

> Be specific — "the spacing is off" is useless. "Card padding is 12px but header padding is 16px — use 16px consistently" is useful

## Where it conflicts with the proposal

- Role split. It is a critic of someone else's output and returns a quality score. The proposal's designer "does not judge the quality of its own design; review is separate". This file is a candidate for that separate reviewer, not for the designer.
- Taste in the role text. Its checklist hard-codes an aesthetic (textured backgrounds, mount animations, scroll reveals); the proposal puts taste in skills or project rule files.
- Design system ignored. Nothing tells it to read the project's tokens or components, and a low score sends the implementer to another library:

> If score is < 6, suggest specific component library alternatives (shadcn, magicui, etc.)

That contradicts the proposal's item (1) and would push a project off its own design system.

- Fixed grid assumption regardless of project:

> Consistent spacing scale (4px/8px grid)

## What looks wrong or untested

- The tool list and the mandatory procedure contradict each other (above). Either the author ran it with a host that ignores the allowlist, or the screenshot step never ran.
- Contrast is judged from a screenshot ("Contrast ratios meet WCAG AA (4.5:1 for text)") with no tool to compute ratios; a model eyeballing a PNG cannot certify 4.5:1.
- "Reference exact files and elements" asks for file locations while the evidence is a screenshot and there is no instruction to map what it saw back to source.
- The checklist mixes page-level items ("Favicon set", "404 page designed (not default)") with component-level ones, so a review of one component will either skip items silently or flag irrelevant ones.
- It asks for four widths but gives no instruction to resize the viewport, and the screenshot step is singular.
- Some doctrine contradicts other roles in the corpus: c00286 tells its reviewer not to recommend "gratuitous gradients and decorative effects", while this one fails a plain background.

## Verdict

Not a base for the designer role: wrong side of the make/review split, taste inline, and no design-system awareness. As a base for a design skill, only the checklist skeleton is reusable after stripping its aesthetic opinions (the interaction-state list, the four widths, reduced motion). Its most useful contribution to the proposal is the "don't review code and guess at visual output" fallback, which the proposal's item (3) needs, together with the lesson its own frontmatter teaches: a render-and-look rule is dead text unless the role's tools actually include the rendering tool, so the designer must say what it does and reports when that tool is absent.
