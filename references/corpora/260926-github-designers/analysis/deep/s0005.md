## What it is for, who consumes the output

It is an anti-slop rulebook for the coding agent that builds marketing surfaces as production React/Next code. The scope is narrow and stated up front: "Landing pages, portfolios, and redesigns. Not dashboards, not data tables, not multi-step product UI." Section 13 repeats this and sends dashboards, data tables, wizards, native mobile and collaborative UIs elsewhere. The consumer is the same agent and, through it, the user.

## Operating procedure in brief

1. Brief inference: read six signals, emit a one-line "Design Read", and ask at most one question.
2. Set three numeric dials (variance, motion, density; baseline 8/6/4) from inference tables.
3. Map the brief to an official design-system package, or name the aesthetic honestly.
4. Build on the default stack: Next.js RSC, Tailwind v4, Motion, and whitelisted icon libraries.
5. Apply roughly 40 bias-correction and "AI tell" bans.
6. For redesigns, detect preserve, overhaul or greenfield, audit first, and apply modernisation levers in a fixed order.
7. Run a pre-flight checklist of about 60 items: "If a single checkbox cannot be honestly ticked, the page is not done."

## How it gets evidence about the UI; can its tools do that

- Reading the existing product happens only on redesigns, and there it is thorough ("11.B Audit Before Touching": brand tokens, information architecture, content blocks, patterns to keep and retire, a dial reading of the existing site, the SEO baseline). A code-level check before dependencies: "Before importing ANY 3rd-party library, check `package.json`."
- Rendering is mentioned only in passing: "Open the page in both modes during development. Do not ship a page you've only seen in one mode." and "Run Lighthouse before declaring a page done." There is no screenshot step and no viewport matrix, and nothing says what to do without a browser. The record's `renders_and_looks: false` is fair.
- The pre-flight check is mostly done by reading code: "**Pre-Flight Check is mechanical:** count instances of `uppercase tracking` (or similar small-caps mono labels above headlines) across all section components." But several items can only be decided by rendering, for example "**CTA Button Wrap**: no CTA label wraps to 2+ lines at desktop?" and "**Hero fits the viewport**: headline ≤ 2 lines, subtext ≤ 20 words AND ≤ 4 lines, CTA visible without scroll". The skill asks for visual verdicts it gives no means to obtain.
- Tools: none declared. The image-generation rule is conditional on the environment ("If ANY image-gen tool is available in the environment" and "you MUST use it"), but rendering is not treated the same way.

## Where taste and craft live

All of it is inline and very large: dial tables, a stack mandate, typography and serif policy, palette bans with hex lists, layout hard rules, image strategy, copy rules, motion skeletons in GSAP and Motion, dark-mode protocol, a vocabulary of about 50 named patterns, and appendices with install commands and doc links. A block library is planned but not written. This is the opposite of the proposal's thin role: the file is taste and stack at full length.

## What it does that the PROPOSED DESIGNER lacks (verbatim)

- The redesign safeguards are the strongest part and map straight onto contract clause (1):
  - "**Do not change information architecture** unless asked. Keep page slugs, anchor IDs, primary nav labels stable for SEO and muscle memory."
  - "**Honor existing accessibility wins.** Do not regress focus states, alt text, keyboard nav, contrast."
  - "**Respect existing analytics events.** Do not rename buttons, form fields, section IDs that downstream tracking depends on."
  - "Never modify without explicit user approval:" followed by "URL structure / route slugs.", "Primary nav labels.", "Form field names or order (breaks analytics + autofill).", "Brand logo or wordmark." and "Existing legal / consent / cookie copy."
- Redesign mode detection: "Misclassifying the mode is the single biggest source of bad redesign output." The ambiguity question is also fixed: "Should this redesign preserve the existing brand, or are we starting visually from scratch?"
- An ordered, risk-weighted set of levers: "Apply in order - stop when the brief is satisfied:" with "**Typography refresh** - biggest visual lift per unit of risk." first and "**Full block replacement** - only when the existing block is unsalvageable." last.
- A one-line direction statement, a concrete form of clause (2): "Before any code, state in one line: **"Reading this as: \<page kind> for \<audience>, with a \<vibe> language, leaning toward \<design system or aesthetic family>."**"
- A limit on questions: "Ask exactly **one** clarifying question - never a multi-question dump - and only when the design read genuinely diverges."
- Honesty about design systems: "if the brief reads as one of the systems above, install and use the **official** package. Do not recreate its CSS by hand. Do not import a system's tokens but then override 90% of them." and "One system per project."
- States spelled out: "LLMs default to "static successful state only." Always implement full cycles:" (loading, empty, error, tactile feedback).
- Placeholder honesty for missing assets: "leave clearly-labeled placeholder slots (`<!-- TODO: hero product photo, 1600x1200 -->`) and at the end of the response say: *"This page needs real images at: \[list of placements\]. Please generate or provide them."*"
- An accessibility floor with numbers: "contrast ratio WCAG AA min (4.5:1 for body, 3:1 for large text 18px+)" and "No placeholder-as-label. Ever."

## Where it conflicts with the proposal

- Contract (1) and the split that puts taste in skills: the skill mandates a stack and a look. Examples are "**Framework:** React or Next.js. Default to Server Components (RSC).", "**Styling:** **Tailwind v4** (default).", "**Discouraged:** `lucide-react`." and "Dark Mode (mandatory for any consumer-facing page)". Some rules carry project-exists overrides ("Tailwind v3 only if the existing project demands it", lucide "Acceptable only when the user explicitly asks for it or the project already depends on it"), but many do not. Dark mode, image generation and the em-dash ban would all be imposed on an existing product that has chosen otherwise.
- Boundary (5): the output is production code. The Design Read goes straight to shipping React components, with no prototype or handoff stage.
- Self-judgment: the pre-flight is a self-certification ("Run every box. If any box fails, the output is not done."). The proposal leaves quality review to a separate step.
- Clause (2) variants: it never produces several variants. The dials pick one point.
- Scope: its own out-of-scope list (dashboards, data tables, wizards, native mobile) covers much of what a product designer in a harness would be asked for.

## What looks wrong or untested

- It contradicts itself on invented numbers. Section 9.D says "**NO fake-perfect numbers.** Avoid `99.99%`, `50%`, `1234567`. Use organic, messy data (`47.2%`, `+1 (312) 847-1928`)." Section 4.9 says "**Fake-precise numbers are flagged.** Numbers like `92%`, `4.1×`, `48k`, `5.8 mm`, `13.4 lb` either:" come from real data, are labelled as mock, or "Are AI-invented spec aesthetics - banned." One section tells the agent to invent messy numbers and the other bans invented precise ones.
- It contradicts itself on animation. The MOTION_INTENSITY 4-7 band prescribes "`transition: all 0.3s cubic-bezier(0.16, 1, 0.3, 1)`", while 6.A says "Animate ONLY `transform` and `opacity`. Never animate `top`, `left`, `width`, `height`." `transition: all` animates every property that changes.
- Some rules need memory the agent does not have: "**Palette-rotation rule:** if the previous premium-consumer project you generated used the beige+brass family, this one MUST use a different family." and the pre-flight item "Different serif from your previous project?" A fresh agent cannot check either.
- It makes many uncited empirical claims: "the #1 violated rule in production tests", "the single most-tested AI tell in production rounds", "It is the #1 LLM-design Tell." No test data is included or linked.
- It contradicts s0037 on headline emphasis (see s0037.md). This skill prescribes "use **italic or bold of the SAME font**", while Anthropic's frontend-design lists single-word italic or bold accenting as a generated tell.
- The baseline dial `DESIGN_VARIANCE: 8` defaults to high asymmetry ("Artsy Chaos" is 10) unless the design read overrides it. That is a strong aesthetic prior presented as neutral configuration.
- On social proof it says "Use real SVG logos" from Simple Icons for "Trusted by" walls. With invented or unverified customers, that puts real brands' marks on claims the product may not be able to make. The skill does not raise this.
- Cost: at about 20k tokens it is expensive to load for every design task, and most of it (GSAP skeletons, the Liquid Glass appendix, install commands) is irrelevant to any single brief.

## Verdict

It is not a base for the role: it mandates a stack and a look and self-certifies. Nor is it the design skill the harness should load by default: it covers marketing pages only, is large, and contradicts itself in the places noted above. Its redesign protocol (Sections 11.A–11.F) is the best material in the five files for the proposal's clause (1). The protected-surfaces list, the preserve/overhaul/greenfield classification, the "Audit Before Touching" inventory and the ordered levers should move into the designer role or a small redesign skill. The one-line Design Read and the single-question limit are good concrete forms for clause (2). The taste rules should not be adopted wholesale. If any are used, they belong in an opt-in "marketing page" skill, ranked below the existing design system and below the brief.
