The deliverable defaults to a local self-contained HTML file with its path reported. It also covers decks, prototypes, component labs, motion studies and redesigns. ## Operating procedure in brief

Its Workflow section has eight steps:
1. Understand the brief (what, for whom, which artifact, which constraints are locked).
2. Gather context: "Identify the visual vocabulary before writing code."
3. Commit to one of seven surface archetypes.
4. Define an artifact-level design system (colours, type, spacing, radii, elevation, motion, component and interaction rules).
5. Choose the format.
6. Build, preserving prior versions.
7. Verify as far as the environment allows, including the ten-tell slop self-audit.
8. Report the path, the contents, caveats and the next step.

Exploration defaults to three variants: conservative, strong-fit and divergent.

## Where it conflicts with the proposal

- It judges its own quality. The slop diagnostic is a self-score: "Score the artifact out of 10 (10 = maximum slop). State the score and list which tells fired, in one short report." It also sets a done-gate on that self-score: "Do not declare done while compositional tells (3, 8, 10) are still firing". The proposal says the designer "does not judge the quality of its own design; review is separate." Either the diagnostic moves to the reviewer, or the proposal's line needs a distinction between "checking your own output against a checklist" and "judging quality".
- It asks the user questions: "If context is missing and fidelity matters, ask concise focused questions instead of producing a generic mockup." A subagent in an unattended run cannot ask mid-run. In the proposal, questions become "open questions" in the report. Its skip rule ("Skip questions when:" followed by, among others, "the missing detail has an obvious default") and "When proceeding with assumptions, label only the important ones." carry over better.
- Boundary (5): "If the user asks for implementation in an existing repo, generate code in the repo's actual stack instead of forcing a standalone HTML artifact." In the proposal that work goes to an implementer by default.
- Stance: it speaks to a human manager ("working with the user as the manager"). The proposal's designer reports to a lead agent.
- Report shape: "artifact path", "what it contains", "verification status" and "next suggested action". This covers path, contents and verification, but not "the direction and why" or "deviations from the design system". The proposal is stricter here.

## What looks wrong or untested

- It presents mechanism claims as fact without evidence: "This conditions generation on a high-level plan first, which collapses the entropy of what gets produced — the same reason a chain-of-thought step improves reasoning." and "designers asked to label AI UIs collapse the "this is AI" signal down to about ten tells". Neither is cited.
- "**Diagnose first, treat second** — auditing and fixing in one breath fails, because the model's prior outweighs the instruction" is also an untested claim, although separating diagnosis from repair is plausible.
- Some tells cannot be decided by looking at the result. "**Default type** — Inter (or system-ui) used by default rather than chosen." is about intent, not about the artifact, so the self-score is partly unfalsifiable.
- The absolute "The hero-plus-three-cards composition is correct for **Decide/Learn only**." together with "This one constraint eliminates more generic-looking UI than any aesthetic rule below." is a strong claim with no test behind it.
- The surface list is web and product oriented. Nothing covers native mobile or the platform conventions of an existing design system beyond "Use the existing type system if one exists." and "Use brand/design-system colors first."
- The "Portable Opening Prompt Pattern" and the hosted-tool remap list (`done()`, `fork_verifier_agent()` and the rest) are plumbing for one translation job and would be noise in a harness role.

## Verdict

This is the best base for a design skill that the designer loads, specifically the process half: context gathering, surface commitment, variant rules, content discipline and slop vocabulary. It already separates process from brand vocabulary through sibling skills, which matches the proposal's intent. It is not a base for the role text as-is, because it addresses a human, asks questions mid-task, writes production code and self-scores. The role should lift three sections from it nearly verbatim: Source-Code Fidelity (for contract clause 1), the tiered Verification section with its "say exactly what was and was not verified" rule (for clause 3 when no browser is present), and the prototype-states line (for clause 4). The slop diagnostic belongs in the reviewer's skill, or it should stay in the design skill as a checklist, so that the role's "no self-judgment" line is not contradicted.
