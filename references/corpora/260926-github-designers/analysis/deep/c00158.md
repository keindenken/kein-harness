## What it is for, who consumes the output

A designer-developer that writes production UI code directly: "Create visually stunning, production-grade UI implementations that users remember." It owns "interaction design, UI solution design, framework-idiomatic component implementation, and visual polish (typography, color, motion, layout)" and explicitly not "backend logic, API design, or information architecture." The consumer is the lead or orchestrator agent, which gets a short report (aesthetic direction, framework, components touched, typography/colour/motion/layout choices, verification).

## Operating procedure in brief

1. Detect the framework from `package.json`.
2. Commit to an aesthetic direction: "Purpose, Tone, Constraints, Differentiation (the ONE memorable thing)".
3. Domain-check against the model's editorial default; override it with concrete hex and typefaces for operational domains.
4. Study existing UI patterns: "component structure, styling approach, animation library".
5. Implement.
6. Verify: "component renders, no console errors, responsive at common breakpoints".

## How it gets evidence about the UI, and whether its declared tools can do it

- Reading: framework detection and pattern study from code ("Detect frontend framework from project files before implementing (package.json analysis)", "study conventions and commit history first").
- Rendering: Playwright MCP tools are listed in prose "(visual verification and responsive testing)", plus the omc skill `/oh-my-claudecode:visual-verdict`. There is no `tools:` frontmatter, so the agent inherits whatever the session has, and the listed tools exist only if that plugin and those MCP servers are installed. Most of the list (`ctx_search`, `lsp_diagnostics`, `ast_grep_search`, `state_read`, `notepad_write_working`, `mcp__ddg-search__search`, `mcp__tavily__tavily_search`) belongs to the oh-my-claudecode environment and will be missing elsewhere.
- The verify step checks that the page works, not how it looks: "Renders: [yes/no] | Responsive: [breakpoints] | Accessible: [ARIA, keyboard nav]". Nothing says to compare the screenshot with the committed direction. Whether it looks right is left to the `visual-verdict` skill, which is not in this file.
- Fallback when no browser: "Playwright fail -> retry with `browser_navigate` once -> manual browser required." The agent hands the check back, but the output template has no field saying that rendering did not happen.

## Where taste/craft lives

Inline, compact, and partly model-specific: the bans ("Avoid: generic fonts (Arial, Inter, Roboto, Space Grotesk), purple gradients on white, predictable layouts"), the direction rule ("Match implementation complexity to aesthetic vision: maximalist = elaborate code, minimalist = precise restraint"), and the "## Domain-Aware Defaults" paragraph with hex codes and typefaces. Engineering principles are pointed to an external file ("[KISS Principle](software-laws.md#kiss-principle)") that the agent has no path to. The upstream c00042 has more taste inline (Success_Criteria, Failure_Modes_To_Avoid, a Good/Bad example); this fork cut those.

## What it does that the PROPOSED DESIGNER lacks

- A mechanism for countering the model's own default look, with the reason a plain ban fails: `Generic negations ("don't use cream") shift to another fixed default — always pair override with concrete target.` This is a claim about how taste instructions behave. Whatever skill holds the designer's taste needs it, and it matches this repo's own observation that a neutral rewording still primes.
- A cheap, fixed format for direction options, and a rule for choosing without a human: "Ambiguous briefs: propose 3-4 directions (bg hex / accent hex / typeface — one-line rationale), select best-fit, proceed." The proposal allows several distinct variants when asked but gives no form for a direction, and does not say what to do on an ambiguous brief with nobody to ask. (The upstream spells out the no-human rule: "Designer is execution-oriented: only request user clarification when the current runtime explicitly supports or requests interactive input — do not pause for user selection by default." The fork dropped that sentence.)
- A precedence rule between the brief and taste defaults: "Explicit user/brand intent always wins over domain defaults."
- Explicit non-responsibilities: "Not responsible for backend logic, API design, or information architecture." The proposal draws the boundary only toward the implementer.
- Direction named as a sentence the designer commits to before coding: "Commit to aesthetic direction before coding: Purpose, Tone, Constraints, Differentiation (the ONE memorable thing)". The proposal's clause (2) is close, but this gives it four named parts.
- Framework detection as the first step: "Detect framework: check package.json for react/next/vue/angular/svelte/solid".

## Where it conflicts with the proposal

- Boundary: it writes production components itself ("Implement working, production-grade, visually striking, cohesive code"). The proposal's clause (5) has the designer decide and prototype, with integration going to an implementer unless the brief says otherwise.
- Order: it commits to a direction (step 2) and domain-checks (step 3) before it studies the existing UI (step 4). The proposal's clause (1) reads the product first and follows its design system unless the brief asks for a new direction.
- Taste against the existing system: "Match existing code patterns" sits next to "Avoid: generic fonts (Arial, Inter, Roboto, Space Grotesk)" and "Create visually stunning, production-grade UI implementations that users remember." In a product built on Inter, the file does not say which rule wins. The proposal resolves this by making the product's system the default.
- Taste in the role: bans, domain palettes and a model's house style live in the role text. The proposal moves all of that to skills.
- Coverage: no empty/loading/error states anywhere. Accessibility and responsiveness appear only as yes/no report fields.
- Return: no screenshots or paths, no deviations from the design system, no open questions. "Accessible: [ARIA, keyboard nav]" is the designer grading itself, which the proposal leaves to review.

## What looks wrong or untested

- The model named in the prose is not the model that runs it. The frontmatter says `model: sonnet` and the description says "(Sonnet)", but the doctrine describes another model: "Opus 4.7 has an editorial-leaning default house style: warm cream/off-white (~`#F4F1EA`), serif display (Georgia/Fraunces/Playfair), italic accents, terracotta/amber accents." The mismatch is inherited from upstream, which also sets `model: sonnet`. The override targets a bias the running model may not have, and the passage will go stale with each model change. This is also why this repo keeps model names out of prompt prose.
- Relative links (`software-laws.md#...`, `rules/tool-priority.md`) point to files that were not copied with the agent. In the LimiNode repos they probably resolve to nothing.
- The tool inventory is copied from another harness. In these three repos, most of the named tools and the `visual-verdict` skill are probably absent, so the "Playwright fail -> retry with `browser_navigate` once -> manual browser required" path may be the normal path.
- "Complete what is asked, no scope creep; work until it works" gives no stopping condition other than "renders".
- "High effort: visual quality is non-negotiable" is an exhortation; nothing in the file checks it.
- The fork removed the upstream's "Unverified implementation: Creating UI code without checking that it renders. Always verify." and its final checklist, so what remains of verification is one line in the protocol plus the report fields.

## Verdict

The closest of the five to the shape of the proposed designer role, so it is usable as a base for the role's skeleton, but only after stripping. Keep: short contract, framework detection, commit to a direction before building, explicit non-responsibilities, and the ambiguous-brief rule (options in a fixed form, pick, proceed; the upstream's no-human sentence restored). Remove: the production-implementation scope, the taste bans, and the model-specific house-style paragraph. Reorder it so reading the product comes first. Add states, deviations, screenshot paths and a rendered/not-rendered field to the return. The "Domain-Aware Defaults" idea belongs in a design skill, not the role: pair every override with a concrete target instead of a negation. It should be rewritten without a model name, and there is no evidence yet that it works; the corpus shows it only as an assertion.
