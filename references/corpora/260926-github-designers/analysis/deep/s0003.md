# s0003 — AgentWorkforce/relay `emil-design-eng` (skill)

Source: `corpus-skills/AgentWorkforce_relay__.agents_skills_emil-design-eng_SKILL.md` (685 lines; stars 793; copies in 2 repos). The text is Emil Kowalski's design-engineering doctrine (author of Sonner and Vaul), vendored into `AgentWorkforce/relay`; the copy count of 2 means two repos carry it, but it is one author's voice. No `references/` are linked, so this file is the whole skill.

## What it is for and who consumes the output

A craft-knowledge skill about UI polish, "component design, animation decisions, and the invisible details that make software feel great" (frontmatter). It has two outputs: code written following its rules, and a review of UI code in a mandated table. The consumer is a human in chat; the skill opens with a greeting and a course link and then waits:

> Do not provide any other information until the user asks a question.

## Operating procedure in brief

There is barely a procedure. It is a body of rules with two procedural pieces:

- An "Animation Decision Framework" to answer in order before writing animation code: should it animate at all (by frequency of use), what is the purpose, which easing, how fast.
- A required review format: one Markdown table "| Before | After | Why |", one row per issue, and a closing review checklist of eleven code smells with fixes.

Everything else is doctrine: springs, component principles (press scale, no `scale(0)`, origin-aware popovers, tooltip delay skipping), CSS transform and `clip-path` techniques, gesture handling, performance, reduced motion, "The Sonner Principles", stagger, and animation debugging.

## How it gets evidence about the UI

Reviews are of code: "When reviewing UI code, you MUST use a markdown table with Before/After columns." The review checklist items are all source-level patterns (`transition: all`, `scale(0)`, `ease-in`, `transform-origin: center`, duration > 300ms). The only rendering advice is addressed to a human developer with hands on a device: "Step through animations frame by frame in Chrome DevTools (Animations panel).", "Connect your phone via USB, visit your local dev server by IP address, and use Safari's remote devtools.", and "Review animations with fresh eyes. You notice imperfections the next day that you missed during development." No tools are declared, and none of these are things an agent can do as written. The corpus flag `renders_and_looks: true` for this record is generous; the skill describes looking, it does not instruct the agent to render.

## Where taste/craft lives

All inline, and it is almost nothing but craft. It is exactly the kind of content the proposal wants in a skill rather than the role: concrete, numeric, with reasons.

## What it does that the PROPOSED DESIGNER lacks

The proposal deliberately keeps craft out of the role, so "lacks" here means content a paired design skill would need. Motion and micro-interaction are absent from the proposal entirely (item (4) lists states, responsive and accessibility, not motion).

- A frequency test for whether to animate at all, which is the kind of rule that prevents generic over-animation: "100+ times/day (keyboard shortcuts, command palette toggle) | No animation. Ever." and "**Never animate keyboard-initiated actions.**"
- A purpose test: “If the purpose is just "it looks cool" and the user will see it often, don't animate.”
- Concrete, checkable values: "**Rule: UI animations should stay under 300ms.**", the duration table ("Button press feedback    | 100-160ms"), custom curves ("--ease-out: cubic-bezier(0.23, 1, 0.32, 1);"), "The scale should be subtle (0.95-0.98).", "Keep stagger delays short (30-80ms between items)."
- Reduced motion defined as fewer, not zero: "Reduced motion means fewer and gentler animations, not zero. Keep opacity and color transitions that aid comprehension. Remove movement and position animations."
- Touch hover gating: "Touch devices trigger hover on tap, causing false positives. Gate hover animations behind this media query."
- Performance constraints tied to rendering: "Only animate transform and opacity" and "Framer Motion's shorthand properties (`x`, `y`, `scale`) are NOT hardware-accelerated."
- A fixed, diff-like review output ("A single markdown table with | Before | After | Why | columns, one row per issue found.") which is a usable shape for the separate reviewer, not for the designer.

## Where it conflicts with the proposal

- It is a doctrine, not a working contract: no reading of the existing product, no user/task, no states, no handoff, no boundary with an implementer. It writes production code directly.
- The initial-response block ("When this skill is first invoked without a specific question, respond only with:" followed by a canned greeting) and the course plug ("check out Emil’s course: [animations.dev](https://animations.dev/)") make it a chat persona; loaded by a dispatched subagent it would either emit the greeting or be ignored.
- Several rules are stated as absolutes that would override a project's design system: "**Never use ease-in for UI animations.**", "No animation. Ever.", "Add `transform: scale(0.97)` on `:active`." The proposal puts the product's design system first; this skill has no clause deferring to what the project already does.
- Its review mode judges code the model may itself have written, which the proposal assigns to a separate reviewer.

## What looks wrong or untested

- Internal contradiction on exit timing: the checklist says "Same enter/exit transition speed | Make exit faster than enter (e.g., enter 2s, exit 200ms)", but the only 2s case in the body is a press-and-hold overlay, not an entrance, and the headline rule is "UI animations should stay under 300ms". An agent applying the checklist row literally would add 2s entrances.
- Of Sonner: "It is slightly slower than typical UI animations and uses `ease` rather than `ease-out` to feel more elegant." The toast examples use "transition: transform 400ms ease;" which breaks both "stay under 300ms" and "Default → ease-out". The text treats this as cohesion; a checklist-driven reviewer would flag it.
- The easing decision tree is garbled in the flattened Markdown (it reads "Is the element entering or exiting?" then "Yes → ease-out (starts fast, feels responsive)" then "No →" then "Is it moving/morphing on screen?", so the "No" branch of entering-or-exiting means neither), readable by a person, ambiguous for a model.
- Under "The opacity + height combination": "There is no formula — you adjust until it feels right." This contradicts "Only animate transform and opacity" (height triggers layout) without resolving it.
- Accessibility coverage is motion-only. Nothing on contrast, focus, semantics or keyboard beyond "Never animate keyboard-initiated actions".
- Evidence for the numbers is anecdotal and brand-specific ("Raycast has no open/close animation", "At Vercel, the dashboard tab animation used Shared Layout Animations and dropped frames during page loads."). They are sensible defaults, not tested thresholds.

## Verdict

Not a base for the role; a strong candidate for (part of) a **design skill**, specifically a motion-and-interaction-polish skill the designer loads when the brief touches animation or component feel. It is the most concrete craft text in this batch and it names the reason behind almost every number, which is what makes it transferable. Before use it needs: the chat greeting and course link removed, the contradictory checklist row fixed, a precedence clause (the project's existing motion tokens win), and its human-only verification advice either dropped or restated as something a subagent can do (render at reduced speed, or say it did not). Its Before/After/Why table is a good format for the separate reviewer, not for the designer.
