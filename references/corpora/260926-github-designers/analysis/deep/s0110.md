# s0110 — suleimanodetoro/skills `review-interface` (skill)

File: `corpus-skills/suleimanodetoro_skills__skills_review-interface_SKILL.md` (168 lines). Stars 816, one repo. Same owner as s0109 and explicitly its partner: "Use `design-interface` as the source of truth for design, state, interaction, and verification rules. This skill owns review scope, evidence, prioritization, consolidation, and verdicts." Count the pair as one voice.

## What it is for and who consumes the output

A read-only review of a screen, flow, component or UI diff, ending in a verdict of `Block`, `Needs changes` or `Approve`. The consumer is the requester, and, when fixes are wanted, the implementer: "finish the review first, preserve its findings as the implementation scope, then hand implementation to `design-interface` and the relevant engineering skill." It is the "review is separate" half that the proposal assumes exists elsewhere.

## Operating procedure in brief

Resolve mode (`quick` with a 5-finding cap, or `full` with 12) and scope; recon the system; trace the primary task from entry to completion through six checkpoints; review reachable states; inspect the rendered UI at narrow, wide and near-breakpoint widths, with keyboard, focus, themes and reduced motion; vet every candidate finding against six conditions; run only non-mutating checks. Output: a coverage table, a findings table (one row per root cause), a "Considered and rejected" table, a verification list, and one verdict.

## How it gets evidence about the UI, and whether its tools can do it

It reads source, renders when possible, and keeps each claim inside what its evidence class can prove. The core is a table: "Source | Semantics, state branches, tokens, declared behavior | Rendered alignment, perceived motion, actual focus order" and "Rendered UI | Visual hierarchy, clipping, contrast pair, visible states | Hidden code paths, accessible tree, data integrity". Rendering is conditional: "When a runnable surface exists, check narrow, wide, and near-breakpoint widths; content stress; light/dark variants; keyboard traversal; focus visibility; reduced motion; and critical transitions. Use browser or device inspection when a finding depends on rendered behavior."

No tools are declared and no browser is named. The missing-tool case is handled: "When evidence is missing, write `Not verified`. Do not convert uncertainty into a finding or an approval." and "Never approve with an unverified primary path." So without a browser it degrades to a source-class review that cannot approve visual claims, which is the correct behaviour.

## Where taste/craft lives

Not here. It borrows all design rules from s0109 and its references ("Load `design-interface` and inspect the relevant state, layout, color, interaction, and verification references."). Its own evidence method is in two uncollected references, `references/evidence-playbook.md` and `references/runtime-review.md`. The file itself is review procedure only.

## What it does that the proposed designer lacks (verbatim)

The proposal's contract (3) says "claims about how the result looks come from that inspection, not from reading the code". This skill makes that precise and generalises it:

- The evidence-class table above, which says what each kind of evidence can and cannot prove. The proposal has only the two-way split (inspection versus code).
- "When evidence is missing, write `Not verified`. Do not convert uncertainty into a finding or an approval."
- "If the requested surface is too large to inspect honestly, choose the smallest complete high-traffic flow and state the boundary. Never imply that unseen screens passed."
- "Do not invent missing states from naming alone. Cite the source branch or render that proves the state exists or is absent." This would sharpen the proposal's contract (4) whenever the designer revises existing UI.
- Separation of project convention from drift before calling something wrong: "Inspect neighboring surfaces to distinguish project convention from local drift."
- Candidate filtering: "Reject candidates that are preference-only, unsupported, intentional and sound, already owned by another root finding, or cost more complexity than user value."
- A read-only boundary for critique work: "Do not edit source, install dependencies, update snapshots, write plans, or commit changes."

## Where it conflicts with the proposal

- Critique as a designer output. The proposal lists "a written critique/opinion" among the designer's output forms, and also says the designer "does not judge the quality of its own design; review is separate". This skill shows that critique of an interface, done well, is a separate discipline with its own evidence rules, severity scale and verdict, and its owner put it in a separate skill that forbids editing. If the designer role also produces critiques, it either inherits this machinery or produces a weaker, opinion-style critique beside a real reviewer. The proposal should decide which: critique of someone else's UI inside the designer (then take this skill's evidence rules), or all critique in the reviewer (then drop "written critique" from the designer's output forms).
- Approval. This skill ends in `Approve`, which is a quality judgement. That is consistent with the proposal only if it runs as the separate reviewer, never inside the designer on its own output.

## What looks wrong or untested

- The "Considered and rejected" quota ("Include 1–3 real candidates in `quick` mode and 2–5 in `full` mode") sits next to "Do not invent filler." A reviewer that genuinely considered nothing else is forced to produce a row; the minimum pushes toward invention that the next line forbids.
- The finding caps (5 and 12) are arbitrary and unexplained; a surface with 13 real HIGH findings would lose one.
- "Run only safe checks that do not mutate project state" conflicts in practice with rendering, which often needs a dev server or a build; it is hedged by "builds known to rewrite files", but the reviewer has to guess which builds those are.
- It depends on s0109 and four uncollected reference files; standing alone it cannot apply any design rule.
- No evidence the severity scale or caps were tested.

## Verdict

Not a base for the designer role; a strong base for the separate design-review role or skill the proposal relies on. Its evidence-class table and the two `Not verified` rules should also be borrowed into the designer's contract (3), since they state the proposal's rule that claims come from inspection more precisely and handle the no-browser case. Before reuse, drop the minimum on rejected candidates and the fixed finding caps, or give them reasons.
