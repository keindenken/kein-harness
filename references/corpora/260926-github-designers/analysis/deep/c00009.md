## What it is for, and who consumes its output

A research-citing design critic. The description routes review work to it: "Use proactively when reviewing UI/UX design, evaluating visual interfaces, auditing web components for usability issues, checking accessibility compliance, or critiquing design aesthetics." It also covers AI chat/copilot interfaces. The consumer is the main agent or the user, who receives a fixed-format markdown critique ("Format every response like this:") with Verdict, Critical Issues, Aesthetic Assessment, What's Working, Implementation Priority, Sources, and "One Big Win". It has no write tools, so every fix is code in the reply.

## Operating procedure in brief

Five-part review: evidence-based issue list (what's wrong / why it matters / research backing / fix / priority) → aesthetic critique (typography, colour, hierarchy, atmosphere) → usability heuristics checklist → accessibility validation (WCAG 2.1 AA plus four WCAG 2.2 criteria) → recommendations ranked by impact × effort. Then the fixed response template.

## How it gets evidence about the UI, and whether its tools can do that

It reads CSS, HTML and tokens with Read/Grep/Glob, and the description says to invoke it "when the user shares screenshots, mockup files, CSS, HTML, design tokens". In Claude Code, Read can display an image file, so a screenshot saved to disk can be seen; WebFetch returns page text, not a rendering. It cannot render or take a screenshot itself. Several checks need a live page it cannot produce: "Focused elements must not be fully hidden by sticky headers, cookie banners, or chat widgets — check with Tab key while scrolled", "Interaction latency acceptable (hover/click responses <100ms; INP target: <200ms at p75)?", and "Always verify with the `prefers-reduced-motion` media query". With these tools those become code-reading guesses, and nothing in the prompt tells it to say so.

## Where its taste/craft content lives

Entirely inline, and it is the densest taste doctrine of the five: "## Aesthetic Guidance: Avoiding Generic Design" (fonts to never use, fonts to use by register, colour "Commit Fully", dark-mode values, motion timing, backgrounds, layout), research-backed principles (F-pattern, left-side bias, banner blindness, Fitts, Hick, thumb zones), AI-interface patterns, and anti-pattern lists. No external files.

## What it does that the PROPOSED DESIGNER lacks

Some of these belong to a reviewer or a skill rather than to the designer, which the verdict separates.

- A named anti-generic stance with concrete targets: "You actively fight against "AI slop" aesthetics:" / "Generic SaaS design (purple gradients, Inter font, cards everywhere)". The proposal pushes all taste to skills but does not say the designer must load one or that a generic result counts as a failure.
- Direction commitment stated as craft: "Commit to a cohesive aesthetic (dark mode, light mode, solarpunk, brutalist)" and "One distinctive font used decisively > multiple safe fonts". The proposal says "commit to one direction" without saying what a direction consists of.
- A per-issue structure for the critique output form the proposal allows: "**What's wrong**", "**Why it matters**", "**Research backing**", "**Fix**", "**Priority**", plus "## ✅ What's Working" and "## 💡 One Big Win". The proposal's return list is written for building, not for a written opinion.
- Priority by cost: "Always prioritize by impact × effort".
- WCAG 2.2 items missing from the proposal's "accessibility baseline": "**Focus not obscured (SC 2.4.11)**", "**Dragging alternatives (SC 2.5.7)**", "**Redundant entry (SC 3.3.7)**", "**Accessible authentication (SC 3.3.8)**".
- AI-product states the proposal's state list does not cover: "Stream results progressively — never show a blank state while AI generates" and "Use skeleton loaders shaped like the expected output".
- A convention-first guard on novelty: "Follow conventions unless you have strong evidence to break them" and "But maintain usability:" under the grid-breaking advice.

## Where it conflicts with the proposal

- It is a critic of others' work, not a maker; the proposal's designer makes things and leaves review to someone else. As a reviewer it would suit the proposal's separate review step better than the designer itself.
- Taste is in the role text, the thing the proposal moves out.
- Its doctrine overrides the product's system. "**Never use these generic fonts:**" / "Inter, Roboto, Open Sans, Lato, Montserrat" and "Default system fonts (Arial, Helvetica, -apple-system)" apply with no exception for a product whose design system already uses them; the proposal's first rule is to follow that system. It even ranks "Generic aesthetic (boring fonts, tired layouts)" as "**Should Fix Soon (High):**".
- It does not render or look; the proposal requires that claims about appearance come from inspection.

## What looks wrong or untested

- Invented precision. The model answer tells the agent to predict outcomes: "This will increase nav interaction rates by 20-40% based on typical A/B test results." and "**Always explain ROI**". Combined with "**Always cite sources**" and no step to verify a citation, this invites fabricated numbers and references. The research figures it states as fact (for example "Users spend 69% more time viewing the left half of screens", "49% of users hold phone with one hand") are not checked in this corpus and should be verified before any are reused.
- Mislabelled principles: "**Recognition Over Recall** (Jakob's Law)" joins two different heuristics, and the Hick's Law section leans on "7±2", which is Miller's working-memory figure. "Hiding navigation behind hamburger on desktop (banner blindness + extra click)" attributes a hidden-nav problem to banner blindness.
- Self-contradiction: "You are not:" / "Prescriptive about subjective aesthetics (unless user impact is clear)" sits beside a hard font blacklist and "Solid white or solid color backgrounds (flat, boring)" under "**Avoid:**".
- Contrast advice pulls against its own accessibility section: "Lower contrast for comfort (not pure black #000000, use #121212)" next to the 4.5:1 non-negotiable, with no note that the two must be reconciled.
- The "distinctive" example palette (`#1a1a2e` with `#efd81d`, "Cabinet Grotesk font with dark (#1a1a2e) + gold (#efd81d) palette creates premium perception") is itself a single fixed recipe; if every run reaches for it, it becomes the new generic.
- It cannot perform several checks it mandates (Tab-while-scrolled, INP, reduced-motion verification) with Read/Grep/Glob/WebFetch.

## Verdict

Not a base for the designer role. It is a good starting point for two other things. First, a design-critique skill or a separate design reviewer: the per-issue structure, impact × effort ranking, "What's Working" and "One Big Win", with citations made optional-and-verified and outcome predictions removed. Second, the anti-generic part of a craft/taste skill, but only behind an explicit rule that the product's existing design system wins, and with the blacklist reframed as defaults to avoid on new directions rather than faults to fix in existing UI. Its WCAG 2.2 items and AI-interface states are worth adding to whichever baseline the designer loads.
