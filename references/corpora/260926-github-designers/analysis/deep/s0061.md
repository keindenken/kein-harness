## What it is for and who consumes the output

A craft doctrine for building app interfaces (dashboards, admin panels, SaaS tools, settings, data views), explicitly not marketing pages ("Redirect those to `/frontend-design`."). It writes UI code directly and, after the task, offers to save design decisions into `.interface-design/system.md` for future sessions. The consumer is the user in a live chat; the workflow asks for their confirmation of the direction before building.

## Operating procedure in brief

If `.interface-design/system.md` exists, read it and apply it ("Decisions are made."). Otherwise: explore the product domain and produce four required outputs (at least 5 domain concepts, a colour world of 5+ colours, one signature element, 3 named defaults to avoid); propose a direction that references all four; get user buy-in; build, stating a six-line Intent/Palette/Depth/Surfaces/Typography/Spacing checkpoint before every component; run the "mandate" checks (swap, squint, signature, token tests) and iterate before showing; offer to save the system.

## How it gets evidence about the UI, and whether its tools can do it

Weakly specified. The central instruction is "**Before showing the user, look at what you made.**" but nothing says how: no render, no screenshot, no browser, no widths. The checks presume vision ("**The squint test:** Blur your eyes. Can you still perceive hierarchy?"), and the only concrete viewport is a desktop one ("At a 1280×800 viewport, what does the user see before scrolling?"). Existing-product evidence is limited to its own memory file ("Read `.interface-design/system.md` and apply."); unlike s0109 or s0024 it never tells the agent to read the product's components, tokens or neighbouring screens. No tools are declared and there is no fallback for a missing browser, so in practice "look at what you made" becomes re-reading the code the agent just wrote, which is exactly what the proposal's contract (3) rules out.

## Where taste/craft lives

Inline, and it is most of the file: the "Where Defaults Hide" section, spatial composition, colour, surface elevation, borders, token architecture, depth, radius, typography, iconography, animation, dark mode and an "Avoid" list. Deeper values and code examples are in `references/principles.md` (not collected). This is the kind of content the proposal wants out of the role text and in a loadable skill.

## What it does that the proposed designer lacks (verbatim)

These are taste and process devices, most of which belong in a skill, not in the role:

- Naming defaults before avoiding them: "**Defaults:** 3 obvious choices for this interface type — visual AND structural. You can't avoid patterns you haven't named."
- A generic-output test with a concrete procedure: "**The test:** Read your proposal. Remove the product name. Could someone identify what this is for? If not, it's generic. Explore deeper." and "**The swap test:** If you swapped the typeface for your usual one, would anyone notice?"
- A direction that must be carried through, not only named: "Saying "warm" and using cold colors is not following through. Intent is not a label — it's a constraint that shapes every decision." and "Check your output against your stated intent. Does every token reinforce it?"
- Spatial composition as a decision made before components, with five questions starting "**How many distinct information regions does this screen have?**" and the diagnosis "Single-column top-to-bottom is the shape that emerges when none of these questions were asked."
- Token naming as a design decision: "Someone reading only your tokens should be able to guess what product this is."
- Human specificity beyond naming the user: "Not "users." The actual person. Where are they when they open this? What's on their mind?" and "Not "use the dashboard." The verb. Grade these submissions. Find the broken deployment. Approve the payment."
- Persisting decisions across sessions, which the proposal does not address at all: "If yes, write to `.interface-design/system.md`:" with "Direction and feel", "Depth strategy (borders/shadows/layered)", "Spacing base unit", "Key component patterns", plus the rule "Add patterns when a component is used 2+ times, is reusable across the project, or has specific measurements worth remembering."

## Where it conflicts with the proposal

- Asking mid-run. "If you cannot answer these with specifics, stop. Ask the user. Do not guess. Do not default." and the workflow step "Confirm — Get user buy-in" require a live user. A dispatched subagent cannot do this; loaded as-is into the designer, it either stalls or ignores the gate.
- Silence versus reporting. "Be invisible. Don't announce modes or narrate process." is aimed at chat; the proposal's return contract requires the direction and why, deviations and open questions.
- Self-judgement. "The Mandate" makes the builder its own critic ("Ask yourself: "If they said this lacks craft, what would they mean?" That thing you just thought of — fix it first." and "If any check fails, iterate before showing."). The proposal says the designer "does not judge the quality of its own design; review is separate". The swap/squint/signature/token tests are quality judgements, not factual inspection.
- Novelty versus the existing system. "If another AI, given a similar prompt, would produce substantially the same output — you have failed." and "**NEVER produce identical output.**" push away from convention. In an existing product with a design system (the proposal's default case), matching the system is the goal. The skill protects the existing system only through its own `system.md`, not through the product's code or tokens.
- Accessibility baseline. "Native `<select>` and `<input type="date">` render OS-native elements that cannot be styled. Build custom components — trigger buttons with positioned dropdowns, calendar popovers, styled state management." This pushes toward custom controls that must then re-implement keyboard and screen-reader behaviour, against the proposal's accessibility baseline and directly against s0109's "Keep controls recognizable. Use native semantics and established component primitives before custom interaction code." The record's `accessibility` and `responsive` flags are both false.

## What looks wrong or untested

- The native-control claim is overstated: both elements accept a good deal of styling, and the cost of custom replacements (keyboard, focus, screen-reader semantics) is not mentioned.
- Taste stated as law with no condition: "**Sidebars:** Same background as canvas, not different.", "**Inputs:** Slightly darker than their surroundings, not lighter.", "Avoid spring/bounce in professional interfaces." These are one house style, which conflicts with its own "No interface should look the same."
- The per-component checkpoint ("**Every time** you write UI code — even small additions — state:" six lines) is costly on every edit and is unverified as useful.
- "look at what you made" with no rendering mechanism; the self-check can be satisfied by reading code.
- Desktop-only framing (1280×800 fold; no mobile or narrow widths anywhere).
- The Commands and references depend on an upstream plugin the embedding repo may not ship.
- The prose style ("You will generate generic output. Your training has seen thousands of dashboards.") is persuasive rather than operational; whether it changes outputs is untested here.

## Verdict

Base for a design skill (app-interface taste and anti-generic doctrine), not for the role. As a skill it offers the corpus's most developed anti-default devices (named defaults, the product-name removal test, the swap and token tests, spatial-composition questions) and a useful idea the proposal lacks, persisting design decisions to a project file. Before reuse it needs: the ask-the-user gates turned into stating the assumption, continuing, and returning the question; the mandate checks moved to the separate reviewer or recast as inspection of rendered output; the native-control rule removed or reversed; an existing-product gate that defers to the product's own components and tokens before any novelty rule; and a responsive and accessibility floor.
