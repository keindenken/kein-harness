# s0013 — ConardLi/garden-skills `web-design-engineer` (skill)

Source: `corpus-skills/ConardLi_garden-skills__skills_web-design-engineer_SKILL.md` (492 lines; stars 10402; copies in 1 repo). Only record from owner `ConardLi`. It routes heavily to a `references/` library (style recipes, redesign protocol, failure patterns, browser acceptance, critique guide, calibration) that was not collected, so every judgement below is about SKILL.md alone.

## What it is for and who consumes the output

A general "design engineer" skill for any browser-rendered visual artifact: "pages / dashboards / prototypes / slide decks / visualizations / animations / UI mockups / design systems", plus critique on request. The consumer is the human user in an interactive session: the workflow is built around stopping for their confirmation at three checkpoints. Its bar is set in the second paragraph: “The bar is "stunning," not "functional."”

## Operating procedure in brief

- Step 0: verify named products, brands or versions by search before designing.
- Step 1: decide how much to ask, from a table of example requests.
- Step 2: gather context in a priority order (user-supplied resources, existing product pages, reference brands, a named style anchor, or scratch). Brand tasks follow an asset protocol (real logo, real product imagery, `brand-spec.md`). Work on existing UI is classified as Extension / Redesign-Preserve / Redesign-Overhaul.
- Step 2b: write a "Design Read" YAML with five 1–10 dials.
- Step 3a/3: answer four positioning questions, then declare the design system in Markdown. Checkpoint 1: wait for the user.
- Step 4: v0 with placeholders and assumptions. Checkpoint 2: wait for the user.
- Step 5: full build; Checkpoint 3 at non-trivial decisions.
- Step 6: pre-delivery checklist as a code/design self-check; browser acceptance only if the user explicitly asks.
- Step 7: 5-dimension scored critique on request or as a self-check.
- Fallback: "Design Direction Advisor" offers three directions from different "schools".

## How it gets evidence about the UI

It reads code and supplied materials and explicitly prefers code over screenshots: "**Code ≫ Screenshots**: When the user provides both a codebase and screenshots, invest your effort in reading source code and extracting design tokens rather than guessing from screenshots". It does **not** render by default. Rendering is opt-in and gated on specific user words:

> Run an executable browser acceptance harness **only when the user explicitly asks for acceptance / 验收, QA, browser testing / 浏览器测试, visual regression, responsive testing / 响应式检查, cross-viewport verification, or equivalent hands-on validation**. Do not infer this request merely from “build,” “finish,” “polish,” or “verify your work.”

and the checklist repeats it: "It does **not** require launching a browser unless the user explicitly requested executable acceptance in Step 6". Yet the same checklist asks for "No text overflow or truncation" and "Visual quality at Dribbble / Behance showcase level", both of which are visual claims made from code. No tools are declared in frontmatter; the checklist assumes WebSearch ("facts verified via WebSearch, not assumed").

## Where taste/craft lives

Both inline and in references. Inline: the anti-cliché table ("Aggressive purple → pink → blue gradient", "Inter / Roboto / Arial / Fraunces / system-ui as display", "Cyber-neon on `#0D1117` dark"), the "Aim to Stun" list, scale minimums, emoji and placeholder rules, a six-school direction library with named studios. References: 25 style-recipe files, `failure-patterns.md`, `design-calibration.md`, `critique-guide.md`. So it mixes contract and taste in one file, the opposite of the proposal's split, though it does push the bulk of concrete values out to recipe files ("**Load only the one recipe file you're using**, not the whole catalog.").

## What it does that the PROPOSED DESIGNER lacks

- A classification of work on existing UI before editing, with a default of the least change: "Classify the task as **Extension**, **Redesign · Preserve**, or **Redesign · Overhaul** before editing." and "choose the smallest change mode that satisfies the request. New elements in Extension mode should be indistinguishable from the originals." The proposal says "follow its design system unless the brief asks for a new direction", a binary; this gives three grades and names what is protected (the routing table lists "protect routes, IA, analytics, forms, accessibility, and brand").
- A written direction statement before tokens, with a reason it is not decorative: "Use the dials as decision variables, not decorative scores. They must affect layout variation, motion, content per viewport, real-asset effort, and preservation strictness." The proposal asks the designer to "commit to one direction" but not to write it down in any form the caller can check.
- A "Design Decisions" block declaring palette, type, spacing, radius, shadow and motion before code. This is a natural place to surface the proposal's "deviations from the design system".
- Placeholders instead of fabrication: "**Placeholders > fabricated data** — fake data damages credibility more than admitting a gap" and "Missing logo → **stop and ask the user**". The proposal says nothing about fake data or missing assets.
- A brand asset hierarchy ("**Asset > Spec.**", "**Color hex codes alone are not a brand**") that is relevant whenever the brief involves a real brand.
- A rule for variants that avoids cosmetic recolours: "Vary the calibrated dials intentionally rather than producing cosmetic recolors." and, for direction proposals, "never recommend 3 picks from the same row". The proposal's "several distinct variants" has no test for "distinct".
- A no-new-hues rule that is checkable: "**never invent new hues from scratch**" and "All colors come from the design system declared in Step 3 — **no rogue hues introduced**".
- Fact-checking named products before designing around them (Step 0).

## Where it conflicts with the proposal

- Rendering is off by default. The proposal's item (3) makes render-and-look mandatory before reporting and says visual claims come from inspection, not code. This skill says the opposite: the self-check "does **not** require launching a browser", and it tells the agent not to read "verify your work" as a request to render. This is the sharpest conflict in the file.
- Three blocking human checkpoints ("Then **actually wait** — don't say it and immediately start coding.", "Push v0 to the user before continuing."). A dispatched subagent has no user to wait for; the proposal expects the brief to carry decisions and the designer to report open questions instead.
- Self-critique before delivery: Step 7 is titled "Critique on Request (or as Self-Check Before Delivery)" and scores 0–10. The proposal says the designer "does not judge the quality of its own design; review is separate."
- Taste inline in the working file (anti-cliché table, "Aim to Stun", six schools), against the proposal's role/skill split.
- Default variant count and Tweaks panel: "At least 3 variants, toggled via the Tweaks panel" for every prototype, and "Even if the user doesn't ask for tweaks, add 1–2 creative ones by default". The proposal produces variants only when asked.
- No implementer boundary: it writes production-grade React and CSS itself and never hands off.
- Summary rule "don't recap what you did; the code speaks for itself" conflicts with the proposal's return (what was made, direction and why, screenshots, deviations).

## What looks wrong or untested

- The core philosophy and the defaults pull against each other. “The bar is "stunning," not "functional."” and "**use them to astonish the user**" sit next to "**Less is more**" and "Respect design systems and brand consistency". In an existing product, "Aim to Stun" ("Use SVG filters, `backdrop-filter`, `mix-blend-mode`, `mask`") is the wrong default for an Extension-mode task, and the file does not say which wins.
- Visual checklist items are ticked without rendering: "No text overflow or truncation" and "Visual quality at Dribbble / Behance showcase level" cannot be established from code, which the skill otherwise prefers. The last one has no test at all.
- Numeric craft rules are stated as universal but sit uneasily with its own "Respect design systems" clause: "Bold type-size contrast (a 4–6× ratio between h1 and body text is normal)" is a marketing-page ratio, far above the critique's own floor ("Title/body ratio ≥ 2.5×") and wrong for dense app UI; "controlled color count (≤ 4)" is a critique criterion that most real product palettes (with status colours) fail. Neither says it yields to an existing design system.
- Hard React rules ("Never use `const styles = { ... }`", "Do not use `scrollIntoView`") are specific to its inline-Babel-in-an-iframe setup and would be wrong advice in a real codebase with a bundler.
- Heavy dependence on reference files that were not collected means the most important procedures (redesign protocol, browser acceptance, critique rubric) cannot be judged here.
- "**Before writing the first line of code**, articulate the design system in Markdown and let the user confirm before proceeding" is required even for "Recreate the composer UI from this codebase", which its own table says needs no questions.

## Verdict

Not a base for the role; a partial source for a **design skill**, and a quarry for a few contract lines. The workflow is built for an interactive human session (three blocking checkpoints), self-grades its own work, and turns rendering off by default, which inverts the proposal's items (3), (5) and (6). What is worth lifting into the role: the Extension / Preserve / Overhaul classification with "smallest change mode", the written direction block before tokens, "no rogue hues", placeholders over fabricated data, and the rule that variants vary real decisions rather than recolour. What is worth lifting into a taste skill: the anti-cliché table in its "default → reason → exceptions" framing (“the only legitimate exception to every anti-cliché rule below is **"the brand spec uses it"**”), and the brand asset protocol. The "stunning" doctrine and the React-in-iframe hard rules should not travel.
