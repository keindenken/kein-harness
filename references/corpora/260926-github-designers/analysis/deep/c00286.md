## What it is for and who consumes its output

A VS Code Copilot custom agent named "UI Design Reviewer", invoked by a human with a URL or screenshots. It returns a prioritised design audit with Tailwind and JSX fixes, and offers a one-click handoff to the default coding agent:

> prompt: Implement the design improvements recommended above. Start with CRITICAL issues first, then address moderate issues.

So the consumer is first the human, then an implementer agent that applies the fixes.

## Operating procedure

1. Get visual evidence: live page through Chrome DevTools MCP, or uploaded screenshots. No evidence, no audit.
2. Capture four viewports, one extra state (empty, error or dense data), and basic accessibility signals.
3. Confirm persona, primary task and constraints; if not given, infer and say so.
4. Evaluate against a ten-point framework.
5. Return critical, moderate and minor issues with Tailwind/JSX fixes, an evidence pack, implementation notes and a summary with a 0–100 score.

## How it gets evidence about the UI, and whether its tools can do it

Evidence is gated, and the gate is well specified:

> You must not provide a full design audit unless you have visual context via either:

> If you do not have visual context, you must request it and do not guess.

The frontmatter declares no `tools` list, so in VS Code it gets whatever tools are enabled, including the Chrome DevTools MCP if connected. Unlike c00263, it plans for the tool being absent:

> If Chrome DevTools MCP tools are unavailable or failing:

> Stop and say you cannot do a live visual review yet.

It never reads source code as evidence, which is a gap in the other direction: it must produce "complete JSX before and after snippets" but is not told to open the files that contain the "before".

## Where taste/craft lives

Inline, but restrained and short: a ten-point review framework, an anti-pattern list and an assumed stack. Most of it is generic enterprise-UI doctrine:

> Aim for restrained, premium, enterprise-grade polish.

The stack assumption is project-specific content in the role body:

> Assume:

followed by React, TypeScript, Tailwind, shadcn/ui and a 4px spacing scale. In the WallRun copy the project-specific part moved to `apps/client/DESIGN.md`.

## What it does that the proposed designer lacks

- An explicit fallback when the user and task are not given, which the proposal's item (2) ("name the user and the task") needs because an orchestrated brief will often omit them:

> If the user does not specify, infer cautiously from page content and explain your assumption.

- A specified render matrix, with sizes, and one state beyond the default screen:

> Desktop: 1440x900

(with 1366x768, 768x1024 and 390x844), and

> a dense data state, if applicable

Dense data is a state the proposal's list (empty, loading, error) omits and that matters for data-heavy UIs.

- An evidence section in the return, stating what was actually seen rather than attaching screenshots alone. This is sharper than the proposal's "screenshots or paths" in item (6), because it records coverage:

> Viewports reviewed

> Any states reviewed (empty, error, dense data)

- Accessibility signals that are checkable from a live page:

> Confirm visible focus states for key interactive elements

> Identify missing labels for key inputs

- A risk and verification handoff to the implementer:

> Verification checklist: what to confirm after implementation

- A privacy rule for a tool that drives a real browser session:

> Avoid capturing or repeating sensitive personal data in the audit

- A closing user-centred check:

> If a user is troubleshooting something important under time pressure, does this change help them succeed faster and with more confidence?

## Where it conflicts with the proposal

- It is a reviewer that scores quality ("Perceived Quality Score: X/100"); the proposal keeps review out of the designer. Its return shape is still useful for the designer's return, minus the score.
- On missing tools it stops and asks the human:

> Ask the user to ensure the Chrome DevTools MCP server is running and connected.

A dispatched subagent in an unattended run cannot ask; the proposal needs the designer to report that no render was possible, and what that limits, instead of stopping to wait.

- Stack and taste baked into the role (Tailwind-first, shadcn-first, "avoid custom CSS"). The proposal wants these in project rules or skills.
- It forbids redesign ("Match the existing design direction. Do not redesign from scratch."); the proposal allows a new direction when the brief asks.

## What looks wrong or untested

- Code fixes from pixels. "Recommendation with exact Tailwind changes" and "complete JSX before and after snippets" are demanded, but the procedure never reads source; the "before" snippet would be reconstructed from a screenshot, which is the failure navikt's role (c00298) forbids.
- Hard-coded default URL (`http://localhost:4200/react-weapons-of-choice/`), which the owner had to edit per repo; a sign that the role is copied, not parameterised.
- "List 3 to 5 items" for both critical and moderate issues forces a count; on a good page the reviewer must invent issues, on a bad one it must drop them.
- Accessibility "obvious contrast failures" is judged by eye; DevTools can compute contrast, but the role does not say to use it.
- "Optional diagnostics ... Slow 3G and 4x CPU throttling" is a good idea with no stated output, so it is unclear what the reviewer does with it.

## Verdict

Not a base for the designer role (it reviews rather than makes, and stops for a human when tools are missing). It is the best base in this batch for a design-review role or a review skill: its evidence gate, viewport matrix, state capture and "EVIDENCE PACK" are directly reusable, and its WallRun variant shows the right layering (role text generic, project taste in `DESIGN.md`). For the designer role, borrow three things: infer-and-state the user and task when the brief omits them; add "dense data" to the state list; and make the return's evidence section list which viewports and states were actually rendered, not only file paths.
