## What it is for and who consumes the output

The intake stage of a design-to-HTML pipeline. It turns design sources (Figma via connector, exports, screenshots, PDFs, JSON, existing HTML or UI code, design notes) into structured maps: source classification, a Source Authority Map, a Preserve/Change/Derive boundary, a Design Source Map, a code-to-HTML mapping, a component mapping, and a coverage ledger for multi-screen work. The consumer is another skill, not a human: "This skill turns design-source evidence into a compact handoff for `ui-design-executor`."

## Operating procedure in brief

1. Access rules: use a real Figma connector if present; with only a URL, do not fake access, offer an "Exact" path that waits for evidence and an optional "Adaptive" path.
2. Classify each source (eight types) and record identity, what was inspectable, confidence and missing data.
3. Resolve the design relationship (`greenfield`, `existing-product-extension`, `source-reconstruction`, `intentional-redesign`) and, when an existing product is in scope, fill a Source Authority Map before authoring.
4. For existing products, pass an evidence gate: route entry, imports, tokens, comparable components, asset convention, and a render "when the available tools and project make that practical".
5. Code-first reconstruction: follow presentation imports, classify each part as direct reuse, structural translation or runtime-only substitution, reconstruct unchanged regions first, then insert the change at the source-supported location.
6. For multi-screen work keep a per-screen ledger with separate `inspected`, `implemented` and `compared` statuses.
7. Pick a fidelity mode (`exact`, `adaptive`, `systemize`, `redesign`), map components, and hand off to sibling skills.

## How it gets evidence about the UI, and whether its tools can do it

Code is the primary evidence and rendering is optional for structure but required for visual claims: "If readable UI code exists, it is the primary structural reconstruction source even when the project cannot run." and "use rendering as optional verification rather than a prerequisite." Visual-equivalence claims have a hard floor: "Claims of pixel-exact or visually identical output require fresh source/result rendering at matching viewport, state, theme, and locale; lack of source rendering limits that visual claim, not the code-first reconstruction itself."

No tools are declared; tools are conditional on what exists ("If a Figma connector, MCP, plugin API, or exported file is actually available, inspect it with the available tool or file reader."). The skill is written for the case the proposal worries about (a role that cannot assume a browser): it lets work proceed from code and caps the claims instead of blocking. The output shape even has a field for it: "Comparison evidence and claim ceiling:".

## Where taste/craft lives

Outside this file entirely, in sibling skills loaded only on trigger: "Add `ui-reference-packs` only if the source lacks a clear style system or the user asks for a named direction." and "Add `ui-design-system` only for reusable tokens/components, `ui-html-renderer` for complex runtime/fidelity work, and `ui-design-review` for a formal review." This is the proposal's separation, carried out: the working contract is here and the taste is elsewhere, loaded conditionally.

## What it does that the proposed designer lacks (verbatim)

- An explicit authority rule when sources compete, which the proposal's contract (1) lacks: "The existing product controls unchanged shell, information architecture, visual language, density, components, icons/assets, and interaction conventions." and "Another reference controls only the structure, workflow, content, or visual attribute the user intended it to contribute. Do not import its shell or visual system merely because it is attached." and "Model invention fills only genuine gaps and cannot silently broaden the change boundary."
- A change boundary for revisions: "Preserve: existing regions and behaviors not authorized to change." / "Change: regions and outcomes the user requested." / "Derive: existing tokens, components, assets, and interaction patterns the new region will reuse."
- A definition of having read the product, which the proposal's "read its code, components, tokens and screens" does not give: "A truncated read, a token-only sample, or a file header that never reaches the relevant component is not completed inspection."
- A rule that a non-running project is not a blocker: "Failure to build or launch the source project is not a blocker when readable presentation code still defines the surface; record only the runtime-dependent details that remain unresolved."
- A claim ceiling that separates what code proves from what a render proves (quoted above), and a list of what different checks prove: "Build success, valid routes or links, shared tokens, no-overflow checks, and spot checks prove different properties; they do not prove visual fidelity for unreviewed screens."
- Coverage honesty for batches: "do not claim complete coverage until every promised row has a fresh rendered/source comparison." and "If the turn stops early, report the exact remaining source rows instead of saying the whole set is complete."
- A ban on filler that also covers sample data in evidence: "Do not fill missing screenshot content with dashboard metrics, sidebars, fake records, or template blocks. If sample data is necessary, label it as sample and keep it out of observed evidence."
- Not faking source access: "Do not claim "Figma imported", "frames inspected", or "variables read"."
- Outside libraries as references only: "Treat shadcn/Radix/Headless UI/React Spectrum/Ant/MUI-style components as behavioral references only unless the local repo already uses them."
- Named fidelity modes, which the proposal's "output form" list does not separate from fidelity: "`exact`", "`adaptive`", "`systemize`", "`redesign`".

## Where it conflicts with the proposal

- Contract (3) says "render what it made and look at it before reporting". This skill says rendering is optional for structural fidelity and only required for visual-equivalence claims. That is a refinement the proposal needs rather than a flat conflict: when there is no browser, the proposal as written has no answer, and this skill's answer is to proceed from code and cap the claim.
- Asking the user. The Figma branch requires a user choice: "Always put both next paths in the visible response before any question/form" and "Do not silently start the adaptive path." It also says "If two inspectable sources still conflict in a way that materially changes the result, ask one focused question." A dispatched subagent in an unattended run cannot ask mid-run; the equivalent is to stop and return the question to the lead, which the proposal lists only as "open questions" in the final return, not as a stop condition.
- Pipeline position. It is an intake stage feeding an executor, not a whole designer. The proposal's designer does intake and building in one role.

## What looks wrong or untested

- Overlapping forms. It defines a Source Authority Map, a Change Boundary, a Design Source Map, a Component Mapping, a code-to-HTML mapping, a coverage ledger and a Design Source Handoff, with repeated fields (authority, Preserve/Change/Derive and unknowns each appear in two or three of them). The final shape is hedged "include this handoff when useful", while the authority map is a hard gate ("do not author until this compact authority map is resolved"). The cost of filling all of this on an ordinary single-screen task is not addressed.
- Several passages read like patches for specific observed failures rather than general rules, for example "If the user says the mocks or screens do not match, reopen the full coverage ledger and compare the inspectable source set again. Do not ask them to supply one example as a substitute for auditing sources already available to the Agent." and the long Figma-URL paragraph with its bolded **Exact**/**Adaptive** paths.
- Product-specific names throughout (`UIDesigner`, `ui-design-executor`, `ui-html-renderer`) and the assumption that the deliverable is HTML ("keep UIDesigner's HTML-first and evidence-first rules").
- No evidence of testing beyond the patch-like passages.

## Verdict

Neither as a whole. It is too coupled to the Orkas pipeline and too form-heavy to be the designer role, and it is not a taste skill. It is the richest source of role-level clauses for the proposal's contract (1) and (3): the authority rules, Preserve/Change/Derive, the truncated-read rule, the failure-to-build rule, and the claim ceiling that separates structural claims from visual ones. Those clauses are the answer to the proposal's open problem of a designer with no browser. A trimmed version could also serve as a reconstruct-from-design-source skill for Figma/screenshot-to-code briefs.
