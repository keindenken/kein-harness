## What it is for, who consumes the output

A design-first worker for Next.js 15+ apps that produces a design system and component specs before any implementer builds them: "**Works BEFORE `fullstack-nextjs-specialist`**: Provides design specs and component guidelines" and "**Works BEFORE `visual-effects-creator`**: Defines animation strategy and key moments". The consumers are the orchestrator and those downstream workers. The deliverable is a long report (design system overview, decisions, Tailwind config, CSS variables, cva component examples, Framer Motion code, screenshots, accessibility report, next steps). Whether it writes files or only returns code in the report is left open: it asks for "**File paths**: Absolute paths for all implementations" but its steps are titled "Implementation Guidance" and "Provide detailed implementation specifications".

## Operating procedure in brief

1. Invoke the external `frontend-aesthetics` skill first, always ("**ALWAYS** use the `frontend-aesthetics` Skill FIRST before creating any designs").
2. Design discovery: brand, audience, competitors, technical constraints (posed as questions).
3. Create a design system: type scale, palette, 4/8pt spacing, component inventory, animation durations.
4. Design components: variants, breakpoints, loading/error states, dark mode.
5. Plan App Router layouts, server/client split, Suspense, metadata.
6. Write implementation guidance (Tailwind config, shadcn installs, CSS, Framer Motion, ARIA).
7. Visual testing via Playwright "if Playwright available".
8. Document everything.

## How it gets evidence about the UI, and whether its tools can do it

- No `tools:` line, so it inherits the session's tools, and it depends on MCP servers from "`.mcp.base.json` or `.mcp.full.json`".
- Rendering is optional and last: "Step 7: Visual Testing (if Playwright available)". It states the fallback plainly: "If `mcp__playwright__*` is unavailable: Skip visual testing, recommend manual validation".
- It never reads the project's own components or tokens. "Discover Existing Patterns" points outward: "Use `mcp__shadcn__ (requires .mcp.full.json)*` to find existing component patterns" and "Use `mcp__context7__*` for Next.js App Router component examples".
- Several checks exceed what the declared tools can do: "Test screen reader compatibility", "Cross-Browser Testing" across "Chrome", "Firefox", "Safari", "Edge", and, under "**Competitor Research** (if applicable)", "Use `mcp__context7__*` to research similar applications" (context7 serves library docs, not other products).

## Where taste/craft lives

Split. The core is deferred to a skill it does not ship in this file: "**MANDATORY: `frontend-aesthetics` Skill**" (with optional `ui-design-system` and `ux-researcher-designer` skills). But a large taste catalogue is also inline: "### Anti-Patterns to Avoid" (typography, colour, layout, animation, accessibility), exact numbers ("fast: 150ms, base: 300ms, slow: 500ms", "Use 4pt or 8pt grid system", "minimum 4.5:1 for text, 3:1 for UI components", "Mobile-first design (320px+)"), and a default type scale "H1 (48px), H2 (36px), H3 (30px), H4 (24px), H5 (20px), H6 (18px), Body (16px)". So the file both defers taste and restates it, and the two can disagree without the agent knowing which wins.

## What it does that the PROPOSED DESIGNER lacks

- An explicit per-tool fallback list, which the proposal needs because it cannot assume a browser: "### Smart Fallback Strategy:" with "If `mcp__playwright__*` is unavailable: Skip visual testing, recommend manual validation". (The fallback itself is weak; see below. The idea of naming it is what the proposal lacks.)
- Theming as part of coverage: "Design dark mode variants for all components" and "Test light and dark mode variants". The proposal's clause (4) names states, responsive and accessibility but not themes.
- Component-level state list beyond page states: "Component state variations (hover, focus, disabled, etc.)" and "Input empty/filled/error: [screenshots]".
- A concrete accessibility floor instead of "baseline": "Color contrast ratios (minimum 4.5:1 for text, 3:1 for UI components)", "Missing focus states", "Color-only indicators".
- Return fields the proposal's list does not have: "**Known limitations**: Design constraints or trade-offs" and "**MCP tools used**: Which servers were consulted and why".
- A named downstream consumer, making the boundary concrete: "**Works BEFORE `fullstack-nextjs-specialist`**".

## Where it conflicts with the proposal

- Starts from taste and from nothing, not from the product. The skill call comes before discovery, and Step 3 is "Create a comprehensive design system foundation". The proposal's clause (1) says read the existing code, components and tokens and follow them unless the brief asks for a new direction. Here no step reads the project's own UI.
- The inline bans would override an existing system: `❌ **Inter/Roboto/Arial**: Generic fonts that scream "AI-generated"`, "❌ **System fonts**: -apple-system, BlinkMacSystemFont (boring and corporate)", "❌ **Generic blue/gray**: Safe, corporate, forgettable", "❌ **Minimal animations**: Just hover states, no orchestration". A product built on system fonts and a blue/gray palette would be "fixed" against its own design system.
- Self-judgement of quality, which the proposal assigns to a separate review: "**Anti-pattern validation**: Confirmation that design avoids generic AI aesthetics", and an accessibility report template that arrives pre-ticked ("✅ Color contrast ratios meet minimum 4.5:1 for text", "Primary text on background: 7.2:1 (AAA)").
- Rendering is optional and last; the proposal makes looking at the result a condition for reporting how it looks.
- Taste in the role text: the proposal keeps the role as a working contract only.
- Stack-bound: Next.js 15+, Tailwind, shadcn/ui, Framer Motion, cva are assumed throughout.

## What looks wrong or untested

- A botched find-and-replace has broken the tool names: "`mcp__shadcn__ (requires .mcp.full.json)*`" and "`mcp__shadcn__search_items_in_registries (requires .mcp.full.json)`". An agent cannot call these strings as written.
- "When invoked, follow these steps:" is followed directly by "## Referenced Skills", so the numbered steps start two sections later. The structure was edited and not re-read.
- The context7 tool name "`mcp__context7__get-library-docs`" does not match the name the context7 server exposes in this environment (`query-docs`), so it may be an older API.
- The Step 2 discovery questions ("What brand personality should it convey?", "What emotional response should users experience?") have no one to answer them. A subagent cannot ask, and no source is named, so in practice the agent makes the answers up.
- The accessibility report template contains filled-in results and ratios. A model filling the template is likely to reproduce "✅" and plausible ratios whether or not anything was measured.
- The anti-pattern rules are presented as fact (`scream "AI-generated"`, "Under 150ms feel jarring") without evidence, and they sit next to a mandatory skill that may say something else.
- It sets 18 or more deliverable sections for every task regardless of size. Nothing scales the output to the brief.

## Verdict

Not a base for the designer role: it builds from scratch instead of from the product, treats rendering as optional, certifies its own work, and is tied to one stack. It is a weak base for a design skill as well. The anti-pattern catalogue and numeric standards are the kind of content the proposal wants in a skill, but here they are unsourced, partly contradict the proposal's rule to follow the existing design system, and depend on another skill that is not in the corpus. Worth lifting into the role: a named fallback when no browser exists (with a better fallback than "recommend manual validation": say plainly that nothing was rendered), dark mode/theme and component states in the coverage clause, and "Known limitations" in the return.
