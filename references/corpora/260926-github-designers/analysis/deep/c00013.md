## What it is for, and who consumes its output

A design adviser that writes guidance for a coding agent: "Produce implementation-ready UI guidance with explicit interaction and accessibility intent." and "Deliver guidance a coding agent can implement without ambiguity." It is invoked "before or during development". The consumer is the implementing agent (or the lead that dispatches one). It produces no files; the read-only sandbox prevents it.

## Operating procedure in brief

Three steps: "1. Read existing UI language, constraints, and user-flow context." "2. Propose concrete layout/interaction changes tied to product goals." "3. Deliver guidance a coding agent can implement without ambiguity." A focus list (hierarchy, states and feedback timing, reuse and system alignment, accessibility, consistency, elegance vs complexity), four design checks, a four-part return contract, and one scope limit.

## How it gets evidence about the UI, and whether its tools can do that

By reading the repository: "Read existing UI language, constraints, and user-flow context." The read-only sandbox allows that. There is no render, screenshot or browser step, and in a read-only sandbox it could not start a dev server to render anyway, so "consistency with existing product visual direction" is judged from code and tokens alone. The prompt does not acknowledge that limit.

## Where its taste/craft content lives

Nowhere explicit. There is no aesthetic doctrine at all; taste is implied by deference to the product ("component reuse and design-system alignment", "consistency with existing product visual direction") and one anti-vagueness rule ("avoid "pretty but vague" recommendations"). This is the same split the proposal wants (role = working contract, craft elsewhere), though here nothing says where craft would come from.

## What it does that the PROPOSED DESIGNER lacks

- A proportionality rule: "Do not prescribe a full redesign when a local interaction/layout fix is sufficient." The proposal allows "a redesign of existing UI" as an output but gives no rule for matching the size of the change to the problem.
- Justifying new system parts: "identify where new tokens/components are truly required vs avoidable". The proposal reports deviations after the fact; this asks the designer to argue for each addition.
- Cost awareness: "tradeoffs between elegance and implementation complexity". Relevant to the proposal's boundary with the implementer, which says who integrates but not that the designer should weigh integration cost.
- Timing, not only states: "interaction states and feedback timing".
- Keyboard behaviour where it changes: "specify focus order and keyboard interaction where interactive elements change". More specific than the proposal's "accessibility baseline".
- A precision bar on the output: "avoid "pretty but vague" recommendations" and "Deliver guidance a coding agent can implement without ambiguity".
- A return contract organised by where the change lands: "design recommendation by screen/component", "interaction-state notes", "implementation guidance and constraints", "unresolved design decisions requiring product input". The last item matches the proposal's "open questions" but names who must answer them (product).
- Tying changes to purpose: "Propose concrete layout/interaction changes tied to product goals."

## Where it conflicts with the proposal

- It cannot make anything. Read-only sandbox, guidance only; the proposal's designer produces mockups, prototypes, components and tokens, and renders them.
- No render-and-look step; the proposal makes inspection the source of every claim about appearance.
- No user/task naming, no direction commitment, no variants. "tied to product goals" is the closest it gets to naming the task.
- It sits closer to the proposal's "written critique/opinion" output than to its making outputs, so as a base it covers one output form of six.

## What looks wrong or untested

- "Deliver guidance a coding agent can implement without ambiguity" is an unmeasured claim; nothing in the file checks it (no example, no required format for values such as spacing or colour).
- The focus list has no priority, so on a small brief it may still touch hierarchy, spacing, tokens, accessibility and tradeoffs all at once, which pulls against its own "local fix" limit.
- "include loading, empty, and error-state expectations" says "expectations", so the agent may list states without designing them.
- Very short; its behaviour depends on the model's defaults for everything the file leaves unsaid (layout craft, visual quality), and nothing tells it to load guidance for those.

## Verdict

The best of the five as a base for the designer role's working contract, because its form already matches the proposal's idea of a role (procedure, checks, return contract, scope limit, no persona, no taste). It needs the proposal's missing parts added, not subtracted: write access, the render-and-look rule with an explicit fallback when no browser exists, user/task naming, direction or variants, and the output-form switch set by the brief. Lines worth carrying over nearly verbatim: the redesign-proportionality limit, "truly required vs avoidable" for new tokens/components, focus order where interactive elements change, "avoid "pretty but vague"", and "unresolved design decisions requiring product input". Not a skill base: it has no craft content to put in one.
