# c00133 — gsd-build/get-shit-done `gsd-ui-auditor` (agent)

File: `corpus/gsd-build_get-shit-done__agents_gsd-ui-auditor.md` (495 lines, 64459 stars). Copies: 3 files, 3 owners (gsd-build, davepoon/buildwithclaude, JHamidun/claude-code-config-pack). The JHamidun copy has no Playwright-MCP section, so it is probably an earlier revision. This is the same voice as c00102 (`gsd-ui-checker`); count them as one family.

## What it is for, who consumes the output

A retroactive audit of frontend code after it has been built. It scores six pillars 1–4 against `UI-SPEC.md` when one exists, "or abstract 6-pillar standards" when not, and writes `$PHASE_DIR/$PADDED_PHASE-UI-REVIEW.md`. The consumers are the `/gsd:ui-review` orchestrator (structured return) and whoever fixes the build. Its stance is adversarial by design: "Assume every pillar has failures until screenshots or code analysis proves otherwise."

## Operating procedure in brief

1. Load `<required_reading>`, `SUMMARY.md`, `PLAN.md`, `CONTEXT.md`, `UI-SPEC.md`.
2. Write a `.gitignore` for screenshots under `.planning/ui-reviews/` before any capture.
3. Probe for a dev server and capture desktop/mobile/tablet screenshots (Playwright MCP if available, else `npx playwright screenshot`), or fall back to a code-only audit.
4. `find` frontend files.
5. Audit each pillar with the provided `grep` commands; score 1–4 with file:line evidence.
6. Registry safety audit of third-party shadcn blocks (network calls, `eval`, env access).
7. Write UI-REVIEW.md; return a summary.

## How it gets evidence about the UI, and whether its tools can do it

This is the file's central weakness, and it bears directly on the proposal's clause (3).

- Screenshots are captured but never looked at. Step 3 says only "Record whether screenshots were captured." Every pillar's "Audit method" is code search ("Grep for string literals", "Grep Tailwind classes and CSS custom properties", "Grep font size and weight classes", "Grep spacing classes"), and no step reads the PNG files back. The report header "**Screenshots:** {captured / not captured (no dev server)}" can read "captured" while every score came from grep.
- The preferred Playwright-MCP branch cannot run. The frontmatter is `tools: Read, Write, Bash, Grep, Glob`, which as an allowlist excludes every MCP tool. The tool names it gives (`mcp__playwright__navigate(url="http://localhost:3000")`, `mcp__playwright__screenshot(name="desktop", width=1440, height=900)`) also do not match the Playwright MCP server's names (`browser_navigate`, `browser_take_screenshot`, with sizing via `browser_resize`).
- The CLI branch captures only the root URL of whichever port answers ("Try port 3000 first, then 5173 (Vite default), then 8080."). The screens the phase actually changed are not captured unless they happen to be the root route.
- The grep commands do not measure what they claim. I ran three of them on a three-line sample `.tsx` (`text-sm` twice, `text-lg`, `p-4`, `item-x`, and the strings `OK` and `TOKEN BOOK`):
  - Typography: `grep -rohn "text-\(xs\|sm\|base\|lg\|xl\|2xl\|3xl\|4xl\|5xl\)" src --include="*.tsx" --include="*.jsx" 2>/dev/null | sort -u` returned `1:text-sm`, `2:text-sm`, `3:text-lg`. The `-n` prefix defeats `sort -u`, so the "distinct font sizes" count is really a count of lines.
  - Copywriting: `grep -rn "Submit\|Click Here\|OK\|Cancel\|Save"` matched `TOKEN BOOK` as a generic label.
  - Spacing: `grep -rohn "p-\|px-\|py-\|m-\|mx-\|my-\|gap-\|space-" src --include="*.tsx" --include="*.jsx" 2>/dev/null | sort | uniq -c | sort -rn | head -20` returned `3:m-` from `item-x` and `1:p-` from `p-4`. It captures the prefix only, never the value, so it cannot check a spacing scale.
- "Find all frontend files modified in this phase" runs `find src -name "*.tsx" -o -name "*.jsx" -o -name "*.css" -o -name "*.scss" 2>/dev/null`, which lists every file, not the modified ones.

## Where taste/craft lives

Inline, in the fallback standards that apply when there is no spec: "Flag if >4 font sizes or >2 font weights in use.", "Flag accent overuse (>10 unique elements) and hardcoded colors.", and the copy greps. Otherwise it borrows taste from `UI-SPEC.md`, which is the right direction: audit against the declared contract first.

## What it does that the PROPOSED DESIGNER lacks

- Stating whether it rendered, as a first-class field, with an explicit code-only fallback. This is exactly what a role that "cannot assume" a browser needs: "Capture screenshots via CLI if dev server is running (code-only audit otherwise)", "Note in output that visual screenshots were not captured.", and the report header "**Screenshots:** {captured / not captured (no dev server)}".
- Keeping screenshot binaries out of git: "**MUST run before any screenshot capture.** Prevents binary files from reaching git history." The proposal's designer returns screenshots or paths but says nothing about where they live.
- A cheap dev-server probe and port order: `DEV_STATUS=$(curl -s -o /dev/null -w "%{http_code}" http://localhost:3000 2>/dev/null || echo "000")` and "Try port 3000 first, then 5173 (Vite default), then 8080."
- Marking what a machine cannot judge: "Items requiring subjective judgment are flagged as `needs_human_review: true`".
- A broader state list than the proposal's empty/loading/error: "Score based on: loading states present, error boundaries exist, empty states handled, disabled states for actions, confirmation for destructive actions."
- Named ways a reviewer goes soft, which is useful material for the separate review role the proposal assumes: `Accepting "the component exists" as evidence the UI is correct without checking spacing, color, or interaction` and "Identifying 3 priority fixes and stopping, when 6+ issues exist".
- A supply-chain check on copied UI code: "`fetch(`, `XMLHttpRequest`, `navigator.sendBeacon` — network access from a UI component".

## Where it conflicts with the proposal

- It is a reviewer of someone else's build; the proposal's designer does not judge its own work. This supports the proposal's split rather than contradicting it.
- Its evidence model contradicts clause (3). The proposal says claims about appearance come from looking at the render, not from reading code; here every score comes from code search, and screenshots only decorate the header.
- Fixed numeric thresholds in role text when there is no spec (">4 font sizes or >2 font weights"), where the proposal puts such rules in skills or project rules. They also ignore the project's existing tokens when no UI-SPEC exists.

## What looks wrong or untested

- The typography, spacing and copy greps give wrong answers on a trivial sample (shown above). Scores built on them are not evidence, although the file insists "**Evidence-based:** Every score cites specific files, lines, or class patterns".
- The MCP branch is unreachable under its own `tools:` allowlist and uses tool names that do not exist.
- Screenshots are taken and never viewed.
- `$PHASE_DIR`, `$PADDED_PHASE` are used in commands but never set by the agent; it relies on the orchestrator to pass them, and does not say so.
- The registry audit writes to `/tmp/shadcn-view-{block}.txt` (fixed shared path) and runs `npx shadcn view` over the network during an audit.
- The frontmatter carries a commented-out PostToolUse hook that would run `npx eslint --fix` on every Write. It is dead config.
- Output asks for "## Top 3 Priority Fixes" while the stance warns against "Identifying 3 priority fixes and stopping, when 6+ issues exist". The detailed findings section covers the rest, but the structured return lists only three.

## Verdict

Not a base for the designer role. As a base for a separate UI reviewer, its structure is good (spec-first baseline, adversarial stance, render-status field, gitignore gate, `needs_human_review`), but its evidence method must be replaced before it can be trusted: read the screenshots, capture the changed routes rather than `/`, and drop or fix the greps. Not skill material: its taste content is a few thresholds. For the proposal it is the clearest negative example in the set: a prompt can say "screenshots" everywhere and still judge appearance entirely from code. That supports making clause (3) specific: look at the captured image, and report "not rendered" when the tool is missing.
