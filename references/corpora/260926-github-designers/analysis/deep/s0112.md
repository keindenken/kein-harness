## What it is for and who consumes the output

A user-invoked skill for building or restyling UI and for aesthetic fixes grounded in screenshots: "Produces distinctive production UI and screenshot-grounded visual polish. Use when building or restyling pages, components, or typography." Its triggers are largely user complaints ("不好看, 不和谐, ... 很丑", "make it look good", "screenshot with visual complaint"). The consumer is the human in the conversation: it asks them questions, offers them options to pick by letter, and ends with instructions "for replacing placeholder content with real content". Its output is the change itself, in the product's code, or a review: "Output: the implemented visual change or a precise visual review with the remaining verification gap named." It is a designer-plus-implementer in one agent, not a role that hands off to one.

## Operating procedure in brief

1. Preflight: load durable preferences, but "current screenshots and rendered output override memory", and "name the current visual problem from the screenshot or source before changing code".
2. Mode picker: bounded fix, screenshot iteration, or generated image asset each load a reference file (not collected); a new page, component or visual system goes to direction lock. Documents and print route out to another skill.
3. Direction lock. For a new surface inside a mature app, the direction is the app: grep the sibling component and reuse its tokens. Otherwise resolve five dimensions (user and context, named aesthetic direction, one design signature, hard constraints, one signature micro-interaction) from evidence in a stated order, with at most one clarification round of at most two sub-questions and stated assumptions for the rest. Exceptions: source repo supplied (read tokens, lift exact values), existing native app (incremental polish, no platform restyle), app shell and dashboards (extra reference sections).
4. State the direction in one sentence, load `design-reference.md`, pick one CSS strategy, write a three-line summary (visual thesis, content plan, interaction thesis); expand to a 9-section DESIGN.md for production or multi-page UIs.
5. Options: at least 3 variations when asked; offer two labeled candidates unasked for taste decisions; get a nod before a structural change.
6. Build under always-on bans and two motion rules; apply a small gotchas table (truncation, widows, too many text styles).
7. Aesthetic review: re-read the thesis after build phases, run the reference's checks and the "AI Slop Test", fix, then render the supported viewport or window range; if the host cannot render, say so.
8. End with direction and justification, non-obvious choices, placeholder-replacement instructions. "After handoff, stop."

## How it gets evidence about the UI

Three sources, all named. It reads the code: "Grep for the existing sibling component first and reuse its container, motion, and typography tokens", and for a supplied repo it reads theme/token files, global stylesheets and the named components ("Lift exact values: hex codes, spacing scale entries, font stacks, border radii."). It takes screenshots as primary evidence, over memory. It renders its own output and specifies the range, including native windows:

> Render the product's supported viewport or window range yourself: web breakpoints on both sides, and native minimum width, minimum height, their combination, and normal size. Test samples do not require new layout branches. Only when the host cannot render, say so and hand the user the exact view to check.

The frontmatter declares no tools (`name`, `description`, `when_to_use`, `dispatch_intent` only), so the skill inherits the session's tools and names no browser, screenshot command or dev-server step; how "render ... yourself" happens is left to the host. It does have an explicit no-render fallback, which matches the proposal's situation, but its fallback hands the check to "the user", who is not present in a dispatched subagent. The "Done when" line requires the rendered check ("the real rendered surface or generated artifact has been checked against the user's visual goal and the relevant viewport states"), yet the end-of-turn list does not ask for screenshots or paths, so the caller cannot see the evidence.

## Where taste/craft lives

Split, with most of it by reference. Inline in SKILL.md: the anti-generic premise ("If it could have been generated by a default prompt, it is not good enough."), the direction vocabulary ("dense editorial, raw terminal, ink-on-paper, brutalist grid, warm analog"), a compact ban list, two motion rules, and three gotchas. By reference, in `design-reference.md`: "Token decisions (color, font, motion), production craft, aesthetic review, DESIGN.md, options, and strategic omissions all live in that one canonical file", plus "the full rewrites, typography, OKLCH color, motion timings, layout defaults, accessibility baseline, and complexity matching". The skill deliberately gives the cheap paths only the inline subset: "Screenshot and quick-fix paths use the compact bans above instead of paying for that full reference." That is a context-cost tiering the proposal does not have, and it is the part of this skill closest to what the proposal wants in a craft skill.

## What it does that the PROPOSED DESIGNER lacks

- An evidence order for direction. The proposal says "follow its design system unless the brief asks for a new direction" but not where to look when there is no written system:
  > Take colour, type, width, and voice from the current product's tokens, sibling components, screenshots, and the repo's git history first; then from other shipped products by the same team or author when they exist; then from the conversation. Model-default palettes, default fonts, and freehand graphics are allowed only when no reference exists.
- A hard default for new surfaces in a mature product, with a burden of proof for departing from it: "the direction is the app" and "inventing a new style needs a stated reason why no existing component fits." Also: "First drafts that ignore the app's own component vocabulary get rejected on sight."
- Fidelity when copying an existing product: "Lift exact values: hex codes, spacing scale entries, font stacks, border radii. A rough approximation is not pixel fidelity." and "Do not reconstruct the UI from memory or training data."
- A redesign guard for existing apps, with a read-back step: "Default to incremental polish on the existing direction: spacing, alignment, hover and focus states, typography hierarchy, copy tightening, motion timing." and "State the existing direction in one sentence before proposing changes so the user can correct the read." The proposal lists "a redesign of existing UI" as an output with no rule about how far a redesign may go.
- An assumption policy instead of blocking questions: "State the strongest inferred answer for every unresolved dimension and ask the user to correct only the material assumptions. An omitted answer accepts the stated assumption." Adapted to a dispatched role, this means stating assumptions in the return and proceeding, which the proposal's "open questions" item only half covers.
- Turning a named reference into properties: "do not accept it as a direction -- extract 3 concrete properties from it: button radius philosophy, surface depth treatment (shadow vs background step vs border), and accent color family."
- "Commit to one direction" made checkable: the three-line summary (visual thesis, content plan, interaction thesis), with "either `none` with one evidence-based reason" for motion, and "A dimension can be "none": a quiet utility surface may deliberately have no signature motion."
- A rule for when benchmarking is worth it: "Survey 2-3 mature products only when the problem is a genuinely unfamiliar interaction pattern or the direction remains underdetermined after reading the current product." and "mandatory benchmarking on every component produces imitation and delays obvious work."
- Variants tied to decision type, not only to the brief: "Offer without being asked when the decision is taste, not correctness: icon, weight, accent, motion feel. Two labeled candidates beat one landed guess, because the reply is a single letter instead of a rewrite round."
- Rules that bend with a recorded reason, and the ones that do not: "when the committed direction genuinely calls for breaking one, break it deliberately and name the tradeoff in the handoff. The accessibility baseline and CSS-pattern bans stay non-negotiable." This is a concrete form of the proposal's "deviations from the design system" item.
- A named render range for native surfaces (quoted above), where the proposal says only "responsive behaviour".
- A report that names what was not verified: "the remaining verification gap named".
- Scope routing out: documents and print are handed to another skill ("do not hand-roll an over-designed document layout here"), and debugging goes elsewhere ("not to `/hunt`"). The proposal has a writer sibling but no line about where document typesetting belongs.

## Where it conflicts with the proposal

- It judges its own design. "Every surface runs the AI Slop Test: would a stranger glancing at the first viewport say "an AI made this"?" and "If any check fails, fix first." The proposal says the designer "does not judge the quality of its own design; review is separate." Part of Waza's review is a drift check against its own thesis ("re-read the visual thesis from direction lock"), which is closer to conformance than to quality judgement and could stay; the Slop Test and the reference's "Aesthetic Review Checks" are quality judgement by the author.
- It implements. The output is "the implemented visual change", with production-code concerns (bundle size, one CSS strategy, `transition: all`) throughout. The proposal sends production integration to an implementer unless the brief says otherwise; this skill has no such boundary.
- It is interactive. It asks the user a clarification round, waits for a letter choice between candidates, and wants "a nod before writing the code" for a structural change. A dispatched role has no user mid-run; these steps need rewriting to fit: state the assumption, or return the variants and stop.
- Taste is partly inline. The ban list and motion rules sit in SKILL.md. That fits the proposal only if this whole file is the craft skill the designer loads, not the role text.
- Output contract differs. It ends with direction, non-obvious choices and placeholder instructions; it does not return screenshots or paths, deviations from the design system as a list, or open questions, all of which the proposal requires.
- Unrequested variants. "Offer without being asked" conflicts with the proposal's "produce several distinct variants when asked", though the conflict is mild and arguably the proposal should adopt it.
- States coverage is missing from SKILL.md (no empty/loading/error line; the record's `states_coverage` flag is false). It may be in `design-reference.md`, which was not collected.

## What looks wrong or untested

- Most of the substance is unverifiable here. The bans' rewrites, the accessibility baseline the skill calls "non-negotiable", the Options Guide, the DESIGN.md scaffold and every non-default mode are in files the corpus did not collect. The SKILL.md alone cannot be judged as a craft source.
- Internal tension between "the direction is the app" and question 3, "What is the design signature?" with its "Pick one and make it obvious." For a mature product the signature is presumably the app's, but the text does not say so; an agent on a new page inside an existing product could read it as licence to add a signature.
- "Always-on bans" that may be broken "deliberately" is two instructions pulling apart; the carve-out keeps "CSS-pattern bans" non-negotiable, but the inline list mixes CSS-pattern bans (`transition: all`, layout-property animation) with taste bans (gradient text, glass cards), and the file does not say which list items fall under which.
- The Slop Test asks the producing model to imagine a stranger's first glance at its own output; with no rendered screenshot required in the return, a passing answer costs nothing.
- The render step names no tool or command and no evidence artifact, so "render ... yourself" can be claimed from source reading. The fallback routes to the user, which does not exist in a subagent.
- Personal-brand output rules (a "🥷" prefix on the first line, a ban on U+2014) are house style, not design, and would be noise in a role.
- `dispatch_intent` is a Waza-specific frontmatter key; nothing in this file shows how it is consumed.
- On the positive side, the Gotchas table (ellipsis truncation, widowed words, five text styles in one card) and the native-app exception's diagnosis ("Wholesale restyling reads as "I do not have a specific design intent, here is the platform's."") read as learned from real failures, not authored in the abstract.

## Verdict

A base for a **design skill**, not for the role. As a craft skill it is strong: an anti-generic premise that is operational (named directions, reference decomposition into three properties, a three-line thesis, bans with rewrites, frequency-based motion rules), tiered loading so cheap fixes do not pay for the full reference, and signs of being tuned against real failures. Its dependence on an uncollected `design-reference.md` means the tw93 references would have to be read before adopting it. As a role base it fails on three of the proposal's points: it implements production code, it reviews its own quality, and it relies on a live user for questions and choices. Several contract pieces should still be lifted into the role text, because they are about working method rather than taste: the evidence order for direction, "the direction is the app" with a stated reason to depart, "Lift exact values", the incremental-polish default with the one-sentence read-back for redesigns, stated assumptions in place of blocking questions, broken rules named with their tradeoff (feeding the proposal's "deviations"), the native render range, and "the remaining verification gap named" as the no-browser report. One voice (single owner, single record); weight it as one source.
