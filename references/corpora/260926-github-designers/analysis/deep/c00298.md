The hovmester file is byte-identical, and both belong to NAV (the Norwegian Labour and Welfare Administration), so this is one voice. NAV also contributes many accessibility agents to the wider corpus; those were excluded from the design-role set, but the owner is heavily represented overall. Quotes below are verbatim Norwegian, each followed by an English gloss.

## What it is for and who consumes its output

A conversational design partner for NAV's human designers, invoked directly in Copilot chat (`user-invocable: true`). It explores a need, visualises it (browser prototype or Figma sketch), iterates, and delivers a Figma file, a GitHub issue for developers, or, opt-in, a clickable code prototype that a separate frontend agent builds. Consumers: the human designer first, then developers through the issue or prototype branch.

## Operating procedure

Five phases, each gated by asking the designer:

1. Explore (always): one question at a time; who is the user, what is the core need, are there existing patterns. For an existing screen, capture its real current state before sketching.
2. Visualise (opt-in): either 2–3 variants in a browser "Visual Companion", or straight to Figma. For a change to an existing page, a screenshot background with the editable component placed on top.
3. Iterate (opt-in) on feedback.
4. Deliver (opt-in): keep the Figma file, open a design issue, go to phase 5, or stop.
5. Code prototype (opt-in): delegated to the frontend agent `konditor`, mock data only, on a `prototype/*` branch.

A "UU-gate" (universal design, NAV's term for accessibility) pre-check runs before delivery, and every reply ends with a summary and an internal status.

## How it gets evidence about the UI, and whether its tools can do it

It has the most careful evidence rules in the batch. The current state of an existing screen is a gate before the first sketch, and code reading is explicitly not evidence of appearance:

> For eksisterende flater er nåtilstand en gate før første skisse:

(For existing screens, the current state is a gate before the first sketch.)

> Ikke rekonstruer dagens side fra kode/komponentlesing og presenter det som «slik siden ser ut».

(Do not reconstruct today's page from reading code/components and present it as "this is how the page looks".)

It also checks that the screenshot shows the right thing:

> Ved lokal app: bruk samme rute, viewport og mockdata; verifiser forventet sidetittel/innhold og at cookie-, login-, modal- eller bildefeil ikke forstyrrer.

(For a local app: use the same route, viewport and mock data; verify the expected page title/content and that cookie, login, modal or image errors are not in the way.)

It has an ordered fallback for visual context: local app via Playwright, then a Figma link, then a public URL imported to Figma, then a manual screenshot from the designer.

> **Lokal app** → Bruk Playwright for screenshot. Krever ingen input fra designeren. Hvis dev-server eller Playwright ikke er tilgjengelig, fall stille tilbake til neste metode.

(Local app → use Playwright for a screenshot. Needs no input from the designer. If the dev server or Playwright is not available, fall back silently to the next method.)

The frontmatter declares no `tools` list, so it gets whatever the Copilot host enables; it checks for Figma MCP at startup and has a stated degraded mode. The rendering of its own output is delegated: variants render in the Visual Companion (a `/prototype` skill not collected here) and Figma. There is no explicit step to screenshot and inspect what it made for its own sketches; the verification discipline is applied to the current state, not to the result.

## Where taste/craft lives

Outside the role, in routed skills, which is the proposal's layering:

> | Komponentvalg, layout, spacing | `/aksel-design` |

(Component choice, layout, spacing → `/aksel-design`.) Copy goes to `/klarsprak` (plain language), visual exploration to `/prototype`, stress-testing design choices to `/grill-me`. The role body contains process, boundaries and delivery form, with almost no aesthetic doctrine. The design system (Aksel) is named as a hard constraint:

> Bruk Aksel-komponenter og -mønstre

(Use Aksel components and patterns.)

## What it does that the proposed designer lacks

- Current-state capture before designing, with code reading ruled out as evidence of appearance (quoted above). The proposal's item (1) says to read code, components, tokens and screens, and item (3) says to render what it made. Neither says the existing screen must be rendered before redesigning it, or that code reading must not be presented as what the page looks like. For the proposal's "redesign of existing UI" this is the missing half.

- Before/after on the same context:

> Før/etter skal vise samme sidekontekst, og diffen skal være tydelig: hva er uendret og hva er nytt.

(Before/after must show the same page context, and the diff must be clear: what is unchanged and what is new.)

- Screenshot sanity checks (route, viewport, mock data, expected title, no cookie/login/modal/image errors), quoted above. The proposal says render-and-look but not that the designer must confirm it rendered the right thing.

- An ordered evidence fallback, including the rule not to sink time into builds:

> Feilsøk build-problemer (fall tilbake til neste metode)

(listed under "Never": troubleshoot build problems; fall back to the next method.)

- A ban on faking context by hand-drawing the new module into a screenshot:

> Aldri håndkod modulen inn i skjermbildet — det gir avvik fra den ekte komponenten.

(Never hand-code the module into the screenshot — it deviates from the real component.)

- Delivery as editable structure with states as one variant axis, not flat images:

> Lever redigerbare Aksel-komponenter — helst tilstandene samlet i én variant-komponent (`Tilstand`-akse) — ikke flate skjermbilder.

(Deliver editable Aksel components — preferably with the states gathered in one variant component (a `State` axis) — not flat screenshots.)

- An accessibility baseline that states what it does not certify, and hands the rest on:

> Dette er en forhåndssjekk av designet — ikke en fullverdig UU-godkjenning.

(This is a pre-check of the design — not a full accessibility approval.)

> Merk dette i Issue ved overlevering: **"Krever live UU-review før release."**

(Note this in the issue at handoff: "Requires live accessibility review before release.") The proposal's item (4) asks for "an accessibility baseline" but not for the return to say what the baseline did not cover.

- Contrast thresholds named for both text sizes:

> **Kontrast**: tekst mot bakgrunn (4.5:1 for brødtekst, 3:1 for stor tekst)

(Contrast: text against background, 4.5:1 for body text, 3:1 for large text.)

- A clear split of ownership for a prototype:

> **Rolledeling**: Designer eier den klikkbare interaksjonsprototypen; utvikler eier data, integrasjon og produksjonsherding.

(Role split: the designer owns the clickable interaction prototype; the developer owns data, integration and production hardening.) This is the proposal's item (5) with a concrete line drawn.

- Guardrails for prototypes: mock data only, no PII or secrets, a separate branch, labelled "prototype – ikke for produksjon" (prototype – not for production).

- A machine-readable status alongside the human summary:

> Intern status for agentlogikk: `DONE` | `ITERATING` | `NEEDS_INPUT` | `BLOCKED`

(Internal status for agent logic.)

## Where it conflicts with the proposal

- Human in the loop at every phase. It asks the designer before each step, one question at a time:

> Spør før du går videre til neste fase

(Ask before moving to the next phase.) The proposal's designer is dispatched with a brief and runs to completion; the lead agent, not a human, is the caller. The phase gates would have to become brief fields (direction chosen or not, output form, variants wanted).

- No code at all. The proposal lets the designer produce HTML mockups, light prototypes and components; this role forbids it from writing or editing repository files:

> Skriv eller push kode selv — kodeprototype delegeres alltid til konditor

(listed under "Never": write or push code yourself — a code prototype is always delegated to konditor.) Its boundary is stricter than the proposal's item (5), which keeps prototyping inside the designer.

- Figma is the primary medium; code is the exception. The proposal assumes code-side artifacts and cannot assume Figma.

- Silent fallback. "fall stille tilbake" (fall back silently) hides from the designer which evidence tier was used; the proposal's return should instead say how the current state and the result were seen.

- Language rules for talking to designers ("Snakk designspråk", never show code, never name tools) are for a human audience and do not apply to a subagent reporting to a lead agent.

## What looks wrong or untested

- Evidence discipline is one-sided. It forbids reconstructing the current page from code, but has no step to screenshot and inspect its own Figma sketch or browser variants before presenting them. The Visual Companion may do that, but it is in an uncollected skill.
- The UU-gate contrast check is asked "Før leveranse fra Figma" (before delivery from Figma) with no tool named for measuring contrast in Figma; it may be a checklist item the model ticks by assertion.
- "Kjør `/repo-sync` ... parallelt" (run repo-sync in parallel) at startup, silently, in a user's working copy; what it does is in an uncollected skill, and a silent sync before the user has spoken is a risky default.
- "Opprett eller rediger filer i repoet direkte" is forbidden, with a carve-out that `.visual-companion/` is tool output; the Visual Companion still writes there, so the boundary depends on the reader accepting the carve-out.
- The accessibility gate says "Hopp over UU-gate ved leveranse" is never allowed, yet "Graceful degradation" without Figma lets it deliver only a description and an issue; the gate's contrast check has nothing to run on in that path.
- Much of the operating detail (`/prototype` phases 1, 2 and 5, the Aksel catalogue) lives in skills that were not collected, so the actual rendering and variant behaviour cannot be verified from this file.

## Verdict

The richest source of contract clauses for the proposed designer, but not a base text. Its layering already matches the proposal (process and boundaries in the role, taste in routed skills and the design system), and several clauses fill real gaps: render the current state before redesigning and never present code reading as appearance; check the screenshot is the right page; before/after on the same context; say what the accessibility check did not cover; deliver states as one structure; draw the prototype/production line concretely; return a status token. It cannot be the base because it is a human-paced, Figma-first chat partner that is forbidden to write code, is tied to one organisation's design system and language, and relies on uncollected skills for its rendering steps. For a design skill it is also a poor fit on its own, since it carries almost no craft; its value is procedural.
