## What it is for, and who consumes its output

A visual design-system specialist: component libraries, token systems, visual hierarchy, dark mode/theming, and developer handoff specs. Consumers are developers ("Provide clear design handoff specifications with measurements and assets") and, per the Deep Reference comment, an orchestrator that reads only the upper half of the file. The main deliverable is a markdown "UI Design System" document from the embedded template plus CSS tokens and base component styles.

## Operating procedure in brief

Step 1 "Design System Foundation" (a `bash` block of three comments: review brand guidelines, analyse patterns, research accessibility) → Step 2 base components and their states → Step 3 typography scale, colour system, spacing system, elevation → Step 4 developer handoff (specs, component docs, asset exports, a design-QA process). The rule set above it is "Design System First Approach" and "Performance-Conscious Design".

## How it gets evidence about the UI, and whether its tools can do that

Only by reading: "Review brand guidelines and requirements" and "Analyze user interface patterns and needs", written as comments inside a shell block with no actual commands. There is no render step, no screenshot, no instruction to look at existing screens, and "Establish design QA processes for implementation accuracy validation" is described as something to set up for others rather than something it does. With no tool list the agent inherits whatever the host gives it, but the prompt never asks it to use a browser.

- Interactive states as part of state coverage: "**Interactive States**: [Default, hover, active, focus, disabled]" alongside "**Loading States**", "**Error States**" and "**Empty States**: [No data messaging and guidance]". The proposal lists only empty, loading, error.

- A structured handoff document for the design-tokens / design-system-docs outputs (Color System, Typography System, Spacing System, Component Library, Responsive Design, Accessibility Standards).

## Where it conflicts with the proposal

- Taste in the role, and a specific one: the embedded tokens are a default look (Inter, Tailwind-blue, card hover lift). A role carrying this will reproduce it unless something stronger overrides it; the proposal keeps such content in skills or project rules precisely so it can be swapped.
- Order of work: "Establish component foundations before creating individual screens". The proposal starts from the existing product and follows its system; this starts by building a system, which is right for a green-field token brief and wrong for a revision of existing UI.
- No user/task framing, no direction commitment, no variants.
- It prescribes a QA process and success metrics for itself ("Design system achieves 95%+ consistency across all interface elements"), which is self-judgement the proposal separates out.

## What looks wrong or untested

- The CSS references tokens it never defines: `var(--color-primary-600)`, `var(--color-secondary-300)`, `var(--color-secondary-200)`. Only the 100/500/900 steps exist, so the button hover and the input/card borders resolve to nothing if copied as is.
- The breakpoint selectors are double-escaped: `.sm\\:grid-cols-2`. In a CSS file that is a class ending in a literal backslash followed by a `:grid-cols-2` pseudo-class, which matches nothing; it looks like a JSON/string-escape artifact that no one rendered.
- It mixes preprocessor-style nesting (`&:focus-visible`, `&:hover:not(:disabled)`) into what is presented as plain CSS; valid only under native CSS nesting support or a preprocessor, which the prompt does not state.
- `transition: all` on every base component and hover `translateY` lifts contradict its own "Performance-Conscious Design" rule.
- The "Deep Reference" comment claims "The orchestrator only needs the sections above this line. Everything below is loaded on demand when the subagent executes." In Claude Code the whole agent body is the subagent's system prompt; whether harmonist's own loader truncates it is not visible here, so this is untested for any other host.
- "**Memory**: You remember successful design patterns" and the "Learning & Memory" section describe a memory the agent does not have.
- Success metrics ("90%+ accuracy", "95%+ consistency") have no measurement method.

## Verdict

Neither as a role base: it is a persona with a hard-coded house style, never looks at what it makes, and its sample code has bugs that show it was not rendered. Two pieces are worth keeping. For the role: the precedence-and-surface rule, generalised to: project rules and the existing system beat skill defaults, and every conflict is stated in the report. For a design-tokens / design-system-docs skill: the section outline of the deliverable template and the five-plus-three state list, with the token values removed (a skill that ships default values will impose them) and the CSS fixed if any is kept.
