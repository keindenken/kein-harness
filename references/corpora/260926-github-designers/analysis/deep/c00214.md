## What it is for and who consumes its output

A persona reviewer for the APM command-line tool. It judges command shapes, help text, error wording and first-run flow against package-manager conventions. It has two consumers: a human invoking it while designing a CLI change, and, in the mode that is spelled out in detail, an automated PR-review orchestrator that spawns it as one panelist among several:

> When the autopilot-pr-review-worker skill spawns you as a panelist task, you operate under these strict rules.

In that mode its only output is a JSON verdict the orchestrator parses.

## Operating procedure

1. Load the canonical docs on demand (CLI reference, quick-start, installation, mental-model page, shipped skill resources).
2. Read the PR title, body and diff from the task prompt.
3. Apply a five-question review lens (discoverability, familiarity, composability, recovery, first-run) and a list of anti-patterns.
4. Sort findings into exactly two buckets, `required` and `nits`, and return JSON as the final message, never writing to GitHub.

## How it gets evidence about the UI, and whether its tools can do it

It reads documents and a diff. It never runs the CLI, never looks at real `--help` output or a real error message. For a CLI the render-and-look step would be cheap (run the command, read stdout/stderr), yet the role does not ask for it; it judges output from the source that produces it. The frontmatter declares no `tools` list, so it inherits whatever the host gives; nothing prevents running the binary, it simply is not asked to.

## Where taste/craft lives

Split. The durable, project-specific truth lives in repository documents the role points at, which is close to the proposal's placement of craft "in skills or project rule files":

> Treat these as the source of truth for APM's command surface and first-run experience; pull into context when reviewing UX-affecting changes:

The doctrine itself ("Mental models to preserve", "Anti-patterns to call out") is inline, and it is specific to this one product.

## What it does that the proposed designer lacks

- A non-web surface. The proposal lists HTML mockups, prototypes, components, tokens, redesigns and critiques; it does not say whether a CLI or TUI is in scope. This role shows a real UX role whose "UI" is terminal text:

> **Failure mode is the product.** Every error must name what failed, why, and one concrete next action. No stack traces in the default path.

That is the CLI version of the proposal's "cover states (empty, loading, error)", stated as a testable property of each error rather than a checklist entry.

- A one-line north star that names user, task and success measure together, which is the proposal's item (2) in its most compact form:

> A new user types `apm init`, `apm install`, then `apm run` and ships something within 5 minutes -- without ever reading docs.

- Documentation as part of the design deliverable:

> If a CLI change is not reflected in `cli-commands.md` in the same PR, that change is incomplete by definition.

The proposal's return lists "deviations from the design system" but not which reference docs the design now contradicts.

- Named escalation targets instead of a generic boundary:

> You do NOT make security calls -- defer to the Supply Chain Security expert when a UX change touches auth, lockfile integrity, or download paths.

- Explicit permission to return nothing, which counters the pressure to produce findings:

> If you have nothing blocking AND nothing worth nitting, return `{persona: "<your-slug>", required: [], nits: []}`. That is a valid and preferred answer when true.

- A strict single output channel for an orchestrated run:

> You MUST NOT touch the PR state. The orchestrator is the sole writer; your only output channel is the JSON return.

## Where it conflicts with the proposal

- It is a reviewer, not a maker. It produces verdicts on someone else's change, with a REJECT consequence. The proposal says the designer "does not judge the quality of its own design; review is separate". This role is on the other side of that line and would belong to the separate review step.
- Its bucket rule forbids exactly the soft "consider" language a designer's open-questions field needs:

> No third bucket, no "consider", no "optional follow-up".

That is right for a gate and wrong for a designer's return, where open questions are one of the six required items.

## What looks wrong or untested

- The reviewer is told what the CLI must feel like ("reads like `npm run`", "quiet on the happy path") but is only given a diff to judge it from. Output volume, stderr/stdout split and exit codes are observable by running the command, and it never does. For its own claims about how output "reads", this is the same gap the proposal's item (3) targets.
- The panelist schema (`assets/panelist-return-schema.json`) lives in another skill and was not collected, so the exact return shape cannot be checked here.
- "Real, actionable, citing file/line where possible" combined with "Anything you put here will produce a REJECT verdict" gives the reviewer a strong incentive to under-report; the line calling an empty return "a valid and preferred answer when true" pushes the same way. Whether that balance was tuned on real PRs is not visible.

## Verdict

Neither a base for the designer role nor a general design skill. It is a strong example of two things the proposal can borrow: (a) a project-local UX rule file (north star, mental models, anti-patterns, pointers to canonical docs), which is exactly where the proposal says taste belongs; and (b) an orchestrator-facing reviewer contract, which fits the proposal's separate review step. The one idea worth carrying into the designer role itself is surface breadth: say whether CLI/TUI output is in scope, and if so, that render-and-look means running the command and reading what it prints.
