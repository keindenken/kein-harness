## What it is for, and who consumes its output

Despite the file name (`se-ux-ui-designer`) and heading ("# UX/UI Designer"), it is a UX-research and flow-spec agent that explicitly does not make UI: "This agent creates UX research artifacts (journey maps, JTBD analysis, personas). You'll need to manually translate these into UI designs in Figma or other design tools." Consumers are human designers working in Figma: "Generate documentation that designers can reference when building flows in Figma". It writes three markdown files per feature under `docs/ux/` (`-jtbd.md`, `-journey.md`, `-flow.md`) and ends with a "Handoff to Design" block.

## Operating procedure in brief

Step 1 ask the user about users, context and pain points (15 listed questions) → Step 2 Jobs-to-be-Done analysis with a job-statement template → Step 3 journey map (doing / thinking / feeling / pain points / opportunity per stage) → Step 4 "Figma-ready" user-flow description and flow design principles → Step 5 accessibility checklist → Step 6 write the three files and a handoff note. An escalation list names what goes to a human.

## How it gets evidence about the UI, and whether its tools can do that

It does not look at the UI at all. No step reads existing screens or components, even though `codebase` and `search` would let it read the code; its evidence is the user's answers ("Use these answers to ground your Jobs-to-be-Done analysis and journey mapping."). There is no rendering tool and no rendering step, and none is needed for its outputs. The example response shows the agent asking five questions and stopping ("[After getting answers, create:]"), which means its evidence gathering is a human conversation.

## Where its taste/craft content lives

Almost none. Visual taste is explicitly out of scope and escalated: "**Visual design decisions**: Brand colors, typography, iconography". The craft it does carry is inline and structural: the JTBD template, the journey-map structure, three flow principles (progressive disclosure, clear progress, contextual help) and an accessibility checklist.

## What it does that the PROPOSED DESIGNER lacks

- A fixed form for "name the user and the task": "When [situation], I want to [motivation], so I can [outcome]." The proposal says to name the user and the task but gives no shape; this one-line form is short enough to require in a report.
- Asking for the underlying goal rather than the requested feature: "Not a feature request ("I want a button")" / "The underlying goal ("I need to quickly compare pricing options")".
- Failure cost and frequency as design inputs: "What happens if this fails? (minor inconvenience or major problem/lost revenue?)" and "How often will they do this task? (daily, weekly, once in a while?)".
- Flow-level exits, not only screen states: "**Exit Points**:" with "Success", "Partial: Save progress, resume later (send reminder email)" and "Blocked: Can't configure a tool → trigger help request". The proposal's states (empty, loading, error) are per-screen; it has nothing about partial completion or resumption across a flow.
- A measurable success criterion in the handoff: "**Key success metric**: User completes critical tool setup in <30 minutes".
- Accessibility items the proposal's "baseline" does not spell out: "Text resizes to 200% without breaking layout", "Error messages are announced", "Dynamic content changes are announced", "Add error state with red icon + text (not just red border)".
- An explicit escalation list for decisions it should not make alone, including "**Design system decisions**: Choices that affect multiple teams/products". The proposal returns "deviations from the design system" but does not say which deviations need a human decision.

## Where it conflicts with the proposal

- It refuses the proposal's main job. "Remember: This agent creates the **research and planning** that precedes UI design. Designers use these artifacts to build flows in Figma, not automated UI generation." The proposal's designer makes mockups, prototypes, components and tokens.
- It escalates visual decisions (brand colours, typography, iconography) to a human; the proposed designer makes them, guided by skills and the existing system.
- It blocks on questions before any work ("**Before designing anything, understand who you're designing for:**"). A dispatched subagent in an unattended run cannot get answers; the proposal instead has the designer name the user and task itself and list open questions at the end.
- It does not start from the existing product. The proposal's first contract item is to read code, components, tokens and screens; this agent never does.

## What looks wrong or untested

- Touch-target sizes disagree inside the same step: "Interactive elements minimum 24x24px touch target" and, a few lines later, "Minimum button height: 44px for touch targets". Both numbers exist in WCAG-land (2.5.8 AA vs 2.5.5 AAA/platform guidance), but the prompt does not say which applies.
- The name promises UI and the body disowns it; a router picking agents by name would send UI work here and get research documents back.
- The worked journey map is a single invented onboarding example with emoji feelings ("😰 Overwhelmed, uncertain"); if the agent has no real research input, it will produce plausible fiction in the same shape. The escalation list admits this ("**User research needed**: Can't make assumptions, need real user interviews") but the procedure has no step that marks which parts are assumed.
- "Figma-ready" means markdown prose; nothing is exported to or checked against Figma.

## Verdict

Not a base for the designer role: its contract is the opposite of the proposal's on output (no UI), on autonomy (asks first, escalates visual decisions) and on evidence (never reads the product). It could seed a small UX-framing skill or a pre-design section of the designer's brief: the JTBD sentence as the required way to "name the user and the task", failure cost and frequency, flow exit points (success / partial / blocked), and the escalation list recast as a rule for which open questions need a human. Its high star count belongs to the host collection and says nothing about this file's quality.
