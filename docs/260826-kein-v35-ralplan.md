## 2. Repo facts, re-probed in the current tree

### 2.1 Admission is blind to paint — and that is a narrower claim than revision 1 made of it

The admission algorithm — `packages/descvi/src/react/overlay/canvas/handle-geometry.ts#export function admitHandles({ box, clip, axes }: AdmissionInput): HandlePlacement[] {` — reads the writable-axis filter, the placement returned by `packages/descvi/src/react/overlay/canvas/handle-geometry.ts#export function placeHandle(`, `packages/descvi/src/react/overlay/canvas/handle-geometry.ts#export function fitsInClip(placement: HandlePlacement, clip: EffectiveClip): boolean {`, `packages/descvi/src/react/overlay/canvas/handle-geometry.ts#export const STRIP_EDGE_COVERAGE_MIN = 0.9;` against `edgeCoverage`, the anchor envelope, and pairwise centre separation. **Not one of those reads a painted dimension.** `edgeCoverage` is computed inside `placeHandle` as the placed HIT box's long-axis span over the element's edge length; the chip is written later and separately, by `packages/descvi/src/react/overlay/canvas/use-resize-handles.ts#function applyHandleStyle(`, onto the node's first child.

**Consequence, stated because the requirements call it the phase's sharpest unresolved question:** removing the strip's paint changes admission by exactly nothing, and interacts with `STRIP_EDGE_COVERAGE_MIN` by exactly nothing. What it DOES change is the constant's *warrant* (§3.8).

⚠ **What this claim does NOT license, corrected at round 1.** Revision 1 read "admission is blind to paint" as also meaning "the corner's HIT size is inert for admission". It is not: `packages/descvi/src/react/overlay/canvas/handle-geometry.ts#export function hitSizeFor(box: HandleRect, compass: HandleCompass): { width: number; height: number } {` feeds the corner's placed box, which `fitsInClip` tests and which `packages/descvi/src/react/overlay/canvas/handle-geometry.ts#function translateIntoRect(e: Edges, clip: EffectiveClip): Edges {` and `packages/descvi/src/react/overlay/canvas/handle-geometry.ts#function pushOutOfArcs(e: Edges, clip: EffectiveClip): Edges {` displace — so the clause-4 drift scales with it. The paint claim is about `HANDLE_CHIP_PX` and `HANDLE_GLYPH_PX` alone.

### 2.3 The corner is centred on its box corner; the strip band hangs outside

`packages/descvi/src/react/overlay/canvas/handle-geometry.ts#function centredOn(point: HandlePoint, size: { width: number; height: number }): Edges {` places corners; `stripBandEdges` places strips wholly outside the edge they name. On an element of height `h`, the E strip's placed centre sits half a band outside the right edge at the edge midpoint, while NE and SE sit ON the corners. So the centre-to-centre distance between the E strip and the nearer corner is `hypot(STRIP_HIT_BAND_PX / 2, h / 2)`. **That expression is the whole of B-Q5's arithmetic**, and §2.11 and §3.9 derive from it.

### 2.4 G42-7's Universe B asserts glyph-bearing on EVERY operable node under the ring layer

`e2e/resize-handles.spec.ts#hasGlyphDescendant: n.querySelector("svg, [data-glyph]") !== null,` collects the predicate; the row asserts it true for every member of the universe, layer-wide and deliberately unpartitioned, because the claim is true of the phase-42 family and the phase-44 spacing family alike. Its failure message names the node and reads `<descriptor> has an svg/[data-glyph] descendant`. A glyphless corner and a glyphless strip both fail it — the "knowingly red" state §5.11 forbids, and R46-O2 is the amendment that avoids it.

The spacing family keeps its glyphs — `packages/descvi/src/react/overlay/canvas/use-spacing-affordances.ts#function createHatchNode(doc: Document, id: string): HTMLElement {`'s siblings build a glyph per affordance root — so the amendment MUST partition by family and not by layer-wide relaxation.

### 2.11 ⚠ THE ROUND-1 FINDING, REPRODUCED: clause 4's drift, and the implication clause 1 silently carries

Two review lanes found the envelope defect independently, on two different shipped fixtures. Re-derived here from the module's own corner path (`centredOn` → `translateIntoRect` → `pushOutOfArcs` → `translateIntoRect`) against the oracle's own clip — a layer at the origin with `#dsh-frame` one border-pixel outside it on every side, and `packages/descvi/src/react/overlay/canvas/handle-geometry.ts#export const FRAME_CORNER_RADIUS_PX = 12;`.

**(a) The clip-forced corner drift has a closed form.** For a corner flush with the frame's own corner, the rect clamp puts the box at the layer origin and the arc then pushes it along the radius by the amount the oracle already asserts at `packages/descvi/src/react/overlay/__tests__/handle-geometry.test.ts#    const arcInset = FRAME_CORNER_RADIUS_PX - FRAME_CORNER_RADIUS_PX / Math.SQRT2 + FRAME.left;`. The resulting drift is

> `drift = √2 × (arcInset + C/2)`, where `C` is the corner hit square.

At the shipped `C` this reproduces the value the oracle brackets at `packages/descvi/src/react/overlay/__tests__/handle-geometry.test.ts#    expect(drift).toBeLessThanOrEqual(HANDLE_HIT_PX);` — whose own comment calls that corner "the worst case in the corpus" — with a small margin. **Revision 1's ruled envelope was below it, so NW would have been refused on the oracle's own flush fixture and on the e2e's rounded-corner fixture, taking §5.6's one-corner floor with it.** A doubly-flush corner needs no arc at all to break a low envelope: there the drift is `√2 × C/2`.

**(b) The implication nobody wrote down.** With the corner half-extent and the separation extent drawn from ONE symbol, clause 1 mathematically implies clause 3. The derivation, in three parts, and it collapses to a single inequality:

- **corner ↔ corner.** `document.elementFromPoint` at one corner's centre returns its neighbour iff the neighbour's square CONTAINS that point — a Chebyshev test, not a Euclidean one. Chebyshev ≥ Euclidean/√2, so a Euclidean separation `S` guarantees Chebyshev `> C/2` iff **`S > C/√2`**.
- **corner ↔ strip.** The E strip's centre lies inside NE's square iff `STRIP_HIT_BAND_PX ≤ C` **and** `h ≤ C`. When `h ≤ C`, the pair's separation `hypot(STRIP_HIT_BAND_PX/2, h/2)` is at most `C/√2` — so the same inequality `S > C/√2` makes clause 1 refuse exactly those configurations. - **strip ↔ strip.** Each strip hangs outside a different edge, so no strip's centre is ever inside another's box. Unconditionally safe.

> **The whole guarantee is the single inequality `HANDLE_SEPARATION_PX > CORNER_HIT_PX / √2`.** At the shipped values it holds with room.

> `C / √2 < hypot(STRIP_HIT_BAND_PX/2, h/2)`, i.e. `C < √2 × hypot(STRIP_HIT_BAND_PX/2, h/2)`.

⚠ **THE READ-FORM RULE — this is what closes the whole class, and it costs nothing.** A gate row in a vitest home may assert **only** a value that production **explicitly sets**, read through the **physical longhand it is asserting**:

1. **Never read an UNSET property.** Every side of every assertion is a value production wrote.
2. **Never read a SHORTHAND *that cssstyle expands*.** Where production writes one and the longhands exist — `styleReadout` writes `node.style.border` — the row reads the **longhands**, which are identical under both majors even after an override.

   ⚠ **THE EXEMPTION, AND IT IS RULED ON A MEASUREMENT RATHER THAN ASSERTED — round-6 finding.** `border-radius` is a shorthand **cssstyle does not expand in either major**, and revision 6's rule 2 made the only correct read illegal. Driven at planning against both: with the radius set inline, the **shorthand** reads back `"4px"` under **both** majors, while the longhand `borderTopLeftRadius` reads `""` under jsdom 25 and `"0"` under jsdom 29 — **divergent, and wrong on a correct build in both.** Production writes exactly that shorthand at `packages/descvi/src/react/overlay/canvas/use-resize-handles.ts#  chip.style.borderRadius = corner ? "4px" : "6px";`.

   **So rule 2's real content is not "shorthands are banned" — it is "never read a property whose read-back depends on an override interplay".** A shorthand cssstyle expands has longhands that can be overridden, so the shorthand's read-back diverges; a shorthand it does not expand has no such interplay and its read-back is invariant. ⚠ **The discriminator is measurable and is the thing to check for any new property: does cssstyle expand this shorthand? Expanded → read the longhands. Not expanded → read the shorthand.** Stating it this way is what keeps the policy inheritable; an unexplained exemption would not be.
3. **Physical longhands only.** A logical property is Class C or it is rewritten physically.
4. **A row must be green under BOTH invocations**, and the story's definition of done runs both. A row that cannot be written to clear all four rules is not Class B — it is Class C and it goes to the browser.

**THE POLICY — three classes, and a row's home follows from its class:**

- **Class A — STRUCTURAL.** Node presence, attributes, child counts, source-text scans, values returned by pure functions. **Home: vitest.** Identical under both majors.
- **Class B — SET PHYSICAL LONGHAND.** A value production writes inline as a physical longhand, asserted through that longhand under the read-form rule. **Home: vitest.** ⚠ **The inline write is part of the contract**, exactly as the layer's `pointer-events` already is and for the same recorded reason. ⚠ **A shorthand is not a class** — it is the longhands beneath it, and revision 5 classed G46-7 as "an inline `border`" with no class for what that actually is.
- **Class C — LAYOUT / CASCADE / LOGICAL / UNSET.** Produced by layout, by a stylesheet, expressed logically, or knowable only as an absence. **Home: the browser suite, and the browser job joins that story's Gates line.**

**THE BOUNDARY RULE, because the policy can be abused in one direction.** A quantity moves from Class C to Class B **only when writing it inline is what the design needs anyway**. Where flex centring is the right implementation, an inline offset would be testability driving design and the row goes to the browser instead. §3.7's tick is the one place this phase crosses that line, and it crosses it because **the reach bound makes centring impossible**: the strip root spans the full outward band, so a mark centred in it sits half a band out and breaches the bound by construction. The explicit offset is the design, and the inline write follows.

⚠ **THE COMPARATIVE RULE.**⚠ **THE COMPARATIVE RULE.** Any row asserting that one node's value EXCEEDS another's must give **both** sides an explicit value. ⚠ **Under jsdom 25 an unset property reads back empty and the comparison is vacuous; under jsdom 29 it reads back a DEFAULT and the comparison silently compares against that default instead** — so the rule is the same but it is now a correctness requirement in both directions, not only an anti-vacuity one. This is G46-18's lesson generalised, restated at round 5 against the environment that actually runs.

⚠ **WHAT CLASS C COSTS, said plainly — and CI has THREE jobs, not two.** `AGENTS.md` puts the browser jobs outside `pnpm gates`' scope on purpose, so **every Class-C row is a gate that `pnpm gates` does not run.** ⚠ **`.github/workflows/ci.yml` declares THREE jobs, and `scripts/gates.mjs` parses only `verify` — its own header says so.** The third, `e2e-contract-gates`, runs `pnpm test:e2e:gate-cx1` and `-cx2`, and **neither is reachable from `pnpm test:e2e`** (plain `playwright test`) **nor from `pnpm gates`**. §5's prose has named the three jobs since revision 1 and cited phase-42's erratum about what a two-job definition of done cost — **and then every story's Gates line listed two commands.** Round 5 found that in five of six stories.

**So the definition of done for any story editing `e2e/**` is THREE commands**: `pnpm gates`, `pnpm test:e2e`, and the two `cx` scripts. ⚠ **Fireable on this phase's own edits, which is why it is not a formality:** cx1's FIRST check is coverage — `scripts/e2e-gate-cx1.mjs#for (const file of onDisk) if (!declaredSet.has(file)) fail(`'s scan RED-s on any `*.spec.ts` on disk that `e2e/fixtures/spec-classes.json` does not declare. **RULED: any NEW spec file is declared in `spec-classes.json` in the same commit, with its class justified against cx1's own criterion — ⚠ and the same applies to any edit that CHANGES an existing spec's class (round-7: the rule covered new files only, while cx1 audits the declaration rather than the filename)** — and G46-13's home is an EXISTING declared spec (`e2e/panel-focus.spec.ts`, class `ambient`), named in §3.15 rather than left as "the browser suite".
