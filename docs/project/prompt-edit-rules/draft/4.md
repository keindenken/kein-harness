# Writing a standing rule

Two kinds of rule live in these files, and they age differently. One describes an external surface — an API, a tool's behaviour, a file format — and gets its edits handed to it: when the surface changes the rule turns false and someone has to fix it, on a schedule nobody here chose. The other describes how you want an agent to work, and nothing will ever tell you it is stale — no API breaks, no test fails, and checking whether it is still needed means violating it. Know which kind you are writing; the checks below exist because of the second kind. And what arrives from outside is an occasion to edit, not a direction.

Whether this rule should exist at all is a different question, decided before this file was opened. What follows governs the form.

**Can it bind?** A rule binds only when the agent could visibly break it with the tools it actually has. A sentence narrating what happens anyway cannot be broken, and a rule that needs an ungranted tool breaks invisibly.

**Does it collide?** Point at the decision where this rule meets an existing one. If you can name that point, one of the two loses there, and you have to say which.

**Content a given run will not read leaves the main file.** This is a rule about what a run reads, not about size. Splitting content that every run reads is pure cost, and progressive disclosure can relocate a mandatory read instead of shrinking it — check which one you are doing.

**Test each premise by negating it.** If a line rests on a stated fact, deny the fact and see whether the instruction survives. Survives: drop the fact. Dies: the line depends on its environment — prefer moving it into a mechanism (a config field, a schema, a runtime check) so the environment enforces it instead of prose asserting it.

**Justification is three different things, and only one goes here.** Mechanism — why the thing behaves this way — goes inline: it is bounded, checkable from source, and is what licenses a later deletion. Provenance — which incident produced the rule — goes in the commit message of the change that adds it, where `git log` on this file retrieves it; a dated war story in the prompt buys nothing the log does not already hold. Environment facts follow the previous check.

**Write only claims whose falsity a reader can establish from what they already have open.** Three shapes qualify: a pointer to the source that regenerates the claim, a fact pinned to a version with the probe that re-checks it, or a mechanism. One shape disqualifies: a value that moves with a defensible choice of method is underdetermined — write the qualitative form instead. A number that is neither regenerable nor anchored gets deleted, not corrected, and a number promoted into a rule stops meaning what it measured.
