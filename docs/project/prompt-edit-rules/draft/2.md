# Changing a standing prompt

A standing prompt goes stale. Models change and environments change, and nothing tells you which lines stopped being true. A rule that describes an external surface — an API, a tool's behaviour, a file format — at least gets its edits handed to it: when the surface moves the rule becomes false and someone has to fix it. A rule that describes how you want an agent to work never gets that. What arrives from outside is an occasion to edit, not a direction.

That is why this is worth slowing down for, and why a rule is easier to add than to check. Finding out whether one still earns its place means running without it, and running without it means disobeying it.

## Before you write the line

Whether the rule should exist at all is decided before this file applies — name its consumer, name what a strong agent at its best would do and check the rule passes it, and ask whether a mechanism could hold it instead. If that has not been done, stop and do it; adding is the part that is too easy.

**Point at the decision where this rule meets an existing one.** If you can name that point, one of the two loses there and you have to say which, in the text. A rule you cannot place against the ones already present has not been thought through.

## Where it goes

**Content leaves the main file when a given run will not read it.** Not because it is long, and not because it is code — the test is whether *this* run reads it. Splitting content that every run reads is pure cost, and progressive disclosure can relocate a mandatory read rather than shrink it: three files that are all obligatory saved nothing.

The main file is not the only destination, and often not the right one. A per-run instruction belongs in the prompt; an opinion about one product or team belongs in a skill that is loaded when it is needed; a thing better shown than described belongs in a reference the reader can open. Keep the always-loaded file for what a run cannot work without, and spend its tokens on what the repository does not already reveal about itself.

## How to write it

**Write only claims whose falsity a reader can establish from what they already have open.** Three shapes qualify: a pointer to the source that regenerates the claim, a fact anchored to a version together with the probe that re-checks it, or a mechanism. One disqualifies — a claim whose value moves with a defensible choice of method is underdetermined, and writing it at whatever number you happened to get is worse than writing the qualitative form. A number that is neither regenerable nor anchored gets deleted, not corrected. And a number promoted into a rule stops meaning what it measured.

**Justification is three different things and they go to three places.** *Mechanism* — why the thing behaves this way — goes inline, because it is bounded, checkable from the source, and is what licenses someone to delete the rule later. *Provenance* — which incident produced the rule — goes into the commit that makes the change, not next to the rule: it is unbounded, it cannot settle a removal, and the file's own history is already the index that finds it. *An environment fact* goes into a mechanism rather than into prose, so a tool list, a config field, or a schema enforces it at runtime instead of an instruction asking for it.

**Test a premise by negating it.** If a line rests on a stated fact, deny the fact and see whether the instruction survives. Survives: drop the fact, it was decoration. Dies: it is an environment fact, and it belongs in the mechanism rather than here.

## When you commit

Say why the file changed, in the commit that changes it. That is where provenance lives, and it is the only record that works for a rule you deleted as well as one you added.
