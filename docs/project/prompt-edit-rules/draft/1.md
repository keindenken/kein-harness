# Changing a standing prompt

The file you are about to edit instructs an agent on every run that reads it. Read this before you write the line.

**First, which kind of rule is this?** A rule that describes an external surface — an API, a tool's behaviour, a file format — gets its edits handed to it: when the surface changes the rule becomes false and someone has to fix it. A rule that describes how you want an agent to work never gets that. Nothing external will ever tell you it went stale, so a stale one just keeps being followed. Almost everything in the file in front of you is the second kind.

## Where it goes

**Content leaves the main file when a given run will not read it.** Not because it is long, and not because it is code. Splitting what every run reads is pure cost, and progressive disclosure relocates a mandatory read as easily as it shrinks one — three files that all get opened anyway have saved nothing.

So settle the destination before the wording. A standing instruction can live in a system prompt, in this file, in a skill that loads when it is called, in a reference the agent opens at the step that needs it, or in a mechanism that makes the instruction unnecessary. The last one is not a fallback; it is usually the strongest answer available.

## What it has to survive

**Does it collide?** Point at the decision where this rule meets one already present. If you can name that point, one of the two loses there and the text has to say which. An unresolved collision does not stay unresolved — it gets settled at runtime, differently each time.

## How it is written

**Write only claims whose falsity a reader can establish from what they already have open.** Two shapes qualify: a pointer to the source that regenerates the claim, or a mechanism — why the thing behaves the way it does. What disqualifies is a value that moves with a defensible choice of method; writing it at whatever number you happened to get is worse than writing the qualitative form. A number that is neither regenerable nor anchored gets deleted, not corrected. And a number promoted into a rule stops measuring whatever it measured.

**Justification is three different things and they go to three places.**

- *Mechanism* — why the thing behaves this way — goes inline. It is bounded, it is checkable, and it is what licenses someone to delete the rule later.
- *Provenance* — which incident produced the rule — goes in the commit message that made the change, not beside the rule. The file's own history is the index, so nothing in the prompt has to point at it.
- *An environment fact* — something true of the current tools or runtime — goes into the mechanism that already enforces it. A sandbox setting enforces read-only. A sentence asking for read-only only hopes.

**Test a premise by negating it.** If a line rests on a stated fact, deny the fact and see whether the instruction survives. Survives: drop the fact, it was decoration. Dies: it was an environment fact, and belongs in a mechanism rather than in this file.

## Removal is on the table

A rule already present can be narrowed, made conditional, moved into a mechanism, or cut — in that order, with cutting last. Deciding which needs more than this file gives you, and that procedure is not written yet. But an edit session that only ever adds is not a neutral default. It is the ratchet, and it is how the file in front of you got this long.
