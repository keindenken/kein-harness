# Writing a standing prompt

You are editing a file that instructs an agent. Rules in such files are of two kinds. One describes an external surface — an API, a tool's behaviour, a file format — and that surface's next change will announce the rule is stale. The other describes how you want an agent to work, and nothing will ever announce it: models and environments move on, and finding out means removing the rule you put in to be followed. So write every line for the reader who must one day decide whether it can go.

Whether this change should exist at all — what it forbids that you would want, who consumes what it requires, whether its standing cost beats its exposure — is a separate decision with its own gate (skill, name TBD), made before the editor opens. If it has not been made, stop and make it first. What follows governs the writing.

**What a given run will not read leaves the main file.** Not because it is long and not because it is code — this is a rule about what a run reads, not a size heuristic. Splitting content that every run reads is pure cost, and progressive disclosure can relocate a mandatory read rather than shrink it: moving is not shrinking. The destinations: a `CLAUDE.md` stays light — never restate what the repository shows any reader by itself; spend the tokens on the gotchas it does not. A skill holds what only some runs need, split further only along the same what-does-this-run-read line. A reference prefers code to prose about code — a test suite, a rubric, a working example carries more constraint per token than a description of one. And say a thing once, at the layer where the run that needs it will look; repeating it across layers is a habit from models that needed the repetition.

**Prefer a stated principle to an enumerated rule, and an interface to an example.** An enumeration reads as complete, so it silently excludes every case you did not list; a principle lets the agent derive the cases. An example narrows the search space as a side effect of illustrating it; a constraint states the boundary and leaves the space open. When you catch yourself listing, write the principle the items are instances of — enumerate only when the items are commands to run, a checklist rather than a rule.

**Every line must be able to bind.** Write only lines the agent could both follow and fail to follow. A line that narrates what already happens cannot be failed, so it instructs nothing; a line that needs a tool the agent was not granted cannot be followed, and fails silently.

**Name the collision point.** Point at the decision where the new line meets an existing one. If you can name that point, one of the two loses there, and the text has to say which.

**Write only claims whose falsity a reader can establish from what they already have open.** This governs claims of fact; a stated preference is not a claim and is not caught by it. Three shapes qualify: a pointer to the source that regenerates the claim, a fact pinned to a version with the probe that re-checks it, and a mechanism. One shape disqualifies: a value that moves with a defensible choice of method is underdetermined, and the qualitative form beats whichever number you happened to get. A number that is neither regenerable nor anchored gets deleted, not corrected.

**Justification is three things, and only one belongs in the file.** *Mechanism* — why the thing behaves this way — goes inline: it is bounded, checkable from source, and is what licenses a later deletion. *Provenance* — which incident produced the line — goes in the commit message: when you commit a prompt change, state the argument for it, because retrieval is already solved by `git log` on the file and what goes missing is the supply. *Environment facts* — true of the current tools and models rather than of the work — move into a mechanism that enforces them: a config field, a schema, a runtime setting. An environment fact that stays as prose is the line that goes stale silently.

**Test each premise by negating it.** If a line rests on a stated fact, deny the fact and see whether the instruction survives. Survives: drop the fact. Dies: the line depends on an environment fact — send it to a mechanism, per the rule above.
