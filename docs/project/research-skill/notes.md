# research 스킬 — 설계 메모

작업 중 메모. 결론이 아니라 지금까지 합의된 것과 아직 안 정해진 것.

## 출발점

`.agents/kein/plans/research-skill.md`는 삭제했다(`1d1d220`에 있음). 이유는 두 겹이다.

1. **없어진 규칙 위에 서 있었다.** 서두 절반과 프리모템, Open Questions가 전부 "6-skill ceiling" 논쟁인데, 그 천장은 `9d79fdd`에서 이미 삭제됐다. 플랜이 작성된 시점에 이미 없던 규칙을 상대로 논증했다.
2. **나머지는 2026-08-18에 무효화됐다.** 플랜이 `docs/purpose.md`의 Operating rule 1~5를 근거로 인용하는데, `fad0241`에서 그 섹션을 통째로 지웠다. Step 4(purpose.md 화해)도 같은 날 다른 형태로 처리됐다.

**살릴 것 셋** — 천장·Operating rules와 무관하게 성립하므로 재도출하지 말 것:

- **브리프가 분해되지 않으면 분해를 지어내지 않는다.** 가벼우면 한 질문 되묻고, 진짜 모호하면 `interview`를 권하고 멈춘다. `research` 안에 작은 인터뷰 루프를 만들지 않는다 — "스킬 하나 감싸서 역할 하나에 스킬 둘"의 재발.
- **새 에이전트가 필요 없다.** 리드가 기본 조사자이자 유일한 작성자. `handoff`가 선례.
- **상태 없음.** 원장도 JSON도 없다. `interview`가 원장을 갖는 건 여러 턴 대화 루프라서고, `ralplan`/`execute`가 갖는 건 실패 가능한 게이트의 라운드 추적 때문인데 셋 다 해당 없음. 아티팩트의 미해결 섹션이 재개 장치다.

§4(리뷰 라운드를 넣지 않음)는 결론은 살아있으나 근거가 홈리스다 — 그게 기대던 "prove before adding"이 purpose.md에서 삭제됐고 아직 어디에도 없다(`grep` 무매치). 재작성 때 근거를 다시 세워야 한다.

## research가 무엇인가

**나와 에이전트가 모르는 것을 알거나, 근거를 확보하는 일.** 주로 웹 — 문서, 레포, 뉴스, 영상, 논문.

리포 내부 조사(코드·히스토리)도 근거의 베이스가 되므로 배제하지 않지만 메인은 아니다.

**근거의 정의는 이미 있다.** `~/Documents/wiki/_rules/standing-prompt.md`가 세 형태를 규정한다 — 재생성하는 소스 포인터 / 버전 고정 사실 + 재확인 프로브 / 검증 가능한 메커니즘. 객관·주관 축이 아니라 "무엇이 이것을 뒤집는가" 축이다. 주관적이지만 설득력 있는 것은 네 번째이고, **의견으로 표시된 채로** 들어간다.

따라서 산출 계약: **모든 주장이 세 형태 중 하나를 달았거나, 의견으로 표시돼 있다.** 프롬프트를 고칠 때 쓰는 증거 기준과 research가 만드는 증거 기준이 하나가 된다.

**외부 URL 인용 0건.** 두 건 모두 웹 검색이 아니라 코퍼스 구축이었다.

코퍼스 작업은 **원래 research 스킬을 위한 것이었다.** 거기까지 못 갔고 대신 `plan` 스킬에 대한 자신감을 얻었다.

**Stage 2가 자기를 정당화한 방식**이 이 설계의 핵심 재료다:

> **Why Stage 1 could not have produced it:** ... **There is not one ❌/✅ pair in the material Stage 1 read.**

빠진 *사실*이 아니라 빠진 *각도*다. 정답을 몰라도 이건 셀 수 있다.

## 노드

```
방법 수립 → 조사(병렬) → 평가 → 맹점 감사 → [맹점 있으면 브리프 재작성 후 다시] → 마무리
```

- **평가** — 같은 주제를 병렬로 돈 n개 결과 사이의 판단. 어느 걸 채택할지, 강점을 어떻게 합칠지, 브리프를 다시 쓸지. **결과들 사이**.
- **맹점 감사** — n개 전부가 공유한 방법이 애초에 낳을 수 없었던 것. **과정 바깥**.

둘 다 필요하다. 평가가 없으면 경합하는 답을 이어붙이고, 감사가 없으면 n개가 사이좋게 같은 방향으로 틀려도 모른다.

## 하나의 스킬이다

"마케팅 아이디에이션"처럼 결론이 주관적인 주제는 맹점 정의가 어려워 보이지만, 260810도 결론이 주관적이었고 감사가 성립했다. 감사가 도는 대상이 **답이 아니라 과정**이기 때문이다. 마케팅에도 "세 레인이 전부 영어 자료만 봤다", "전부 B2B를 가정했다"는 정의된다.

발견형이면 안 본 소스가 답을 뒤집고, 생성형이면 안 떠올린 각도가 더 나은 안을 숨긴다. 같은 감사다.

스킬을 가르면 시작할 때 어느 쪽인지 알아야 하는데 보통 조사가 돌아와야 안다. 그리고 이 리포는 이미 가르지 않는 쪽을 두 번 택했다 — `team`은 스킬이 안 됐고 `ralplan`은 게이트가 생겼을 때만 갈라졌다.

## 정지 규칙 — 미결

자동 진행이 전제다. 랄프/루프는 사용자 판단이 반드시 필요한 경우가 아니면 끊기지 않는 것을 덕목으로 삼는다. 260810은 스테이지 사이에 사람이 있었으므로, 그 자리를 규칙이 받아야 한다.

**하드 n회는 이 리포의 기존 결정과 충돌한다.** `ralplan/SKILL.md:51`은 다섯 회를 "diagnostic trigger, not a maximum"이라 명시하고, 73행은 하드캡을 기각 사유와 함께 기록한다 — "A hard retry cap forces a bad terminal state."

대안: **감사가 맹점과 그것을 메울 소스 종류를 둘 다 지목해야 다음 라운드가 열린다.** 소스 종류가 유한하므로(문서 / 코드 코퍼스 / 논문 / 뉴스·토론 / 영상 / 리포 내부) 라운드마다 최소 하나를 소진해 자기 종료한다. 그리고 캡과 달리 **왜 멈췄는지가 아티팩트에 남는다** — "이 맹점이 남았지만 볼 소스가 없다"가 다음 세션의 브리프가 된다.

라운드 수는 진단 트리거로만 두는 쪽이 `ralplan`과 일관된다. 확정 아님.

## 방법 수립 — 알파이자 오메가, 미결

이 노드가 정하는 것이 최소 셋이다.

1. **질문 분해** — 독립적으로 답할 수 있는 단위로. 안 되면 지어내지 말 것(위 살릴 것 참조).
2. **팬아웃 모양** — 다른 주제 병렬 / 한 주제 여러 각도. 후자가 n개 종합 케이스.
3. **소스와 방법론 배정** — 한 주제를 하나의 방법론으로 갈 수도, 각기 다른 방법론·소스로 갈 수도 있다.

**그리고 이게 이 스킬의 천장을 정한다.** 좋은 방법 수립은 바닐라 상태에서 조사할 수 없던 것을 조사하게 만든다. 조사 창구가 될 수도 있고 워크플로우가 될 수도 있다. `260811` 코퍼스가 정확히 그 사례다 — 어떤 웹 검색도 5,398개 SKILL.md와 그 커밋 히스토리를 주지 못한다. `harvest.py`를 써야 나온다.

즉 방법 수립의 산출은 세 종류일 수 있다:

- **레인 배정** — 질문을 나누고 소스 종류를 붙인다. 가장 싸다.
- **도구 제작** — 브라우징으로는 못 모으는 데이터를 모으는 스크립트. 코퍼스 케이스. 산출물이 재사용 가능한 자산으로 남는다.
- **방법론 선택** — 같은 질문에 다른 인식 경로를 붙이고 종합한다.

**미결**: 프롬프트가 도구 제작을 신뢰성 있게 유도할 수 있는가. 잠정 의견 — 방법 수립이 도구를 *만드는* 게 아니라 *필요함을 알아채는* 것까지만 맡는다. 신호는 "답에 N개 표본이 필요한데 브라우징으로는 5개"처럼 셀 수 있는 형태.

## 레인 — 소스 종류로

지운 플랜의 레인 표는 에이전트 역할 기준이었다. 맹점 감사가 소스 집합에 대해 도는 것이라면 레인도 소스 종류여야 감사가 성립한다.

| 소스 | 도구 | 이게 못 보여주는 것 |
|---|---|---|
| 공식 문서·API 레퍼런스 | `WebFetch`, `context7` | 실제로 사람들이 어떻게 쓰는지 |
| 코드 코퍼스 | API 수확 + 로컬 클론 | 왜 그렇게 했는지 |
| 논문 | `WebSearch` → `WebFetch` | 현장에서 재현되는지 |
| 뉴스·토론·이슈 | `WebSearch` | 대표성 (시끄러운 소수) |
| 영상 | 자막·트랜스크립트 | 검색 가능성이 낮음 |
| 리포 내부 | 직접 조사 | 바깥에서 뭐가 표준인지 |

오른쪽 열이 맹점 감사의 재료다.

에이전트 투입 여지: `document-specialist`, `critic` 외에 `tracer`, `analyst`도. `analyst`가 경우에 따라 스페셜리스트보다 적절할 수 있다 — 내용에 따라 달라짐. 확정 아님.

## 이름

`research` 유지. 노드가 **방법 수립으로 시작**하는 것 자체가 조사가 아니라 연구다 — 조사는 그 안의 한 노드. 영어 `research`는 시장조사와 논문연구를 다 덮으므로 트리거로도 무리 없고 `ocs` 서브커맨드와 겹치지 않는다.

조사 쪽에 초점을 두려면 `survey`·`investigate`가 후보지만 그러면 방법 수립 노드가 이름과 어긋난다.
