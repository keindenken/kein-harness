# React 화면기획서 도구 (screen + spec overlay)

Status: Approved
Date: 2026-08-04

## Context

기획자가 리액트 화면(와이어프레임/프로토타입)과 그 화면에 대한 기획 스펙을 한 곳에서 나란히 확인할 수 있는 도구가 없어, LLM과 사람이 같은 자료를 함께 읽고 유지보수하기 어렵다. 화면 코드와 기획 설명이 분리된 문서(피그마, 별도 워드/노션 문서 등)에 흩어져 있으면 서로 어긋나기 쉽다. 이 작업은 화면 코드 옆에 기획 스펙을 함께 두고, 화면과 스펙이 컴포넌트 단위로 서로 연결되는 개발용 오버레이 도구를 만들어 이 문제를 해결한다. 특정 프로젝트 한 번 쓰고 버리는 것이 아니라, 여러 프로젝트에 재사용 가능한 범용 도구/템플릿으로 만든다.

## Desired outcome

개발자가 로컬에서 이 도구를 실행하면, 왼쪽에는 실제로 동작하는 화면(React 컴포넌트)이, 오른쪽에는 그 화면의 기획 스펙(설명·상태·인터랙션)이 표시된다. 기획자는 사이드의 화면 목록에서 원하는 화면을 클릭해 전환하고, 스펙 패널에서 컴포넌트의 상태를 선택하면 화면이 실제로 그 상태의 모습으로 바뀌는 것을 확인할 수 있다. 스펙 항목과 화면의 컴포넌트는 서로 호버 시 상대편을 강조해주어 어떤 설명이 어떤 컴포넌트를 가리키는지 직관적으로 알 수 있다. 스펙 내용은 LLM이 기획자의 요청을 받아 파일로 직접 작성/수정하며, 기획자는 오버레이에서 그 결과를 확인한다.

## Scope

### In scope

- `src/` 하위에 화면 단위 폴더 구조(폴더 라우트와 유사)로 `page.tsx`(화면)와 `spec.ts`/`spec.json`(스펙)이 짝을 이루는 구조.
- `overlay/`: 왼쪽 대부분 영역에 선택된 화면을 렌더링하는 screen 섹션, 오른쪽 사이드에 해당 화면의 스펙을 보여주는 패널.
- 오버레이 사이드에 `src/` 구조를 반영한 화면 목록(트리) 상시 노출, 클릭으로 화면+스펙 동시 전환.
- 스펙 항목: 화면/컴포넌트 설명, 상태 변화, 사용자 인터랙션/플로우.
- "상태"는 UI 상태(로딩/에러/빈 값 등)와 도메인 상태(예: 주문 상태 흐름에 따른 화면 변화)를 모두 포함하며, **컴포넌트별로 독립적인 상태 목록**을 가짐.
- 오버레이에서 컴포넌트의 상태를 선택하면 화면이 실제로 해당 상태의 모습으로 리렌더링됨(Storybook 컨트롤과 유사한 동작).
- 스펙 패널의 컴포넌트 설명에 호버 시 화면의 해당 컴포넌트가 강조되고, 화면의 컴포넌트에 호버 시 스펙 패널의 해당 설명이 강조되는 양방향 연동.
- 로컬 개발 환경에서 실행 가능한 형태(예: `npm run dev` → localhost로 확인).
- 여러 프로젝트에 재사용 가능하도록, 특정 서비스 로직에 종속되지 않는 범용 구조/템플릿으로 설계.

### Out of scope

- 오버레이 내에서 스펙을 직접 편집하는 UI(폼 편집기 등). 스펙은 LLM이 파일로 직접 작성/수정하고, 오버레이는 확인(뷰어) 용도로만 동작한다.
- 별도 웹 배포/공유 URL 제공. 로컬 실행만 지원한다.
- 다중 사용자 실시간 협업(동시 편집/동시 접속 동기화).
- 비즈니스 규칙/제약조건을 별도 스펙 필드로 관리하는 것.

## Requirements

- `src/` 폴더 구조를 스캔해 오버레이 사이드에 화면 목록 트리를 표시한다.
- 트리에서 화면을 클릭하면 좌측에 해당 `page.tsx` 화면이, 우측에 해당 `spec.ts`/`spec.json` 내용이 함께 전환되어 표시된다.
- 스펙 패널은 화면/컴포넌트 설명, 상태 목록, 사용자 인터랙션/플로우를 사람이 읽을 수 있는 형태로 보여준다.
- 화면 안의 각 컴포넌트는 자신만의 독립적인 상태 목록을 가지며, 스펙 패널에서 특정 컴포넌트의 상태를 선택하면 좌측 화면의 해당 컴포넌트만 그 상태의 모습으로 바뀐다(다른 컴포넌트 상태에는 영향 없음).
- 스펙 패널에서 컴포넌트 관련 설명에 마우스를 올리면 좌측 화면의 대응 컴포넌트가 시각적으로 강조된다.
- 좌측 화면에서 컴포넌트에 마우스를 올리면 스펙 패널의 대응 설명이 시각적으로 강조된다.
- LLM이 대화를 통해 요구사항을 전달받아 `spec.ts`/`spec.json` 파일을 직접 작성·수정할 수 있는 구조(사람이 읽기 쉬운 포맷)여야 한다.
- 도구는 특정 프로젝트의 화면 목록/내용에 의존하지 않고, 새 프로젝트에 폴더 구조와 오버레이를 복사해 재사용할 수 있어야 한다.

## Constraints

- 다른 프로젝트 디렉토리를 검색하거나 다른 프로젝트 파일을 읽지 않는다(사용자 요청에 따른 이번 인터뷰 진행 제약이며, 산출물 자체의 기술적 제약은 아님).
- v1은 로컬 개발 실행 환경만 대상으로 하며, 프로덕션 배포 파이프라인을 고려하지 않는다.

## Decision boundaries

- 스펙 파일 포맷(`spec.ts` vs `spec.json`)과 구체적 스키마 설계는 구현자가 결정한다. LLM의 파싱 용이성과 타입 안정성을 고려해 `spec.ts`(TypeScript 객체) 우선을 권장한다.
- 컴포넌트별 상태를 화면(`page.tsx`)에 실제로 반영하는 기술적 방식(props 주입, context, mock provider 등)은 구현자가 결정한다.
- 화면-스펙 간 하이라이트 연동을 위한 식별자 부여 방식(예: `data-spec-id` 속성 등)은 구현자가 결정한다.
- v1 데모/예시로 포함할 샘플 화면의 개수와 내용은 구현자가 합리적으로 결정할 수 있다.

## Acceptance criteria

- [ ] `src/` 폴더 구조에 화면(`page.tsx`)+스펙(`spec.ts`/`spec.json`) 쌍을 추가하면, 오버레이 사이드 트리에 자동으로 노출된다.
- [ ] 트리에서 화면을 클릭하면 좌측 화면과 우측 스펙 패널이 함께 해당 화면 내용으로 전환된다.
- [ ] 스펙 패널에 화면/컴포넌트 설명, 상태 목록, 인터랙션/플로우가 표시된다.
- [ ] 스펙 패널에서 특정 컴포넌트의 상태를 선택하면 좌측 화면의 해당 컴포넌트가 실제로 그 상태의 모습으로 바뀐다.
- [ ] 같은 화면 안에서도 서로 다른 컴포넌트는 각자 독립적으로 상태를 전환할 수 있다.
- [ ] 스펙 패널의 설명 항목에 호버하면 좌측 화면의 대응 컴포넌트가 강조 표시된다.
- [ ] 좌측 화면의 컴포넌트에 호버하면 스펙 패널의 대응 설명이 강조 표시된다.
- [ ] `npm run dev` 등 로컬 명령 한 번으로 오버레이가 실행되어 브라우저에서 확인 가능하다.
- [ ] 새로운 화면 폴더를 추가하는 것만으로 다른 코드 수정 없이 도구가 동작해, 다른 프로젝트에도 이 구조를 그대로 복사해 재사용할 수 있음을 확인할 수 있다.

## Decisions and rationale

- **범용 도구/템플릿으로 개발:** 특정 프로젝트 1회성 도구가 아니라 여러 프로젝트에 재사용 가능한 구조로 만들기로 함. 특정 서비스 로직에 종속되지 않는 설계가 필요해짐.
- **스펙은 LLM이 파일로 작성, 오버레이는 뷰어 전용:** 기획자가 오버레이에서 직접 타이핑하는 대신, LLM에게 요구사항을 설명하면 LLM이 `spec.ts`/`spec.json`을 직접 작성/수정하는 워크플로를 채택. v1 구현 범위를 줄이고, "LLM도 사람도 똑같이 읽고 작성할 수 있는" 목표에 부합.
- **상태는 컴포넌트별 독립 관리:** 화면 전체가 하나의 상태를 공유하는 대신, 화면 안의 각 컴포넌트가 각자 상태 목록을 갖도록 함. 쇼핑몰 관리자 화면처럼 화면 안에 여러 성격의 상태(로딩/에러, 주문 상태 등)가 동시에 존재하는 실사용 사례를 반영.
- **상태 선택 시 화면 실제 리렌더링:** 상태를 글로만 설명하지 않고 오버레이에서 선택하면 화면이 실제 그 모습으로 바뀌도록 함. 기획 문서와 실제 동작 화면 간 괴리를 없애기 위함.
- **로컬 실행만 지원, 배포는 범위 밖:** 접근 주체가 개발자 PC를 통해서만 확인하면 되므로, 배포 파이프라인 구축에 드는 노력을 v1에서는 들이지 않기로 함.

## Relevant system evidence

- 이번 작업의 대상 프로젝트(리액트 화면기획서 도구)는 아직 별도로 존재하지 않으며, 사용자 요청에 따라 다른 프로젝트 디렉토리를 검색·열람하지 않았다. 현재 작업 저장소(`kein-harness`)는 무관한 Claude 스킬/에이전트 프레임워크 저장소이며 이 요구사항과 직접적인 코드 연관이 없다.

## Assumptions and risks

- 컴포넌트별 독립 상태 관리와 상태 선택 시 실제 리렌더링 요구사항으로 인해, `page.tsx`가 미리보기 목적의 상태를 주입받을 수 있는 구조(props/context 등)로 작성되어야 한다는 제약이 화면 코드 작성 방식에 생긴다. 이는 일반적인 프로덕션 화면 코드와는 다른 작성 관례를 요구할 수 있다.
- 스펙을 LLM이 전적으로 작성하는 워크플로를 전제로 하므로, 기획자가 스펙 내용을 직접 미세 조정하고 싶을 때는 다시 LLM에게 요청해야 하는 우회 경로만 존재한다(v1 한정).
- 화면-스펙 간 하이라이트 연동은 컴포넌트에 식별자를 부여하는 구현 방식에 의존하므로, 기존에 식별자 관례가 없는 컴포넌트 코드에는 소규모 계측(instrumentation) 작업이 추가로 필요할 수 있다.

## Deferred items

- 비즈니스 규칙/제약조건을 스펙의 별도 필드로 관리하는 기능: v1 스펙 항목에서 제외. 스펙 스키마를 확장하는 시점에 재검토.
- 오버레이 내 스펙 직접 편집(폼 편집기) 기능: v1은 뷰어 전용으로 확정. v1 사용 경험을 바탕으로 필요성 재검토.
- 웹 배포/공유 URL 제공: v1은 로컬 실행 전용. 배포가 필요해지면 별도 요구사항으로 다룸.
