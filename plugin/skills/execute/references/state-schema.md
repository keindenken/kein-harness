# Execute State Schema

Store state at `<run-root>/<YYMMDD-HHMMSS>-<slug>/state.json`, where the run root is `ocs state-dir runs/execute`.

Active, blocked, and interrupted states retain run identity, input identity, canonical worktree and Git common directory, baseline and observed fingerprints, the task ledger, current task and round, latest verification, unresolved findings, final-audit facts, and the exact next action. They never store transcripts, raw logs, or agent handles.

A finding carries `reviewer_role`, `claim`, `evidence`, `impact`, `required_correction`, `severity` (`critical`, `important`, `minor`), `confidence` (`high`, `medium`, `low`), and `blocks` — `null`, a verbatim clause of the task's `completion_condition` (whitespace and case folded), or text prefixed `regression: ` or `instruction: `. A finding carried on an accepted task may add `carried_because`; an `important` or `critical` one must. A finding fixed before acceptance is listed under the acceptance's `fixed`, with `blocks` null and no `carried_because`; when that list is non-empty the reviewers' verdicts stand at the fingerprint they read and the acceptance at the corrected one, and the task's verification must be current at the corrected one. A verdict is `PASS`, `REVISE`, or `BLOCK`, and at acceptance it is checked against the findings of the same `reviewer_role`: `BLOCK` needs one that cites, `REVISE` needs at least one and none that cite, `PASS` needs none.

A finding recorded before `blocks` existed stands where it stood, unchanged, until something is accepted over it; acceptance, the final audit and the receipt require the field, and any finding written new carries it.

`unresolved_findings` on an accepted task is what that task carries — findings with `blocks: null` a `REVISE` lane returned and the lead chose not to promote. A finding that cites cannot be retained by an accepted task, by a final audit, or by completion. The same rule holds for the run-level list.

A final-audit verdict is checked against the run-level `unresolved_findings` the same way an acceptance verdict is checked against a task's own: `PASS` needs none of that `reviewer_role`'s findings there, `REVISE` needs at least one and none that cites, and completion accepts either verdict where that holds. `BLOCK` cannot complete — and could not satisfy this check regardless, since a citing finding is refused at the final-audit phase before completion is attempted at all. This is what lets the final audit's stopping rule end a sequence on a `REVISE` that carries a non-blocking finding rather than relabelling it `PASS`. The completed receipt holds its own `final_audit` facts to the same rule, read against its `carried_findings`.

The `carried_because` requirement on an `important` or `critical` finding is not only a task's own acceptance rule: it applies the same way to the run-level `unresolved_findings` a completion is about to freeze, and to a completed receipt's own `carried_findings`, both checked with the identical predicate task acceptance already uses rather than a second copy of it. This is what keeps the final audit's stopping rule from becoming a free way to end an audit silently: a long audit that ends by carrying findings at run level still owes a reason for each one above minor, the same as a task would. A receipt written before this rule existed, holding a final-audit `PASS` over a run-level finding of the same `reviewer_role`, is exactly the relabelled-REVISE shape this whole rule exists to end — a finding real enough to block a coherent `PASS`, called `PASS` anyway. Such a receipt now fails `validate` and `reconcile` by design, not as a regression, and no run is left stuck by it: the failure surfaces on a terminal receipt nothing resumes from.

Every state carries a zero-based monotonic `revision`. Each candidate increments the revision observed in the current checkpoint; a stale candidate is rejected after the canonical-worktree lock is acquired.

**Write `"auto"` for anything derived rather than decided, and `checkpoint` fills it in.** It accepts the sentinel for `revision`, for `worktree.observed`, for `worktree.baseline` on the first checkpoint only, and for any `worktree_fingerprint` or `final_fingerprint` wherever it appears — the latest verification, each task's verification and acceptance, every verdict, and the final audit. All of them are computed from the predecessor and the worktree, which the checkpoint reads anyway in order to check what was written; asking for them creates one way to be wrong per field and no way to be right that those two sources do not already determine.

`"auto"` for `worktree.baseline` after the run has started is an error rather than a re-derivation, because the baseline is what drift is measured against.

Each fingerprint contains `head`, `index_sha256`, `tracked_diff_sha256`, `untracked_sha256`, and the combined `fingerprint`. A task's `scope_fingerprint` is the same four components read over the task's `scope` alone; `"auto"` inside a task fills with that, and outside a task with the whole tree's. It changes for HEAD, staged, unstaged, and untracked content changes, except for untracked paths under `.agents/kein/runs/`. That exclusion is what keeps the fingerprint measurable: the run ledger lives inside the worktree, so a checkpoint writing its own `state.json` would otherwise change the untracked set it had just recorded and every following `reconcile` would report drift over work nobody did. Deliverables elsewhere under `.agents/kein/` — plans among them — stay in the fingerprint.

A task's `dispatch_scope_fingerprint` is not a fingerprint in that sense. It is an object mapping every path the scope currently covers to the sha256 of that path's own content, sealed once on the checkpoint that moves the task from `pending` to `implementing`, before any executor is told to start writing. Reading `git diff` against HEAD, the way `scope_fingerprint` does, is the wrong tool here: this repository commits each verified unit, so HEAD moves for reasons that have nothing to do with this task, and a diff-shaped seal would call a sibling's ordinary commit a change to a task that a lead never touched, or, in the other direction, call a task's own uncommitted draft restored the moment that draft itself gets swept into a commit, since the diff against the new HEAD goes quiet over it though the draft is still sitting there. The path set is the scope's own `git` pathspec read against the index (`git ls-files`) and the visibly untracked files under it (`git ls-files --others --exclude-standard`), so a gitignored path is excluded the same way `worktree_fingerprint` excludes one, and so is the run ledger under `.agents/kein/runs/`. A scope entry with no path parts — `.`, `./`, an empty string — covers the whole tree rather than nothing, both here and where the ledger contract reads scopes against each other: it meets every other task's scope, so a task scoped that way collides with a write-active sibling, an earlier pending or parked task, and a later task in turn, the same as any narrower scope does. A whole-tree scope's own `scope_fingerprint` includes untracked files the same way an unscoped call does, since neither restricts the pathspec `worktree_fingerprint` reads its untracked component from. What is hashed per path is content read straight off the paths, nothing else: a symlink's target, or a regular file's bytes read in chunks rather than loaded whole; never a blob id out of the index, which can move across an `add` and a `commit` while the worktree bytes underneath do not. That is byte-for-byte what is really there, independent of which commit HEAD names. `dispatch_scope_fingerprint` changes on exactly two transitions — `pending -> implementing`, where it is sealed fresh, and `parked -> pending`, where `unpark` drops it so the next dispatch seals again — and `checkpoint` refuses any other transition that changes it, including `accepted -> correcting`, and refuses a `pending -> implementing` literal value that does not match what the checkpoint itself computes. A task's `parked` record is frozen the same way once it is parked: a checkpoint that leaves a task's `status` at `parked` must carry its `parked` object forward unchanged, and only `unpark` (dropping it) or a fresh `park` after that (writing a new one) may move it. The initial checkpoint of a run has no predecessor for that rule to compare against, so it is checked on its own terms instead: no task may carry `dispatch_scope_fingerprint` there, and a `parked` task's `parked.from` must equal `pending` -- nothing else could have legitimately dispatched or restored a task before the run's first checkpoint exists. Between the two, a hand-authored candidate can neither forge the seal nor carry a stale one forward, on the first checkpoint or any later one. It is optional: absent on a task written outside the normal checkpoint flow (a state from before the field existed, or one built directly rather than through `checkpoint`), and a task holding one sealed in the pre-correction shape — `worktree_fingerprint`'s `head` plus its three diff hashes plus the combined one — is treated the same way, since neither answers the restored-scope question; either way the task cannot park from a write-active status. `parked` carries `question`, `from` (`pending`, `implementing`, or `correcting`), `decision_ref`, and `at`; it is required exactly when a task's `status` is `parked` and refused otherwise. Both fields are optional, so a state written before either existed still validates. A park leaving `implementing` or `correcting` asks the seal comparison per path, not of the whole scope: a path clears either by still hashing to its seal entry or, failing that, by being clean against HEAD right now, and only a path that fails both is evidence of unaccepted work. When one or more paths fail the seal and every one of those is clean against HEAD, the task parks anyway on the second route, and `route` (`clean_against_head` is the only value it ever takes) and `diverged_paths` (every path the seal comparison found diverging, the same set `_scope_digest_diff` would name in a refusal — not only the ones that happened to be dirty along the way), present together or not at all, record it. `_scope_head_status` in `scripts/state.py` carries the full argument for why a path clean against HEAD -- no staged or unstaged modification on it, and not visibly untracked either -- is a second sound answer to the same question the seal answers for that path, rather than an exemption from it: an untracked path the seal already holds unchanged clears on the seal answer alone and is never asked the HEAD question at all, which is what let it block a park that had nothing to do with it before this correction. That same docstring names its one limit: a path an operator has marked `git update-index --assume-unchanged` or `--skip-worktree` reads clean here even with moved worktree bytes, a gap `worktree_fingerprint` shares and this harness does not itself open. `route` and `diverged_paths` appear only where this route is actually taken: a scope that matches its seal outright everywhere never diverged from anything to report, and neither field appears there, nor on a park `from` `pending`, which held no seal to diverge from in the first place.

The scope-collision rule above (a task's scope must not meet a write-active sibling's, an earlier pending or parked task's, or a later task's in turn) is enforced in `checkpoint`, not read as a standing fact about a state in isolation: it applies to the tasks a transition newly dispatches (`pending -> implementing`) or reopens into correction (`accepted -> correcting`), checked against every other task's current scope, not re-checked against tasks that were already write-active before this transition and stay that way. This is what lets a run whose already-active tasks predate the root-scope reading above (an empty-parts entry meeting every other entry, including another one shaped the same way) still be checkpointed — including to `aborted` — rather than stranding it: `checkpoint` re-validates the predecessor on every call, and a rule enforced there instead would refuse that predecessor forever, `abort` included. `split-check` answers the same "could these dispatch together" question independently, on request rather than on every checkpoint.

Completed receipts retain only input reference/hash, worktree root/final fingerprint, accepted task summaries — each with the `carried_findings` its task carried and, when there were any, the `fixed_findings` its acceptance fixed — final verification, fresh independent final-audit PASS-or-coherent-REVISE facts, and the run-level `carried_findings`. Both carried lists are exact projections of the checkpointed state; a receipt that drops one is refused, because the receipt is what the next reader inherits. Aborted receipts retain identity, worktree root, time, and stop reason.

Use:

```text
ocs state execute validate <state.json>
ocs state execute reconcile <state.json>
ocs state execute check-worktree <run-root> <worktree>
ocs state execute split-check <state.json> <task-id>...
ocs state execute start --run-root <runs/execute> --slug <slug> --kind plan --input <path> --worktree <path> --tasks <tasks.json>
ocs state execute checkpoint <state.json> <candidate.json>
ocs state execute amend <state.json> --reason <text> [--summary <text>]
ocs state execute dispatch <state.json> <task-id>...
ocs state execute park <state.json> <task-id>... --question <text> [--ref <id>]
ocs state execute unpark <state.json> <task-id>...
```

`start` writes a run's first checkpoint from its parts rather than from a hand-authored candidate. It names the run directory — `<run-root>/<YYMMDD-HHMMSS>-<slug>/state.json`, printed, and what every later checkpoint takes as its positional — reads the canonical root and Git common directory out of `--worktree`, hashes `--input` or `--summary` for the input identity, and opens the ledger from `--tasks`: a JSON array whose entries carry `id`, `title`, `scope`, `completion_condition`, `verification_path` and `rationale` and nothing else. The five remaining fields on each task are a run's opening position and are filled in. Pass a `state.json` path instead of `--run-root` with `--slug` when the directory already exists. Nothing needs creating first; a checkpoint makes its own parent directory.

`checkpoint` promotes a hand-authored candidate and stays the escape hatch for a state nothing else builds.

`amend` moves the run's input identity in place. A plan is edited while its run is live whenever an owner ruling or a factual correction lands in it, and that is a change to the input, not a new run: `amend` re-reads a plan input from its path (or takes `--summary` for a brief), refuses an unchanged input, and appends `{at, reason, from, to}` to `input.amendments`, which the completed receipt carries. A candidate that moves the hash without that entry is still refused, and `reconcile` names `amend` as the exit when it finds the input changed. Amend between tasks; a plan edit is a worktree change like any other, and inside a review round it moves the fingerprint the round was reviewed at.

`dispatch` promotes named `pending` tasks to `implementing`, sealing each one's `dispatch_scope_fingerprint` from its scope's current content before the command returns. The lead tells an executor to start only after `dispatch` succeeds, never before; that ordering is what makes the seal the task's content at dispatch rather than whatever a partial write leaves behind. `dispatch` is the documented route to this transition, but the seal is not conditional on using it: `checkpoint` fills the same field the same way for any `pending -> implementing` candidate that leaves it unset, so a hand-authored checkpoint reaching that transition still seals rather than silently producing a task that can never park.

`park` promotes named `pending`, `implementing`, or `correcting` tasks to `parked`, stamping `parked.at` and clearing `latest_verification` and `acceptance`. A write-active task parks once every path in its scope clears one of two routes, asked per path rather than of the whole scope at once. The first: the path hashes the same as its entry in the sealed `dispatch_scope_fingerprint`, checked with no read of HEAD at all — a scope that matches everywhere clears this way alone and reads HEAD not at all. The second, asked only of a path that fails the first: the path carries no staged or unstaged modification against HEAD and is not visibly untracked either — a path an operator's earlier `git status` would call clean. A path that fails both is evidence of unaccepted work; the task parks once no path does, and `parked.route` and `parked.diverged_paths` record that the second route was needed and name every path the seal comparison found diverging, whether or not each one happened to be dirty against HEAD along the way — an untracked path the seal already holds unchanged clears on the first route alone and is never asked the second question, so it is neither an obstacle nor named here. `park` itself opens no worktree to decide which route applies; it marks both fields `"auto"` on a park leaving `implementing` or `correcting`, and `checkpoint` fills or drops them from the live tree the same way it fills `dispatch_scope_fingerprint`. When some path clears neither route, the refusal names only the paths actually blocking: which of them still differ, added, removed, or changed, and that HEAD does not clear them either.

`checkpoint` validates transitions, input identity, current worktree fingerprint, and single-run exclusivity before an atomic same-directory replace. `reconcile` never promotes partial work; drift requires inspection and fresh verification before selecting a continuation.
