# fsd State Schema

Store state at `<run-root>/<YYMMDD-HHMMSS>-<slug>/state.json`, where the run root is `ocs state-dir runs/fsd`. Unlike `execute` and `ralplan`, a terminal state is not compacted to a smaller field set: `completed`, `paused`, `halted`, and `aborted` all use the exact same shape as `active`, because `report` reads assumptions, questions, lessons, and the retrospective path in every lifecycle, and there is no worktree fingerprint or revision counter here to strip away on completion.

```json
{ "schema_version": 1, "workflow": "fsd", "run_id": "…", "lifecycle": "active | paused | completed | halted | aborted",
  "worktree": "<canonical root>", "entry": "interview | ralplan | execute",
  "input": {"kind": "idea | requirements | plan", "reference": "<path> | null", "summary": "<text>"},
  "agents_md": [{"span_started_at": "<time>", "sha256": "<hex> | null", "respan": {"from": "<ref>", "commit": "<sha>", "reason": "…"}}],
  "halt": null | {"reason": "<text>"},
  "stages": {"interview|ralplan|execute|closeout": {"status": "skipped | pending | entered", "run": "<associated state/ledger path> | null", "resolved_reference": "<absolute path> | null"}},
  "assumptions": [{"id": "A1", "stage": "…", "decision": "…", "chosen": "…", "alternatives": ["…"], "reversal_cost": "…", "where": "…"}],
  "questions":   [{"id": "Q1", "stage": "…", "question": "…", "options": ["…"], "recommended": "…", "why_irreversible": "…", "parks": "<task or story ids, or 'whole run'>", "answer": null | "<text>"}],
  "lessons":     [{"id": "L1", "line": "<proposed AGENTS.md line>", "why": "…"}],
  "retrospective": "<path> | null", "next_action": "…",
  "chain": {"previous": "<absolute path of the predecessor's state.json>", "slice": 2},
  "continued": {"covered": ["AC1", "AC3"], "reason": "…", "next": "<absolute path of the successor's state.json>"} }
```

A span's `respan` is optional, and only `respan` writes it; see "`respan`" below. `chain` and `continued` are both optional; see "Chained slices" below for their writer, their shapes, and how they coexist on one state.

No `revision` field: fsd is written by one lead's checkpoints in order, with no concurrent-lane scope machinery the way `execute` has, so there is nothing here that needs a lost-update counter. `checkpoint`, the escape hatch, promotes a hand-authored candidate onto a run `start` already created exactly as it does in `execute` and `ralplan` — it refuses outright, naming `start`, when `destination` does not exist yet, never creating one of its own — except over two things a hand-authored candidate is never trusted to set on its own even for an existing run: a stage's own `run` and `resolved_reference` change only through `attach`, the `post-bash` hook, or `enter` (see "Stage association" below), never through `checkpoint`, and a new `agents_md` span is opened only by `resume` (on `paused -> active`) or `respan` (on an active run), never by `checkpoint` — `checkpoint` refuses both outright rather than letting a candidate bypass the belonging test on one or the AGENTS.md-hash comparison on the other. There is no `"auto"` sentinel for `agents_md`'s hash, because nothing in this shape is derived from a worktree read the way a fingerprint is — `start`, `resume`, `respan`, and `continue` (for its successor) compute it internally rather than asking a candidate to fill a placeholder.

A stage's own `run` field has no companion `snapshot` field: an earlier design tried to infer a stage's association after the fact from a directory listing taken at `enter`, and that inference is gone (see "Stage association" below). `run` is either `null` (no association yet) or a path a write command — never a directory listing — put there. Its companion `resolved_reference` is either `null` (no association yet, or one recorded before this field existed, or one `attach` could not compute a value for) or the absolute path the next stage in this flow compares against — interview's own resolved `output_path`, ralplan's own resolved `plan.path` — computed once, at the moment `run` was pinned, from that candidate's own recorded directory while it was still live and readable. `execute` carries no `resolved_reference` of its own: nothing downstream of it in this flow ever compares against one, so the field stays `null` there, the same as `closeout`'s own `run` stays empty for having no run root of its own.

`assumptions`, `questions`, and `lessons` are append-only lists; an existing entry never changes and an id, once minted, is never reused. `questions` has one exception: `answer <id> --text` fills a single entry's `answer` from `null` to non-empty text, in place, and nothing else about that entry may move in the same checkpoint.

## Commands

```text
ocs state fsd validate <state.json>
ocs state fsd checkpoint <state.json> <candidate.json>
ocs state fsd start --run-root <runs/fsd> --slug <s> --input <path-or-text> [--worktree <path>]
ocs state fsd enter <state.json> interview|ralplan|execute
ocs state fsd attach <state.json> interview|ralplan|execute <path>
ocs state fsd gap <state.json>
ocs state fsd status <state.json>
ocs state fsd assume <state.json> --stage <s> --decision <text> --chosen <text> --alternatives <a1,a2> --reversal-cost <text> --where <text>
ocs state fsd question <state.json> --stage <s> --question <text> --options <o1,o2> --recommended <text> --why-irreversible <text> --parks <text>
ocs state fsd answer <state.json> <question-id> --text <text>
ocs state fsd lesson <state.json> --line <text> --why <text>
ocs state fsd guard <state.json>
ocs state fsd closeout <state.json>
ocs state fsd close <state.json> --retro <path>
ocs state fsd continue <state.json> --covered <AC ids> --reason <text>
ocs state fsd halt <state.json> --reason <text>
ocs state fsd report <state.json>
ocs state fsd resume <state.json>
ocs state fsd respan <state.json> --from <ref> --reason <text>
ocs state fsd abort <state.json> --reason <text>
```

`start` classifies `--input` mechanically, in this order: a file that validates as a requirements document (`interview`'s own artifact validator, imported read-only) enters `ralplan` when its `Status` line reads `Approved` and `interview` otherwise; failing that, a file that validates as a plan (`ralplan`'s own plan-text validator, imported read-only) enters `execute` when `Approved` and `ralplan` otherwise; anything else — free text, or a path that is neither shape — is an idea, and enters `interview`. A relative `--input` is joined onto the canonical worktree root — the repository top level `--worktree` resolves to (`canonical_worktree`), not `--worktree`'s own literal path — rather than against the process's own current working directory, which may name a different place entirely. The join itself is a plain `Path` join, with no further `.resolve()` call on the result, so a `..`-bearing or symlinked relative `--input` is not itself normalized; that unresolved joined path, exactly as constructed, is what `input.reference` stores. Stages before the entry are marked `skipped` and stay that way for the run's whole life; nothing ever transitions a stage into or out of `skipped` again. `start` opens the first `agents_md` span with AGENTS.md's hash (`null` when the file is absent), and refuses when a nonterminal fsd run already exists for the worktree, naming that run's path and lifecycle.

## Stage association

A stage's association is **recorded when its run is created, not inferred afterward.** An earlier design tried the opposite — read a snapshot of the stage's run root taken at `enter`, diff it against the run root's current contents to find "the one new directory," fall back to a repository scan for `ralplan`/`interview`, and let whichever run currently held `execute`'s own per-worktree claim override a stale kept link — and review found that approach could not be made both strict and complete at once: `ralplan`'s and `execute`'s own terminal receipts drop the very `input` field a strict match needs, so a strict-only reading lost the flow's own completed `ralplan` once it compacted, while a reading loose enough to keep it also admitted runs that were never this flow's own. A later round tried a narrower exception instead — `attach` alone kept a looser worktree-sharing fallback for a candidate the strict test could not check, and both the strict and loose readings still accepted a terminal receipt whose own surviving fields happened to match — and review kept finding another hole in that exception too: an interview ledger's own `repository` line, hand-written by the skill rather than derived, was trusted without being canonicalized against this flow's own worktree, and a completed ledger's surviving `requirements_path` was treated as good enough to link on.

This round removes every exception rather than patching another one in. A stage's association — `stages.<stage>.run`, the "kept link" — is written only by two callers: `attach <state> <stage> <path>` (explicit, from the lead) and the `post-bash` hook (automatic; see `hook.py`), which watches every Bash call for the command that creates or first validates a stage's run — `ocs state ralplan start …`, `ocs state execute start …`, or `ocs validate interview ledger <path>` for interview, which has no `start` builder of its own — and, once that command's own printed path (or, for interview, its own argument) names a candidate that passes the stage's strict belonging test, attaches it. Both callers apply the identical strict test (`_candidate_belongs`), and neither has a fallback to reach for when it refuses: a candidate belongs only when it is checked while **live** — nonterminal — never once it has compacted to a terminal shape, however faithfully that shape's own surviving fields might still match; `post-bash` links a run at creation, while it is still live, so there is nothing left for a terminal reading to rescue. `execute` belongs by its own `input.reference` against the plan this flow executes (`_expected_execute_plan_reference` — the fsd input's own `reference` when `execute` is the entry stage, or, when `ralplan` led here, `stages.ralplan.resolved_reference` — the plan's own absolute path stored when `ralplan` was attached, falling back to a raw re-read of `ralplan`'s completed receipt's `plan.path` only for a state written before that field existed or a link `attach` could not compute one for), compared as resolved paths rather than raw strings (`_same_plan_reference`, covering the relative-vs-absolute and unresolved-worktree-symlink spellings `execute start` and `classify_input` can each produce). `expected_reference` is resolved against `flow_worktree_root`; `candidate_reference` is resolved against the candidate's own root, and that root must itself canonicalize to this flow's canonical worktree — the two are compared as canonical worktrees (`_execute.canonical_worktree(Path(root))[0]`), not as raw paths, which is what keeps a second repository's run with an identical relative filename from reading as a match. For `execute`, "the candidate's own root" is `worktree.root`, which `execute start` already canonicalized to the repository's top level at the time it ran — an execute run's own record carries no cwd of its own, only that already-canonical root — so a relative `input.reference` resolves against the repository's own top level, not against whatever directory `execute start` actually ran from: an absolute `--input`, or one typed relative to the repository root, links; one typed relative to a subdirectory `execute start` was actually invoked from does not, because nothing in an execute run's own record says which subdirectory that was. `ralplan` records one thing more: `working_directory`, the literal, uncanonicalized directory `ralplan start` actually ran from — distinct from `repository`, the field `--repository` defaults to the same `Path.cwd()` but which is still canonicalized before being compared to this flow's own worktree, the same as `execute`'s `worktree.root` — and a ralplan candidate's relative reference resolves against that literal `working_directory` instead of against the candidate's canonicalized root. That is what lets a `ralplan start` run from a subdirectory of the repository still match whether its own `--input`/`--plan` were typed absolute or relative to that same subdirectory: `repository` (and, left to its own default, `working_directory` alongside it) is not this flow's worktree by a raw comparison, only by the canonical one `_same_plan_reference` applies to `repository`, while the relative reference itself resolves against `working_directory` exactly as typed. `ralplan` belongs by its own `input.reference` or `plan.path` — whichever is the semantically right comparison for what `_expected_ralplan_reference` names — against the fsd input this flow classified at `start`, or against interview's own completed ledger's `requirements_path`, by the identical live-and-canonical-root test, with its own relative reference resolved against `working_directory` as just described. `interview`, which carries fsd no reference of its own to compare against at all (an idea input's `input.reference` is always `null`), belongs only when its own ledger is `active` — a completed ledger is terminal and never belongs, whatever `requirements_path` it still carries, so validating it for the first time only after it has already completed no longer links it — its own `repository` canonicalizes to this flow's canonical worktree, and its own `output_path`, resolved against the ledger's own `working_directory` when it is relative rather than against `repository` (`_interview_output_reference` — the same reasoning `_same_plan_reference` applies to a ralplan candidate's relative reference, since a ledger written from a subdirectory can record `output_path` relative to that subdirectory rather than to the repository's own top level), resolves to a path inside that same worktree. The expected reference for an interview is simply "none yet", so the first active ledger to clear those checks is accepted.

If the flow's own expected reference is not knowable yet — `ralplan` led here by an interview not yet complete, or `execute` led here by a `ralplan` not yet complete — a candidate never belongs either, regardless of anything else about it: there is nothing to compare it against, and an unknown expected reference is never treated as a wildcard match.

**The chain breaking one stage later, and `resolved_reference`.** Resolving a candidate's own relative reference against its own recorded directory (`working_directory` for ralplan, the same field for interview) is what lets the *belonging test itself* accept a subdirectory-started run. But `_expected_ralplan_reference` and `_expected_execute_plan_reference` are also the functions the *next* stage's own belonging test calls to learn what it has to match — and once the earlier stage's run has compacted to a terminal shape, re-deriving that expected reference by re-reading the terminal receipt no longer has a `working_directory` to resolve a relative field against: `ralplan`'s completed receipt keeps `plan.path` exactly as `ralplan start` was given it, and interview's completed ledger keeps `requirements_path` exactly as the skill wrote it, but neither compacted shape carries the directory either field might be relative to. Re-resolving that raw value against the *flow's own* worktree root instead (the only root left to try) lands on the wrong file whenever the original run was started from a subdirectory with a relative reference — the very case `_same_plan_reference` was fixed to accept one stage earlier — so the chain that linked at attach time would silently break one stage later, at exactly the moment nothing is left to re-derive it correctly from.

This is closed by recording the answer once, while the evidence for it still exists, rather than re-deriving it later from evidence that may no longer suffice: whenever `attach` links `interview` or `ralplan` (and so whenever `post-bash` does, since it calls `attach`), it also computes that candidate's own absolute reference — interview's `output_path`, ralplan's `plan.path` — resolved against the candidate's own recorded directory while it is still live and readable, and pins it to `stages.<stage>.resolved_reference` in the same commit (`_resolved_reference_for_attach`). That commit happens the moment the link is pinned, not once the run completes, so the stored value exists well before the earlier stage is actually done. `_expected_ralplan_reference` and `_expected_execute_plan_reference` therefore still read the kept link's own current file first, exactly as before this field existed, and only once it reads back completed (ralplan's own `lifecycle`, interview's own ledger `status`) do they return anything at all — the stored absolute when present, falling back to the old re-derive-from-the-completed-receipt logic only for a state written before this field existed, or a link `attach` could not compute one for. This ordering is what keeps "the flow's own expected reference is not knowable yet" (above) true regardless of `resolved_reference`: a link pinned while the earlier stage is still live carries a stored value already, but neither `_expected_ralplan_reference` nor `_expected_execute_plan_reference` will return it — or anything else — until that stage's own kept run reads back completed, so an execute (or ralplan) candidate started while the stage feeding it is still open never belongs, exactly as it never did before this field existed. `gap`'s own two `invoke /kein:...` rows and `_guard_action`'s own `--input` (by calling `_expected_execute_plan_reference` directly) read the identical stored value once it is available, so the path a lead is told to invoke the next stage against is the one that actually opens, not a relative spelling re-resolved against the wrong root. `execute` itself never gets a `resolved_reference`: nothing downstream of it in this flow ever compares against one.

Once written, a kept link is trusted outright and never re-verified or overridden by anything that happens to the run's own file afterward — not a later snapshot read (there is none any more), not whichever run currently holds `execute`'s own worktree claim. It is also never *replaced while it is still live*: once `stages.<stage>.run` is set, a call naming a different path — from `attach` or from `post-bash` — is refused outright as long as the run currently sitting behind the kept link is itself still nonterminal (`_kept_link_still_live`), and a call naming the exact same path, resolved, is always a harmless no-op that writes nothing, live or not. Once the currently kept run has itself gone terminal — the ordinary shape of `guard`'s own abort-then-restart recovery below, where the kept link still names the run that was just aborted — or can no longer be read at all, a call naming a different, live, correctly-belonging path is accepted, moving the kept link there: this is what lets the recovery's own replacement, which necessarily starts at a new path since `execute start` refuses to reuse an existing one, ever actually get attached, and what lets a kept association that has become unreadable (`GUARD_NO_ASSOCIATION`, below) be repaired with a plain `attach` instead of staying stuck. `_flow_stage_run`, the one resolver every reader goes through (`enter`, `gap`, `guard`, `close`, `status`, `resume`), reads exactly the kept link and nothing else: `(None, "not entered")` before the stage has any run to speak of, `(None, "not applicable")` for `closeout`, `(None, "none")` once the stage is entered but has no kept link yet, or `(path, "kept")`. There is no `"resolved"` or `"ambiguous"` reading any more — both belonged to the deleted snapshot-diff mechanism. `status <state>` adds one thing `_flow_stage_run` itself does not carry: alongside a `"none"` stage it names `association_reason` — the specific start/validate command and the one argument this flow's own strict test actually reads (e.g. ralplan's `--input <requirements>` or `--plan <plan-path>`, whichever `_expected_ralplan_field` names for this flow), and the `attach` invocation to try explicitly — so a lead reading `status` with no memory of what already happened to this run (after a compaction, say) knows what to do next rather than only that nothing has happened yet. It is not a promise that `attach` will succeed: `attach` works only on a live run of this flow, by the identical test `post-bash` applies, so a run whose own reference is present but genuinely contradicts this flow's, one that has already gone terminal, or one checked before this flow's own expected reference was knowable is refused by `attach` too, exactly as it would be by `post-bash`.

A stage that never had a strictly-verified live candidate pinned to it has no association at all, by design, not by oversight: `gap`, `guard`, and every other reader treat that exactly the same as a stage genuinely unresolved, allowing by default rather than guessing either way. This trades one thing away — a run the lead started outside the commands `post-bash` watches needs an explicit `attach`, which applies the identical strict, live-only test rather than a looser one, so a run that has already gone terminal before ever being attached has nothing left to rescue it — for a resolver with nothing left to get wrong: every kept link was, at the moment it was written, a real, strictly-matching, still-live run, full stop.

Allowing by default is silent on its own: `gap`'s own `{gap, completed, next, action}` fields say only "no gap," the same answer a stage that is genuinely still running gives. `gap` closes that silence with a fifth field, `diagnosis`, carried on every return it makes: on the two returns where `gap` itself is `False` and the run is still live enough for a lead to act on it — `paused`'s own early return, and the no-gap return an `active` run falls through to — it maps every entered stage whose association still reads `"none"` to the identical reason `status` already shows beside it (`_none_association_reason`), so a lead calling `gap` alone — without also calling `status` — still sees which stage is entered but unlinked rather than reading silence as nothing wrong. It is `null` on every `gap: True` return, since that row already carries its own `action` naming the one thing to do next, and a second, unrelated fact beside it would only send a lead chasing the stage `diagnosis` names instead of the one `action` already points at. Only `active` and `paused` are nonterminal enough for a lead to act on a diagnosis at all — `attach` refuses a terminal state outright, before its own belonging test ever runs — so a `completed`, `halted`, or `aborted` run takes that identical early return but stays `null` there too, where naming a stage to remediate would point at a door already closed.

`enter <state> interview|ralplan|execute` marks a stage entered. It no longer discovers or adopts a pre-existing run of its own the way an earlier design's snapshot-diff-or-resume logic did — there is nothing left to snapshot, and nothing to scan a run root or a worktree claim for. It is idempotent once a stage is already `entered`, and leaves any existing association — kept by a prior `resume`, or by an `attach`/`post-bash` call that already landed — exactly as it is. A stage that enters with no run at all is the ordinary window between `enter` and the stage's own `start` command (or, for interview, its ledger's own creation): no reader turns "entered, no kept link yet" into a gap or a guard violation, and it is never the ground of a hook's block either -- the Stop hook's own mid-stage block fires on the entry, link or no link, and only quotes `diagnosis` in its reason. Calling `gap` by itself already names the missing link, in `diagnosis` -- see above -- the same text `status` shows beside the stage, and without `gap`'s own answer changing. `enter execute` alone still checks one thing before marking itself entered: whether a nonterminal execute run already occupies the worktree's own per-worktree claim and does not belong to this flow. An occupant equal to the stage's own kept link belongs without re-running the strict test at all — a resumed run's own kept association is trusted outright here exactly as everywhere else a kept link is read — and only when that shortcut does not apply does the ordinary strict test run. When the strict test passes and no link is kept yet, `enter` pins that occupant as the kept link in the very same commit that marks execute entered, exactly as `attach` would (though never a `resolved_reference`: `execute` has none of its own). This is what links a *resumed* occupant — a worktree a prior session's own `execute start` already claimed, with `/kein:execute` now resuming it rather than restarting it — without ever needing a `start` call in this session for `post-bash` to have watched, and without needing a separate explicit `attach` either. When the strict test fails outright, `execute` is not marked entered at all, and nothing is linked: `run` stays exactly as it was, `stages.execute.status` stays at `pending`, which is what keeps `gap`'s own occupant-aware message (`_execute_occupant_block`, below) reachable at all. `gap`'s own occupant-block wording applies the identical kept-link shortcut before it ever asks the strict test about an occupant, so a resumed, pending, still-live kept run never gets misread as a stranger to abort merely because the strict test happens to be momentarily unable to confirm it.

`attach <state> interview|ralplan|execute <path>` pins a stage's association explicitly — the only writer of a kept link besides `post-bash`, which calls this same function once it has already run the identical check on its own. It applies the identical strict, live-only belonging test above, and no other — there is no looser fallback left to reach for. A candidate that fails it is refused outright, by name, whatever the reason: a genuinely different reference, an expected reference not yet knowable, or a candidate that has already compacted to a terminal shape, whether or not its own surviving fields happen to still match. When the refused candidate is genuinely this flow's own `stage` run, refused solely for having gone terminal (`_candidate_terminal_but_matches`, gated on a completed lifecycle or ledger status: for `execute`, the identical field-exact reference test the live check applies; for `interview` and `ralplan`, whose completed shapes drop the field that test needs, the candidate's own file resolving inside this flow's canonical worktree and, once a `resolved_reference` is already pinned, its own surviving document resolving to it), the refusal carries one further sentence, in one of two forms depending on whether `stage` already has a kept `run`. With none, it says the stage stays unlinked for the rest of this run; for `interview` or `ralplan` it names the document the next stage takes — the completed ledger's own surviving `requirements_path` (the live-resolved `output_path` a `_resolved_reference_for_attach` re-read would prefer is never available here, since a completed ledger's compact shape has already dropped the `repository` line that resolution needs), or ralplan's own `plan.path` — whenever that document can be trusted without the directory the terminal shape dropped (already absolute, or resolving to a file that still exists), naming none rather than a wrong path once it cannot; for `execute`, which has no next stage of this flow's own that takes a document at all — closeout runs against the fsd state path a lead calling `attach` already has in hand, not a document — it names no document at all, only that the next stage should be invoked with the path already in hand. With one already kept, it says instead that the stage stays linked to that run and this candidate is not replacing it, since the flow's own rows already fire off the kept link regardless of this refusal. Every other refusal — unreadable, a candidate that went terminal by aborting rather than completing, one whose own file lives outside this flow's canonical worktree, or one whose own document contradicts an already-pinned `resolved_reference` — keeps the cause-only text. This is what lets the lead pin a run `post-bash` never saw (one started by some means other than the three commands it watches) while refusing everything a confirmed mismatch, an unknown expected reference, or terminality would already have refused automatically. As noted above, a kept link is never replaced while it is still live either: a second `attach` naming a different path for an already-linked stage is refused as long as the currently kept run is still nonterminal, accepted once it has gone terminal or become unreadable, and naming the exact same path is always a no-op. For `interview` and `ralplan`, `attach` also pins `resolved_reference` in the same commit as `run` (see above) — the one thing a hand-authored `checkpoint` candidate is refused from ever setting directly (below), since it is exactly the value the belonging test was run to produce.

`ocs state fsd checkpoint <state.json> <candidate.json>`, the escape hatch, refuses a candidate outright, before ever committing it, in four cases neither `attach` nor `enter` can ever trigger: a `state.json` that does not exist yet (`start` is the one builder of a new fsd run; a checkpoint naming a destination `start` has not already created is refused by name, pointing at `start` -- the per-stage `run`/`resolved_reference` comparison just below has no `previous` state to run against otherwise, which would let a first checkpoint to a brand-new destination commit a hand-authored `run`, `resolved_reference`, and `agents_md` span exactly as given, the identical bypass reached a different way), a change to any stage's own `run` or `resolved_reference` on an existing run (a link changes only through `attach`, the `post-bash` hook, or `enter`, each of which commits its own candidate directly rather than through `checkpoint`, so this refusal never touches them), a new `agents_md` span appended on any transition (`resume` and `respan` open spans through their own commits; a candidate's hash was written by hand), and a move into `paused` (`close` is its one builder, and a hand-authored pause would let `resume` open a span over any AGENTS.md at all). The last three close the same kind of gap: a hand-authored candidate that copies a `run` value from somewhere else would bypass the belonging test entirely, and one that appends a span with a fabricated `sha256`, or pauses a run so `resume` spans over an edited AGENTS.md, would let `close`'s own AGENTS.md comparison pass against bytes no builder ever vouched for.

## `guard`

`guard <state>` checks the kept `execute` link whenever one exists, whatever the stage's own status — not only while it reads `entered`: `resume` can pin a kept link back onto a stage it resets to `pending` (a parked task's own run still nonterminal across a pause), and that run's tasks are exactly what still needs checking across the pause. `guard` is clean whenever there is no kept link at all to check — before the stage has any run, entered with none yet (`none`), a skipped stage (which the schema forbids from ever carrying a run), or a `pending` stage `resume` never touched. Once a kept link exists, a run `guard` cannot actually read is *not* reported clean: `guard` says so (`{"clean": false, "violations": [], "reason": "…"}`, pointing at `attach`) rather than letting the absence of evidence read as the absence of a problem.

Past that, `guard` reads the associated `execute` state and lists every task whose `scope` meets AGENTS.md. Before reading a scope entry it is normalized against the worktree root: `execute start` itself accepts an absolute path (the repository root, or `AGENTS.md`'s absolute path) or a relative one carrying `..` (`docs/../AGENTS.md`), as long as it still resolves inside the repository — confirmed empirically, since `execute start` refuses a scope entry that resolves outside it (git's own pathspec check: `':(literal)/': '/' is outside repository` for a bare `/`, which is therefore the one root-spelling that cannot reach a real ledger) — and the scope a task carries is exactly whatever text the ledger wrote, not a canonical form. An absolute entry's *parent* is run through `os.path.realpath` before the rest of the normalization (`os.path.normpath`, `os.path.relpath` — pure string math from there on), and its own final path component is left exactly as named: `state["worktree"]` is itself resolved, but a ledger's absolute scope entry need not be — on macOS a temp directory under `/var/...` is a symlink to `/private/var/...`, and `execute start` stores an absolute scope entry exactly as given, unresolved — so without resolving the parent, an unresolved absolute spelling of the repository root or of AGENTS.md would not normalize to the same path as the resolved worktree root and would read as not covering it. Resolving the whole entry instead of just its parent would introduce a different bug: `os.path.realpath` follows a symlinked leaf too, so an absolute path naming AGENTS.md would resolve to wherever AGENTS.md itself points, if it is a symlink, rather than staying "AGENTS.md" relative to the worktree — confirmed empirically with a symlinked AGENTS.md, and that is why only the parent is resolved. A relative entry, whose directory prefix is already the resolved worktree root, is left to the plain string math throughout. Once normalized to a path relative to the worktree root, an entry with at least one path part is read with `execute`'s own scope-collision reading (`_scopes_collide`), imported read-only. An entry that normalizes to zero path parts — a scope entry naming the repository root: `.`, `./`, an empty string, or the repository's own absolute path all strip to this — is treated as covering AGENTS.md unconditionally, before `_scopes_collide` is ever asked about it, so `guard` does not depend on how `_scopes_collide` happens to read an empty-parts entry on either side of that check, only on `_scope_parts`. That is what keeps a task scoped to the whole repository — however it spelled that — from slipping past a check meant to catch exactly it.

The comparison against AGENTS.md is case-insensitive, unconditionally rather than only on a case-insensitive filesystem: a scope entry that normalizes to `agents.md`, `Agents.MD`, or any other case variant is folded to lowercase, alongside `AGENTS.md` itself, before the collision check runs, so it is caught the same as an exact-case spelling would be.

`guard` exits nonzero when it finds a violation, and its JSON carries an `action` field naming what actually clears it (`_guard_action`). Parking the offending task does **not** clear a guard failure: a parked task's scope is unchanged, so `guard` (which reads every task regardless of status) keeps failing and `close` keeps refusing. The fix `action` names is short: abort this execute run and start its replacement, without the offending task, in the *same Bash tool call*, joined with `&&` (`ocs state execute checkpoint <this execute run's own state.json> <aborted-candidate.json> && ocs state execute start --kind plan --input <the plan this flow executes> --worktree <the run's own worktree> --tasks <replacement-tasks-ledger.json, without the offending task>`) — the checkpoint call's own first argument is the very run `guard` already read to find the violation, so `_guard_action` substitutes it directly rather than leaving it for the lead to supply. Chaining the two commands into one tool call is what closes the window between the abort and the replacement: `PreToolUse`/`PostToolUse`/`Stop` fire around whole tool calls, never in the middle of one shell line, so nothing ever reads fsd's own state with the old run aborted and no replacement yet. The `post-bash` hook attaches the replacement automatically, from that same `execute start` call's own stdout, once it strictly belongs — no `attach` step is named in the recovery at all, and no marker file either: an earlier design wrote one to tell a later `gap` read that a restart was pending, and it is gone along with the closeout row it protected (see "`close`, `halt`, and `resume`" below for where that row went). The `--input` names the actual plan path (`_expected_execute_plan_reference`) whenever it can be read, never `--kind brief`: a brief replacement stores a `null` `input.reference`, which never strictly belongs, reopening the exact gap this design closes. `--worktree` is likewise the run's own actual worktree rather than a placeholder — `execute start` requires it, and the printed command would fail as given without it. If the run cannot be restarted, `close` keeps refusing and the run ends `halted`. Every path this (or any other) printed command substitutes — the violating run's own state.json, the plan reference, and the worktree here, an fsd stage's own target in a `gap` row's `invoke /kein:<stage> …` action, the occupant and its own aborted-candidate path in the entry-stage occupant's abort command, and the resolved state.json path `hook.py` substitutes for a row's own `<state>` placeholder — is passed through `shlex.quote`, and an inline script substituted as part of one is passed as a single `shlex.quote`d argument rather than wrapped in bare quotes, so the line still runs as printed even when a repository path holds a space.

## `close`, `halt`, and `resume`

`close <state> --retro <path>` refuses, unchanged, when AGENTS.md's bytes no longer hash to the current `agents_md` span's recorded `sha256`, when `guard` is not clean (a violation, or a kept association it cannot read), when the retrospective file does not exist, or when it exists but does not cite every one of the run's assumption, question, and lesson ids — the retrospective is the durable copy of all of them, so citing only some silently drops the rest from the record the next reader inherits; the refusal names exactly which ids are missing. Past those checks it has three outcomes, tried in this order:

1. **`paused`**, when any fsd question is unanswered — regardless of the associated `execute` run's own state. A question can be unanswered while `execute` is already a completed receipt (a lesson-conflict or AGENTS.md-story question raised after execution finished) or while `execute` never started at all (one recorded before a `ralplan` or `interview` abort, or an AGENTS.md story turned into a whole-run question by the AGENTS.md rule). Either way the run must still be able to pause rather than being carried past the open question into `completed`. On this outcome the retrospective is left exactly where it was handed in — except that while `execute`'s own run exists and has not reached a terminal lifecycle, `--retro` must already be a path under this worktree's `.agents/kein/runs/`, refused otherwise; see below.
2. **`completed`**, when nothing is unanswered and `execute`'s side of the flow is done: either its associated run is a `completed` receipt, or it never started at all because `interview` or `ralplan` aborted first, so the flow was never going to reach it. Only on this outcome is the retrospective relocated — see below.
3. **Refused**, naming the unfinished stage, when neither of the above holds — most concretely, when nothing is unanswered but `execute` still has real work ahead of it (still running, blocked, or itself aborted without upstream having aborted first).

This ordering is what keeps two situations apart that would otherwise collide on the same evidence: after a task parks, blocks execution, and the lead answers the parking question, `close` immediately after `resume` must refuse — naming `execute`, since it is still blocked and has real work left — rather than quietly completing just because nothing is unanswered anymore. Checking "unanswered" first, ahead of "execute's side done", is what produces that refusal instead of a premature completion; it is also what lets a *leftover* unanswered question — one unrelated to any parked task — still pause a run whose `execute` side is otherwise entirely done, or never reached at all.

`close`'s "execute's side done" reading requires a `completed` lifecycle on the associated run — never `aborted`. `gap`'s own execute-derived closeout row reads the identical way: it fires only for a `completed` execute lifecycle. An **aborted** execute run, by itself, is never treated as evidence of a stage-to-stage gap any more. This is a deliberate narrowing, not an oversight: once `guard`'s own recovery can abort a violating run and start its replacement, an aborted receipt with nothing live yet to replace it is inherently ambiguous between "a restart is about to start" (the abort half of the chained recovery command above) and "the lead has given up on `execute` altogether" — both leave the exact same tasks-less aborted receipt behind, with nothing left in fsd's own recorded-at-creation state to tell them apart without reintroducing some form of after-the-fact inference (an earlier design used a marker file for exactly this, and it is gone). Rather than guess, `gap` simply does not fire on an aborted execute at all; this is also what keeps the guard-recovery window from ever producing a false closeout push, since the same reading covers the mid-restart moment and a genuine give-up uniformly. A genuine give-up still reaches a terminal outcome through the ordinary path: the lead (or fsd's own orchestrating skill) invokes `ocs state fsd closeout <state>` on its own judgment once it decides `execute` will not be restarted; `close` then refuses correctly, naming `execute` as aborted, not completed, and the lead calls `halt`.

Everywhere `close` and `halt` read execute's own status — the retrospective-location rule just below, and the refusal text both raise when nothing else applies — they read the plain kept link, the same as `guard`.

`halt <state> --reason <text>` is the end state for a run `close` refused, and it is refused in turn when `close` would succeed: when AGENTS.md matches, `guard` is clean, and either `execute`'s side is done or some question is still unanswered (the same conditions `close` needs, checked without a retrospective in hand, since a missing or ill-formed retrospective is always within the lead's power to fix and is never a genuine dead end). `report` on a halted run opens with a `## Halted` section carrying `halt.reason` verbatim before the usual four sections, so the reason the lead supplies should name what failed — `guard`'s own `action` field, or its unresolved-association `reason`, is written to be quoted directly into it.

`resume <state>` refuses while any question is unanswered, and also refuses, rather than guessing, when `execute`'s associated run exists but cannot actually be read. Otherwise it moves `paused → active`, opens a new `agents_md` span over AGENTS.md's current bytes (keeping every earlier span), and always resets `closeout` to `pending`. Whether it also resets `execute` to `pending` depends on what `execute`'s association is at that moment: when it is present and still nonterminal (a task parked, the question got answered, and there is real work left to continue), `execute`'s stage is reset to `pending` and its `run` is pinned to that same path, so the very next `enter execute` keeps the identical association. In every other case `execute`'s own stage is left exactly as it was, and only `closeout` resets, so the next `gap` decides where the run goes from what it finds rather than from anything `resume` assumed. Four distinct situations route through that one "leave it alone" branch: `execute`'s associated run is present but already terminal (a completed or aborted receipt), in which case `gap` reports the same execute-derived row again (or, for an aborted run, no row at all — see above) and the next action is `closeout`; `interview` or `ralplan` aborted before `execute` was ever going to run, in which case `gap` reports the same aborted-stage row again and the next action is `closeout`; `ralplan` completed but `execute` was never entered (a question paused the run before the lead invoked it), in which case `gap` reports the ralplan-completed row again and the next action is to invoke `execute`; or `execute` was entered but never got an association at all, in which case `gap` still reports no gap — entered but unlinked is never gap evidence on its own — while its `diagnosis` names execute's own no-association reason, the identical text `status` shows beside it, until `attach` or `post-bash` resolves it.

### `respan`

`respan <state> --from <ref> --reason <text>` opens a new `agents_md` span on an active run whose AGENTS.md changed because its branch took a commit from elsewhere, a rebase onto or a merge of `<ref>`, rather than because the run edited it. Without it such a run has only `halt`. `close` and `continue` both refuse on the drift before anything else, and `resume` needs a paused run that `close` can no longer produce.

It checks against the base, the commit where this branch last shared history with `<ref>` (their merge-base). That way `<ref>` moving on after the rebase does not refuse. It accepts the change only when all three of these hold:
- the worktree's AGENTS.md is exactly HEAD's;
- no commit between the base and HEAD touched AGENTS.md;
- the base's AGENTS.md has those same bytes.

An uncommitted edit is refused, and so is any edit, revert or deletion the run made in an ordinary commit after the base. What git cannot show is who wrote the base itself: `--from HEAD~1` over the run's own earlier commit passes, and so does a merge whose resolution sets AGENTS.md back to an older base's bytes. A branch with no commits of its own, fast-forwarded or rebased onto `<ref>`, cannot be respanned: its HEAD is `<ref>`'s commit, so there is no base short of HEAD to take the change from, and the run ends `halted`. The new span records `respan: {from, commit, reason}`: the ref as given, the base commit the check used, and the reason, so that choice is on the record. The lifecycle stays `active`, and nothing else changes except `next_action` when `--next` is given. An AGENTS.md that is a symlink is always refused: git stores the link's target path, and the worktree hash reads the target's contents.

It refuses, writing nothing, in these cases:
- the run is not active;
- `--reason` is empty;
- AGENTS.md still matches the current span;
- `<ref>` names no commit, or shares no history with HEAD;
- `<ref>` already contains HEAD (HEAD itself included);
- AGENTS.md differs from HEAD's;
- the branch touched AGENTS.md after the base;
- the base's AGENTS.md differs.

## The retrospective's location while `execute` is nonterminal

`execute`'s worktree fingerprint excludes untracked paths only under `.agents/kein/runs/` — the whole tree, every workflow's run directories, not `runs/execute/` alone. A retrospective written directly to the durable `ocs state-dir retros/<YYMMDD>-<slug>.md` path *before* `execute` has reached a terminal lifecycle is an untracked file outside that prefix, and so would register as drift on the very next `execute reconcile` — the fingerprint a clean, work-free `blocked` checkpoint had just recorded would no longer match.

This is enforced mechanically, not left to the caller's discipline: when the outcome is `paused` and `execute`'s own run exists and has not reached a terminal lifecycle, `close` refuses a `--retro` path that does not resolve under this worktree's `.agents/kein/runs/` — this fsd run's own directory (`ocs state-dir runs/fsd/<run>/…`) is the natural choice, since it is covered by the same exclusion and nothing else reads it. Once `execute` has reached a terminal lifecycle (or never started), nothing is left to protect and the check does not apply.

`close` only ever *relocates* the file — to the durable `retros/<YYMMDD>-<slug>.md` path, `<slug>` taken from the run's own `run_id` — on the `completed` outcome, and the move happens *before* the checkpoint that names the durable path is committed: if the commit is then refused, the move is undone and the run stays `active`, exactly as `close` found it, so the caller can simply retry; if the move itself fails, its error propagates before anything is committed, so the run is likewise untouched either way. If `--retro` already names the durable path (the caller wrote the retrospective straight there), nothing is moved and the checkpoint just records that path. Otherwise, `close` refuses outright, before moving anything, if a file already sits at the durable path — a same-day double-close on one run is surfaced rather than silently overwritten. On `paused`, or on any refusal, the file is left exactly where it was handed in, and `execute reconcile` on the still-blocked run keeps reporting the run's own `next_action`, not drift.

## Chained slices

A chain is a sequence of whole fsd states, each covering some of one requirements document's acceptance criteria and handing the rest to its successor. A criterion has no identity of its own in the requirements document — no id, no anchor — so `continue` numbers the `- [ ]` / `- [x]` lines under `## Acceptance criteria` as `AC1`, `AC2`, … in document order, reading only up to the next heading so a checkbox parked under `## Deferred items` is never counted; a requirements document with no checkbox criteria has no `AC` ids at all, and every `--covered` against it is refused.

`chain` and `continued` are the two facts a chain adds, each with exactly one writer:

- `chain` names a slice's predecessor and its own position: `{"previous": "<absolute path>", "slice": <integer ≥ 2>}`. It is written once, when `continue` mints the slice, requires that slice's `entry` be `ralplan`, its `input.kind` be `requirements`, and `stages.interview.status` be `skipped` — the shape `start` already builds for any other requirements-entry run — and never changes, appears, or disappears afterward; `checkpoint` refuses any candidate that differs from the stored value.
- `continued` names what a slice handed off when `continue` closed it: `{"covered": ["AC1", "AC3"], "reason": "<text>", "next": "<absolute path>"}`, present only once that slice's own `lifecycle` is `completed` and its own `retrospective` is still `null` — a mid-chain close, never the chain's last state, which carries a real retrospective instead. `covered` is a non-empty list of ids matching `^AC[1-9][0-9]*$`, distinct and in ascending number order; it names what this slice took, and may repeat an id an earlier slice already covered, since `continue` only refuses when none of the named ids is new. `continued` may appear only on an `active → completed` transition, and `checkpoint` refuses a candidate whose `continued` differs from the one already stored.

A mid-chain close uses the ordinary `completed` lifecycle, not a new one: every reader that already treats `completed` as terminal — `_find_nonterminal_fsd_run`, the hooks' own state lookup — needs nothing new to see a mid-chain slice as done, and `continued` alongside a `null` retrospective is what tells it apart from the chain's last state. This is also why a slice that paused and resumed before it was finally continued still ends with `retrospective` `null`: `continue` overwrites it to `null` in the same commit that adds `continued`, since only the last state's `close` ever writes a real one, and the draft file a pause left behind stays exactly where it was, under that slice's own run directory.

The next slice starts with the closing slice's own `assumptions`, `questions`, and `lessons` copied verbatim, not read through the chain later: `_mint_id` then keeps numbering past every id already copied, so ids stay unique across the whole chain for free, and every reader that reads one state's own lists — `report`, the retrospective's id check — keeps working unchanged. `continue` refuses while any question is unanswered, so every question a later slice inherits is already answered.

`ocs state fsd continue <state.json> --covered <AC ids> --reason <text>` ends the slice at `<state.json>` and starts its successor in one call. Repeated ids in `--covered` collapse to one; on success it prints the successor's absolute path, the same as `start` prints its own destination. It is its own subcommand rather than a `close` flag: `close` already has three outcomes about one retrospective, while `continue` takes none and always both ends one slice and starts the next.

The successor is minted under the same run root and the same slug slice 1 used (`_run_slug` of the run being continued), so a chain's every slice shares one run directory prefix and the final `close` still names the durable retrospective after that one slug. Because the slug is shared, a mint in the same wall-clock second as the slice being closed would name that same directory; `continue` checks for that and, on a collision, waits for the clock to move to the next second before minting once more, refusing only if that second mint also collides.

`continue` refuses before writing anything: every check below reads only files already on disk, and a refusal from any of them leaves the closing slice's bytes and the run root's own listing exactly as they were. Checked in this order, first match wins:

| # | Refused when | Message contains |
|---|---|---|
| 1 | lifecycle is not `active` | `continue requires an active run` |
| 2 | `--reason` empty after stripping | `continue needs --reason` |
| 3 | no requirements document is linked to continue from, or its `Status` is not `Approved` | `no approved requirements document` |
| 4 | a question is unanswered | `cannot continue while a question is unanswered` |
| 5 | the linked `execute` run is not a `completed` receipt | `not completed` |
| 6 | AGENTS.md changed since the current span began (when the branch took the change from another ref, `respan` clears this) | `AGENTS.md changed since the current span began` |
| 7 | an earlier slice cannot be read, is invalid, carries no `continued`, or does not step down by one slice | `earlier slice could not be read` |
| 8 | `--covered` names nothing | `names no acceptance criterion` |
| 9 | a named id is not one of the requirements' own criteria | `no such acceptance criterion` |
| 10 | every named id is already covered by an earlier slice | `adds no acceptance criterion not already covered` |
| 11 | nothing would remain for the next slice | `no acceptance criterion would remain` |
| 12 | another nonterminal fsd run already exists for this worktree | `a nonterminal fsd run already exists` |
| 13 | both of the successor's minted destinations already exist | `already exists` |

The requirements document `continue` reads criteria from, and stores as the successor's own `input.reference`, is decided on this slice's own `entry`, never on `input.kind` first: at entry `interview` — whatever `input.kind` this run started with, a still-Draft requirements document included, since that document's own `input.reference` names the Draft, never the Approved document the interview goes on to produce — the completed interview's own `resolved_reference` or its ledger's `requirements_path`, the identical reading `gap`'s own interview row already uses; at entry `ralplan` over a requirements input, this slice's own `input.reference` directly. It is always absolute: a relative value is joined onto the worktree root with the same plain join `classify_input` applies, with no further resolve.

Once every check passes, `continue` builds both the successor and the closed candidate in memory and validates each with `validate_transition` before writing either. It commits the successor first — minting its directory — then commits the closing slice; if that second commit fails, the successor's file and its directory are both removed before the error is re-raised, so a failed call never leaves the closing slice orphaned behind a successor that was never actually handed off. If the first commit fails, nothing was written at all.

`status` on a state carrying `chain` gains one key, unchanged on any other state:

```json
"chain": {"slice": 2, "previous": "<path>", "requirements": "<path>",
          "covered_by_earlier_slices": ["AC1"],
          "remaining": [{"id": "AC2", "text": "…"}, {"id": "AC3", "text": "…"}],
          "earlier_slices": [{"slice": 1, "state": "<path>", "plan": "<path> | null",
                               "ralplan": "<path> | null", "execute": "<path> | null",
                               "covered": ["AC1"], "reason": "…"}]}
```

`covered_by_earlier_slices` is the de-duplicated union of every earlier slice's own `continued.covered`, sorted by criterion number — a fact about the whole chain behind this state, not only its immediate predecessor. `remaining` is every criterion the requirements document holds, in document order, that is not in that union. When an earlier slice or the chain's own requirements document cannot be read, `chain` carries only `{"slice": …, "previous": "<path>", "error": "<text>"}` instead.

`status` on a state carrying `continued` gains a second key, unconditionally on whether it also carries `chain`: `"continued"`, exactly the state's own `continued` field. Slice 1 of a chain carries `continued` once `continue` hands it off to slice 2, but never a `chain` of its own — only slice 2 onward do — so this is not folded into the `chain` key above; a lead reading `status` on a state that has already continued sees its successor's own path (`continued.next`) either way.

`gap`'s entry-row action on a chained state whose `ralplan` is pending carries the same `invoke /kein:ralplan <requirements path>` any other ralplan-pending row does, then a suffix appended after `CHAIN_SUFFIX_SEPARATOR` (a newline): this slice's own number, each remaining criterion as `AC<n>` with its own text, the instruction to give this slice's plan a path of its own, and, for every earlier slice, its plan path, ralplan receipt path, execute receipt path, and continue reason. Covered criteria are never named there — only what remains is this slice's own planner's business. `continue` computes the successor's own `next_action` the same way, before either of its two writes, reading the slice it is closing from the candidate about to be committed rather than from the file that does not carry `continued` yet. When an earlier slice or the requirements document itself cannot be read, the row still fires, with a clause naming that instead of the suffix. `hook.py`'s `_gap_action` substitutes the printed `<state>` placeholder only in the part of the action before that first separator, so a criterion whose own text happens to contain the literal string `<state>` still reaches the lead verbatim.

`report` on a state carrying `chain` prints `## Slices` right after `## Halted` (when present) and before `## Assumptions`: one line per earlier slice, in order, naming its plan path, ralplan receipt path, execute receipt path, covered ids, and continue reason, then one line for the state itself marked as the current slice, naming its own plan, ralplan receipt, and execute receipt (each or `none linked`), never covered ids or a reason, since this state has not necessarily continued as of this report. When an earlier slice or the requirements document itself cannot be read, that line names the error instead of the earlier-slice walk; the current slice's own line still prints, since it depends on nothing upstream. A state without `chain` prints no `## Slices` section at all.

`report` on a state carrying `continued` prints `## Continued` right after `## Slices` (when present, i.e. this state is itself slice 2 or later) or right after `## Halted` otherwise, and before `## Assumptions` either way: one line naming the successor's own path (`continued.next`), the covered ids, and the continue reason (collapsed to one line the same way the `## Slices` section's own earlier-slice lines are). This is not folded into `## Slices`' own current-slice line, and not gated on `chain` at all: slice 1 of a chain carries `continued` once it hands off to slice 2 but no `chain` of its own, so `report` on slice 1 after it has continued prints no `## Slices` section yet still names its successor through `## Continued`. A state without `continued` prints no such section at all.

## `report`

`report <state>` renders in every lifecycle: a `## Halted` section first when `lifecycle` is `halted`, then `## Slices` when the state carries a `chain`, then `## Continued` when the state carries `continued` (see "Chained slices" above for both), then `## Assumptions`, `## Parked questions` (each with how to answer — re-invoke `/kein:fsd` with the answers), `## Lesson proposals` (numbered, each vetoable), and `## Retrospective`. An empty list prints `None.`
