# fsd State Schema

Store state at `<run-root>/<YYMMDD-HHMMSS>-<slug>/state.json`, where the run root is `ocs state-dir runs/fsd`. Unlike `execute` and `ralplan`, a terminal state is not compacted to a smaller field set: `completed`, `paused`, `halted`, and `aborted` all use the exact same shape as `active`, because `report` reads assumptions, questions, lessons, and the retrospective path in every lifecycle, and there is no worktree fingerprint or revision counter here to strip away on completion.

```json
{ "schema_version": 1, "workflow": "fsd", "run_id": "…", "lifecycle": "active | paused | completed | halted | aborted",
  "worktree": "<canonical root>", "entry": "interview | ralplan | execute",
  "input": {"kind": "idea | requirements | plan", "reference": "<path> | null", "summary": "<text>"},
  "agents_md": [{"span_started_at": "<time>", "sha256": "<hex> | null"}],
  "halt": null | {"reason": "<text>"},
  "stages": {"interview|ralplan|execute|closeout": {"status": "skipped | pending | entered", "snapshot": ["<run dirs present at entry>"], "run": "<associated state/ledger path> | null"}},
  "assumptions": [{"id": "A1", "stage": "…", "decision": "…", "chosen": "…", "alternatives": ["…"], "reversal_cost": "…", "where": "…"}],
  "questions":   [{"id": "Q1", "stage": "…", "question": "…", "options": ["…"], "recommended": "…", "why_irreversible": "…", "parks": "<task or story ids, or 'whole run'>", "answer": null | "<text>"}],
  "lessons":     [{"id": "L1", "line": "<proposed AGENTS.md line>", "why": "…"}],
  "retrospective": "<path> | null", "next_action": "…" }
```

No `revision` field: fsd is written by one lead's checkpoints in order, with no concurrent-lane scope machinery the way `execute` has, so there is nothing here that needs a lost-update counter. `checkpoint`, the escape hatch, promotes a hand-authored candidate exactly as it does in `execute` and `ralplan`; there is no `"auto"` sentinel, because nothing in this shape is derived from a worktree read the way a fingerprint is — `start` and `resume` compute `agents_md`'s hash internally rather than asking a candidate to fill a placeholder.

`assumptions`, `questions`, and `lessons` are append-only lists; an existing entry never changes and an id, once minted, is never reused. `questions` has one exception: `answer <id> --text` fills a single entry's `answer` from `null` to non-empty text, in place, and nothing else about that entry may move in the same checkpoint.

## Commands

```text
ocs state fsd validate <state.json>
ocs state fsd checkpoint <state.json> <candidate.json>
ocs state fsd start --run-root <runs/fsd> --slug <s> --input <path-or-text> [--worktree <path>]
ocs state fsd enter <state.json> interview|ralplan|execute
ocs state fsd attach <state.json> interview|ralplan|execute <path>
ocs state fsd gap <state.json>
ocs state fsd status <state.json>
ocs state fsd assume <state.json> --stage <s> --decision <text> --chosen <text> --alternatives <a1,a2> --reversal-cost <text> --where <text>
ocs state fsd question <state.json> --stage <s> --question <text> --options <o1,o2> --recommended <text> --why-irreversible <text> --parks <text>
ocs state fsd answer <state.json> <question-id> --text <text>
ocs state fsd lesson <state.json> --line <text> --why <text>
ocs state fsd guard <state.json>
ocs state fsd closeout <state.json>
ocs state fsd close <state.json> --retro <path>
ocs state fsd halt <state.json> --reason <text>
ocs state fsd report <state.json>
ocs state fsd resume <state.json>
ocs state fsd abort <state.json> --reason <text>
```

`start` classifies `--input` mechanically, in this order: a file that validates as a requirements document (`interview`'s own artifact validator, imported read-only) enters `ralplan` when its `Status` line reads `Approved` and `interview` otherwise; failing that, a file that validates as a plan (`ralplan`'s own plan-text validator, imported read-only) enters `execute` when `Approved` and `ralplan` otherwise; anything else — free text, or a path that is neither shape — is an idea, and enters `interview`. A relative `--input` is joined onto the canonical worktree root — the repository top level `--worktree` resolves to (`canonical_worktree`), not `--worktree`'s own literal path — rather than against the process's own current working directory, which may name a different place entirely. The join itself is a plain `Path` join, with no further `.resolve()` call on the result, so a `..`-bearing or symlinked relative `--input` is not itself normalized; that unresolved joined path, exactly as constructed, is what `input.reference` stores. Stages before the entry are marked `skipped` and stay that way for the run's whole life; nothing ever transitions a stage into or out of `skipped` again. `start` opens the first `agents_md` span with AGENTS.md's hash (`null` when the file is absent), and refuses when a nonterminal fsd run already exists for the worktree, naming that run's path and lifecycle.

## Stage association

A stage's run is either the one `resume` kept, or the one directory `enter` associated directly at entry, or the one new directory that has appeared under the stage's run root since `enter`'s snapshot — resolved live, every time, by every reader that needs it (`gap`, `status`, `close`, `guard`), never cached beyond what `enter`, `resume`, or `attach` themselves wrote into `stages.<stage>.run`. `report` reads none of this; it only renders the fields already on the fsd state itself. When there is no association or more than one candidate, there is no association at all, and so no gap evidence names that stage: the flow allows by default. `status` reports which case it found for each stage — `kept` (an explicit `run` is recorded), `resolved` (exactly one new directory since the snapshot), `none` (zero), `ambiguous` (more than one), or `not entered` / `not applicable`. Every read of an associated run's content — its own state or ledger, or the requirements or plan document it names — is wrapped in `gap`, so a missing or malformed file yields no row for that stage and evaluation moves on to the next row rather than raising.

`enter <state> interview|ralplan|execute` marks a stage entered. It is idempotent once a stage is already `entered` — a second call changes nothing. Otherwise, before snapshotting, it checks for a stage run that already exists, nonterminal, for this worktree — a run being *resumed* rather than created, which the snapshot-diff heuristic alone cannot see, since a pre-existing directory is never "new". For `execute` this check reuses `execute`'s own per-worktree claim (`find_occupying_run`), which is what makes it unique by construction; for `ralplan` and `interview`, which carry no such claim, it scans the stage's run root for a nonterminal run whose `repository` (or ledger frontmatter `repository`) resolves to this worktree, and treats more than one match the same as none. When a unique resumed run is found, `stages.<stage>.run` is set directly and no snapshot is taken; otherwise the stage's run root's current directory listing becomes `stages.<stage>.snapshot`, for a later reader to diff. `closeout` has no run root of its own: the `closeout` command marks it entered directly.

`find_occupying_run` names any nonterminal execute run for the worktree, regardless of which flow started it, so for `execute` the uniqueness check alone is not enough: `enter` additionally requires that occupant's own `input.reference` name the same plan this fsd run is executing — the fsd input's own `reference` when `execute` is the entry stage, or the plan path on `ralplan`'s completed receipt (`plan.path`) when `ralplan` led here. The two references are compared as paths, not as the raw strings each side happened to store (`_same_plan_reference`): `execute start` and `ralplan start` keep a reference exactly as given, relative or absolute, and `classify_input` joins a relative one onto the worktree root without ever calling `.resolve()` on the result, so the same plan can be spelled two different ways — relative here, absolute there, an absolute spelling `os.path.realpath` has not touched — and still has to read as a match. An occupant that does not match — an operator's own `/kein:execute` run, or one left over from something else entirely, still sitting in the worktree — is refused by name and lifecycle, the same way `start` refuses an occupying fsd run, rather than adopted as this flow's own or silently stepped around by snapshotting past it (a snapshot would only defer the same conflict to `execute start`'s own occupied-worktree refusal, later and less clearly named). The refusal is worded by which of the two ways a match failed to establish itself: when the plan this flow executes cannot be read at all yet (`ralplan` has not completed, or its receipt is unreadable), the refusal says so and names `attach` as the way past a false negative, for the case the occupant genuinely is this flow's own run; when both references are known but genuinely differ, the refusal names both and tells the lead to finish or abort the occupying run before rerunning `enter` — `attach` is not offered there, since a confirmed mismatch is not the spelling gap the comparison exists to close.

`attach <state> interview|ralplan|execute <path>` pins a stage's association explicitly, past whatever the automatic mechanism found — the alternative the state shape names for a case `enter`'s snapshot-diff or resumed-run check cannot resolve on its own. It checks the run's own worktree or repository field before accepting it; a terminal receipt that carries no such field at all (`ralplan`'s completed/aborted shape, or `interview`'s compact completed/aborted ledger) is trusted rather than refused, since there is nothing left in that shape to check a path against and `attach` exists precisely for cases the automatic path cannot cover.

## `guard`

`guard <state>` is clean when `execute` has not been entered yet, or has been entered but has no run there yet at all (`none`) — the ordinary transient window between `enter execute` and the skill's own `execute start`, where there is genuinely nothing to check. Once `execute` is entered, an `ambiguous` association (more than one candidate, so no read is safe) or an associated run `guard` cannot actually read is *not* reported clean: `guard` says so (`{"clean": false, "violations": [], "reason": "…"}`, pointing at `attach`) rather than letting the absence of evidence read as the absence of a problem.

Before reading tasks, `guard` checks the kept association against `execute`'s own per-worktree claim (`find_occupying_run`) for a *different*, matching nonterminal execute run than the one it names — the same plan-reference match `enter` uses, not merely "some other run is there" (`_occupying_execute_run`). Between `_guard_action`'s own `checkpoint ... aborted` and the `attach` that repoints the kept association at the replacement, `stages.execute.run` still names the just-aborted run — now a compact receipt with no `tasks` field left to read at all — while the matching replacement already holds the worktree's claim; reading the stale link would find nothing and report vacuously clean rather than checking anything real. When a different, matching live run is found, `guard` reads that run's own tasks instead of the kept link's; an occupant that does not match — an operator's own unrelated `/kein:execute` run sharing the worktree while this flow's own kept link happens to be terminal — is never read by `guard` at all, and never told to abort by its `action` field either.

Past that, `guard` reads the associated `execute` state and lists every task whose `scope` meets AGENTS.md. Before reading a scope entry it is normalized against the worktree root: `execute start` itself accepts an absolute path (the repository root, or `AGENTS.md`'s absolute path) or a relative one carrying `..` (`docs/../AGENTS.md`), as long as it still resolves inside the repository — confirmed empirically, since `execute start` refuses a scope entry that resolves outside it (git's own pathspec check: `':(literal)/': '/' is outside repository` for a bare `/`, which is therefore the one root-spelling that cannot reach a real ledger) — and the scope a task carries is exactly whatever text the ledger wrote, not a canonical form. An absolute entry's *parent* is run through `os.path.realpath` before the rest of the normalization (`os.path.normpath`, `os.path.relpath` — pure string math from there on), and its own final path component is left exactly as named: `state["worktree"]` is itself resolved, but a ledger's absolute scope entry need not be — on macOS a temp directory under `/var/...` is a symlink to `/private/var/...`, and `execute start` stores an absolute scope entry exactly as given, unresolved — so without resolving the parent, an unresolved absolute spelling of the repository root or of AGENTS.md would not normalize to the same path as the resolved worktree root and would read as not covering it. Resolving the whole entry instead of just its parent would introduce a different bug: `os.path.realpath` follows a symlinked leaf too, so an absolute path naming AGENTS.md would resolve to wherever AGENTS.md itself points, if it is a symlink, rather than staying "AGENTS.md" relative to the worktree — confirmed empirically with a symlinked AGENTS.md, and that is why only the parent is resolved. A relative entry, whose directory prefix is already the resolved worktree root, is left to the plain string math throughout. Once normalized to a path relative to the worktree root, an entry with at least one path part is read with `execute`'s own scope-collision reading (`_scopes_collide`), imported read-only. An entry that normalizes to zero path parts — a scope entry naming the repository root: `.`, `./`, an empty string, or the repository's own absolute path all strip to this — is treated as covering AGENTS.md unconditionally, before `_scopes_collide` is ever asked about it, so `guard` does not depend on how `_scopes_collide` happens to read an empty-parts entry on either side of that check, only on `_scope_parts`. That is what keeps a task scoped to the whole repository — however it spelled that — from slipping past a check meant to catch exactly it.

The comparison against AGENTS.md is case-insensitive, unconditionally rather than only on a case-insensitive filesystem: a scope entry that normalizes to `agents.md`, `Agents.MD`, or any other case variant is folded to lowercase, alongside `AGENTS.md` itself, before the collision check runs, so it is caught the same as an exact-case spelling would be.

`guard` exits nonzero when it finds a violation, and its JSON carries an `action` field naming what actually clears it (`_guard_action`). Parking the offending task does **not** clear a guard failure: a parked task's scope is unchanged, so `guard` (which reads every task regardless of status) keeps failing and `close` keeps refusing. The only fix `action` names is to abort the execute run (`ocs state execute checkpoint <state.json> <aborted-candidate.json>`, execute's own escape hatch — it has no `abort` builder), start a new one without the task (`ocs state execute start --kind plan --input <the plan this flow executes> --worktree <the run's own worktree> …`), and `ocs state fsd attach <state.json> execute <new-state.json>` before rerunning `guard`. The `--input` names the actual plan path (`_expected_execute_plan_reference`) whenever it can be read, never `--kind brief`: a brief replacement stores a `null` `input.reference`, which `_same_plan_reference` can never call a match, reopening the false-closeout and vacuous-guard windows between this abort and the `attach` that ends the recovery. `--worktree` is likewise the run's own actual worktree rather than a placeholder — `execute start` requires it, and the printed command would fail as given without it. If the run cannot be restarted, `close` keeps refusing and the run ends `halted`.

## `close`, `halt`, and `resume`

`close <state> --retro <path>` refuses, unchanged, when AGENTS.md's bytes no longer hash to the current `agents_md` span's recorded `sha256`, when `guard` is not clean (a violation, or an unresolved association on an entered `execute`), when the retrospective file does not exist, or when it exists but does not cite every one of the run's assumption, question, and lesson ids — the retrospective is the durable copy of all of them, so citing only some silently drops the rest from the record the next reader inherits; the refusal names exactly which ids are missing. Past those checks it has three outcomes, tried in this order:

1. **`paused`**, when any fsd question is unanswered — regardless of the associated `execute` run's own state. A question can be unanswered while `execute` is already a completed receipt (a lesson-conflict or AGENTS.md-story question raised after execution finished) or while `execute` never started at all (one recorded before a `ralplan` or `interview` abort, or an AGENTS.md story turned into a whole-run question by the AGENTS.md rule). Either way the run must still be able to pause rather than being carried past the open question into `completed`. On this outcome the retrospective is left exactly where it was handed in — except that while `execute`'s own run exists and has not reached a terminal lifecycle, `--retro` must already be a path under this worktree's `.agents/kein/runs/`, refused otherwise; see below.
2. **`completed`**, when nothing is unanswered and `execute`'s side of the flow is done: either its associated run is a `completed` receipt, or it never started at all because `interview` or `ralplan` aborted first, so the flow was never going to reach it. Only on this outcome is the retrospective relocated — see below.
3. **Refused**, naming the unfinished stage, when neither of the above holds — most concretely, when nothing is unanswered but `execute` still has real work ahead of it (still running, blocked, or itself aborted without upstream having aborted first).

This ordering is what keeps two situations apart that would otherwise collide on the same evidence: after a task parks, blocks execution, and the lead answers the parking question, `close` immediately after `resume` must refuse — naming `execute`, since it is still blocked and has real work left — rather than quietly completing just because nothing is unanswered anymore. Checking "unanswered" first, ahead of "execute's side done", is what produces that refusal instead of a premature completion; it is also what lets a *leftover* unanswered question — one unrelated to any parked task — still pause a run whose `execute` side is otherwise entirely done, or never reached at all.

Neither the `gap`'s execute-derived closeout row nor `close`'s "execute's side done" reading fires while a different, matching nonterminal execute run occupies the worktree than the one `stages.execute.run` names (`_occupying_execute_run`, the same plan-reference match `enter` and `guard` use). `_guard_action`'s own recovery opens exactly this window between its `checkpoint ... aborted` and the `attach` that repoints the association: for as long as the kept link still names the just-aborted run while a matching replacement already holds the worktree's claim, `gap` reports no gap and `close` treats execute's side as not done, rather than reading the stale terminal link — a completed or aborted receipt carries no live tasks at all — as though the flow's own execute stage had genuinely ended. This applies equally when the stale link reads `completed` rather than `aborted`: a genuinely finished execute stage whose worktree a matching replacement has since re-occupied is not done either, for the same reason. An occupant that does not match this flow's plan is not this reading's concern at all — it neither opens this window nor keeps it open, so `gap` and `close` read the kept link exactly as its own content says regardless of what an unrelated run elsewhere in the worktree is doing.

Everywhere `close` and `halt` read execute's own status — the retrospective-location rule just below, and the refusal text both raise when nothing else applies — they read it the same substituted way `guard` does (`_close_execute_run`, preferring `_occupying_execute_run`'s live, matching run over a stale kept link). A refusal that names a live substitution also names that run's own path and points at `ocs state fsd attach`, rather than describing only a lifecycle word for a run the flow has already moved past.

`halt <state> --reason <text>` is the end state for a run `close` refused, and it is refused in turn when `close` would succeed: when AGENTS.md matches, `guard` is clean, and either `execute`'s side is done or some question is still unanswered (the same conditions `close` needs, checked without a retrospective in hand, since a missing or ill-formed retrospective is always within the lead's power to fix and is never a genuine dead end). `report` on a halted run opens with a `## Halted` section carrying `halt.reason` verbatim before the usual four sections, so the reason the lead supplies should name what failed — `guard`'s own `action` field, or its unresolved-association `reason`, is written to be quoted directly into it.

`resume <state>` refuses while any question is unanswered, and also refuses, rather than guessing, when `execute`'s associated run exists but cannot actually be read. Otherwise it moves `paused → active`, opens a new `agents_md` span over AGENTS.md's current bytes (keeping every earlier span), and always resets `closeout` to `pending`. Whether it also resets `execute` to `pending` depends on what `execute`'s association is at that moment: when it is present and still nonterminal (a task parked, the question got answered, and there is real work left to continue), `execute`'s stage is reset to `pending` and its `run` is pinned to that same path, so the very next `enter execute` keeps the identical association rather than re-snapshotting. In every other case `execute`'s own stage is left exactly as it was, and only `closeout` resets, so the next `gap` decides where the run goes from what it finds rather than from anything `resume` assumed. Four distinct situations route through that one "leave it alone" branch: `execute`'s associated run is present but already terminal (a completed or aborted receipt), in which case `gap` reports the same execute-derived row again and the next action is `closeout`; `interview` or `ralplan` aborted before `execute` was ever going to run, in which case `gap` reports the same aborted-stage row again and the next action is `closeout`; `ralplan` completed but `execute` was never entered (a question paused the run before the lead invoked it), in which case `gap` reports the ralplan-completed row again and the next action is to invoke `execute`; or `execute` was entered but never got an association at all (no run created yet, or an ambiguous one), in which case `gap` finds no evidence either way and reports no gap until `attach` or a fresh `execute start` resolves it.

## The retrospective's location while `execute` is nonterminal

`execute`'s worktree fingerprint excludes untracked paths only under `.agents/kein/runs/` — the whole tree, every workflow's run directories, not `runs/execute/` alone. A retrospective written directly to the durable `ocs state-dir retros/<YYMMDD>-<slug>.md` path *before* `execute` has reached a terminal lifecycle is an untracked file outside that prefix, and so would register as drift on the very next `execute reconcile` — the fingerprint a clean, work-free `blocked` checkpoint had just recorded would no longer match.

This is enforced mechanically, not left to the caller's discipline: when the outcome is `paused` and `execute`'s own run exists and has not reached a terminal lifecycle, `close` refuses a `--retro` path that does not resolve under this worktree's `.agents/kein/runs/` — this fsd run's own directory (`ocs state-dir runs/fsd/<run>/…`) is the natural choice, since it is covered by the same exclusion and nothing else reads it. Once `execute` has reached a terminal lifecycle (or never started), nothing is left to protect and the check does not apply.

`close` only ever *relocates* the file — to the durable `retros/<YYMMDD>-<slug>.md` path, `<slug>` taken from the run's own `run_id` — on the `completed` outcome, and the move happens *before* the checkpoint that names the durable path is committed: if the commit is then refused, the move is undone and the run stays `active`, exactly as `close` found it, so the caller can simply retry; if the move itself fails, its error propagates before anything is committed, so the run is likewise untouched either way. If `--retro` already names the durable path (the caller wrote the retrospective straight there), nothing is moved and the checkpoint just records that path. Otherwise, `close` refuses outright, before moving anything, if a file already sits at the durable path — a same-day double-close on one run is surfaced rather than silently overwritten. On `paused`, or on any refusal, the file is left exactly where it was handed in, and `execute reconcile` on the still-blocked run keeps reporting the run's own `next_action`, not drift.

## `report`

`report <state>` renders in every lifecycle: a `## Halted` section first when `lifecycle` is `halted`, then `## Assumptions`, `## Parked questions` (each with how to answer — re-invoke `/kein:fsd` with the answers), `## Lesson proposals` (numbered, each vetoable), and `## Retrospective`. An empty list prints `None.`
